## 黄巾起义第一版开发

- 按 `docs/系统设计/黄巾起义最终开发文档.md` 开发黄巾起义第一版，保持“稳定核心 + 玩法模块”边界。
- 新增军事建筑“千帐营”，老存档和新存档都会拥有 1 级千帐营；千帐营使用金币升级，20 级口粮上限配置为 20 亿，最高级升级费用 2000 金币。
- 新增 `go/config/yellow_turban.json` 和 `game_configs.yellow_turban` 配置入口，GM 后台可编辑完整黄巾配置并手动触发一次全服检测。
- 玩家当前口粮按现有兵种配置 `stats.upkeep` 计算，只统计战斗兵种，不统计商人/运输/非战斗单位。
- 军事视图返回 `foodPressure`，玩家左侧军队卡片展示“当前口粮 / 千帐营上限”，超限时红色显示风险等级和压力百分比。
- 黄巾城池在世界地图中以 `yellow_turban` 假玩家势力展示，不创建真实账号或玩家，不进入排行榜、联盟、普通 PVP 目标身份。
- 黄巾来袭使用独立 `yellow_turban_marches` 队列保存来源城池、压力等级、玩家口粮、千帐营上限和黄巾兵力快照。
- 黄巾派兵按玩家当前总口粮乘以压力等级倍率生成，不按超出部分计算；黄巾兵种从魏/蜀/吴对应阵营战斗兵种中生成，排除侦察和非战斗单位。
- 黄巾行军按世界地图距离和黄巾速度倍率计算，到达后复用战斗引擎结算玩家防守兵力损耗，黄巾不掠夺、不返程、战斗后消失。
- 黄巾战报通过统一战报入口保存为防守战报，来源为 `yellow_turban`。
- 当前已提供玩家状态/检测/结算接口和 GM 全服检测入口；常驻每 10 分钟自动分片扫描 daemon 尚未启用，后续应基于现有检测服务接调度器。
- 验证通过：`go test ./...`、玩家前端 `npm run build`、GM 后台 `npm run build`、`python3 scripts/openapi_bundle.py`。

## 黄巾起义发布与迁移

- 用户要求发布并迁移线上数据库。
- 发布前确认当前分支为 `main-core`，远程仓库为 `https://github.com/xieyuqiyu-source/Hero3.git`。
- 本次线上数据库结构变更通过后端启动迁移创建 `yellow_turban_marches`，不手工直接改线上库。
- 首次发布提交 `4b01af6` 已推送并触发 Actions，但线上服务启动失败，日志显示 `yellow turban config load failed`，原因是校验误把风险等级第一档 `minPressure = 1.0` 判定为无效。
- 已修复黄巾配置校验，允许文档要求的 100% 起步阈值，并补充默认配置校验测试；验证通过 `go test ./...`。
- 发现生产环境 `hero3-server` 默认跳过启动迁移；为满足本次“发布并迁移”要求，发布脚本改为安装新 `hero3-dbtool` 后从 `/etc/hero3/hero3.env` 读取数据库地址并显式执行 `/opt/hero3/go/bin/hero3-dbtool migrate`，再重启服务。
- 迁移脚本首次尝试直接 source `/etc/hero3/hero3.env`，因线上 DSN 含 `tcp(...)` 且 env 文件未按 shell 语法加引号导致失败；修正为只提取 `HERO3_DATABASE_DSN=` 行并导出给 `hero3-dbtool migrate`。
- 线上 DSN 行存在反斜杠续行，单行读取会把 `parseTime=true\` 传给 MySQL 驱动；发布脚本继续修正为支持 DSN 续行拼接。
- DSN 续行解析需兼容 CRLF 行尾，否则 `\r` 会导致反斜杠续行判断失效。
- 为避免发布脚本自解析线上 env 文件继续偏离 systemd 语义，迁移改为通过 `systemd-run --property=EnvironmentFile=/etc/hero3/hero3.env` 执行临时服务，让 systemd 读取同一份环境文件。
- systemd-run 已成功进入真实迁移阶段，但首次连接本机 MySQL 时出现 `i/o timeout`；发布脚本增加迁移 3 次重试，降低线上库瞬时繁忙导致发布失败的概率。
- 三次迁移重试仍然在连接本机 MySQL 时超时，判断为运行中服务对数据库压力较高；发布脚本改为迁移前短暂停止 `hero3` 服务，迁移完成后再启动，迁移失败时也尝试重启服务避免中途停服。
