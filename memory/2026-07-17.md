## 战报标准化规则与修复

- 战报模板结构固定：数据少时保留空占位，数据多时完整显示；无将领的普通攻防也保留身份栏，不再删除模块。
- 实际参战增援方与守城方获得同等级完整战报，包含攻防双方、全部实际参战增援、兵力战损、武将、特性和奖励；情报投影仍统一控制不可见敌方内容。
- 修复将领特性展示：前端同时显示持久化配置参数与本场真实结算值，并兼容历史进攻、防守和增援视角。后端 `traitOutcomes` 仍以 `traitId` 为唯一键，敌我同特性同时触发时只能保存一份实际结果，该核心边界继续等待后续决策。
- Bug 8“进攻方经验为 -”经核对属于正常：该场 NPC 进攻未携带将领，刘备仍在增援占用中，没有参战将领就不产生将领经验。
- Bug 9 属于不正常：原标准契约只在 `detail.rewards.generalExp` 保存战报拥有者经验，防守视角虽然有进攻将领快照，却没有其经验。
- Bug 9 修复后，每名攻防将领在快照中独立保存 `generalExpGained / generalLevelBefore / generalLevelAfter`；同一事件的进攻、防守和增援战报共享客观结果，同将领 ID 出现在敌我双方时按绝对角色隔离。
- 历史详情不批量迁移 JSON，而是在读取时按 `eventId` 汇合同事件兄弟战报，用各视角已有的拥有者经验补齐全部参战将领，再执行情报投影；隐藏敌方将领时经验和等级变化必须一起隐藏。
- 玩家战报列表和筛选列表也必须执行与详情相同的情报投影，禁止通过列表载荷读取敌方将领、经验、特性或援军快照。
- 增援派出时保存武将累计经验作为服务端等级计算基线；写入战报时只保留本场经验、战前等级和战后等级，并清除累计经验，避免泄露额外成长信息。旧版 Web 与 web-wlsg 都固定按“攻击方 → 防守方 → 增援方”展示完整增援战报。

- PVP 积分、复仇记录和保护期只在本次事务确实新建攻防战报时执行，避免已结算行军重复触发非幂等副作用。
- 黄巾协防复用同一幂等规则；已结算事件重复调用时会读取既有同事件援军战报并补发遗漏奖励，正常重复调用不会增加第二次经验。
- 玩家增援接口投影会移除累计经验和内部发奖标记，服务端仍保留连续战斗所需基线；对应回归测试覆盖重复调用、错误传播、恢复补发和公开字段脱敏。
- MySQL 的增援事务与 PVP 事务补齐武将快照变更检测和 `syncPlayerGeneralsTx`，武将经验会同时写入权威 `player_generals` 与玩家 JSON，避免重启/重载后经验回退而幂等标记阻止补发。
