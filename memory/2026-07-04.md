## 每日更新公告文案规则调整

- 用户明确要求自动发布公告不能直接展示代码修改、文件修改、提交标题或专业实现内容。
- 每日更新公告应面向玩家表达：这次更新了什么玩法、优化了什么体验、解决了什么游戏 BUG。
- 公告生成逻辑改为只用 git 提交范围判断是否有新版本，正文来源固定为 `announcements/daily/YYYY-MM-DD.md`，不再从 `memory/YYYY-MM-DD.md` 读取玩家公告内容。
- 自动公告正文改为受限 HTML 富文本排版，包含引导文、更新列表和说明；玩家端公告详情新增白名单 HTML 渲染，普通纯文本公告仍按换行展示。
- 文档同步更新 README、服务器部署文档和公告系统设计文档，明确每日公告只描述玩法/体验/BUG，不展示内部代码信息。
- `memory/YYYY-MM-DD.md` 继续记录较专业的开发内容，不适合直接做玩家公告来源；`announcements/daily/YYYY-MM-DD.md` 是唯一玩家公告源。
- 如果当天公告源不存在或没有 `## 玩家公告` 条目，即使有代码更新也不发布每日公告。

## NPC 一键扫荡任务化与性能治理

- 线上请求日志显示 `/api/v1/map/npc-cities/sweep` 是近期主要慢请求来源，决定将一键扫荡从同步 HTTP 长请求治理为后台任务。
- 一键扫荡改为创建 `sweep_task` 后前端轮询结果；旧 `/api/v1/map/npc-cities/sweep` 和新 `/api/v1/map/npc-cities/sweep-tasks` 都走后台任务语义。
- 扫荡内部不再逐城调用完整 `attackNpc` 写战报流程，而是在一次批量战斗资产事务内连续结算多个 NPC，最终只保存一条 `battle_type=sweep` 聚合战报。
- 奖励流水和道具流水支持批量写入，战报奖励事件和战斗完成事件按聚合战报发布一次，避免每城重复副作用。
- 为了避免并发双击或重复请求，同一玩家同一时间只允许一个 `queued/running` 扫荡任务；任务创建在仓储层原子检查并写入。
- 当前后台任务由服务进程内 goroutine 执行；服务启动时会把上一次进程遗留的活跃扫荡任务标记为失败，避免玩家永久卡在任务执行中。
- 后台任务 panic 会被兜底捕获并写成 failed；前端轮询增加 120 秒超时，避免页面无限等待。
- 单次后台扫荡目标上限定为 50 个 NPC；超过上限前后端都会拒绝并提示玩家减少勾选等级。
- `npc_sweep_tasks` 任务记录用于近期排查，完成或失败超过 14 天后由服务启动清理，并为状态和完成时间增加索引。
- README、NPC 城池系统设计、架构体检报告和 OpenAPI 文档已同步这些边界。

## 战报写入根治、删除语义与军情体验

- 线上排查确认：部分扫荡任务 `npc_sweep_tasks.result_json.battleReport.id` 已生成，但 `battle_reports` 表缺少对应行，根因是扫荡战报保存失败后仅记录 warn，任务仍被标记 completed，造成“任务完成但军情无战报”的假成功。
- 统一战报入口 `CreateBattleReports` 增加保存重试和写后查回确认；如果战报最终无法写入，NPC 攻击、侦查、一键扫荡不再静默成功，避免打完没有战报。
- 军情列表读取前会按当前玩家和最近时间窗口，从扫荡任务结果快照补写缺失的扫荡战报；补写会校验玩家 ID，避免串号。
- 战报列表改为读取摘要列，详情打开时再取完整 `detail_json`；扫荡聚合战报的每城防守方明细改为轻量结构，减少写入体积和列表读取压力。
- 用户明确要求前端删除战报应真正删除，删除接口已从软删改为物理删除：删除 `battle_reports`、`battle_report_states`、`battle_report_links`、`battle_report_participants`，并清理无引用的 `battle_events`。
- 为避免物理删除后的扫荡战报被自动补写恢复，删除时会移除对应 `npc_sweep_tasks.result_json.battleReport` 快照；清理工具也保护仍被扫荡任务快照引用的战报。
- 军情页“清空全部”增加独立处理中状态：按钮显示“清空中”、列表遮罩显示“清空军情中”、禁止重复点击，失败不再表现为无响应。
- 验证通过：`go test ./...`、`npm run build`；另已重启本地后端到新代码用于联调。
