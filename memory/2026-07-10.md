# 2026-07-10 记忆

## 战报系统完整性与安全修复

- 确认并修复战报系统八类问题：轮回防守胜负反转、情报仅前端隐藏、内部战报 ID 可匿名读取、零损援军无战报/经验、战斗事件关联信息缺失、MySQL 列表摘要字段不足、视角兼容迁移污染、扫荡/侦查批量删除筛选错位。
- 战报核心新增事件与多视角战报原子保存接口；内存和 MySQL 仓储都保存显式 `BattleEvent`，PVP 事务补齐行军 ID、攻防/援军快照和结算数据。
- 玩家战报响应统一做服务端情报投影，按 `visibility` 移除敌方剩余兵力、资源、武将、城防和援军兵力；GM 原始查询保持不脱敏。
- 同事件玩家上下文移除 GM 诊断载荷，PVP 战斗详情/列表也按对应战报投影，堵住从事件或 PVP 原始快照绕过情报规则的旁路。
- 内部详情接口现在要求登录、`playerId` 和归属校验，公开分享只允许 token 路径；地图战斗结果弹窗会先创建分享 token 再复制链接。
- 实际参战的驻防援军即使零损失也会写独立协防战报并获得武将经验；协防详情不再重复渲染同一增援方。
- MySQL 军情列表摘要补齐玩家结果、奖励和损失；批量删除统一支持 `viewType / battleType`，与军情当前 Tab 的查询条件一致。
- 历史 `view_type` 修复改为一次性迁移，只处理明确旧值和已知 `plunder` 污染，不再每次启动无条件用玩法类型覆盖视角。
- 更新 OpenAPI、README 和战报系统设计文档；同步修正两条已落后于当前地图默认页签/据点实现的前端静态测试断言。

- 用户要求提交并推送本次战报系统修复到 `main-core`。
- 已确认推送 `main-core` 会触发 GitHub Actions 自动部署代码，但现有生产部署只执行 `hero3-dbtool migrate-yellow-turban`，生产服务启动也会跳过通用 `MigrateMySQL`。
- 本次没有新增表或字段，代码部署不依赖结构迁移；`view_type` 历史兼容回填不会随本次推送自动运行，且未获授权前不扩大生产迁移范围、不直接修改生产数据库。
