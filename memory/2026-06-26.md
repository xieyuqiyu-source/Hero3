## `players.state_json` 缩身与性能结论

- 用户继续追问数据库写入慢、单个建筑升级是否仍整包读写，以及 `players.state_json` 是否还很大。
- 已把 `players.state_json` 写入改为轻量快照：不再保存资源、背包、建筑、资源田、军队、征兵队列、武将、武将派驻和 Buff 等权威资产。
- 新增 `mysql_state_snapshot.go`，统一生成 `playerStateSnapshot`，只保留玩家基础字段、金币、兑换时间、限时加成、NPC 状态、地图目标、未读数和服务端时间等兼容数据。
- 已更新 MySQL 创建/更新玩家状态、信函和钓鱼小游戏写回逻辑，避免重新把权威表资产塞回 `state_json`。
- 当前性能结论：
  - 比旧版整包 JSON 快，尤其减少了大字段序列化和写入体积。
  - 但还不是最终形态，因为部分业务仍会锁 `players` 行并写轻量 `state_json`。
  - 后续更深层优化方向是把建筑升级、征兵、资源结算等高频业务改为更小范围的事务写入。

## 本地压测结论

- 用户要求按开服冲榜场景压测并给出能承受多少人。
- 新增 `scripts/loadtest_hero3.py`，用标准库模拟登录、建档、补资源和混合业务请求。
- 本地 `test_hero3` 压测混合模型：
  - 55% 拉取状态。
  - 20% 拉取 NPC 城池。
  - 15% 建筑升级。
  - 10% 征兵。
- 压测结果显示当前本地环境舒适区约 25-40 RPS，极限约 50 RPS；100 并发时 P95 延迟约 5.6 秒并出现少量超时和 MySQL unix socket I/O timeout。
- 面向“开服冲榜”的口径：
  - 50 人同时高频操作比较稳。
  - 100 人基本可承受但会变慢。
  - 200 人属于勉强可用，需要观察和优化。
  - 300 人开始明显卡顿。
  - 500-1000 人同时高频冲榜不建议直接开，需要先做限流、缓存、慢 SQL 分析和高频事务拆分。
