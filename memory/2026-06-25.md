# Hero3 Memory - 2026-06-25

## 本日核心共识

- Hero3 是以玩家城池发展为核心循环的 SLG 策略游戏。
- 游戏基础循环：新建存档 -> 升级建筑 -> 生产资源 -> 征兵 -> 打 NPC/玩家 -> 获取资源和奖励 -> 继续成长。
- 项目方向是“稳定核心 + 可扩展玩法模块”，但不要把暂定玩法写成长期必做规则。
- 核心不是所有玩法集合，而是玩家长期拥有的基础资产和基础能力。
- 玩法模块通过标准接口接入核心，不能绕过核心直接改玩家状态。

## 核心边界

- 游戏核心包含：玩家存档、资源、建筑、兵力、武将、道具、货币、Buff/加成、时间结算、奖励发放、通知/信函/战报接口、存档读写、事件管线。
- 技术核心包含：路由、统一响应、错误码、鉴权、配置、日志、数据库、事务、OpenAPI。
- 讨论“核心”时必须先区分技术核心和游戏核心。
- 如果新需求出现核心不兼容、需要绕过核心、需要直接乱改玩家状态的情况，必须先指出来，让用户决定是否补核心。

## 模块判断规则

- 具体玩法默认属于模块，不直接并入核心。
- 模块典型特征：有自己的参与规则、结算规则、读取/消耗玩家资产、产出奖励或模块状态，可以单独开发、开关、替换或暂缓上线。
- 尚未确定一定开发的玩法名称，不应写入长期决策规则。
- 每个新玩法模块设计前，先回答：读取什么状态、修改什么状态、使用或锁定什么资产、发放什么奖励、触发什么事件、是否需要自己的模块状态。

## 可扩展内容规则

- 资源是核心能力，但资源类型不应该写死在核心代码里。
- 新增资源类型应优先通过配置或注册表接入，不应该修改核心流程代码。
- 未来可能由多个模块新增、产出、修改或监听的内容，应优先考虑配置化或注册化。
- 优先配置化/注册化类型：资源类型、兵种、道具、武将、Buff/加成 key、奖励类型、事件类型。

## 当前架构观察

- `go/` 目前是 Go 后端单体服务。
- `internal/api/handlers.go` 过大，后续适合按模块拆分。
- `internal/game` 目前按 service 文件平铺，目录层次不够清晰，后续适合逐步向核心 + 模块目录演进。
- 现阶段不要一口气大拆；优先固化规则、记忆和文档，再做低风险结构调整。
- 数据库写入存在潜在性能和一致性风险：大量动作当前采用 `GetState -> 修改 -> SaveState`，会频繁整包读写 `players.state_json`。后续应考虑统一玩家状态事务入口，并逐步把高频资产拆成独立表。
