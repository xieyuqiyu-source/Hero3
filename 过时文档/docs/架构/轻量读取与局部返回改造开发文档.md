# <span style="color:#0ea5e9">Hero3 轻量读取与局部返回改造开发文档</span>

最后更新：2026-06-27

## <span style="color:#0ea5e9">1. 文档目的</span>

本文档用于指导 Hero3 完成“轻量读取接口 + 写操作局部返回”的性能闭环。

当前项目已经完成第一层改造：

- 已拆出资源、建筑、资源田、兵力、征兵队列、武将、武将占用、背包、Buff 等权威表。
- 已新增 `/api/v1/game/summary`、`/api/v1/city/view`、`/api/v1/resources/view`、`/api/v1/military/view`、`/api/v1/inventory/view`、`/api/v1/generals/view` 等局部视图接口。
- 前端已经有 `loadCityView`、`loadResourceView`、`loadMilitaryView`、`loadGeneralsView` 等局部刷新入口。

但当前仍未达成性能目标，核心原因是：

- 局部视图接口后端仍然先读取完整 `GameState`，再裁剪返回。
- 多个写操作仍返回完整 `GameState`。
- 前端仍有多个场景调用 `loadGameState()`。
- 压测脚本仍高频请求 `/api/v1/game/state`，没有模拟真实轻量化后的访问模式。

本文档的目标是把这件事做完，而不是只停留在“接口看起来轻量”。

## <span style="color:#0ea5e9">2. 最终目标</span>

完成后应达到以下状态：

- 高频页面不再请求完整 `GameState`。
- 局部视图接口不再通过完整 `GetState` 投影。
- 写操作默认不返回完整 `GameState`。
- 前端写操作成功后只合并局部结果，必要时再刷新对应局部视图。
- `/api/v1/game/state` 只作为低频兼容、排查、GM 或初始化兜底接口。
- 压测脚本按真实前端行为压测局部接口。

一句话目标：

```text
高频请求只读必要表，只返回必要字段；写请求只锁必要资产，只返回局部变化。
```

## <span style="color:#0ea5e9">3. 改造边界</span>

本次改造只解决玩家端高频读写路径，不引入 Redis，不重构 PVP，不改变玩法规则。

本次改造包含：

- 局部视图查询仓储。
- 局部视图服务。
- 写操作局部响应。
- 前端 `loadGameState()` 替换。
- 压测脚本访问模式更新。
- 文档和测试补齐。

本次改造不包含：

- Redis 缓存。
- 排行榜。
- 异步队列。
- 线上迁移执行。
- 战斗系统大重构。
- 完整删除 `GameState`。

## <span style="color:#0ea5e9">4. 当前问题定位</span>

### <span style="color:#0ea5e9">4.1 局部接口只是返回轻，读取不轻</span>

当前 `GetCityView`、`GetResourceView`、`GetMilitaryView` 等方法内部仍调用 `s.GetState(playerID)`。

这意味着：

- 返回体比完整状态小。
- 但数据库读取仍可能读取完整玩家聚合。
- 后端仍要组装完整 `GameState`。
- 并发高时，轻量接口性能提升有限。

必须把局部视图改为直接查询对应权威表。

### <span style="color:#0ea5e9">4.2 写操作返回完整状态</span>

当前大量写操作返回：

```json
{
  "state": { "完整 GameState": "..." }
}
```

这会导致：

- 写事务结束后又读取或组装完整状态。
- 响应体过大。
- 前端每次动作都覆盖整份状态。
- 页面局部刷新能力被浪费。

必须改为局部响应。

### <span style="color:#0ea5e9">4.3 前端仍有完整状态兜底滥用</span>

前端仍存在多个 `loadGameState()` 调用场景。

允许保留的场景：

- 首次选择存档后的兼容初始化。
- GM 或调试入口。
- 低频完整刷新按钮。

不应继续使用的场景：

- 页面布局自动刷新。
- 资源栏刷新。
- 城池页进入。
- 军事页进入。
- 升级建筑后。
- 征兵后。
- 地图操作后。
- 队列完成后。

### <span style="color:#0ea5e9">4.4 压测脚本仍在测旧路径</span>

当前压测脚本中约一半请求仍是：

```text
GET /api/v1/game/state
```

这会导致压测结论主要反映完整状态接口，而不是轻量化后的真实访问模式。

改造完成前后必须分别压测：

- 兼容旧模式。
- 玩家端真实模式。
- 纯局部读模式。
- 写操作局部返回模式。

## <span style="color:#0ea5e9">5. 后端目标结构</span>

### <span style="color:#0ea5e9">5.1 新增只读视图仓储接口</span>

在应用层新增或整理只读视图仓储接口：

```go
type PlayerViewRepository interface {
    GetPlayerSummaryView(playerID string) (PlayerSummaryView, error)
    GetCityView(playerID string) (CityView, error)
    GetResourceView(playerID string) (ResourceView, error)
    GetMilitaryView(playerID string) (MilitaryView, error)
    GetInventoryView(playerID string) (InventoryView, error)
    GetGeneralsView(playerID string) (GeneralsView, error)
}
```

要求：

- 只读。
- 不使用 `FOR UPDATE`。
- 不写 `players.state_json`。
- 不调用通用 `GetState`。
- 不触发修复逻辑。
- 不同步权威表。

### <span style="color:#0ea5e9">5.2 MySQL 只读查询职责</span>

MySQL 实现应按视图直接查表。

#### 玩家摘要视图

读取表：

- `players`
- `accounts`，如需要账号信息时
- `mails` 或 unread 计数字段
- `battle_reports` 或 unread 计数字段

返回字段：

- 玩家 ID
- 昵称
- 阵营
- 城金
- 未读信函数
- 未读战报数
- 服务器时间

不读取：

- 建筑
- 资源田
- 背包
- 兵力
- 武将完整列表
- `state_json` 大字段，除非过渡期某个字段还没有权威表

#### 资源视图

读取表：

- `player_resources`
- `player_buildings`，只用于产量和容量计算所需建筑
- `player_resource_slots`，只用于产量来源
- `player_buffs`，只读取未过期 Buff
- 必要时读取玩家轻量字段

返回字段：

- 当前资源
- 容量
- 产量
- 资源结算时间
- 产量加成
- 容量加成
- 生效 Modifier
- 服务器时间

注意：

- 只读接口可以做内存投影，展示“当前应该有多少资源”。
- 只读接口不能把投影结果写回资源表。
- 资源最终落库应由写命令或定时结算命令完成。

#### 城池视图

读取表：

- `players`
- `player_resources`
- `player_buildings`
- `player_resource_slots`
- `player_buffs`

返回字段：

- 玩家基础信息
- 建筑列表
- 资源田格子
- 当前资源展示
- 当前产量
- 城金
- 生效 Modifier
- 服务器时间

不读取：

- 背包
- 兵力
- 征兵队列
- 武将完整列表，除非建筑页面明确需要展示派驻武将

#### 军事视图

读取表：

- `player_army_units`
- `player_recruit_queues`
- `player_generals`
- `player_general_assignments`
- `player_buffs`
- 必要玩家轻量字段

返回字段：

- 兵力
- 征兵队列
- 当前主将
- 可用武将列表
- 武将占用
- 服务器时间

不读取：

- 背包
- 建筑完整列表
- 资源田完整列表，除非征兵速度需要建筑等级参与计算

#### 背包视图

读取表：

- `player_inventory`

返回字段：

- 背包物品
- 服务器时间

不读取：

- 资源
- 建筑
- 兵力
- 武将

#### 武将视图

读取表：

- `player_generals`
- `player_general_assignments`
- `player_buffs`

返回字段：

- 当前主将
- 武将列表
- 武将占用
- 生效 Modifier
- 服务器时间

不读取：

- 完整资源
- 完整建筑
- 背包
- 兵力，除非页面明确需要展示武将对兵力影响后的结果

### <span style="color:#0ea5e9">5.3 Service 层改造</span>

当前：

```go
func (s *Service) GetCityView(playerID string) (CityView, error) {
    state, err := s.GetState(playerID)
    ...
}
```

目标：

```go
func (s *Service) GetCityView(playerID string) (CityView, error) {
    return s.repo.GetCityView(playerID)
}
```

要求：

- 局部视图服务不再依赖完整 `GetState`。
- 共享投影逻辑可以抽函数，但输入必须是局部查询结果。
- 缺失旧数据时返回明确错误或空安全结果，不在查询中修复。

## <span style="color:#0ea5e9">6. 写操作局部返回设计</span>

### <span style="color:#0ea5e9">6.1 通用原则</span>

写接口默认返回：

- 本次命令结果。
- 受影响的局部视图。
- 必要的事件或提示。

写接口默认不返回：

- 完整 `GameState`。
- 与本次操作无关的模块数据。

建议响应格式：

```json
{
  "result": {},
  "patch": {},
  "serverTime": "2026-06-27T00:00:00Z"
}
```

或者按业务命名：

```json
{
  "building": {},
  "resources": {},
  "resourceProduction": {},
  "serverTime": "2026-06-27T00:00:00Z"
}
```

### <span style="color:#0ea5e9">6.2 建筑升级返回</span>

接口：

```text
POST /api/v1/city/buildings/upgrade
```

当前返回：

```json
{
  "state": {}
}
```

目标返回：

```json
{
  "building": {},
  "resources": {},
  "resourceSlots": [],
  "resourceProduction": {},
  "cityGold": 0,
  "serverTime": "..."
}
```

适用接口：

- `POST /api/v1/city/buildings/upgrade`
- `POST /api/v1/city/buildings/upgrade-batch`
- `POST /api/v1/city/buildings/instant`

验收：

- 升级后前端只更新建筑、资源、资源田、产量。
- 不刷新完整 `GameState`。
- 响应体明显小于完整状态。

### <span style="color:#0ea5e9">6.3 资源操作返回</span>

接口：

- `POST /api/v1/city/resources/fill`
- `POST /api/v1/city/resources/fill-paid`
- `POST /api/v1/city/boost`
- `POST /api/v1/city/capacity-boost`

目标返回：

```json
{
  "resources": {},
  "resourceProduction": {},
  "resourceSettledAt": "...",
  "productionBoost": 0,
  "productionBoostEnd": "...",
  "capacityBoost": 0,
  "capacityBoostEnd": "...",
  "cityGold": 0,
  "cost": 0,
  "serverTime": "..."
}
```

验收：

- 资源栏局部更新。
- 城金局部更新。
- 不返回背包、兵力、武将、信函、战报。

### <span style="color:#0ea5e9">6.4 征兵返回</span>

接口：

- `POST /api/v1/military/recruit`
- `POST /api/v1/military/recruit/instant`

目标返回：

```json
{
  "army": [],
  "recruitQueues": [],
  "resources": {},
  "serverTime": "..."
}
```

验收：

- 征兵后前端只更新军队队列、兵力和资源。
- 不刷新完整 `GameState`。

### <span style="color:#0ea5e9">6.5 武将操作返回</span>

接口：

- `POST /api/v1/military/general/stat`
- `POST /api/v1/military/general/reset-stats`
- `POST /api/v1/military/general/change`

目标返回：

```json
{
  "general": {},
  "generals": [],
  "generalAssignments": [],
  "activeModifiers": [],
  "accountGold": 0,
  "serverTime": "..."
}
```

验收：

- 武将页只更新武将相关字段。
- 洗点和切换武将只额外更新账号金币。

### <span style="color:#0ea5e9">6.6 地图和战斗返回</span>

接口：

- `POST /api/v1/map/npc-cities/attack`
- `POST /api/v1/map/npc-cities/scout`
- `POST /api/v1/map/npc-cities/refresh`

目标返回：

攻击：

```json
{
  "battleReport": {},
  "resources": {},
  "army": [],
  "npcCity": {},
  "serverTime": "..."
}
```

侦查：

```json
{
  "success": true,
  "battleReport": {},
  "npcCity": {},
  "serverTime": "..."
}
```

刷新：

```json
{
  "cities": [],
  "lastRefreshedAt": "...",
  "serverTime": "..."
}
```

验收：

- 地图操作后不调用 `loadGameState()`。
- 只更新地图、战报、资源、兵力等受影响字段。

### <span style="color:#0ea5e9">6.7 信函和奖励返回</span>

接口：

- `POST /api/v1/mails/{mailId}/claim`
- 小游戏兑换接口
- 后续活动领奖接口

目标返回：

```json
{
  "claimed": true,
  "rewards": [],
  "resources": {},
  "inventory": {},
  "army": [],
  "generals": [],
  "cityGold": 0,
  "accountGold": 0,
  "serverTime": "..."
}
```

验收：

- 领奖只返回实际受影响资产。
- 不因为奖励系统统一而返回完整状态。

## <span style="color:#0ea5e9">7. 前端改造清单</span>

### <span style="color:#0ea5e9">7.1 `loadGameState()` 保留范围</span>

允许保留：

- 选择存档后第一次进入游戏。
- 手动完整刷新按钮。
- 调试和排查入口。
- 后端返回局部补丁失败后的兜底。

必须替换：

- `Layout` 自动刷新。
- `Sidebar` 切换存档后的重复刷新。
- `ResourceBar` 资源刷新。
- `CityPage` 进入和操作后刷新。
- `MilitaryPage` 进入和操作后刷新。
- `BuildingCard` 升级后刷新。
- `ResourceSlot` 操作后刷新。
- `RecruitQueuePanel` 操作后刷新。
- `NpcCityTab` 攻击、侦查、刷新后刷新。

### <span style="color:#0ea5e9">7.2 Store 局部合并规则</span>

前端 store 应保留一个 `patchState`，但要明确局部响应对应哪些字段。

建议新增专门方法：

```ts
patchCityView(view)
patchResourceView(view)
patchMilitaryView(view)
patchGeneralsView(view)
patchInventoryView(view)
patchBuildingActionResult(result)
patchRecruitActionResult(result)
patchBattleActionResult(result)
```

要求：

- 不用完整 `state` 覆盖局部状态。
- 不因为某个局部响应缺字段而清空其他模块。
- 响应里没有的字段保持原值。
- `serverTime` 和 `stateReceivedAt` 统一更新。

### <span style="color:#0ea5e9">7.3 页面刷新规则</span>

资源栏：

- 页面启动时调用 `loadResourceView()`。
- 资源相关操作后合并资源结果。

城池页：

- 进入页面调用 `loadCityView()`。
- 升级建筑后合并建筑操作结果。
- 不再调用 `loadGameState()`。

军事页：

- 兵力和征兵页签调用 `loadMilitaryView()`。
- 武将页签调用 `loadGeneralsView()`。
- 征兵后合并征兵结果。
- 武将操作后合并武将结果。

地图页：

- NPC 列表调用地图接口。
- 攻击后只合并战报、资源、兵力、NPC 城池结果。
- 侦查后只合并侦查结果和 NPC 城池结果。

增援页：

- 列表继续走增援接口。
- 发起增援后只刷新军队视图和增援列表。
- 不刷新完整状态。

## <span style="color:#0ea5e9">8. 压测脚本改造</span>

### <span style="color:#0ea5e9">8.1 新增压测模式</span>

压测脚本新增参数：

```text
--mode legacy
--mode frontend
--mode readonly
--mode write-local
```

模式含义：

- `legacy`：旧模式，保留高频 `/game/state`，用于对比。
- `frontend`：模拟真实前端，主要访问局部视图和局部写接口。
- `readonly`：只测局部只读视图。
- `write-local`：只测升级、征兵等局部写操作。

### <span style="color:#0ea5e9">8.2 frontend 模式请求比例</span>

建议比例：

```text
resources/view       25%
city/view            20%
military/view        15%
map/npc-cities       15%
city upgrade         10%
military recruit     10%
game/summary          5%
game/state            0%
```

注意：

- `game/state` 在 frontend 模式中应为 0%。
- 如果必须保留完整刷新，只能单独做低频场景。

### <span style="color:#0ea5e9">8.3 验收压测档位</span>

继续使用：

```text
10:200,25:500,50:1000,100:2000
```

可以追加：

```text
150:3000,200:4000
```

但追加档位只在 100 并发表现稳定后执行。

## <span style="color:#0ea5e9">9. 阶段开发计划</span>

### <span style="color:#0ea5e9">阶段一：修正压测口径</span>

目标：

- 先让压测脚本能区分旧模式和真实前端模式。

任务：

- 给 `scripts/loadtest_hero3.py` 增加 `--mode`。
- 保留 `legacy` 模式。
- 新增 `frontend` 模式。
- 新增 `readonly` 模式，分别请求局部视图。
- 输出结果中按接口名统计。

验收：

- 可以复现旧压测。
- 可以跑不含 `/game/state` 的新压测。
- 结果能看出每类接口的请求量和状态码。

### <span style="color:#0ea5e9">阶段二：局部视图后端真实轻量化</span>

目标：

- 所有局部视图不再调用 `GetState`。

任务：

- 新增 `PlayerViewRepository`。
- MySQL 实现各局部视图只读查询。
- MemoryRepository 实现兼容版本。
- Service 层局部视图改为调用仓储局部方法。
- 补测试确认局部视图不触发完整状态读取。

验收：

- `GetCityView` 等方法不再调用 `s.GetState`。
- MySQL 局部视图不读无关权威表。
- `go test ./...` 通过。
- `readonly` 压测相比旧 `game/state` 明显下降延迟。

### <span style="color:#0ea5e9">阶段三：建筑和资源写接口局部返回</span>

目标：

- 城池和资源操作不返回完整状态。

任务：

- 定义建筑操作响应结构。
- 定义资源操作响应结构。
- 后端 handler 改响应。
- OpenAPI 更新。
- 前端 API 类型更新。
- 前端城池页、资源栏改为合并局部结果。

验收：

- 建筑升级后不调用 `loadGameState()`。
- 资源补满、购买加成后不调用 `loadGameState()`。
- 页面展示正确。
- 响应体不包含完整 `state`。

### <span style="color:#0ea5e9">阶段四：军事和武将写接口局部返回</span>

目标：

- 征兵、队列完成、武将操作不返回完整状态。

任务：

- 定义征兵响应结构。
- 定义武将操作响应结构。
- 改 handler 和 OpenAPI。
- 前端军事页按结果合并。
- 清理军事相关 `loadGameState()`。

验收：

- 征兵后只更新资源、兵力、征兵队列。
- 武将加点、洗点、切换只更新武将相关字段。
- 响应体不包含完整 `state`。

### <span style="color:#0ea5e9">阶段五：地图、信函、小游戏局部返回</span>

目标：

- 高频玩法操作不再返回完整状态。

任务：

- NPC 攻击只返回战报、资源、兵力、NPC 城池。
- NPC 侦查只返回侦查结果、战报、NPC 城池。
- 信函领奖只返回奖励实际影响的资产。
- 小游戏兑换只返回库存、兵力、奖励结果。
- 前端页面合并局部结果。

验收：

- 地图页操作后不调用 `loadGameState()`。
- 信函领奖后不调用 `loadGameState()`。
- 小游戏兑换后不调用 `loadGameState()`。

### <span style="color:#0ea5e9">阶段六：清理完整状态依赖</span>

目标：

- 玩家端高频路径基本不依赖完整状态。

任务：

- 全局搜索 `loadGameState()`。
- 给每个调用点标注用途。
- 高频调用全部替换。
- 只保留白名单调用。
- 搜索 API 返回 `{ state: GameState }`。
- 高频写接口全部改掉。

验收：

- 玩家端普通操作流程不会请求 `/api/v1/game/state`。
- `/api/v1/game/state` 只在初始化、手动刷新或调试时出现。
- 压测 `frontend` 模式不包含完整状态请求。

### <span style="color:#0ea5e9">阶段七：复测和容量判断</span>

目标：

- 用真实访问模式重新判断开服冲榜容量。

任务：

- 跑 `legacy` 模式，保留对比。
- 跑 `frontend` 模式，作为正式容量依据。
- 跑 `readonly` 模式，检查读路径上限。
- 跑 `write-local` 模式，检查写事务上限。
- 记录 RPS、P95、P99、错误码、业务冲突比例。

验收建议：

- 并发 50：P95 小于 500ms。
- 并发 100：P95 小于 1000ms。
- 并发 100：无 5xx，无超时。
- 业务冲突可以存在，但需要区分资源不足、重复升级等正常拒绝。

## <span style="color:#0ea5e9">13. 预期效果</span>

完成本改造后，预期变化：

- 并发下延迟明显下降。
- 写接口响应体明显变小。
- 数据库读取表数量减少。
- 完整状态接口不再成为玩家端高频瓶颈。
- 后续加 Redis 时可以直接缓存局部视图，而不是缓存完整大状态。

保守目标：

- 当前本地测试环境下，并发 100 的玩家端真实模式 P95 应明显低于旧模式。
- 如果仍达不到开服冲榜目标，再进入 Redis、连接池、SQL 索引和热点缓存优化阶段。

## <span style="color:#0ea5e9">14. 不允许的做法</span>

- 不允许局部视图继续调用完整 `GetState` 后声称性能完成。
- 不允许写操作继续返回完整 `GameState` 后只在前端裁剪。
- 不允许为了省事让前端操作后统一 `loadGameState()`。
- 不允许把 Redis 当作掩盖重接口的第一方案。
- 不允许新增业务接口默认返回完整状态。
- 不允许压测继续只看旧 `/game/state` 结果后判断真实容量。
