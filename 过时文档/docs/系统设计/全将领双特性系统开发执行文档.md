# 全将领双特性系统开发执行文档

最后更新：2026-07-03

## 1. 文档定位

本文档是将领双特性系统的开发执行文档，用于指导 AI 或开发者按统一方向完成系统开发。

实现备注（2026-07-03）：当前代码中的现有将领配置实际为 25 位（魏 9、蜀 8、吴 8），不是删除到 24 位；验收口径调整为“全部现有启用将领都必须拥有 `specialTrait` 和 `bonusTrait`”。后端核心注册表已覆盖不少于 24 条特殊特性和 24 条加成特性。

本文档不绑定具体文件路径，不要求逐行指定实现位置。开发时应先阅读并遵循：

- `PROJECT_RULES.md`
- `docs/系统设计/全将领特性平衡设计文档.md`
- 当前代码中的将领、战斗、行军、征兵、增援、战报和 GM 配置实现

如果本文档和设计文档出现冲突，以本开发执行文档中的开发边界和验收标准为准；玩法细节以设计文档为准。

## 2. 最终目标

完成 Hero3 全将领双特性系统。

最终效果：

- 每个将领固定拥有两条特性：
  - 一个特殊特性 `specialTrait`
  - 一个加成特性 `bonusTrait`
- 当前全部现有将领配置完整，至少覆盖 24 位将领、48 条将领特性；代码当前实际覆盖 25 位现有将领。
- 特性不按稀有度分强弱。
- 图片中的百分比、固定值和特殊效果进入 GM 可配置参数。
- 特性通过核心事件管线生效，不散落硬编码到 PVP、NPC、增援等玩法代码里。
- 战斗、行军、征兵、增援、掠夺、战报、GM 和前端展示都能识别双特性。

一句话目标：

> 玩家换不同将领，应当真实改变战斗、行军、征兵、掠夺、增援或资源体验，而不是只改变前端展示。

## 3. 核心规则

### 3.1 双特性规则

每个将领必须同时拥有：

- `specialTrait`：特殊特性
- `bonusTrait`：加成特性

特殊特性示例：

- 曹操：每分钟获得虎卫
- 甄宓：俘虏敌兵
- 刘备：复活阵亡士兵
- 周瑜：火烧赤壁
- 张飞：震慑全军
- 吕蒙：隐秘行军
- 黄盖：压制敌方特性

加成特性示例：

- 步兵攻击提升
- 骑兵攻击提升
- 全军防御提升
- 队伍速度提升
- 武将攻击提升
- 武将防御提升
- 敌方防御降低

### 3.2 无稀有度强弱

现有 `rarity` 字段只能作为历史兼容字段，不参与：

- 战斗强度
- 特性强度
- 排序权重
- 抽取价值判断
- 玩家选择引导

不允许设计“高稀有将领天然更强”。

### 3.3 GM 可配置

图片中的数值必须进入 GM 配置或配置文件参数，不能写死在代码里。

必须支持的典型参数：

- `triggerChance`
- `effectRate`
- `captureRate`
- `maxCapturePerUnit`
- `resourceCostReduction`
- `guardPerMinute`
- `attackBonusRate`
- `defenseBonusRate`
- `speedBonusRate`
- `generalAttackFlat`
- `generalDefenseFlat`
- `unitAttackFlat`
- `targetUnitType`
- `scope`
- `minMarchSeconds`

强效果必须配置安全上限，避免无限复活、无限俘虏、无限压制、无限秒到。

## 4. 开发边界

### 4.1 应该做

- 建立或完善双特性配置结构。
- 兼容旧的单特性或 `traits: []` 配置。
- 将全部现有将领补齐为双特性配置，至少覆盖 48 条特性。
- 让特性通过核心事件管线触发。
- 战斗、行军、征兵、掠夺、增援等流程接入特性事件。
- 战报显示实际触发的特性结果。
- GM 后台可以查看、配置、启用、禁用双特性。
- 前端将领详情展示特殊特性和加成特性。
- 增援武将参与防守时，符合边界地触发特性。
- 增加必要测试。
- 同步文档。

### 4.2 不应该做

- 不要把周瑜、刘备、张飞等特性写死在 PVP 或 NPC 代码里。
- 不要让玩法模块绕过核心直接改长期资产。
- 不要让将领稀有度影响特性强度。
- 不要把图片中的百分比写死。
- 不要让增援武将默认加成全体守军。
- 不要让某个特性无上限影响全军、全服、所有战斗。
- 不要为了快速实现而复制多套战斗逻辑。

## 5. 核心事件接入方向

需要通过统一事件或统一能力接入，而不是每个玩法单独写一套。

必须考虑的事件阶段：

| 阶段 | 用途 |
|---|---|
| 战斗前 | 偷袭、震慑、俘虏、水淹、奇门遁甲、隐秘攻击 |
| 战斗结算后 | 火烧、追加伤害、破防、减损、反击 |
| 战斗结束后 | 复活、返还损失、战败止损、战报记录 |
| 行军创建时 | 速度加成、闪电战、隐秘行军 |
| 征兵消耗时 | 资源消耗降低、征兵返还 |
| 资源结算时 | 资源产量加成 |
| 掠夺结算时 | 掠夺收益提高或降低 |
| 增援参战时 | 增援武将特性触发 |
| 侦查结算时 | 后续侦查类特性预留 |

## 6. 增援特性规则

增援队伍携带武将时，武将特性可以在防守战中触发。

默认规则：

- 增援武将特性只影响自己的增援队伍。
- 不影响接收方主城兵。
- 不影响其他玩家援军。
- 主动进攻限定特性默认不在增援防守中触发。
- 如果某特性要影响全体守军，必须显式配置 `scope=all_defenders`。
- 战报必须说明是哪位玩家的哪支援军触发了什么特性。

## 7. 战报目标

战报必须能显示特性触发结果。

战报至少应表达：

- 触发方
- 触发将领
- 特性名称
- 特性类型
- 作用对象
- 关键参数
- 实际结果

示例：

```text
周瑜触发【火烧赤壁】，敌方步兵额外损失 1200。
刘备触发【仁德天下】，己方阵亡士兵复活 50%。
玩家 A 的援军武将张飞触发【震慑全军】，敌方部分进攻兵力未参战。
黄盖触发【苦肉计】，敌方本场部分将领特性失效。
```

## 8. GM 目标

GM 后台最终需要支持：

- 查看全部特性。
- 按特殊特性、加成特性筛选。
- 查看特性参数 schema。
- 给将领配置 `specialTrait`。
- 给将领配置 `bonusTrait`。
- 调整百分比、固定值、作用范围、触发概率。
- 启用或禁用单条特性。
- 保存时做配置校验。

配置校验必须包括：

- 每个启用将领必须有一个特殊特性和一个加成特性。
- 特性 ID 必须存在。
- 特性类型必须正确。
- 参数不能超过上下限。
- 百分比使用 0 到 1 的小数。
- 强效果必须有作用范围或上限。

## 9. 前端目标

玩家侧前端需要做到：

- 将领详情页展示两条特性。
- 特殊特性和加成特性视觉上区分。
- 显示触发条件、效果说明和关键数值。
- 不展示稀有度强弱引导。
- 战报中展示实际触发的特性。
- 增援相关战报显示援军来源和触发武将。

## 10. 开发阶段建议

### 10.1 第一阶段：结构与兼容

目标：

- 完成双特性结构。
- 兼容旧配置。
- 将当前全部现有将领补齐为双特性配置。
- GM 和前端能读取双特性。

完成后，即使特性还没有全部生效，也应能看到正确配置和展示。

### 10.2 第二阶段：战斗类特性

目标：

- 接入战斗前、战斗结算后、战斗结束后事件。
- 实现火烧、震慑、俘虏、复活、破防、增伤、减损等。
- 战报能显示触发结果。

### 10.3 第三阶段：行军、征兵、资源、掠夺

目标：

- 接入速度类特性。
- 接入征兵消耗降低。
- 接入资源产量加成。
- 接入掠夺收益加成。
- 支持闪电战、隐秘行军等特殊效果。

### 10.4 第四阶段：增援和高级规则

目标：

- 增援武将特性参与防守。
- 特性默认只影响自己的增援队伍。
- 支持特性压制、敌方特性失效等高级效果。
- 补齐战报展示和测试。

## 11. 测试方向

必须覆盖：

- 将领没有双特性时配置校验失败。
- 特性 ID 不存在时配置校验失败。
- 百分比超出范围时配置校验失败。
- 战斗前特性可以改变参战结果。
- 战斗后特性可以改变损失结果。
- 战斗结束后特性可以复活或返还。
- 行军速度特性影响行军时间。
- 征兵消耗特性影响资源消耗。
- 掠夺特性影响掠夺收益。
- 增援武将特性只影响自己的援军。
- 战报显示实际触发的特性。

## 12. 验收标准

功能验收：

- 全部现有将领都有 `specialTrait` 和 `bonusTrait`。
- 至少 48 条特性均有 ID、名称、类型、参数 schema 和展示文案。
- 图片中的百分比和固定值进入配置，GM 可调。
- 特性通过统一事件管线触发。
- PVP、NPC、增援相关战斗可以触发对应特性。
- 行军、征兵、资源、掠夺类特性可以生效。
- 战报能显示特性触发结果。
- GM 后台可以配置双特性。
- 前端将领页展示双特性。

架构验收：

- 不按稀有度决定强度。
- 不在各玩法中硬编码具体将领。
- 不绕过核心直接修改长期资产。
- 旧配置有兼容或迁移方案。
- 强效果都有 GM 上限和作用范围。

文档验收：

- 更新设计文档。
- 更新开发相关 README 或 docs。
- 如新增或修改接口，同步 OpenAPI。
- 如修改 GM 能力，同步 GM 后台说明。
