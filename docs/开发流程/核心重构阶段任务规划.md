# <span style="color:#0f766e">Hero3 核心重构阶段任务规划</span>

最后更新：2026-06-26
## <span style="color:#0f766e">1. 文档目的</span>

本文档用于把 Hero3 当前“稳定核心 + 多模块组装”的重构工作拆成可连续执行的阶段任务。

后续开发不再反复询问“下一步做什么”，默认按本文档推进；如果用户提出新的优先级，则先判断是否和 `PROJECT_RULES.md` 冲突，再调整阶段顺序。

本文档不是玩法最终设计文档，而是工程实施规划。具体玩法规则仍放在产品、系统设计或未来开发规划文档中。

## <span style="color:#0f766e">2. 总体目标</span>

最终目标：

- 玩家长期资产从 `players.state_json` 逐步拆成权威表。
- `players.state_json` 保留为玩家视角兼容快照，不再承担高频资产权威判断。
- 所有玩法模块通过核心事务、奖励、Effect Pipeline、注册表和事件管线接入长期资产。
- 后端目录按核心系统、应用系统、玩法模块、基础设施归口，避免继续出现超长文件和职责混杂。
- 数据库迁移、回填、校验、复制测试库形成固定流程，避免线上玩家数据被重构误伤。
- Web、Admin、OpenAPI、README、docs 随业务变化同步更新。

## <span style="color:#0f766e">3. 当前已完成基线</span>

### <span style="color:#0f766e">3.1 核心事务基线</span>

已完成：

- `UpdatePlayerState`：统一玩家状态事务入口。
- `UpdateAccountPlayerState`：账号资产 + 玩家状态组合事务入口。
- `UpdateMailPlayerState`：信函 + 玩家 + 账号组合事务入口。
- `UpdateMiniGamePlayerState`：小游戏记录 + 玩家组合事务入口。
- 旧 `SaveState` 直接覆盖入口已移除。

验收状态：

- 后续业务不得重新引入散落式 `GetState -> 修改 -> SaveState`。
- 新模块涉及玩家长期资产时，必须优先找核心事务入口。

### <span style="color:#0f766e">3.2 标准奖励与效果管线基线</span>

已完成：

- 标准 Reward 契约。
- `ApplyRewardsToStateWithContext`。
- `GrantRewards`。
- `ExecuteEffects`。
- `ExecuteEffectsWithAccount`。
- Reward / Building Mutation / Modifier 三类基础 Effect。

验收状态：

- 道具、信函、小游戏等产出长期资产时，应转换为标准 Effect 或标准 Reward。
- 如果新玩法需要影响长期资产，优先接入 Effect Pipeline，不直接改状态字段。

### <span style="color:#0f766e">3.3 已拆出的权威表</span>

已完成：

- `player_resources`：玩家资源权威表。
- `player_inventory`：玩家背包权威表。
- `player_buildings`：玩家建筑权威表。
- `player_resource_slots`：玩家资源田格子权威表。
- `player_army_units`：玩家兵力权威表。
- `player_recruit_queues`：玩家征兵队列权威表。
- `player_generals`：玩家武将权威表。
- `player_general_assignments`：玩家武将占用权威表。
- `player_buffs`：玩家 Buff/Modifier 权威表。
- `backfill-resources` / `verify-resources`。
- `backfill-inventory` / `verify-inventory`。
- `backfill-buildings` / `verify-buildings`。
- `backfill-resource-slots` / `verify-resource-slots`。
- `backfill-army` / `verify-army`。
- `backfill-recruit-queues` / `verify-recruit-queues`。
- `backfill-generals` / `verify-generals`。
- `backfill-buffs` / `verify-buffs`。
- `clone-data` 复制测试库后自动刷新资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表。
- `event_processing_records`：玩法模块事件处理幂等记录。

当前结论：

- 资源和背包已经不应再依赖 `state_json` 做最终判断。
- 建筑和资源田格子已经进入权威表第一轮。
- 兵力和征兵队列已经进入权威表第一轮。
- 武将和武将占用已经进入权威表第一轮。
- Buff/Modifier 已经进入权威表第一轮。
- `state_json.resources`、`state_json.inventory`、`state_json.buildings`、`state_json.resourceSlots`、`state_json.army`、`state_json.recruitQueues`、`state_json.general`、`state_json.generals`、`state_json.generalAssignments` 和 `state_json.buffs` 只作为兼容快照。

## <span style="color:#0f766e">4. 阶段一：建筑权威表与资源田格子</span>

阶段状态：第一版完成。建筑和资源田格子权威表、回填校验工具、事务接入、建造司金币升级、建造司按等级新增资源田已经完成第一轮。

目标：

- 把玩家建筑从 `players.state_json` 拆到 `player_buildings`。
- 把资源田格子拆成独立结构，支持建造司按等级增加资源田。
- 为后续模块新增建筑、损坏建筑、占领建筑、禁用建筑提供稳定地基。

核心任务：

- 新增 `player_buildings` 表，保存玩家建筑 ID、等级、状态、升级时间、扩展数据。
- 新增 `player_resource_slots` 表，保存资源田格子、资源类型、解锁来源、建筑绑定关系。
- 保留 `state_json.buildings` 兼容快照。
- 建筑读取以 `player_buildings` 为准。
- 资源田展示以 `player_resource_slots` 为准。
- 建造司等级规则接入资源田格子计算。
- 建造司升级使用账号金币或指定金币资产时，必须走账号 + 玩家组合事务。
- 新增 `backfill-buildings` / `verify-buildings`。
- 新增 `backfill-resource-slots` / `verify-resource-slots`。
- 更新数据库设计、核心地基设计、未来开发规划。

验收标准：

- `go test ./...` 通过。
- `make verify-resources` 通过。
- `make verify-inventory` 通过。
- `make verify-buildings` 通过。
- `make verify-resource-slots` 通过。
- Web 城池页能显示原有建筑和新增资源田。
- Admin 能查看玩家建筑和资源田状态。
- 旧存档可通过回填工具迁移。
- 建造司 1/5/10/15/20 级各解锁 1 个额外资源田；25 级暂不新增，避免和“总共 5 个新资源田”的规则冲突。

暂停条件：

- 如果现有建筑模型无法表达“模块新增建筑”或“资源田格子”，必须先补核心注册表，不允许硬编码特殊玩法。

## <span style="color:#0f766e">5. 阶段二：兵力与征兵权威表</span>

阶段状态：第一版完成。兵力和征兵队列权威表、回填校验工具、事务接入和测试库验证已经完成第一轮。

目标：

- 把玩家兵力、征兵队列从 `state_json` 拆成权威表。
- 支持后续玩法消耗兵、返还兵、临时兵、超级兵、模块专属兵种。

核心任务：

- 新增 `player_army_units` 表，保存玩家长期兵力。
- 新增 `player_recruit_queues` 表，保存征兵队列。
- 兵种类型继续走注册表，不在核心流程硬编码。
- 超级兵、特殊兵种必须先注册为标准兵种或模块兵种，再进入兵力表。
- 战斗扣兵、征兵完成、奖励发兵必须统一走核心兵力入口或 Effect。
- 保留 `state_json.army` 和征兵队列兼容快照。
- 新增 `backfill-army` / `verify-army`。
- 新增 `backfill-recruit-queues` / `verify-recruit-queues`。

验收标准：

- 征兵、取消、完成、战斗扣兵、奖励发兵全部通过权威表。
- 兵力不足判断以 `player_army_units` 为准。
- 战斗回放和战报不因拆表丢失兵力信息。
- `go test ./...`、web/admin lint/build 通过。

暂停条件：

- 如果特殊兵种生命周期无法用现有兵种注册表表达，先补注册表字段，不允许在战斗模块里写私有兵种分支。

## <span style="color:#0f766e">6. 阶段三：武将权威表与多武将体系</span>

阶段状态：第一版完成。武将权威表、武将占用表、标准 `general` 奖励类型、回填校验工具、事务接入和测试库验证已经完成第一轮。

目标：

- 支持玩家拥有多个武将。
- 武将获取、升级、属性点、上阵、复活兵、特性触发都走统一武将系统。
- 为“物品增加一个新武将”“天下名将派将玩法”留出接口。

核心任务：

- 新增 `player_generals` 表，保存玩家已拥有武将。
- 新增 `player_general_assignments` 表，保存武将上阵、驻守、派遣、模块占用关系。
- 武将配置走注册表，新增武将不改核心流程代码。
- 物品产出武将时，转换为标准 Effect 或标准 Reward。
- 多武将兼容旧存档主将结构。
- 武将特性仍接入核心特性总线，不让玩法模块直接改长期资产。
- 新增 `backfill-generals` / `verify-generals`。

验收标准：

- 旧玩家主将可迁移为 `player_generals` 中的一名武将。
- 玩家可拥有多个武将。
- 道具发放武将不需要改核心代码。
- 战斗读取上阵武将稳定。
- 派遣类玩法能锁定武将占用状态。

暂停条件：

- 如果派遣、上阵、驻守互斥关系不清晰，先补武将占用状态规则，不直接开发玩法。

## <span style="color:#0f766e">7. 阶段四：Buff、Modifier 与长期加成权威化</span>

阶段状态：第一版完成。`player_buffs` 权威表、回填校验工具、事务接入和测试库验证已经完成第一轮；Modifier 管线继续保留现有聚合机制。

目标：

- 让所有加成来源可追踪、可过期、可叠加、可审计。
- 支持建筑、武将、道具、据点、副本、活动、联盟等来源共同影响产量、容量、征兵、战斗。

核心任务：

- 新增 `player_modifiers` 或 `player_buffs` 权威表。
- 明确 Buff、DeBuff、永久加成、模块占领加成的字段差异。
- Modifier key 全部注册化。
- 加成计算只读统一 Modifier 聚合结果。
- 保留 `state_json.buffs` 兼容快照。
- 新增 `backfill-buffs` / `verify-buffs`。

验收标准：

- 资源产量、容量、征兵速度、战斗属性等加成来源可追踪。
- 过期 Buff 不继续生效。
- 同类加成叠加规则有测试覆盖。
- 新增据点加成时不需要改资源计算核心流程。

暂停条件：

- 如果新加成 key 没有注册，不允许直接在业务里用字符串计算。

## <span style="color:#0f766e">8. 阶段五：事件管线与模块接入标准</span>

阶段状态：第一版完成。已新增模块事件处理幂等表和 `ClaimEventForModule` 标准入口；事件仍通过现有 EventBus 发布，后续模块监听事件前必须先声明边界和幂等处理 key。

目标：

- 给副本、据点、NPC 反攻、信函、任务、运营活动提供统一事件订阅和模块接入方式。

核心任务：

- 明确核心事件类型注册表。
- 明确事件载荷结构和版本。
- 玩法模块先登记边界，再监听事件。
- 事件不能直接绕过核心写长期资产，只能触发 Effect 或模块自身状态更新。
- 增加事件审计或调试日志。
- 新增 `event_processing_records` 幂等记录。
- 新增 `ClaimEventForModule(moduleID, handlerKey, event)` 标准入口。
- 为后续任务、成就、活动累计提供事件基础。

验收标准：

- 新模块接入前必须声明：读取什么、修改什么、监听什么、发放什么。
- 事件触发和 Effect 执行有测试覆盖。
- 任一模块不能直接写资源、背包、兵力、建筑、武将权威表。
- 模块事件处理必须先 claim 幂等 key，重复事件不得重复发奖。

暂停条件：

- 如果事件监听会导致循环触发或重复发奖，先补幂等 key 和事件处理状态。

## <span style="color:#0f766e">9. 阶段六：玩法模块框架</span>

阶段状态：第一版完成。已新增玩法模块通用实例表、参与记录表和结算记录表；具体副本、据点、活动规则仍待后续按模块单独实现。

目标：

- 把副本、据点、活动、NPC 动态事件都放入统一玩法模块框架。
- 核心只提供接口，不理解具体玩法细节。

核心任务：

- 建立玩法模块目录规范。
- 建立模块配置、模块状态、模块参与记录、模块奖励结算的通用约定。
- 新增活动/副本通用表，例如模块实例、参与记录、结算记录。
- 新增据点类模块通用结构，例如归属、占领、加成、刷新。
- 新增 NPC 动态事件模块结构，例如触发条件、目标选择、行军、结算。
- 先选一个最小玩法做样板，验证模块框架。

验收标准：

- 新玩法可以按模板新增目录、配置、状态表、接口、测试。
- 玩法模块修改长期资产必须通过 Effect Pipeline。
- 玩法模块可独立开关。
- Admin 可以查看模块状态和关键配置。

暂停条件：

- 如果具体玩法规则不确定，只搭模块框架，不硬做数值和平衡。

## <span style="color:#0f766e">10. 阶段七：API、Web、Admin 与 OpenAPI 收口</span>

阶段状态：第一版完成。Web/Admin 类型、OpenAPI、README/docs 已同步；Admin 玩家详情/抽屉已补资源、背包、建筑、资源田、武将、武将派驻、Buff、军队、征兵队列等核心资产展示；本地浏览器联调和 API 核心链路已通过。

目标：

- 后端重构完成后，前端、后台和接口文档同步收口。

核心任务：

- Web 适配建筑、资源田、兵力、武将、Buff 拆表后的返回结构。
- Admin 增加权威表查看、回填校验状态、玩家资产调试入口。
- OpenAPI 更新所有变更接口。
- README 和 docs 更新本地开发、迁移、校验命令。
- 删除或标记过期接口。

验收标准：

- web lint/build 通过。
- admin lint/build 通过。
- 核心玩家流程浏览器联调通过：注册、建档、升级建筑、资源刷新、征兵、战斗、道具、信函。
- OpenAPI 可导入并与后端接口一致。

验收记录：

- 已重启当前工作区 dev 服务后执行验证，避免旧服务进程污染结论。
- 新测试账号创建魏/曹操存档后，`player_generals` 与 `player_general_assignments` 正确写入，`GameState.generals` 和 `GameState.generalAssignments` 返回正常。
- API 核心链路通过：资源刷新、建筑升级与加速、征兵与加速、NPC 战斗、GM 发道具、使用道具、GM 发信函、信函列表读取。
- 浏览器玩家端可正常加载城池页，显示资源、产量、曹操等级、青州军数量，无控制台错误。
- 浏览器 Admin 可正常加载玩家列表和详情；详情中能看到资源、建筑、资源田格子、武将、武将派驻和军队。
- 本地旧测试存档如果缺少新权威表行，会触发明确错误；必须先执行对应 `backfill-*` 和 `verify-*`。本轮已在 `test_hero3` 执行资源、背包、建筑、资源田、兵力、征兵队列、武将、Buff 全量回填和校验通过。

暂停条件：

- 如果前端依赖旧 JSON 字段，应先提供兼容返回，不直接让页面大面积崩掉。

## <span style="color:#0f766e">11. 阶段八：线上迁移与发布</span>

目标：

- 在不影响稳定玩家的前提下，把本地核心重构安全迁移到线上。

核心任务：

- 对照线上库和本地库表结构。
- 编写正式迁移脚本或迁移步骤。
- 先在本地 `test_hero3` 复制线上数据做迁移演练。
- 每个权威表执行 backfill 和 verify。
- 记录迁移耗时、影响行数、失败回滚方式。
- 发布前备份线上数据库。
- 发布后观察错误日志、接口延迟、玩家核心流程。

验收标准：

- 本地克隆线上数据迁移演练通过。
- 所有 verify 工具通过。
- 线上迁移步骤可重复、可回滚、可审计。
- 发布后核心流程可用。

暂停条件：

- 如果本地表结构和线上结构不一致且没有迁移脚本，不允许直接部署后端。
- 如果 verify 工具不通过，不允许继续发布。

## <span style="color:#0f766e">12. 固定执行顺序</span>

默认执行顺序：

1. 建筑权威表与资源田格子。
2. 兵力与征兵权威表。
3. 武将权威表与多武将体系。
4. Buff、Modifier 与长期加成权威化。
5. 事件管线与模块接入标准。
6. 玩法模块框架。
7. API、Web、Admin 与 OpenAPI 收口。
8. 线上迁移与发布。

每个阶段完成前必须做：

- 更新对应 docs。
- 更新当天 memory。
- 补回填和校验工具。
- 补关键测试。
- 跑后端全量测试。
- 跑相关前端 lint/build。
- 检查 `git diff --check`。

## <span style="color:#0f766e">13. 不允许跳过的原则</span>

- 不允许玩法模块直接写玩家长期资产权威表。
- 不允许新增资产类型只改前端，不补后端注册表。
- 不允许只改 `state_json`，不维护权威表。
- 不允许上线前没有 backfill 和 verify。
- 不允许数据库结构变化没有文档记录。
- 不允许为了短期功能把核心边界写乱。
- 不允许把新 SQL 全部堆回单个长文件。
- 不允许用未标记状态的 docs 作为开发依据。
