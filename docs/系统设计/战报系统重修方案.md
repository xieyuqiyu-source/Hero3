# Hero3 战报系统重修方案

最后更新：2026-07-06

## 1. 文档定位

本文档是 Hero3 战报系统当前翻修的执行方案，用于承接现有《战报系统重构开发文档》的长期目标，并针对当前代码审查发现的问题给出可落地的重修顺序。

本次重修不只调整页面样式，而是同时修正战报数据语义、玩法接入契约、前端详情布局和 GM 排查能力。

目标：

- 玩家能在军情中清楚区分进攻、防守、协防、侦查、扫荡、黄巾、副本等战报。
- 战报详情以标准 `detail` 为唯一主渲染契约，旧字段只作为后端兼容输入。
- PVP、黄巾、NPC、扫荡、副本等玩法通过统一入口接入，不继续向前端暴露各自散乱字段。
- 战报 UI 参考传统页游战报的高密度信息结构，但按 Hero3 的三国题材和现有前端主题重做。
- GM 后台能按战斗事件还原多玩家视角、参战方、援军、奖励和异常结果。

## 2. 当前主要问题

### 2.1 视角、玩法和结果混在一起

当前系统里 `type`、`viewType`、`battleType`、`result` 的职责不够清晰。

典型问题：

- `scout` 侦查报告会被推断成 `viewType=attack`，但前端侦查 Tab 按 `viewType=scout` 查询。
- `result` 同时表达客观胜方和当前玩家输赢，后端存在 `defender_defeat`，前端类型却只声明 `attacker_victory / defender_victory / draw`。
- 黄巾战报接入了 `sourceType=yellow_turban`，但前端展示配置和 OpenAPI 枚举没有同步。

### 2.2 前端没有真正消费标准详情

后端已经有 `BattleReportDetail`：

```text
detail.primarySide
detail.secondarySide
detail.rewards
detail.traits
detail.visibility
detail.extra
```

但当前详情页仍主要读取旧字段：

```text
dispatchedUnits
lostUnits
defenderUnits
defenderLostUnits
pvpAttackerGenerals
pvpDefenderGenerals
pvpReinforcements
traitTriggered
traitOutcomes
```

这导致每新增一个玩法，前端都要补一批特殊兼容逻辑。

### 2.3 扫荡数据和 UI 展示不一致

后端为了控制体积，把扫荡每城明细设计成轻量快照，只保存目标、战力、结果、是否可见，不保存每城兵种和资源。

但前端把扫荡每个目标当完整防守卡渲染。结果玩家可能看到“对方战损低于 25%，无法显示详细兵力情报”这类错误原因。

扫荡必须二选一：

- 继续轻量化，只展示目标摘要列表。
- 或者保留每城完整战损快照，但需要控制单次扫荡上限和写入体积。

### 2.4 协防战报上下文不足

协防玩家收到的报告目前更像“我的援军损失通知”，不是完整战斗报告。

缺少：

- 谁攻击了谁。
- 我协防的是哪座城。
- 主战双方战力和结果。
- 我方援军贡献、损耗、武将经验。
- 同一事件下攻击方、防守方、协防方的关联。

### 2.5 黄巾战报缺专属信息层

黄巾已经复用 PVP 防守和协防结算，但战报里没有稳定的黄巾专属展示契约。

需要结构化进入战报的黄巾信息：

- 黄巾来源城池。
- 风险等级。
- 口粮压力。
- 来袭队列 ID。
- 黄巾兵力倍率或生成依据摘要。
- 是否触发协防。

### 2.6 GM 排查能力缺前端

后端已有 GM 战报、战斗事件、参与方接口，但 GM 后台还没有对应页面。

线上出现战报缺失、战损争议、协防异常、黄巾异常时，运营无法在 GM 页面按事件还原完整链路。

## 3. 重修核心原则

### 3.1 标准详情是前端唯一主契约

前端战报详情页只围绕 `report.detail` 渲染。

允许保留旧字段，但用途限定为：

- 后端 `NormalizeBattleReport` 兼容历史数据。
- 列表页展示少量摘要。
- 老战报没有 `detail` 时临时降级。

不允许新玩法继续让前端直接读取玩法私有字段拼详情。

### 3.2 四类语义分层

战报必须拆清楚四类语义。

```text
sourceType    来源：npc_city / player_city / yellow_turban / dungeon / stronghold
battleType    动作：attack / plunder / scout / sweep / yellow_turban / dungeon_reincarnation_attack
viewType      玩家身份：attack / defense / reinforcement / scout / system
ownerOutcome  当前玩家结果：victory / defeat / draw / intel_success / intel_failed / notice
```

建议新增或标准化字段：

```text
winnerSide    客观胜方：attacker / defender / draw / none
ownerSide     当前玩家所在侧：attacker / defender / reinforcement / observer
ownerOutcome  当前玩家感知结果
```

`result` 可以短期保留，但新 UI 不应直接用它判断“胜/败”。

### 3.3 玩法特殊信息只进入 `detail.extra`

通用展示使用固定字段：

```text
primarySide
secondarySide
rewards
traits
visibility
```

玩法扩展放入：

```text
detail.extra.pvp
detail.extra.scout
detail.extra.sweep
detail.extra.yellowTurban
detail.extra.dungeon
detail.extra.reinforcement
```

前端可以为这些 extra 提供专属面板，但不能绕过标准侧边、奖励、特性、可见性结构。

### 3.4 战报只保存事实快照

战报展示不应读取玩家当前状态来补历史数据。

必须保存快照：

- 参战兵种。
- 战前数量。
- 战损数量。
- 剩余数量。
- 参战武将。
- 武将等级。
- 特性触发结果。
- 奖励快照。
- 情报可见性。

## 4. 标准数据契约建议

### 4.1 BattleReport 顶层

建议最终顶层保留为列表和查询友好字段：

```text

eventId
ownerPlayerId
viewType
sourceType
battleType
result
winnerSide
ownerSide
ownerOutcome

```

`type`、`playerPower`、`enemyPower`、`dispatchedUnits` 等旧字段后续只作为兼容字段，不再作为前端详情主数据源。

### 4.2 BattleReportDetail

建议标准详情结构：

```text
id
eventId
viewType

battleType
result
winnerSide
ownerSide
ownerOutcome
title
summary
occurredAt
primarySide
secondarySide
rewards
traits

```

### 4.3 BattleReportSide

每一方必须能独立展示，不依赖当前玩家状态：

```text
role
playerId
playerName
cityId
cityName
faction
factionLabel
targetType
targetId
targetName
level
power
generals
units

```

### 4.4 BattleReportUnit

兵种矩阵统一使用：

```text
unitType
unitName
faction
category
amountBefore
dispatched
lost
survived
```

其中：

- 进攻方行名显示“出动 / 阵亡 / 剩余”。
- 防守方行名显示“驻守 / 阵亡 / 剩余”。
- 侦查方行名显示“派出 / 损失 / 返还”。
- 扫荡聚合可显示“首战出动 / 总阵亡 / 扫荡结束剩余”。

### 4.5 BattleReportVisibility

可见性不要只用布尔值，还要能解释原因。

```text

```

示例原因：

```text

scout_failed
full_reveal
owner_defender
reinforcement_limited
sweep_lightweight
```

## 5. 战报 UI 布局方案

### 5.1 总体视觉方向

Hero3 战报应是“三国军情文书 + 战损矩阵”的风格。

设计关键词：

- 暗色底。
- 金属边框。
- 阵营色点缀。
- 紧凑表格。
- 高密度但可扫读。
- 少量战果印章。

避免：

- 通用后台卡片堆叠。
- 大面积营销式 Hero 区。
- 装饰性渐变球。
- 纯文本调试面板。
- 用当前玩家状态临时补历史快照。

### 5.2 列表页布局

军情列表每条报告建议结构：

```text
[来源标签] [视角标签] [结果印章] 标题                         时间
摘要：战力 / 战损 / 奖励 / 特殊事件
```

列表筛选建议：

```text
全部
进攻
防守
协防
侦查
扫荡
```

筛选逻辑建议：

- 进攻、防守、协防按 `viewType`。
- 侦查按 `battleType=scout` 或新增专门 `viewType=scout` 后统一。
- 扫荡按 `battleType=sweep`。
- 黄巾不一定单独做一级 Tab，可用来源筛选或来源徽标表现。

### 5.3 详情页布局

详情页建议固定为六段。

#### 第一段：战报标题栏

```text
左：返回、来源标签、视角标签
中：标题
右：胜/败/平/侦查成功印章、分享按钮
```

展示：

- 来源：NPC / 玩家 / 黄巾 / 副本 / 据点。
- 战斗类型：进攻 / 掠夺 / 侦查 / 扫荡 / 黄巾来袭。
- 发生时间。
- 当前玩家结果。

#### 第二段：战斗双方身份区

参考传统战报图，但不要照搬老页游粗糙样式。

```text
攻击方身份卡 | 结果印章 | 防守方身份卡
```

每张身份卡展示：

- 城池或目标名。
- 玩家名或 NPC 名。
- 阵营。
- 战力。
- 主将。
- 武将等级。
- 来源身份：玩家城、NPC 城、黄巾军、协防军。

#### 第三段：战前效果区

用于展示战前加成和特殊规则。

内容来源：

- 武将特性。
- 城墙/建筑加成。
- 黄巾风险等级。
- 侦查成功率或反侦查。
- PVP 积分变化预览不放这里，放结算区。

示例：

```text
防守方刘备触发仁德，战后复活部分阵亡兵力。
黄巾来袭等级：暴乱，来源：南阳黄巾营。
```

#### 第四段：兵种战损矩阵

这是战报核心。

桌面端：

```text
兵种    步兵    骑兵    攻城    特殊 ...
出动    1000    300     20      0
阵亡    120     40      5       0
剩余    880     260     15      0
```

移动端：

```text
步兵  出动 1000 / 阵亡 120 / 剩余 880
骑兵  出动 300 / 阵亡 40 / 剩余 260
```

规则：

- 兵种顺序沿用项目固定顺序：步兵、骑兵、攻城、特殊。
- 运输、商人等非战斗单位不展示。
- 数字必须格式化。
- 未出动但属于阵营配置的兵种可以显示 0，但移动端默认折叠 0 项。

#### 第五段：结算区

分成几类小面板：

```text
资源变化
道具掉落
城金 / 溢出奖励
武将经验
PVP 积分
俘虏 / 复活
建筑 / 城墙损坏
```

要求：

- 奖励必须区分“已获得”和“预览”。
- 转生副本如果当前只是预览奖励，UI 必须标成“可能获得”或“通关奖励预览”。
- 建筑损坏没有数据时不要硬编码显示“无”，应只在有数据或有明确规则时展示。

#### 第六段：事件上下文区

根据玩法显示。

PVP：

```text
攻击方报告
防守方报告
协防方报告
同一事件 ID
```

黄巾：

```text
风险等级
口粮压力
来源黄巾城
是否触发协防
```

扫荡：

```text
请求目标数
成功数
失败数
是否中止
每城摘要列表
```

侦查：

```text
侦查结果
派出侦察兵
损失侦察兵
目标资源情报
目标兵力情报
失败原因
```

## 6. 各玩法接入规则

### 6.1 NPC 普通攻击

标准：

- `sourceType=npc_city`
- `battleType=attack / plunder`
- `viewType=attack`
- `ownerSide=attacker`
- `ownerOutcome=victory / defeat / draw`

必须展示：

- 我方出动和阵亡。
- NPC 驻守和阵亡。
- 掠夺资源。
- 道具掉落。
- 武将经验。
- 特性触发。

### 6.2 NPC 扫荡

推荐短期方案：继续轻量化，但 UI 改成扫荡摘要，不渲染每城完整防守卡。

`detail.extra.sweep.defenders` 每项展示：

```text
目标名
阵营
战力
结果
是否可见
```

不展示每城兵种和资源，避免误导。

中期可选增强：

- 对前 5 个关键目标保存完整明细。
- 对有武将升级、掉落、异常失败的目标保存完整单场快照。
- 其他目标仍保留摘要。

### 6.3 PVP 攻防

PVP 一场战斗必须有一个 `eventId`，并生成多份视角报告。

```text
攻击方：viewType=attack
防守方：viewType=defense
协防方：viewType=reinforcement
```

攻击方和防守方都应能看到：

- 主战双方。
- 参战武将。
- 本方损耗。
- 对方损耗。
- 协防摘要。
- 城墙/建筑效果。
- PVP 积分变化。

可见性由 `detail.visibility` 控制，不在前端硬编码 25%。

### 6.4 协防报告

协防报告不能只显示自己损失。

必须补充：

```text
我协防的玩家
我协防的城
攻击来源
整场结果
我的派出兵力
我的损失
我的武将经验
我的驻防武将
```

协防报告可以隐藏敌方完整兵力，但不能缺少事件上下文。

### 6.5 侦查报告

侦查建议作为独立战斗类型，不和普通攻击混淆。

短期修正：

- 前端侦查 Tab 改为 `battleType=scout` 查询。
- 或后端主动侦查报告统一写 `viewType=scout`。

长期规则：

```text
主动侦查方：viewType=scout
被侦查方：viewType=defense，battleType=scout
```

侦查结果：

```text
ownerOutcome=intel_success / intel_failed
```

侦查详情必须展示：

- 派出侦察兵数量。
- 侦察兵损失。
- 对方反侦查损失。
- 是否获得兵力情报。
- 是否获得资源情报。
- 失败原因。

### 6.6 黄巾来袭

黄巾属于据点/事件来源，不是普通 NPC。

建议：

```text
sourceType=yellow_turban
battleType=yellow_turban
viewType=defense / reinforcement
```

`detail.extra.yellowTurban`：

```text
marchId
sourceCityId
sourceCityName
riskLevelId
riskLevelName
foodPressure
foodCapacity
currentFood
spawnMultiplier
```

前端显示：

- 黄巾来袭徽标。
- 风险等级。
- 来源黄巾城。
- 本次因口粮压力触发。
- 防守武将和协防武将。

### 6.7 副本和转生

副本战报必须区分：

- 本波实际获得。
- 通关后预览奖励。
- 最终结算奖励。

如果当前字段是 `RewardPreview`，前端不应展示成“已获得”。

建议：

```text
detail.extra.dungeon.rewardMode = preview / granted / settlement
```

## 7. GM 后台重修建议

新增 GM 战报事件页面。

列表筛选：

```text
玩家 ID
事件 ID
来源类型
战斗类型
结果
行军 ID
协防 ID
时间范围
```

事件详情：

```text
事件基础信息
攻击方快照
防守方快照
协防参与方
所有玩家视角战报
奖励快照
损耗快照
extra 原始数据
```

用途：

- 排查战报缺失。
- 排查协防损失。
- 排查黄巾结算。
- 排查扫荡聚合。
- 排查玩家反馈的战损争议。

## 8. 实施阶段

### 第一阶段：语义修正

目标：先让分类和结果稳定。

任务：

- 明确 `viewType / sourceType / battleType / ownerOutcome / winnerSide` 的职责。
- 修正侦查 Tab 查询规则。
- 补齐 `yellow_turban` 前端标签和 OpenAPI 枚举。
- 处理 `defender_defeat` 与前端类型不一致问题。
- 为 `BattleReportDetail` 增加必要字段，保持旧字段兼容。

验收：

- 侦查报告能稳定进入侦查分类。
- 黄巾报告有正确来源标签。
- 防守失败不依赖未知 result 字符串判断。

### 第二阶段：详情页重写

目标：前端以 `detail` 为主契约重写战报详情。

任务：

- 拆分 `BattleReportHeader`。
- 拆分 `BattleSideCard`。
- 拆分 `UnitLossMatrix`。
- 拆分 `RewardPanel`。
- 拆分 `TraitPanel`。
- 拆分 `IntelPanel`。
- 拆分 `EventContextPanel`。
- 保留旧战报降级渲染。

验收：

- NPC、PVP、协防、侦查、扫荡、黄巾都不再通过散乱旧字段拼主详情。
- 移动端没有文字重叠。
- 扫荡轻量明细不再误显示 25% 情报门槛。

### 第三阶段：玩法数据补齐

目标：把各玩法缺失的信息补进 `detail.extra` 和标准侧边。

任务：

- 协防报告补主战上下文。
- 黄巾报告补 `extra.yellowTurban`。
- 侦查报告补 `ownerOutcome` 和失败原因。
- PVP 报告补墙体/建筑/城防展示数据。
- 副本报告区分预览奖励和已获得奖励。

验收：

- 玩家看协防报告能知道自己帮谁、挡了谁、损失多少、获得什么。
- 玩家看黄巾报告能知道为什么触发、来自哪里、风险等级如何。
- 侦查失败不是普通战败文案。

### 第四阶段：GM 排查页面

目标：战斗事件可运营排查。

任务：

- GM 新增战斗事件列表。
- GM 新增事件详情页。
- 支持按事件查看所有视角战报和参与方。
- 支持复制事件 ID、报告 ID。

验收：

- GM 能通过玩家 ID 找到某次战斗。
- GM 能从单条战报跳到同事件其他视角。
- GM 能看到协防参与方和损耗。

### 第五阶段：历史兼容和清理

目标：减少旧字段长期污染。

任务：

- 后端保留旧字段读入兼容。
- 新战报写入时确保 `detail` 完整。
- 前端列表页逐步减少对旧字段依赖。
- 文档和 OpenAPI 同步。
- 清理已经无用的占位 UI 文案。

验收：

- 新玩法接入战报时只需要构造标准详情或标准输入。
- 前端不再为每个玩法新增大量特殊字段判断。

## 9. 优先级建议

必须先做：

1. 修正侦查分类。
2. 修正胜负语义。
3. 补齐黄巾来源配置。
4. 扫荡 UI 改成轻量摘要。
5. 详情页改为 `detail` 主契约。

可以后做：

1. GM 战斗事件页面。
2. 扫荡关键单场完整快照。
3. 建筑损坏和城墙损坏展示。
4. 副本奖励预览/发放完整区分。

暂不建议做：

1. 大规模迁移历史战报 JSON。
2. 为所有历史报告补全完整 `detail`。
3. 在数据语义未稳定前重做大量视觉样式。

## 10. 风险和注意事项

- 战报属于核心能力，玩法模块必须通过统一入口接入，不能绕过核心直接写自定义前端字段。
- 战报写入量已经影响过性能，扫荡完整明细需要谨慎控制体积。
- 前端重写详情页时必须保留老战报降级，否则历史报告可能打不开。
- `ownerOutcome` 等新增字段上线时，应兼容旧客户端和旧数据。
- GM 页面只能用于排查，不能直接修改战报或战斗结果。
