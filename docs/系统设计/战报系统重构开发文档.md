# <span style="color:#7c3aed">Hero3 战报系统重构开发文档</span>

最后更新：2026-06-28

## <span style="color:#7c3aed">1. 文档定位</span>

本文档定义 Hero3 战报系统的最终标准设计，用于指导后续 NPC、PVP、增援、副本、据点、资源点和活动战斗等所有战斗类玩法接入统一战报系统。

战报系统不是某个玩法的附属 JSON 字段，而是游戏战斗结果的统一归档、展示、分享和 GM 排查系统。

最终目标：

- 所有战斗类玩法都生成统一结构战报。
- 玩家端按进攻、防守、增援视角查看战报。
- NPC、玩家、据点、副本等来源类型使用不同颜色区分。
- 进攻、防守、增援等玩家视角使用不同颜色区分。
- 战报详情使用标准结构展示，不因玩法不同而重写一套页面。
- 武将、兵种、资源、掉落、经验、特性触发和 PVP 积分都能进入统一结构。
- PVP 一场战斗可以生成攻击方、防守方、多个增援方多份视角战报。
- GM 可以按玩家、事件、来源、行军、增援记录查询和排查。
- 分享链接使用独立 token，不直接公开内部战报 ID。

## <span style="color:#7c3aed">2. 最高设计原则</span>

战报数据结构必须标准。

任何玩法模块生成战报时，必须转换为统一战报结构。后续无论 NPC、PVP、副本、据点、活动 Boss 或资源点战斗，都只能基于标准结构调整类型、来源、奖励和扩展字段，不允许每个玩法随意暴露一套前端字段。

标准战报大体展示：

```text
战报类型：进攻 / 防守 / 增援
战报来源：NPC / 玩家 / 据点 / 副本 / 资源点 / 活动
出动方城池名字
出动方武将
出动方所有兵种，未出动显示 0
对阵方信息，可为空
资源
掉落
经验
武将特性触发
扩展结算信息
```

硬规则：

- 前端战报详情页必须优先按标准结构渲染。
- 玩法特殊字段只能进入 `extra`，不能破坏通用展示结构。
- 兵种必须按阵营全量展示，未出动、未损耗、无剩余均显示 0。
- 战报必须记录战斗发生时的快照，不依赖玩家当前状态。
- 战报只记录事实和奖励快照，不负责发放奖励。
- 奖励发放仍走 Reward 或 Effect Pipeline。

## <span style="color:#7c3aed">3. 当前系统问题</span>

当前系统已有基础战报能力：

- `battle_reports` 表可保存战报 JSON。
- 玩家端有军情列表和详情页。
- 战报支持阅读、删除、分页和分享。
- NPC 战斗、NPC 侦查、PVP 攻防已经可以生成战报。
- 武将特性触发已有 `traitTriggered` 和 `traitOutcomes` 字段。

但当前结构存在长期问题：

- `battle_reports.report_json` 承载过重，缺少标准事件层。
- 同一场 PVP 战斗的攻击方、防守方、增援方战报缺少统一事件归属。
- 战报分类主要依赖玩法类型，不是玩家视角。
- 战报列表无法稳定按进攻、防守、增援分类。
- 增援派出方独立战报能力不足。
- 分享直接依赖战报 ID，缺少分享 token 和过期控制。
- GM 不能按战斗事件、行军、增援批次完整追查。
- 前端详情页和当前玩家状态仍有耦合，旧战报快照不够独立。
- 新玩法接入战报时容易继续往旧 `BattleReport` 里堆字段。

## <span style="color:#7c3aed">4. 核心概念</span>

### <span style="color:#7c3aed">4.1 战斗事件</span>

`BattleEvent` 表示一次真实发生的战斗、侦查或战斗结算事件。

一场 PVP 战斗只有一个 `BattleEvent`，但可以派生多份玩家视角战报。

示例：

```text
event_pvp_001
  -> report_attacker_001
  -> report_defender_001
  -> report_reinforcement_owner_001
  -> report_reinforcement_owner_002
```

### <span style="color:#7c3aed">4.2 玩家视角战报</span>

`BattleReport` 表示某个玩家收到的一份战报。

玩家视角决定战报放在哪个 Tab：

```text
attack         进攻
defense        防守
reinforcement  增援
scout          侦查，后续可独立 Tab 或归入进攻类
```

当前玩家端主 Tab：

```text
进攻
防守
增援
```

后续可扩展：

```text
全部
侦查
系统
```

### <span style="color:#7c3aed">4.3 战报来源</span>

`sourceType` 表示战报来自什么玩法目标。

必须预留：

```text
npc_city        NPC 城池
player_city     玩家城池
stronghold      据点
dungeon         副本
resource_point  资源点
alliance        联盟建筑或联盟玩法
event_target    活动目标
world_boss      世界 Boss
system          系统事件
```

来源类型不决定玩家视角。玩家打 NPC 是 `sourceType=npc_city`、`viewType=attack`；玩家被其他玩家攻击是 `sourceType=player_city`、`viewType=defense`。

## <span style="color:#7c3aed">5. 战报展示规则</span>

### <span style="color:#7c3aed">5.1 进攻战报</span>

进攻战报用于玩家主动发起的攻击、掠夺、侦查、挑战和副本战斗。

侦查和掠夺在战报视角上都归入进攻类，只是 `battleType` 不同：

```text
attack   普通进攻
plunder  掠夺
scout    侦查
```

掠夺战报照普通进攻战报展示，额外在奖励区和 `extra.pvp.plunderedResources` 展示掠夺资源。

侦查战报照进攻战报结构展示，但兵种规则和情报可见性按侦查规则处理。

显示结构：

```text
上方：我方进攻信息
下方：敌方防守信息
```

上方展示：

- 我方城池名字。
- 我方玩家名。
- 我方阵营。
- 我方战力。
- 我方参战武将。
- 我方武将特性触发。
- 我方阵营全部兵种。
- 每个兵种出动、损耗、剩余。

下方展示：

- 目标名字。
- 目标类型。
- 目标阵营。
- 目标战力。
- 目标武将或守军首领。
- 目标全部兵种。
- 每个兵种出战、损耗、剩余。

敌方剩余兵种信息可见性：

- 如果进攻方有部队存活并返回，按正常战报展示敌方剩余兵种。
- 如果进攻方全灭，默认不能直接看到敌方剩余兵种。
- 进攻方全灭时，只有当敌方损失比例超过阈值，才可以看到敌方剩余兵种信息。
- 默认阈值为 25%。
- 烽火台可以提高这个阈值，使防守方更不容易暴露剩余兵力。
- 该阈值必须通过核心 Modifier 管线或建筑加成读取，不允许战报系统硬编码读取建筑等级。

示例：

```text
敌方战前 1000 兵，损失 300，损失比例 30%
默认阈值 25%
进攻方虽然全灭，但可以看到敌方剩余兵种
```

如果烽火台把阈值提高到 40%：

```text
敌方损失比例 30% < 40%
进攻方全灭后不能看到敌方剩余兵种
```

适用来源：

```text
NPC 城池
玩家城池
副本
据点
资源点
活动目标
```

### <span style="color:#7c3aed">5.2 防守战报</span>

防守战报用于玩家被攻击后的视角。

显示结构：

```text
上方：敌人进攻信息
下方：自己防守信息
```

防守战报和进攻战报使用同一套组件，只是 `primarySide` 和 `secondarySide` 的含义不同。

上方展示攻击者：

- 敌方城池名字。
- 敌方玩家名。
- 敌方阵营。
- 敌方战力。
- 敌方参战武将。
- 敌方出动兵种。
- 敌方损耗。

下方展示自己：

- 自己城池名字。
- 自己玩家名。
- 自己阵营。
- 自己防守武将。
- 自己防守兵种。
- 自己损耗。
- 参与防守的驻防或援军摘要。

### <span style="color:#7c3aed">5.3 增援战报</span>

增援战报用于援军派出方查看自己的援军参战结果。

显示结构：

```text
上方：我的增援队伍
下方：无
```

增援战报不展示完整敌我双方，避免信息泄露。

展示内容：

- 增援目标。
- 增援驻扎城池。
- 参战时间。
- 增援方城池名字。
- 增援方玩家名。
- 增援武将。
- 增援兵种。
- 增援损耗。
- 增援剩余。
- 是否全灭。
- 关联战斗结果摘要。

### <span style="color:#7c3aed">5.4 侦查战报</span>

侦查战报可以作为独立视角，也可以在玩家端归入进攻类。当前规则：玩家端主 Tab 不单独开侦查时，侦查进入进攻 Tab。

最终结构仍使用标准战报：

```text
primarySide = 侦查方
secondarySide = 被侦查方
```

侦查结果可通过 `visibility` 控制字段展示：

- 已侦查到资源。
- 已侦查到兵种。
- 已侦查到武将。
- 已侦查到城防。
- 被特性伪装后的假数据。

侦查兵种限制：

```text
蜀国：飞鸢
魏国：战鹰骑探
吴国：密探
```

侦查只能派出本阵营侦察兵，不能携带普通战斗兵种。

侦查结算规则：

- 侦查方派出侦察兵。
- 防守方以自己的侦察兵或反侦查力量参与侦查战斗。
- 双方比较侦察兵实力并产生损耗。
- 只要侦查方至少有 1 个侦察兵存活并返回，就能探查到对方情报。
- 如果侦查方侦察兵全灭，则侦查失败，只生成失败战报，不展示目标详细情报。
- 侦查战报仍记录侦查方出动、阵亡、剩余。
- 防守方是否看到被侦查通知，可由后续防守侦查战报或系统通知扩展。

侦查可见性：

```text
scout.success = true   至少 1 个侦察兵返回，展示侦查到的情报
scout.success = false  侦察兵全灭，不展示目标详细情报
```

## <span style="color:#7c3aed">6. 颜色和标签规则</span>

战报必须同时展示来源标签和视角标签。

### <span style="color:#7c3aed">6.1 来源颜色</span>

来源类型颜色由前端统一配置，不由后端下发 CSS。

建议：

```text
npc_city        NPC      青色
player_city     玩家     玫红
stronghold      据点     琥珀
dungeon         副本     紫色
resource_point  资源点   绿色
event_target    活动     粉色
world_boss      世界 Boss 赤红
```

### <span style="color:#7c3aed">6.2 视角颜色</span>

```text
attack         进攻   红色
defense        防守   蓝色
reinforcement  增援   绿色
scout          侦查   黄色
system         系统   灰色
```

列表示例：

```text
[玩家] [进攻]  许昌 攻击 成都
[玩家] [防守]  成都 遭到 许昌 攻击
[NPC]  [进攻]  洛阳 攻击 黄巾营地
[据点] [进攻]  攻击 白马据点
[副本] [进攻]  挑战 虎牢关副本
[玩家] [增援]  增援成都参战
```

## <span style="color:#7c3aed">7. 标准数据结构</span>

### <span style="color:#7c3aed">7.1 战报详情</span>

后端统一返回 `BattleReportDetail`。

```text
BattleReportDetail
id
eventId
ownerPlayerId
viewType
viewLabel
sourceType
sourceLabel
battleType
result
title
summary
occurredAt
primarySide
secondarySide
rewards
traits
visibility
extra
read
share
```

字段说明：

- `viewType`：进攻、防守、增援、侦查。
- `sourceType`：NPC、玩家、据点、副本等来源。
- `battleType`：攻击、掠夺、侦查、守城、增援参战等业务类型。
- `primarySide`：详情页上半部分。
- `secondarySide`：详情页下半部分，增援战报可为空。
- `rewards`：资源、掉落、城金、经验等奖励快照。
- `traits`：武将特性触发。
- `visibility`：本视角下哪些敌方信息可见。
- `extra`：PVP 积分、复仇、俘虏、复活、活动积分等扩展信息。

### <span style="color:#7c3aed">7.1.1 可见性结构</span>

```text
BattleReportVisibility
showEnemyRemainingUnits
showEnemyResources
showEnemyGenerals
showEnemyCityDefense
reason
threshold
actualLossRatio
```

用途：

- 进攻方全灭时控制是否展示敌方剩余兵种。
- 侦查失败时控制是否展示敌方资源、兵力、武将和城防。
- 特性伪装时说明展示数据是否可能被伪装。

进攻方全灭场景：

```text
showEnemyRemainingUnits = enemyLossRatio >= threshold
threshold = 0.25 + 烽火台或其他反侦查加成
```

侦查场景：

```text
showEnemyResources = scout.success
showEnemyRemainingUnits = scout.success
showEnemyGenerals = scout.success
showEnemyCityDefense = scout.success
```

### <span style="color:#7c3aed">7.2 战报方阵结构</span>

```text
BattleReportSide
role
playerId
playerName
cityId
cityName
faction
factionLabel
targetType
targetId
targetName
level
power
generals
units
resources
```

`role` 可选：

```text
attacker
defender
reinforcement
npc
dungeon_guard
stronghold_guard
resource_guard
event_guard
```

### <span style="color:#7c3aed">7.3 兵种结构</span>

```text
BattleReportUnit
unitType
unitName
faction
amountBefore
dispatched
lost
survived
```

硬规则：

- 兵种列表必须由阵营配置生成全量列表。
- 未出动兵种 `dispatched = 0`。
- 未损耗兵种 `lost = 0`。
- 无剩余兵种 `survived = 0`。
- NPC、副本、据点等没有玩家阵营时，也必须从目标配置生成完整守军兵种列表。

### <span style="color:#7c3aed">7.4 武将结构</span>

```text
BattleReportGeneral
id
name
level
role
power
attributes
traits
```

武将必须保存战斗时快照，不读取当前玩家武将状态。

### <span style="color:#7c3aed">7.5 特性触发结构</span>

```text
BattleReportTrait
traitId
traitName
ownerSide
ownerRole
generalId
generalName
summary
detail
```

现有 `traitTriggered`、`traitOutcomes` 可以作为旧字段兼容，但最终前端应优先读取 `traits`。

### <span style="color:#7c3aed">7.6 奖励结构</span>

```text
BattleReportRewards
resources
drops
cityGold
generalExp
generalLevelBefore
generalLevelAfter
overflow
```

`drops` 结构：

```text
BattleReportDrop
type
itemId
name
amount
quality
```

注意：

- 战报记录奖励快照。
- 实际发放必须已经由奖励系统完成。
- 如果发放失败，不能生成“已获得奖励”的战报。

### <span style="color:#7c3aed">7.7 扩展结构</span>

`extra` 用于玩法扩展。

允许字段：

```text
pvp
reinforcement
scout
capture
revive
season
activity
```

示例：

```text
extra.pvp.pointsDelta
extra.pvp.revengeId
extra.pvp.plunderedResources
extra.pvp.enemyLossRevealThreshold
extra.pvp.enemyLossRatio
extra.reinforcement.reinforcementId
extra.reinforcement.isAnnihilated
extra.scout.success
extra.scout.scoutUnitType
extra.scout.scoutPower
extra.scout.counterScoutPower
extra.capture.capturedUnits
extra.revive.revivedUnits
```

侦查兵种扩展示例：

```text
extra.scout.scoutUnitType = flying_kite / eagle_rider_scout / spy
extra.scout.success = survivedScouts > 0
```

敌方剩余兵力可见性扩展示例：

```text
extra.pvp.enemyLossRevealThreshold = 0.25
extra.pvp.enemyLossRatio = defenderLost / defenderBefore
visibility.showEnemyRemainingUnits = attackerSurvived || enemyLossRatio >= enemyLossRevealThreshold
```

## <span style="color:#7c3aed">8. 数据库设计</span>

### <span style="color:#7c3aed">8.1 battle_events</span>

```text
id                     VARCHAR(64) PRIMARY KEY
source_type            VARCHAR(32) NOT NULL
source_id              VARCHAR(64) NOT NULL DEFAULT ''
scene                  VARCHAR(32) NOT NULL
battle_type            VARCHAR(32) NOT NULL
result                 VARCHAR(32) NOT NULL
attacker_player_id     VARCHAR(64) NOT NULL DEFAULT ''
defender_player_id     VARCHAR(64) NOT NULL DEFAULT ''
attacker_name          VARCHAR(64) NOT NULL DEFAULT ''
defender_name          VARCHAR(64) NOT NULL DEFAULT ''
attacker_faction       VARCHAR(32) NOT NULL DEFAULT ''
defender_faction       VARCHAR(32) NOT NULL DEFAULT ''
related_march_id       VARCHAR(64) NOT NULL DEFAULT ''
related_reinforcement_id VARCHAR(64) NOT NULL DEFAULT ''
summary_json           JSON NULL
snapshot_json          JSON NULL
result_json            JSON NULL
occurred_at            DATETIME(6) NOT NULL
created_at             DATETIME(6) NOT NULL
```

索引：

```text
idx_battle_events_source(source_type, source_id)
idx_battle_events_players(attacker_player_id, defender_player_id, occurred_at)
idx_battle_events_march(related_march_id)
idx_battle_events_reinforcement(related_reinforcement_id)
idx_battle_events_occurred(occurred_at)
```

### <span style="color:#7c3aed">8.2 battle_reports</span>

```text
id                  VARCHAR(64) PRIMARY KEY
```

### <span style="color:#7c3aed">8.3 battle_report_states</span>

```text
id                 VARCHAR(64) PRIMARY KEY
report_id          VARCHAR(64) NOT NULL
player_id          VARCHAR(64) NOT NULL
is_read            TINYINT(1) NOT NULL DEFAULT 0
read_at            DATETIME(6) NULL

```

唯一索引：

```text

```

查询索引：


```text

expires_at     DATETIME(6) NULL

```

唯一索引：

```text

```

规则：

- 分享时生成 token。
- 公共访问使用 token，不使用 report id。
- 删除战报不影响已生成事件，但可以让分享链接失效。

## <span style="color:#7c3aed">10. 各玩法接入规则</span>

### <span style="color:#7c3aed">10.1 NPC 城池</span>


如果玩家端不单独展示侦查 Tab，则 NPC 侦查战报归入进攻 Tab。展示结构仍按进攻战报处理。

### <span style="color:#7c3aed">10.2 PVP</span>

PVP 攻击、掠夺或侦查生成：

```text
1 个 BattleEvent
1 份攻击方进攻战报
1 份防守方防守战报
N 份增援方增援战报
```

掠夺：

```text
battleType = plunder
viewType = attack
展示结构 = 进攻战报
```

侦查：

```text
battleType = scout
viewType = attack 或 scout
展示结构 = 进攻战报
```

侦查只能派出本阵营侦察兵：

```text
蜀国：飞鸢
魏国：战鹰骑探
吴国：密探
```

侦查成功条件：

```text
侦查方至少 1 个侦察兵存活返回
```

攻击方：

```text
viewType = attack
primarySide = 攻击方
secondarySide = 防守方
```

防守方：

```text
viewType = defense
primarySide = 攻击方
secondarySide = 防守方
```

增援方：

```text
viewType = reinforcement
primarySide = 增援方本批队伍
secondarySide = nil
```

PVP 扩展字段：

```text

```

### <span style="color:#7c3aed">10.3 增援</span>

当援军参与战斗时必须生成增援战报。

## <span style="color:#7c3aed">13. 兼容策略</span>

旧 `BattleReport` 不立即删除。

兼容阶段：

1. 新增新表和新模型。
2. 新战报写入新结构。
3. 旧接口继续返回兼容字段。
4. 前端详情页优先读新结构，缺失时 fallback 到旧字段。
5. NPC、PVP、增援逐步改为统一战报创建服务。
6. 确认稳定后清理旧字段依赖。

旧表 `battle_reports` 可选择两种处理方式：

方案 A：

```text
保留原表，新增字段，逐步演进。
```

方案 B：

```text
新增 battle_reports_v2，稳定后迁移并替换。
```

建议使用方案 A，减少迁移风险。
