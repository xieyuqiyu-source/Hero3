# <span style="color:#f59e0b">天机轮转老虎机系统设计</span>

最后更新：2026-07-01

## <span style="color:#8b5cf6">定位</span>

天机轮转是万象幻境下的第三个小游戏模块，玩法形态是老虎机。

它不进入建筑、资源、战斗主循环，也不绕过核心资产系统。玩家使用已有兵种作为押注，后端完成结算，胜利奖励进入小游戏库存，玩家后续手动兑换。

稳定定位：

- 展示名称：天机轮转
- 玩法类型：老虎机
- 所属入口：玩家端 `地图 -> 万象幻境`
- 后端 `gameType`：`slot`
- 资产规则：押注先扣兵，中奖奖励进可兑换库存
- 结算权威：后端结算，前端只播放后端返回结果
- 数据归属：复用 `minigame_records`

## <span style="color:#8b5cf6">核心原则</span>

1. 不允许前端上报中奖结果。
2. 不允许前端决定随机结果。
3. 不允许未扣押注就写中奖库存。
4. 不新增独立库存表，复用小游戏记录库存体系。
5. 所有长期资产变更必须走后端事务。
6. 输赢都写记录，方便 GM 后续排查。
7. 中奖库存只在玩家主动兑换时进入军队或驻防。

## <span style="color:#8b5cf6">玩家流程</span>

1. 玩家进入 `万象幻境`。
2. 点击 `天机轮转`。
3. 选择押注兵种。
4. 选择押注数量。
5. 点击 `启动轮转`。
6. 前端请求后端结算接口。
7. 后端校验兵种与数量，扣除押注兵力。
8. 后端随机生成 3 个转轮图案。
9. 后端判断是否中奖并写入 `minigame_records`。
10. 后端返回最新军队、转轮图案、倍率、中奖数量和记录。
11. 前端播放转轮动画，最终停在后端返回的图案。
12. 如果中奖，玩家可在 `天机库存` 中兑换奖励。

## <span style="color:#8b5cf6">押注规则</span>

### 允许押注的兵种

第一版只允许押注玩家本阵营的可战斗兵种。

校验方式：

- 必须存在于当前玩家阵营的兵种配置。
- 必须是玩家当前军队里已有的兵种。
- 不能是运输、商队、侦察或其他非战斗兵种。
- 复用后端 `validateAndConsumeArmy` 或同等核心校验逻辑。

### 押注数量

第一版采用固定上下限，避免出现历史赌场那种超大额滚雪球。

| 项 | 值 |
| --- | ---: |
| 最小押注 | 1,000 |
| 单局固定上限 | 1,000,000 |
| 单局比例上限 | 当前该兵种数量的 5% |

最终上限：

```text
maxBet = min(1,000,000, floor(currentUnitAmount * 0.05))
```

有效押注范围：

```text
1,000 <= betAmount <= maxBet
```

如果 `maxBet < 1,000`，该兵种不能参与天机轮转。

### 扣兵时机

点击启动后，后端在结算事务内立即扣除押注兵力。

规则：

- 输了：押注兵力不返还。
- 赢了：押注兵力也不返还，但发放 `押注数量 × 倍率` 的可兑换库存。
- 前端必须使用后端返回的 `army` 更新玩家当前军队。

## <span style="color:#8b5cf6">转轮规则</span>

第一版使用 3 轴老虎机。

每轴独立随机一次，使用同一套权重表。

只有 3 个图案完全相同才中奖；两个相同不中奖。

这样规则简单、容易解释，也能避免玩家误解“差一点也应该有奖励”。

## <span style="color:#8b5cf6">图案与倍率</span>

第一版配置如下：

| 图案 ID | 显示名 | 稀有度 | 单轴权重 | 三同概率 | 倍率 | 中奖说明 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| `bronze_charm` | 玄铜符 | 普通 | 35 | 4.2875% | ×5 | 小奖 |
| `silver_charm` | 白银符 | 稀有 | 25 | 1.5625% | ×12 | 稳定奖 |
| `gold_charm` | 赤金符 | 稀有 | 18 | 0.5832% | ×30 | 中奖 |
| `jade_seal` | 玉玺 | 史诗 | 12 | 0.1728% | ×80 | 大奖 |
| `tiger_tally` | 虎符 | 史诗 | 7 | 0.0343% | ×250 | 特大奖 |
| `heaven_order` | 天命令 | 传说 | 3 | 0.0027% | ×1000 | 头奖 |

总权重为 100。

单局中奖率约：

```text
6.643%
```

理论返奖率约：

```text
82.83%
```

理论长期亏损率约：

```text
17.17%
```

说明：

- 这里的返奖率按“押注先扣除、中奖奖励为 gross 奖励”计算。
- 例如押注 10,000，中了 `玄铜符`，库存奖励为 50,000。
- 因为押注兵已经扣除，玩家净增约等于 40,000 的同兵种库存。

## <span style="color:#8b5cf6">中奖奖励</span>

奖励兵种第一版固定为押注兵种。

示例：

- 玩家押注 `骁骑营 ×10,000`
- 转轮结果为 `赤金符 / 赤金符 / 赤金符`
- 倍率为 ×30
- 后端写入库存奖励 `骁骑营 ×300,000`

输局记录也要写入 `minigame_records`，但：

- `reward_unit = ''`
- `reward_amount = 0`
- `remaining_amount = 0`

中奖记录：

- `reward_unit = 押注兵种中文名`
- `reward_amount = betAmount * multiplier`
- `remaining_amount = reward_amount`

## <span style="color:#8b5cf6">数据模型</span>

复用 `minigame_records`。

字段使用约定：

| 字段 | 天机轮转写入规则 |
| --- | --- |
| `game_type` | 固定为 `slot` |
| `result_name` | 例如 `赤金符三连 ×30`、`未中奖` |
| `rarity` | 根据中奖图案写入 `common` / `rare` / `epic` / `legendary`，输局写 `common` |
| `reward_unit` | 中奖时为押注兵种中文名，输局为空 |
| `reward_amount` | 中奖数量，输局为 0 |
| `remaining_amount` | 可兑换数量，中奖时等于 `reward_amount`，输局为 0 |
| `bet_unit` | 押注兵种中文名 |
| `bet_amount` | 押注数量 |
| `created_at` | 后端结算时间 |

第一版不新增表。

如果后续要做排行榜、每日限额、保底、累计奖池，再新增专用模块状态表。

```json
  "won": true,
  "symbols": ["gold_charm", "gold_charm", "gold_charm"],

  "multiplier": 30,
  "betUnitId": "qiQiYing",
  "betUnit": "骁骑营",
  "betAmount": 10000,

```

错误码建议：

| 场景 | HTTP 状态 | 错误 |
| --- | ---: | --- |
| 存档不存在 | 404 | `player not found` |
| 押注兵种不存在 | 422 | `押注兵种不存在` |
| 押注兵力不足 | 422 | `押注兵力不足` |
| 押注数量低于下限 | 422 | `押注数量太低` |
| 押注数量超过上限 | 422 | `押注数量超过上限` |
| 同一存档操作过快 | 429 | `操作太快，请稍后再试` |

### 记录查询

复用：

```http
GET /api/v1/minigame/records?playerId=xxx&gameType=slot
```

### 单条兑换

复用：

```http
POST /api/v1/minigame/redeem
```

### 全部兑换

复用：

```http
POST /api/v1/minigame/redeem-all
```

请求中的 `gameType` 传：

```json
{
  "playerId": "player_xxx",
  "gameType": "slot"
}
```

### 禁止旧上报接口

`POST /api/v1/minigame/record` 不能接受 `gameType = slot`。

原因：

- 天机轮转必须后端结算。
- 不允许前端伪造图案、倍率或中奖记录。

## <span style="color:#8b5cf6">后端实现要求</span>

建议新增文件：

- `go/internal/app/game/service_slot.go`
- `go/internal/transport/api/handlers_slot.go` 或继续放入 `handlers_minigame.go`
- 如需要配置化，新增 `go/config/slot.json` 和 `slot_config.go`

核心服务方法建议：

```go
func (s *Service) ResolveSlotRound(playerID string, betUnitType string, betAmount int) (SlotRoundResult, error)
```

实现步骤：

1. 清理并校验 `playerID`、`betUnitType`、`betAmount`。
2. 获取玩家级互斥锁，避免同存档连点并发结算。
3. 使用 `UpdateMiniGamePlayerState` 或等价玩家资产事务。
4. 事务内读取权威军队。
5. 校验押注上限。
6. 使用核心出兵校验扣除押注兵力。
7. 使用后端随机数生成 3 个图案。
8. 判断是否三同。
9. 生成 `MiniGameRecord` 并插入记录列表。
10. 设置 `state.ServerTime`。
11. 事务提交后返回 `army`、`record`、`symbols` 和结果信息。

随机数要求：

- 第一版可以使用 `crypto/rand`。
- 不允许使用前端随机。
- 不允许请求中传入图案或随机种子。

### 前端结算流程

1. 玩家点击启动。
2. 前端禁用按钮，显示 `结算中...`。
3. 调用 `gameApi.resolveSlotRound`。
4. 收到后端结果后，开始播放转轮动画。
5. 动画最终停在后端返回的 `symbols`。
6. 调用 `patchState({ army, serverTime })`。
7. 将返回 `record` 加入本地记录列表。
8. 如果中奖，库存按钮显示角标。

前端禁止：

- 自己随机最终图案。
- 自己判断是否中奖。
- 自己计算奖励并上报。
- 直接调用 `/minigame/record` 写 `slot` 记录。

## <span style="color:#8b5cf6">库存兑换</span>

天机轮转库存复用小游戏兑换接口。

前端可以复制赌场库存弹窗的模式，但展示文字改为：

- 标题：天机库存
- 空态：转出三连奖励后会存入这里
- 标签：显示 `resultName`，例如 `赤金符三连 ×30`

兑换规则：

- 本阵营兵种加入军队。
- 非本阵营兵种进入驻防队伍。
- 第一版奖励等于押注兵种，所以通常会进入军队。

后端需要把 `slot` 加入可兑换玩法判断：

```go
miniGameRecordHasRedeemableReward("slot") == true
```

GM 小游戏记录面板需要支持筛选或展示：

- 押注兵种
- 押注数量
- 奖励兵种
- 奖励数量
- 剩余可兑换数量

排查 SQL 示例：

```sql
SELECT player_id, result_name, reward_unit, reward_amount, remaining_amount, bet_unit, bet_amount, created_at
FROM minigame_records
WHERE game_type = 'slot'
ORDER BY created_at DESC
LIMIT 100;
```

按玩家汇总库存：

```sql
SELECT player_id, reward_unit, SUM(remaining_amount) AS stock
FROM minigame_records
WHERE game_type = 'slot' AND remaining_amount > 0
GROUP BY player_id, reward_unit;
```

## <span style="color:#8b5cf6">上线注意事项</span>

第一版不需要数据迁移。

原因：

- `minigame_records.game_type` 是字符串，支持新玩法类型。
- 新玩法没有历史记录需要回填。
- 复用现有库存兑换体系。

上线前必须确认：

- 新接口已部署。
- 前端已改为调用后端结算。
- `gameType=slot` 已禁止走旧上报接口。
- 线上 `minigame_records.reward_amount` 是 `INT`，所以单局最大奖励不能超过 2,147,483,647。
- 本文配置下最大押注 1,000,000，最大倍率 1000，最大奖励 1,000,000,000，低于 MySQL `INT` 上限。
