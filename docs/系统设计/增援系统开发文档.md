# <span style="color:#16a34a">Hero3 增援系统开发文档</span>

最后更新：2026-06-27

## <span style="color:#16a34a">1. 文档定位</span>

本文档是 Hero3 增援系统的完整开发设计文档。

本次只设计增援系统，不包含 PVP 系统。PVP、保护期、冷却、免战、复仇、每日次数、赛季积分等内容只作为后续接入点预留，不进入本次开发范围。

增援系统的核心目标：

- 玩家可以派出自己的兵力和武将前往另一个玩家城池。
- 援军到达后作为驻军常驻。
- 派出方可以召回援军。
- 接收方可以遣返援军。
- 援军参与接收方的防守战斗计算。
- 援军损耗、战报、邮件和奖励都按队伍来源独立记录。
- 增援不能变成接收方的长期兵力资产。

## <span style="color:#16a34a">2. 核心原则</span>

增援系统必须遵循项目“稳定核心 + 玩法模块”的架构规则。

必须遵守：

- 增援是玩法模块，不是核心长期资产本身。
- 派出的兵力和武将仍然归派出方所有。
- 援军驻扎在接收方城池，但不能写入接收方长期兵力表。
- 兵力派出、损耗、返还必须通过核心或军事系统标准入口处理。
- 武将派出、占用、返还必须通过武将系统标准入口处理。
- 战斗计算复用标准战斗引擎。
- 战报、邮件、奖励必须走现有标准能力或后续统一接口。
- 如果现有核心无法表达“兵力派出中、武将派出中、损耗同步、返还”，应先补核心或军事应用层基础能力，再继续实现增援。

不允许：

- 接收方直接获得援军兵力。
- 接收方消耗、训练、升级、遣散援军兵力。
- 增援模块绕过核心直接改玩家长期兵力、武将、资源或道具。
- 援军损耗只写模块记录，不同步回派出方。
- 召回或遣返时重复返还兵力。
- 战斗失败时出现“扣兵成功但没有战报和状态记录”的半完成状态。

### <span style="color:#16a34a">2.1 通用驻防边界</span>

当前代码层已把增援批次扩展为更通用的驻防批次模型。

增援仍然是玩家之间的玩法模块，但驻防批次不再只表达“玩家 A 增援玩家 B”，也可以表达非本阵营军队的编外驻防来源。

字段语义：

```text
owner_player_id  队伍归属玩家
host_player_id   队伍驻防所在玩家
source_type      reinforcement / captured / mercenary / event_reward / system
source_id        来源记录 ID
rules_json       是否允许召回、遣返、返程、参战、转化、释放
```

规则：

- `source_type = reinforcement` 时，仍按普通增援处理，允许召回、遣返、返程和防守参战。
- `source_type = captured / mercenary / event_reward / system` 时，视为编外驻防队伍。
- 编外驻防队伍不进入玩家常规 `player_army_units`。
- 编外驻防队伍可以参与防守战斗，但是否能转化、释放、返程由 `rules_json` 决定。
- 非本阵营兵种通过编外驻防承载，不直接混入常规军队。

## <span style="color:#16a34a">3. 玩法规则</span>

### <span style="color:#16a34a">3.1 增援对象</span>

当前开发范围：

- 只支持增援玩家城池。
- 目标是另一个玩家的主城或玩家城池实体。

暂不支持：

- NPC 城池增援。
- 资源点增援。
- 联盟建筑增援。
- 世界地图野外驻扎点增援。

预留扩展：

```text
target_type = player_city
target_id   = 目标玩家或目标城池 ID
```

未来可以扩展：

```text
alliance_building
world_city
resource_point
event_stronghold
```

NPC 当前不能作为增援目标。如果后续要支持 NPC 城池增援，需要重新确认 NPC 城池是否拥有长期驻军状态、权限规则和战报归属。

### <span style="color:#16a34a">3.2 增援容量和队列</span>

当前规则：

- 增援总兵力无上限。
- 接收方最多同时容纳 5 个不同玩家的驻防队伍。
- 同一个派出玩家对同一个接收玩家只占 1 个驻防队伍槽。
- 同一个派出玩家可以多次增援同一个接收玩家，但展示和战斗时按同一来源玩家归组，内部仍按批次保存。
- 每一批增援独立保存派出时间、到达时间、兵力、武将、损耗和战报记录。

队列判断：

```text
接收方当前有效驻防来源玩家数 < 5 时，允许新的来源玩家增援
接收方已有该派出玩家驻防时，允许继续追加新的增援批次
```

有效驻防状态包括：

```text
marching    正在前往目标，已占用接收方驻防来源槽
stationed   已到达并驻扎
fighting    正在参与战斗
returning   正在返回，不再占用接收方驻防来源槽
```

是否让 `marching` 占用来源槽：当前建议占用，避免第 6 个来源玩家同时发兵后到达时才失败。

### <span style="color:#16a34a">3.3 行军时间</span>

基础行军时间固定为 3 小时。

实际行军时间按速度计算：

```text
实际行军秒数 = 3 小时秒数 / 行军速度倍率
```

初始规则：

- 基础行军时间：10800 秒。
- 行军速度倍率默认：1.0。
- 速度倍率可以来自后续科技、Buff、道具、活动或建筑加成。
- 当前没有速度加成时，去程固定 3 小时。

最小时间和最大时间建议预留配置：

```text
min_march_seconds
max_march_seconds
base_reinforcement_march_seconds
```

第一期可以只写死基础值，但代码结构应保留配置化入口。

### <span style="color:#16a34a">3.4 召回和遣返</span>

派出方可以召回援军。

接收方可以遣返援军。

召回和遣返规则：

- 未到达的援军可以召回。
- 已驻扎的援军可以召回。
- 正在战斗中的援军不能召回或遣返。
- 已进入返回状态的援军不能重复召回或遣返。
- 召回时间等于返程时间。
- 遣返时间也按返程时间处理。
- 返程时间默认使用和去程相同的速度规则。

返程计算：

```text
返程秒数 = 3 小时秒数 / 当前返程速度倍率
```

第一期可以直接使用去程速度倍率。后续如果要支持返程加速、撤军加速、紧急召回，可以单独加配置。

### <span style="color:#16a34a">3.5 接收方权限</span>

当前不做接收方权限系统。

当前默认规则：

- 任意玩家是否能增援另一个玩家，由基础校验控制。
- 第一版可以先允许所有玩家互相增援，或由开发时再接入好友、联盟、同阵营等条件。
- 接收方权限策略必须预留，但不实现复杂规则。

预留权限项：

```text
allow_all
friends_only
alliance_only
same_faction_only
manual_approval
blocked_players
```

后续增加权限时，应只改变增援发起校验，不改变已驻扎援军的数据结构。

### <span style="color:#16a34a">3.6 武将规则</span>

援军可以携带武将。

武将规则：

- 派出武将仍属于派出方。
- 派出的武将在增援期间处于占用状态，不能被派出方重复用于其他行动。
- 武将随援军到达目标后参与防守战斗。
- 武将提供 Buff，但只作用于自己所在的援军部队。
- 武将 Buff 不作用于接收方自有部队。
- 武将 Buff 不作用于其他玩家的援军部队。
- 援军返还后，武将回到派出方可用状态。

如果当前武将系统还没有“派出中、驻防中、返回中”的占用状态，需要先补武将占用能力。

### <span style="color:#16a34a">3.7 战斗参与规则</span>

援军参与接收方防守战斗。

防守方战斗力量由以下部分组成：

```text
接收方自有防守部队
接收方自有防守武将
已到达并驻扎的援军批次
援军携带的武将
```

战斗组装规则：

- 只读取 `stationed` 状态的援军。
- `marching` 未到达，不参与战斗。
- `returning` 已返程，不参与战斗。
- `failed`、`returned`、`cancelled` 不参与战斗。
- 多路援军一批一批独立进入战斗。
- 每批援军保留来源玩家、增援记录、兵种数量、武将和 Buff。
- 战斗引擎可以统一计算，但战斗前后必须保留来源映射。

来源标识建议：

```text
source_type       self / reinforcement
source_player_id  部队归属玩家
source_record_id  增援批次 ID
unit_type         兵种
amount            数量
general_ids       武将 ID 列表
```

### <span style="color:#16a34a">3.8 损耗规则</span>

援军损耗按战斗规则计算。

结算规则：

- 接收方自有部队损耗扣接收方。
- 每批援军损耗扣对应派出方。
- 多批援军分别记录损耗。
- 用户已确认：援军战败惩罚就是兵力全死，随后队伍进入返程归档，携带武将返回派出方。

推荐状态处理：

```text
部分损耗：更新 remaining_troops_json，继续 stationed
全部死亡：更新 remaining_troops_json 为空，状态改为 returning，返程完成后 completed
```

说明：

- 即使全军覆没，也建议保留返程流程，用于表现“武将返回、战报送达、队伍归档”。
- 如果携带武将，武将默认不会死亡，随返程回到派出方。
- 如果后续要做武将受伤、被俘、死亡，需要另开武将战损规则。

### <span style="color:#16a34a">3.9 奖励规则</span>

增援奖励需要有，但具体奖励数值后续再补。

当前设计预留：

- 派出方可获得协防参与奖励。
- 接收方可获得防守战斗奖励。
- 援军实际参战后才发放奖励。
- 没有参与战斗的驻扎不直接发奖励。
- 奖励必须通过标准 Reward 或 Effect Pipeline 发放。

奖励来源建议：

```text
reinforcement_defense_participation
reinforcement_defense_victory
reinforcement_defense_loss
```

第一期可以只记录奖励上下文，不实际配置奖励；但数据结构和战报字段要保留。

### <span style="color:#16a34a">3.10 战报和邮件</span>

增援相关战报和邮件必须有。

需要通知的对象：

- 接收方。
- 派出方。
- 多个派出方分别收到自己的援军战斗结果。

战报系统后续需要单独改造，本次文档只定义增援对战报的需求，不展开战报系统重构。

战报中必须能看到：

- 防守方自有部队。
- 每个援军来源玩家。
- 每批援军参战兵力。
- 每批援军损耗。
- 每批援军携带武将。
- 援军武将触发的 Buff 或特性摘要。
- 战斗胜负。
- 奖励摘要。

邮件通知建议：

```text
援军到达通知：派出方、接收方
援军被召回通知：派出方、接收方
援军被遣返通知：派出方、接收方
援军参战通知：派出方、接收方
援军返回通知：派出方
援军异常通知：GM 或系统日志
```

## <span style="color:#16a34a">4. 状态模型</span>

### <span style="color:#16a34a">4.1 增援批次状态</span>

推荐状态：

```text
marching     前往目标中
stationed    已到达并驻扎
fighting     正在参与战斗结算
returning    返回派出方中
completed    已完成并归档
cancelled    未出发或未到达前取消
failed       异常状态，需要修复
```

不建议单独使用 `annihilated` 作为最终状态。全军覆没可以用字段记录：

```text
is_annihilated = true
status = returning / completed
```

这样方便统一走返程和归档流程。

### <span style="color:#16a34a">4.2 状态流转</span>

```text
marching -> stationed
marching -> returning
stationed -> fighting
fighting -> stationed
fighting -> returning
stationed -> returning
returning -> completed
marching -> failed
stationed -> failed
fighting -> failed
returning -> failed
```

说明：

- `marching -> returning` 表示未到达时召回。
- `stationed -> returning` 表示派出方召回或接收方遣返。
- `fighting -> returning` 表示战斗后全军覆没或系统要求返程。
- `fighting -> stationed` 表示战斗后仍有剩余兵力，继续驻扎。

### <span style="color:#16a34a">4.3 幂等要求</span>

以下操作必须幂等：

- 到达结算。
- 召回。
- 遣返。
- 战斗损耗应用。
- 返程完成。
- 邮件发送。
- 战报关联。

重复执行不能导致：

- 兵力重复返还。
- 武将重复释放。
- 邮件重复刷屏。
- 战报重复关联。
- 队列槽重复占用。

## <span style="color:#16a34a">5. 数据库设计</span>

### <span style="color:#16a34a">5.1 增援批次表</span>

表名：`player_reinforcements`

用途：保存每一批增援的生命周期、兵力快照、剩余兵力、武将、损耗和通知状态。

```text
id                       BIGINT PK
reinforcement_id         VARCHAR(64) UNIQUE
from_player_id            VARCHAR(64)
to_player_id              VARCHAR(64)
target_type               VARCHAR(64)
target_id                 VARCHAR(64)
status                    VARCHAR(32)
troops_json               JSON
remaining_troops_json     JSON
generals_json             JSON
losses_json               JSON
buff_snapshot_json        JSON
speed_multiplier          DECIMAL(10,4)
march_seconds             INT
return_seconds            INT
sent_at                   DATETIME
arrived_at                DATETIME NULL
recalled_at               DATETIME NULL
expelled_at               DATETIME NULL
return_started_at         DATETIME NULL
returned_at               DATETIME NULL
last_battle_report_id     VARCHAR(64) NULL
last_battle_at            DATETIME NULL
is_annihilated            BOOLEAN
reward_state_json         JSON
mail_state_json           JSON
metadata_json             JSON
created_at                DATETIME
updated_at                DATETIME
```

字段说明：

- `troops_json`：派出时原始兵力。
- `remaining_troops_json`：当前剩余兵力，战斗损耗后更新。
- `generals_json`：携带武将快照和占用信息。
- `losses_json`：累计损耗明细。
- `buff_snapshot_json`：援军自身 Buff 快照，只作用于自己的部队。
- `speed_multiplier`：本次行军速度倍率。
- `march_seconds`：本次去程秒数。
- `return_seconds`：本次返程秒数。
- `is_annihilated`：是否全军覆没。
- `reward_state_json`：奖励发放状态，用于幂等。
- `mail_state_json`：邮件通知状态，用于幂等。
- `metadata_json`：预留扩展信息。

推荐索引：

```text
UNIQUE KEY uk_reinforcement_id(reinforcement_id)
KEY idx_from_status(from_player_id, status)
KEY idx_to_status(to_player_id, status)
KEY idx_target_status(target_type, target_id, status)
KEY idx_arrive(status, sent_at)
KEY idx_return(status, return_started_at)
KEY idx_last_battle_report(last_battle_report_id)
```

### <span style="color:#16a34a">5.2 接收方驻防来源计数</span>

第一期可以不单独建表，查询 `player_reinforcements` 计算有效来源玩家数。

如果后续性能需要，可以增加聚合表：

```text
player_reinforcement_slots
```

当前不建议第一期就加聚合表，避免双写复杂度。

### <span style="color:#16a34a">5.3 兵力和武将占用</span>

增援系统需要军事系统提供“派出中”能力。

如果已有兵力权威表，应补充或确认以下能力：

```text
扣出可用兵力
记录派出中兵力
返还剩余兵力
应用战斗损耗
防止同一兵力重复派出
```

如果已有武将权威表，应补充或确认以下能力：

```text
锁定武将为 reinforcement
释放武将
查询武将是否可派出
防止武将重复出战
```

这部分不一定必须由增援表承担，优先由军事系统和武将系统提供标准入口。

## <span style="color:#16a34a">6. 服务接口设计</span>

### <span style="color:#16a34a">6.1 玩家接口</span>

发起增援：

```text
POST /api/v1/reinforcements
```

请求：

```text
target_player_id
troops
general_ids
```

返回：

```text
reinforcement_id
status
sent_at
arrive_at
march_seconds
troops
generals
state
```

查看派出的增援：

```text
GET /api/v1/reinforcements/sent
```

查看收到的增援：

```text
GET /api/v1/reinforcements/received
```

召回援军：

```text
POST /api/v1/reinforcements/{reinforcement_id}/recall
```

遣返援军：

```text
POST /api/v1/reinforcements/{reinforcement_id}/expel
```

查看单个增援批次：

```text
GET /api/v1/reinforcements/{reinforcement_id}
```

### <span style="color:#16a34a">6.2 后端服务方法</span>

建议服务方法：

```text
SendReinforcement
ListSentReinforcements
ListReceivedReinforcements
GetReinforcement
RecallReinforcement
ExpelReinforcement
MarkReinforcementArrived
ApplyReinforcementBattleResult
CompleteReinforcementReturn
BuildDefenseReinforcementUnits
```

### <span style="color:#16a34a">6.3 定时结算入口</span>

需要有后台结算入口或请求触发结算入口：

```text
结算到达：marching 且 sent_at + march_seconds <= now
结算返程：returning 且 return_started_at + return_seconds <= now
```

第一期可以用“请求触发 + 后台任务预留”的方式：

- 玩家打开增援页面时结算自己的到达和返回。
- 玩家进入防守或战斗前结算目标相关增援。
- 后续再加定时任务兜底。

## <span style="color:#16a34a">7. 战斗接入</span>

### <span style="color:#16a34a">7.1 防守队伍构建</span>

防守战斗开始前，需要调用：

```text
BuildDefenseReinforcementUnits(target_player_id)
```

输出：

```text
reinforcement_id
from_player_id
troops
generals
buffs
source_tags
```

构建规则：

- 先结算到达。
- 只读取 `stationed` 状态。
- 每批增援单独转换为战斗单位。
- 每批增援武将只给本批增援单位提供 Buff。
- 输出必须保留来源，方便战后拆损耗。

### <span style="color:#16a34a">7.2 战后损耗应用</span>

战斗结束后，战斗系统需要把援军损耗传给增援系统：

```text
ApplyReinforcementBattleResult(report_id, reinforcement_losses)
```

损耗格式建议：

```text
reinforcement_id
from_player_id
unit_type
before_amount
lost_amount
remaining_amount
```

增援系统负责：

- 更新 `remaining_troops_json`。
- 追加 `losses_json`。
- 记录 `last_battle_report_id`。
- 记录 `last_battle_at`。
- 如果剩余兵力为 0，标记 `is_annihilated`。
- 如果全军覆没，进入返程流程。
- 生成派出方邮件或通知。
- 生成奖励上下文。
