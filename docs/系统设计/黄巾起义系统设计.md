# <span style="color:#b45309">黄巾起义系统设计</span>

最后更新：2026-07-01

## <span style="color:#b45309">1. 定位</span>

黄巾起义是地图页下的独立世界事件玩法。

它不是副本，不是据点，也不是赛季系统。它的核心作用是对玩家兵力膨胀和口粮压力形成动态约束：当玩家当前兵力对应的口粮压力超过配置阈值后，系统会生成一批黄巾军，以 AI 攻击方的形式进攻玩家城池。

前端入口：

```text
地图 -> 黄巾起义
```

后端模块：

```text
moduleID = yellow_turban
displayName = 黄巾起义
category = world_event
```

第一版目标：

- 玩家可以在地图页查看自己的黄巾风险。
- 后端按玩家当前口粮压力判断是否会触发黄巾起义。
- 起义触发后生成一个或多个波次。
- 每个波次都会生成一支虚拟黄巾军。
- 黄巾军按 PVP 攻城逻辑进攻玩家城池。
- 防守方自有兵力、驻防、城内武将和家里加成照常生效。
- 黄巾军攻击方不创建真实账号，也不落成普通玩家。
- 战斗产生标准防守战报，玩家能在军情里看到黄巾来袭。

## <span style="color:#b45309">2. 核心原则</span>

黄巾起义必须遵循 Hero3 稳定核心规则：

- 黄巾起义是玩法模块，不进入核心资产系统。
- 黄巾起义可以读取玩家兵力、武将、驻防、资源、建筑和 Buff。
- 黄巾起义造成的防守方损耗必须通过标准玩家状态事务写回。
- 黄巾起义战报必须走标准战报体系。
- 黄巾起义奖励如需发放长期资产，必须走 Reward 或 Effect Pipeline。
- 黄巾军攻击方使用虚拟 `GameState` 快照，不创建普通玩家。
- 不允许为了复用 PVP 而把黄巾军写进普通玩家排行榜、联盟、目标搜索或 GM 普通玩家列表。

明确禁止：

- 不允许黄巾军通过注册登录流程创建账号。
- 不允许每波黄巾都创建普通 `accounts/players` 数据。
- 不允许把黄巾军加入联盟或玩家排行。
- 不允许绕过 PVP 战斗结算直接扣玩家兵。
- 不允许同一个黄巾波次被重复结算。
- 不允许口粮超过阈值后每次刷新都无限触发新波次。

## <span style="color:#b45309">3. 和现有 PVP 的关系</span>

现有 PVP 主链路强依赖 `players` 表：

- `CreatePvpMarchWithState` 会同时锁定攻击方和防守方玩家状态。
- `ResolvePvpBattleTransaction` 会按 `attacker_player_id` 和 `defender_player_id` 再次读取双方 `players.state_json`。
- 现有 PVP 行军返程、召回、攻击方兵力返还、攻击方武将占用都默认攻击方是真实玩家。

因此黄巾起义第一版不直接调用普通 `StartPvpAttack` 和普通 `ResolvePvpBattleTransaction`。

正确接入方式：

```text
黄巾模块生成虚拟攻击方 GameState
        |
        v
黄巾专用事务只锁防守玩家 + 防守方驻防 + 黄巾事件
        |
        v
复用 resolvePvpCombat 或抽出的公共 PVP 战斗结算核心
        |
        v
只写回防守玩家、驻防、黄巾事件、战报和战斗记录
```

黄巾军表现上像玩家：

- 有名字，例如 `黄巾-诸葛夏`。
- 有阵营。
- 有兵种。
- 可以带武将。
- 武将可以触发特性。
- 战报里显示为进攻方。

黄巾军数据上不是普通玩家：

- 不需要账号。
- 不需要登录。
- 不进入普通玩家列表。
- 不进入 PVP 目标列表。
- 不进入联盟。
- 不进入普通玩家排行榜。
- 不需要返程。
- 战斗后幸存兵力默认消失，或进入同次起义的下一波配置逻辑。

## <span style="color:#b45309">4. 玩法流程</span>

### <span style="color:#b45309">4.1 风险计算</span>

后端根据玩家当前兵力计算口粮压力。

建议公式：

```text
foodPressure = currentArmyFoodUpkeep / safeFoodCapacity
```

其中：

- `currentArmyFoodUpkeep`：玩家当前常规军队的口粮消耗。
- `safeFoodCapacity`：配置给该玩家当前发展阶段的安全口粮阈值。

第一版如果暂时没有完整口粮系统，可以先用替代公式：

```text
foodPressure = currentArmyFoodUpkeep / configuredBaseSafeFood
```

但文档约束是：最终必须接入口粮系统，而不是长期用总兵力数量粗算。

### <span style="color:#b45309">4.2 触发判断</span>

每个玩家单独判断黄巾起义风险。

触发来源可以有三种：

1. 玩家打开 `地图 -> 黄巾起义` 时刷新状态。
2. 玩家完成征兵、兑换兵力、战斗返程等兵力变化后由事件触发检查。
3. 后台定时任务批量扫描高风险玩家。

第一版推荐只做 1 和 2：

- 打开页面时一定能看到最新风险。
- 兵力变化后尝试触发一次。
- 不做全服大扫描，避免额外压力。

触发保护：

- 同一玩家同一时间只能存在一个 `active` 或 `pending` 黄巾事件。
- 同一玩家完成一次起义后进入冷却。
- 低于阈值不触发。
- 在冷却期内不触发。
- 玩家处于新手保护或系统维护保护时，第一版可以不触发。

## <span style="color:#b45309">5. 起义等级</span>

黄巾等级由口粮压力决定。

建议第一版 5 级：

| 等级 | 名称 | 口粮压力范围 | 波次数 | 定位 |
| ---: | --- | ---: | ---: | --- |
| 1 | 流民骚乱 | 100% - 130% | 1 | 轻度提醒 |
| 2 | 小股黄巾 | 130% - 180% | 1 - 2 | 有实际损耗 |
| 3 | 黄巾袭城 | 180% - 250% | 2 | 中等威胁 |
| 4 | 黄巾大军 | 250% - 350% | 3 | 高压力惩罚 |
| 5 | 黄巾围城 | 350% 以上 | 3 - 5 | 极高兵力压力惩罚 |

规则：

- 口粮超出越多，黄巾等级越高。
- 等级越高，黄巾兵力越多。
- 等级越高，波次数越多。
- 等级越高，黄巾武将数量和品质越高。
- 等级越高，黄巾可能获得额外 Buff。

第一版不需要做全服共享等级，先按玩家个人压力触发。

## <span style="color:#b45309">6. 黄巾军生成</span>

### <span style="color:#b45309">6.1 虚拟攻击方快照</span>

黄巾军每个波次生成一个虚拟攻击方 `GameState`。

示例：

```json
{
  "player": {
    "id": "system_yellow_turban_wave_xxx",
    "nickname": "黄巾-诸葛夏",
    "faction": "shu"
  },
  "army": [
    { "unitType": "shuInfantry", "amount": 120000 },
    { "unitType": "shuArcher", "amount": 60000 }
  ],
  "generals": [],
  "generalAssignments": [],
  "buffs": []
}
```

注意：

- 这个 `player.id` 只用于战报、战斗快照和事件追踪。
- 不需要在 `players` 表存在。
- 不需要在 `accounts` 表存在。
- 不参与任何普通玩家查询。

### <span style="color:#b45309">6.2 名字生成</span>

黄巾军名字用固定前缀：

```text
黄巾-诸葛夏
黄巾-张曼成
黄巾-波才
黄巾-管亥
黄巾-程远志
```

规则：

- 必须带 `黄巾-` 前缀。
- 名字只用于展示。
- 不允许作为玩家昵称唯一性判断依据。
- 战报和地图页都应明确显示黄巾标识。

### <span style="color:#b45309">6.3 阵营和兵种</span>

黄巾军阵营由配置决定：

```text
factionMode = random | fixed | follow_defender | weighted
```

第一版推荐：

```text
factionMode = random
```

兵种生成：

- 只从该阵营已注册兵种里随机。
- 兵种数量范围来自 GM 配置。
- 可按等级配置兵种类型数量。
- 不允许生成不存在的兵种。
- 不允许生成非战斗兵种。

兵力规模建议参考玩家当前口粮压力和等级：

```text
yellowTurbanArmyFood = defenderArmyFood * random(level.armyFoodRatioMin, level.armyFoodRatioMax)
```

示例：

| 等级 | 黄巾兵力口粮倍率 |
| ---: | ---: |
| 1 | 5% - 10% |
| 2 | 10% - 18% |
| 3 | 18% - 30% |
| 4 | 30% - 45% |
| 5 | 45% - 70% |

这里使用口粮倍率而不是兵力数量倍率，是为了适配不同兵种的强弱和消耗差异。

### <span style="color:#b45309">6.4 武将和特性</span>

黄巾军可以带虚拟武将。

第一版建议：

| 等级 | 武将数量 | 武将等级范围 | 特性 |
| ---: | ---: | ---: | --- |
| 1 | 0 - 1 | 1 - 20 | 可无 |
| 2 | 1 | 10 - 35 | 普通特性 |
| 3 | 1 - 2 | 25 - 55 | 普通/稀有 |
| 4 | 2 | 45 - 75 | 稀有 |
| 5 | 2 - 3 | 65 - 90 | 稀有/强力 |

实现规则：

- 虚拟武将不写入 `player_generals`。
- 虚拟武将只存在于本次波次攻击方快照。
- 武将 ID 使用 `yt_general_xxx`。
- 武将特性可以复用现有特性注册表。
- 战报里需要显示黄巾军参战武将快照。
- 黄巾武将不获得经验。
- 防守方在家武将照常获得经验。

如果现有 `buildActiveTraitsForGeneralIDs` 只能从 `GameState.Generals` 查武将，则虚拟攻击方只要构造完整 `GameState.Generals` 和 `GeneralAssignments` 即可复用。

## <span style="color:#b45309">7. 波次规则</span>

一个黄巾事件可以包含多个波次。

事件状态：

```text
pending     已生成，等待第一波到达
active      有波次正在行军或结算
resolved    所有波次已结算
cancelled   GM 取消或系统取消
expired     超时未结算，待 GM 修复
```

波次状态：

```text
marching    正在来袭
resolving   正在结算
resolved    已结算
cancelled   已取消
```

波次时间：

- 第一波生成后进入倒计时。
- 后续波次可以在上一波结算后再生成，也可以事件创建时全部排定。
- 第一版推荐事件创建时全部排定，简单可查。

行军时间：

```text
arrivalSeconds = level.arrivalSeconds + random(-jitter, +jitter)
```

第一版建议：

| 等级 | 首波到达时间 | 后续波间隔 |
| ---: | ---: | ---: |
| 1 | 10 分钟 | - |
| 2 | 10 分钟 | 10 分钟 |
| 3 | 15 分钟 | 10 分钟 |
| 4 | 20 分钟 | 8 分钟 |
| 5 | 30 分钟 | 5 分钟 |

这样玩家能看到预警，不会无感瞬间扣兵。

## <span style="color:#b45309">8. 数据模型</span>

### <span style="color:#b45309">8.1 yellow_turban_incidents</span>

保存一次黄巾起义事件。

```sql
CREATE TABLE yellow_turban_incidents (
  id VARCHAR(64) PRIMARY KEY,
  player_id VARCHAR(64) NOT NULL,
  status VARCHAR(32) NOT NULL,
  level INT NOT NULL,
  level_name VARCHAR(64) NOT NULL,
  pressure DECIMAL(10,4) NOT NULL,
  army_food INT NOT NULL DEFAULT 0,
  safe_food INT NOT NULL DEFAULT 0,
  wave_count INT NOT NULL DEFAULT 0,
  current_wave INT NOT NULL DEFAULT 0,
  cooldown_until DATETIME(6) NULL,
  metadata_json JSON NULL,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  resolved_at DATETIME(6) NULL,
  INDEX idx_yellow_turban_player_status (player_id, status, updated_at),
  INDEX idx_yellow_turban_due (status, updated_at)
);
```

### <span style="color:#b45309">8.2 yellow_turban_waves</span>

保存每一波黄巾军。

```sql
CREATE TABLE yellow_turban_waves (
  id VARCHAR(64) PRIMARY KEY,
  incident_id VARCHAR(64) NOT NULL,
  player_id VARCHAR(64) NOT NULL,
  wave_index INT NOT NULL,
  status VARCHAR(32) NOT NULL,
  attacker_id VARCHAR(64) NOT NULL,
  attacker_name VARCHAR(64) NOT NULL,
  attacker_faction VARCHAR(32) NOT NULL,
  attack_troops_json JSON NOT NULL,
  attack_generals_json JSON NULL,
  attacker_snapshot_json JSON NOT NULL,
  arrives_at DATETIME(6) NOT NULL,
  resolved_at DATETIME(6) NULL,
  battle_id VARCHAR(64) NOT NULL DEFAULT '',
  defender_report_id VARCHAR(64) NOT NULL DEFAULT '',
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  UNIQUE KEY uk_yellow_turban_incident_wave (incident_id, wave_index),
  INDEX idx_yellow_turban_wave_player_status (player_id, status, arrives_at),
  INDEX idx_yellow_turban_wave_due (status, arrives_at)
);
```

### <span style="color:#b45309">8.3 PVP 表是否复用</span>

第一版不建议把黄巾波次写进 `pvp_marches`。

原因：

- `pvp_marches` 当前代表玩家对玩家行军。
- 普通 PVP 结算会按 `attacker_player_id` 加载 `players`。
- 黄巾军没有真实攻击方玩家。
- 写入 `pvp_marches` 容易被普通 PVP 列表、返程、召回、加速逻辑误处理。

更稳妥的方式：

- 黄巾波次独立存在 `yellow_turban_waves`。
- 结算时复用 PVP 战斗计算函数和战报模型。
- 战报 `battle_type` 使用 `yellow_turban_defense`。
- `source_type` 可新增 `yellow_turban` 或复用事件类 source，但必须能在前端识别。

## <span style="color:#b45309">11. 黄巾专用事务</span>

需要新增 Repository 端口：

```go
type YellowTurbanRepository interface {
    GetYellowTurbanStatus(playerID string, now time.Time) (YellowTurbanStatus, error)
    CheckAndCreateYellowTurbanIncident(playerID string, now time.Time, update func(state *GameState, active *YellowTurbanIncident) (YellowTurbanIncident, []YellowTurbanWave, error)) (GameState, YellowTurbanIncident, []YellowTurbanWave, error)
    ResolveYellowTurbanWave(waveID string, now time.Time, update func(defender *GameState, reinforcements []Reinforcement, incident *YellowTurbanIncident, wave *YellowTurbanWave) (YellowTurbanWaveResolution, []Reinforcement, error)) (GameState, YellowTurbanWaveResolution, error)
}
```

事务要求：

- `CheckAndCreateYellowTurbanIncident` 锁定目标玩家状态和该玩家黄巾事件。
- `ResolveYellowTurbanWave` 锁定波次、事件、防守玩家、玩家驻防。
- 同一个波次只允许一个事务进入 `resolving`。
- 结算成功后写回：
  - 防守玩家兵力。
  - 防守玩家武将经验。
  - 防守玩家资源损失，如第一版开启掠夺。
  - 驻防损耗。
  - 波次状态。
  - 事件进度。
  - 战斗记录。
  - 防守战报。
  - 驻防参战战报。

第一版建议黄巾不掠夺资源，只造成兵力损耗。这样范围更稳。

## <span style="color:#b45309">12. 战斗结算规则</span>

### <span style="color:#b45309">12.1 复用内容</span>

必须复用：

- `internal/core/combat` 战斗引擎。
- PVP 防守方自有兵力构建逻辑。
- PVP 驻防队伍参战和损耗分摊逻辑。
- PVP 守城武将逻辑。
- PVP 武将特性触发逻辑。
- PVP 武将经验计算逻辑。
- 标准战报结构。

### <span style="color:#b45309">12.2 黄巾差异</span>

黄巾与普通 PVP 不同：

- 黄巾攻击方不扣长期兵力。
- 黄巾攻击方不占用武将。
- 黄巾攻击方不返程。
- 黄巾攻击方不获得经验。
- 黄巾攻击方不进入 PVP 积分。
- 黄巾攻击方不生成玩家可见攻击战报。
- 防守方需要生成防守战报。
- 驻防方如参战，需要生成增援/驻防战报。
- 黄巾战斗不生成复仇机会。
- 黄巾战斗不消耗玩家每日 PVP 次数。

### <span style="color:#b45309">12.3 战报展示</span>

防守战报应显示：

```text
标题：黄巾军来袭
进攻方：黄巾-诸葛夏
防守方：玩家昵称
战斗类型：黄巾起义
```

字段建议：

- `battle_type = yellow_turban_defense`
- `source_type = yellow_turban`
- `event_id = yellow_turban_wave_id` 或 `yellow_turban_battle_id`
- `target_name = 黄巾-诸葛夏（黄巾军）`

前端军情详情需要识别黄巾战报：

- 不显示“玩家”字样。
- 不显示复仇入口。
- 不显示 PVP 积分变化。
- 显示起义等级和波次。

## <span style="color:#b45309">14. 前端设计</span>

入口：

```text
地图 Tab -> 黄巾起义
```

页面信息：

- 当前口粮压力。
- 安全阈值。
- 当前风险等级。
- 起义冷却时间。
- 当前是否有黄巾军来袭。
- 来袭波次数。
- 每波到达倒计时。
- 黄巾军名称、阵营、兵力预览。
- 最近黄巾战报。

第一版交互：

- `刷新状态`：调用 `GET /yellow-turban/status`。
- `检查起义`：调用 `POST /yellow-turban/check`。
- 到期波次显示 `结算中`，前端可以触发 resolve，也可以等待后端自动结算。
- 点击最近战报跳转军情详情。

不需要：

- 不需要玩家主动报名。
- 不需要玩家选择出兵。
- 不需要玩家手动迎战。
- 不需要黄巾地图移动动画。
- 不需要联盟协助。

## <span style="color:#b45309">15. 触发时机</span>

第一版建议在以下操作后触发检查：

- 征兵完成，兵力增加。
- 小游戏兑换兵力后，兵力增加。
- 信函领取兵力奖励后，兵力增加。
- PVP 返程后，兵力回到家里。
- NPC 战斗返程或结算后，兵力回到家里。
- 玩家打开黄巾起义页面。

不要在每个普通读接口中自动触发写操作。

推荐方式：

- 资产变化事件发布后，黄巾模块监听 `army.changed` 或等价事件。
- 第一版如事件不完整，可以在关键服务方法末尾显式调用轻量检查。
- 检查函数必须有玩家级互斥和冷却保护，避免并发重复创建事件。

## <span style="color:#b45309">16. 奖惩设计</span>

第一版核心目的是限制过量兵力，不建议奖励过强。

建议：

- 防守成功：少量声望、道具、城金或黄巾战功。
- 防守失败：只承受兵力损失，第一版不掠夺资源。
- 黄巾等级越高，战报奖励略高，但不能让玩家主动刷黄巾获利。

奖励必须通过 Reward 或 Effect Pipeline 发放。

如果后续要做黄巾战功商店，应另建 `yellow_turban_points` 或通用活动货币，先讨论是否属于核心货币体系。

## <span style="color:#b45309">17. 测试要求</span>

### <span style="color:#b45309">17.1 服务层测试</span>

必须覆盖：

1. 口粮压力低于 100% 不触发。
2. 口粮压力达到等级 1 会创建 1 级事件。
3. 口粮压力达到等级 5 会创建更高等级和更多波次。
4. 同一玩家已有 active 事件时不会重复创建。
5. 冷却期内不会触发新事件。
6. 黄巾波次到期前不能结算。
7. 黄巾波次到期后能结算。
8. 同一波次重复结算不会重复扣兵或重复战报。
9. 防守方自有兵力损耗会写回。
10. 防守方驻防损耗会写回对应驻防记录。
11. 防守方城内武将参与守城。
12. 防守方武将击杀黄巾后获得经验。
13. 黄巾虚拟武将特性能触发。
14. 黄巾攻击方不写入普通玩家状态。
15. 黄巾攻击方不生成 PVP 复仇记录。
16. 黄巾攻击方不影响 PVP 积分。

### <span style="color:#b45309">17.2 存储测试</span>

必须覆盖：

1. 创建事件和波次写入 `yellow_turban_incidents`、`yellow_turban_waves`。
2. 结算事务失败时，波次、防守玩家、驻防和战报全部回滚。
3. 并发结算同一波次只有一个成功。
4. 查询玩家状态时能返回当前 active 事件。
5. GM 取消事件后，待结算波次不会继续结算。

### <span style="color:#b45309">17.3 前端测试</span>

至少覆盖：

1. 地图页出现 `黄巾起义` Tab。
2. 低风险状态展示安全。
3. 高风险状态展示等级、阈值和提示。
4. 有来袭波次时展示倒计时。
5. 波次结算后刷新战报入口。
6. 黄巾战报详情不显示复仇和 PVP 积分。

## <span style="color:#b45309">18. 上线顺序</span>

建议分三步：

### <span style="color:#b45309">18.1 第一阶段：只读风险</span>

- 新增配置。
- 新增黄巾状态接口。
- 前端显示口粮压力和风险等级。
- 不触发战斗。

### <span style="color:#b45309">18.2 第二阶段：GM 手动触发</span>

- GM 可以对指定玩家触发黄巾事件。
- 玩家端显示波次倒计时。
- 到期后可结算战斗。
- 验证防守结算、战报、驻防损耗。

### <span style="color:#b45309">18.3 第三阶段：自动触发</span>

- 兵力变化后自动检查。
- 冷却生效。
- 黄巾正式成为兵力口粮压力约束系统。

## <span style="color:#b45309">19. 完成标准</span>

达到以下条件才算第一版完成：

- `地图 -> 黄巾起义` 页面上线。
- 后端有 `yellow_turban` 独立模块和配置。
- 黄巾军不创建普通玩家。
- 黄巾攻击方使用虚拟 `GameState` 快照。
- 黄巾波次能按口粮压力生成等级和兵力。
- 黄巾波次到期后能进攻玩家城池。
- 防守方自有兵力、驻防、守城武将、武将特性和武将经验按 PVP 规则生效。
- 黄巾战斗生成标准防守战报。
- 黄巾事件有冷却和幂等保护。
- GM 能查询、触发、取消和强制结算。
- 测试覆盖服务层、存储层和前端主要路径。

## <span style="color:#b45309">20. 后续扩展</span>

第一版不做以下内容：

- 全服共同大事件。
- 联盟协防黄巾。
- 黄巾占领地图据点。
- 黄巾资源掠夺。
- 黄巾战功商店。
- 黄巾首领世界 Boss。
- 赛季化排行。

这些内容后续可以作为第二阶段扩展。第一版先把“兵力口粮压力 -> 黄巾虚拟攻击方 -> PVP 防守结算”这条主链路做稳。
