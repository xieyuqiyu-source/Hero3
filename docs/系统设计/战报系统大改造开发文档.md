# Hero3 战报系统大改造开发文档

最后更新：2026-07-06

## 1. 文档定位

本文档是 Hero3 战报系统大改造的前后端开发文档。

本次改造不是局部修 UI，也不是给现有详情页继续打补丁，而是对战报系统进行一次完整重修：

- 后端统一战报语义。
- 后端补齐各玩法战报快照。
- 前端重写军情列表和战报详情布局。
- 增援/协防方战报改成能看懂的完整参战报告。
- GM 后台补战斗事件排查能力。

本文档以玩家之前提供的传统页游战报图为版式参考，提取其“高密度战报信息骨架”，但不照搬旧视觉。

## 2. 改造目标

### 2.1 玩家目标

玩家打开军情后，应能快速判断：

- 这是一场进攻、防守、侦查、扫荡、协防、黄巾还是副本战报。
- 我是攻击方、防守方、协防方还是侦查方。
- 我赢了还是输了。
- 我派了什么兵，损失了多少，剩了多少。
- 对方是什么目标，损失了多少，哪些情报可见。
- 武将是否参战、是否获得经验、是否触发特性。
- 协防方为什么收到这封战报，自己帮了谁、挡了谁、损失了什么。
- 黄巾战报为什么触发，风险等级是什么，来源是哪座黄巾城。
- 扫荡战报包含多少目标、成功多少、失败多少、是否中断。

### 2.2 技术目标

- 前端详情页以 `BattleReport.detail` 为主契约。
- 后端所有玩法通过统一战报入口写入。
- 旧字段继续兼容历史战报，但不再作为新 UI 主数据源。
- 战报分类、来源、玩法动作、玩家输赢不再混用同一个字段。
- 战报写入体积可控，不重新制造扫荡战报膨胀问题。
- GM 可按 `eventId` 还原同一战斗下的所有玩家视角。

## 3. 当前问题总结

### 3.1 布局混乱

当前前端详情页把进攻、防守、PVP、扫荡、协防、掉落、特性混在一个组件里，通过大量旧字段和条件判断拼 UI。

结果：

- 标题和身份不够清楚。
- 战斗双方关系不直观。
- 兵种矩阵不稳定。
- 特性、奖励、协防、黄巾都像附加补丁。
- 移动端信息层级弱。

### 3.2 增援方显示不明确

当前增援/协防战报最大问题是“只像损失通知，不像战报”。

协防玩家看到的内容缺少：

- 我协防的是谁。
- 我协防的是哪座城。
- 谁来打这座城。
- 这场战斗最终谁赢。
- 我的援军出动、损失、剩余。
- 我的武将是否参战，获得多少经验。
- 我在整场战斗中的身份和作用。

### 3.3 侦查、扫荡、黄巾语义不稳定

- 侦查 Tab 和后端 `viewType` 不一致。
- 扫荡后端是轻量摘要，前端却当完整防守卡展示。
- 黄巾已有战报来源，但前端标签、OpenAPI、详情上下文不完整。

### 3.4 胜负字段混乱

当前 `result` 同时承担：

- 客观胜方。
- 当前玩家输赢。
- 防守方视角结果。
- 侦查成功或失败。

这会导致前端判断胜败时越来越难维护。

## 4. 新战报信息架构

### 4.1 四层语义

战报必须拆成四层。

```text
sourceType     来源类型：npc_city / player_city / yellow_turban / dungeon / stronghold
battleType     战斗动作：attack / plunder / scout / sweep / yellow_turban / dungeon_reincarnation
viewType       玩家视角：attack / defense / reinforcement / scout / system
ownerOutcome   当前玩家结果：victory / defeat / draw / intel_success / intel_failed / notice
```

新增或标准化字段：

```text
winnerSide     客观胜方：attacker / defender / draw / none
ownerSide      当前玩家所在侧：attacker / defender / reinforcement / scout / observer
ownerOutcome   当前玩家视角结果
```

短期兼容：

- `result` 保留。
- 新 UI 优先读 `ownerOutcome`。
- 如果历史战报没有 `ownerOutcome`，前端用兼容函数从 `viewType + result` 推导。

### 4.2 标准详情结构

新战报详情必须围绕以下结构渲染：

```text
BattleReportDetail
  id
  eventId
  sourceType
  sourceLabel
  battleType
  battleLabel
  viewType
  viewLabel
  result
  winnerSide
  ownerSide
  ownerOutcome
  title
  summary
  occurredAt
  primarySide
  secondarySide
  rewards
  traits
  visibility
  extra
```

`primarySide` 和 `secondarySide` 是详情页主显示来源，不再由前端临时从旧字段组装。

### 4.3 侧边快照结构

```text
BattleReportSide
  role
  playerId
  playerName
  cityId
  cityName
  faction
  factionLabel
  targetType
  targetId
  targetName
  level
  power
  generals
  units
  resources
  modifiers
```

### 4.4 增援方专用上下文

增援/协防报告必须在 `detail.extra.reinforcement` 中补齐上下文：

```text
reinforcementId
hostPlayerId
hostPlayerName
hostCityName
attackerPlayerId
attackerName
attackerCityName
battleEventId
battleResult
ownerContribution
```

`ownerContribution`：

```text
troopsBefore
troopsLost
troopsSurvived
generalExp
generals
```

协防方详情中：

- `primarySide` 显示“我的援军”。
- `secondarySide` 可以显示“主战攻击方摘要”，但按可见性控制具体兵力。
- `extra.reinforcement.host` 显示被协防玩家和城池。

### 5.2 视觉方向

风格：

- 暗色军情底。
- 深铁灰面板。
- 金色细边框。
- 阵营色点缀。
- 小号紧凑表格。
- 结果印章使用红、绿、金三类。

避免：

- 老页游广告推荐栏。
- 无数据也硬显示“建筑损坏 无”。
- 多层圆角卡片套卡片。
- 大面积营销式标题。
- 装饰性渐变背景。

### 5.3 移动端

移动端不强行横向展示全矩阵。

移动端布局：

```text

骑兵  出动 300   阵亡 40   剩余 260
```

0 数量兵种默认折叠，提供“显示全部兵种”按钮。

### 7.2 模型字段补齐

`BattleReport` 增加：

```go
WinnerSide   string `json:"winnerSide,omitempty"`
OwnerSide    string `json:"ownerSide,omitempty"`
OwnerOutcome string `json:"ownerOutcome,omitempty"`
```

`BattleReportDetail` 增加同名字段。

兼容：

- 老数据没有这些字段时，由 `NormalizeBattleReport` 推导。
- 推导逻辑必须集中在 `report_standard.go`。

### 7.3 结果推导规则

客观胜方：

```text
attacker_victory -> winnerSide=attacker
defender_victory -> winnerSide=defender
draw             -> winnerSide=draw
```

玩家结果：

```text
ownerSide=attacker + winnerSide=attacker -> victory
ownerSide=attacker + winnerSide=defender -> defeat
ownerSide=defender + winnerSide=defender -> victory
ownerSide=defender + winnerSide=attacker -> defeat
ownerSide=reinforcement + host defender victory -> victory
ownerSide=reinforcement + host defender defeat -> defeat
```

侦查：

```text
scout success -> intel_success
scout failed  -> intel_failed
```

禁止新增 `defender_defeat` 这类混合语义 result。短期可以兼容读取，长期不再写入。

### 7.4 侦查后端改造

主动侦查方：

```text
viewType=scout
battleType=scout
ownerSide=scout
ownerOutcome=intel_success / intel_failed
```

被侦查方：

```text
viewType=defense
battleType=scout
ownerSide=defender
ownerOutcome=notice / victory / defeat
```

`detail.extra.scout` 补齐：

```text
success
scoutUnitType
scoutSent
scoutLost
scoutReturned
counterScoutUnitType
counterScoutLost
revealResources
revealUnits
reason
```

### 7.5 PVP 攻防后端改造

每场 PVP 使用一个 `eventId`。

攻击方报告：

```text
viewType=attack
ownerSide=attacker
```

防守方报告：

```text
viewType=defense
ownerSide=defender
```

协防方报告：

```text

```

所有报告都必须有：

```text

ownerOutcome
primarySide
secondarySide
extra.pvp
```

### 7.6 协防后端改造

`buildPvpReinforcementReports` 必须补上下文。

协防报告中：

```text
primarySide = 我的援军
secondarySide = 攻击方摘要或被协防城摘要
extra.reinforcement.host = 被协防玩家和城池
extra.reinforcement.attacker = 攻击来源摘要
extra.reinforcement.ownerContribution = 我的贡献
```

即使协防方不允许看敌方完整兵力，也必须知道攻击来源名称和被协防对象。

### 7.7 黄巾后端改造

黄巾战报：

```text

```

```text
marchId

currentFood
foodCapacity

```

黄巾协防报告复用协防上下文，但 `sourceType` 仍为 `yellow_turban`。

### 7.8 扫荡后端改造

短期不扩大写入体积。

保持：

```text
detail.extra.sweep.defenders 为轻量摘要
```

但增加明确标记：

```text
detail.extra.sweep.detailMode = lightweight
```

前端看到 `lightweight` 时只能渲染摘要列表。

中期增强：

```text
detail.extra.sweep.defenders[].units
detail.extra.sweep.defenders[].resources
```

只对关键目标保存完整明细：

- 失败目标。
- 掉落史诗物品目标。
- 武将升级目标。
- 战损异常高目标。

### 7.9 副本后端改造

副本奖励必须区分：

```text
preview
granted
settlement
```

`detail.extra.dungeon.rewardMode`：

```text
preview / granted / settlement
```

前端据此显示“奖励预览”或“已获得”。

## 10. 实施顺序

### 第一阶段：分类和结果修正

目标：先让现有战报不再错分、错显。

任务：

- 后端新增 `winnerSide / ownerSide / ownerOutcome`。
- 修正 `defender_defeat` 写入逻辑。
- 修正侦查分类。
- 前端补 `yellow_turban` 来源标签。
- OpenAPI 同步。
- 列表 Tab 调整为全部、进攻、防守、协防、侦查、扫荡。

验收：

- 侦查能进入侦查分类。
- 黄巾显示黄巾来源。
- 防守失败显示为当前玩家失败，而不是未知 result。
- 协防列表项能看出是协防。

### 第二阶段：战报详情页重写

目标：按参考图骨架重做详情。

任务：

- 拆分详情组件。
- 使用 `detail.primarySide / secondarySide` 渲染双方。
- 使用 `detail.rewards` 渲染奖励。
- 使用 `detail.traits` 渲染特性。
- 使用 `detail.visibility` 渲染情报隐藏原因。
- 扫荡轻量模式渲染摘要列表。

验收：

- NPC、PVP、防守、协防、侦查、扫荡、黄巾都有清晰布局。
- 增援方首屏能看懂自己协防了谁。
- 没有无意义占位文案。
- 移动端不重叠。

### 第三阶段：玩法上下文补齐
