# 将领特性持续治理任务提示词

最后更新：2026-07-20

## 使用方式

后续每次开启“将领特性治理、开发、修复、验收”相关任务时，可以把下面这段提示词作为任务开头。

## 持续任务提示词

你现在要持续治理 Hero3 的将领特性系统。

主要范围只围绕“将领特性”的开发完整性和验收，不扩展成整个将领系统重构，不做无关玩法大改。

开始前必须先阅读：

- `AGENTS.md`
- `PROJECT_RULES.md`
- `docs/系统设计/将领特性短期治理开发文档.md`
- `docs/系统设计/现有将领特性盘点.md`
- 最近的 `memory/YYYY-MM-DD.md`

本任务的核心目标：

1. 检查现有将领特性是否完整开发。
2. 检查每个特性是否能在正确场景触发。
3. 检查每个特性是否真实影响战斗输入、战斗结算或战后状态。
4. 检查战报中的特性展示是否正确。
5. 检查战报里的数值是否正确，包括出动兵力、损失、追加伤害、减损、复活、俘虏、掠夺、经验、等级变化和特性结果明细。
6. 如果战报数值不正常，必须同步修复；如果字段缺失或逻辑未完成，必须开发完整。
7. 影响玩家可见内容时，必须同时检查并同步修改 `web` 和 `web-wlsg` 两个玩家前端。

工作方式：

1. 先盘点本次要处理的特性，确认它属于哪一类：
   - 战前特性
   - 战斗结算后特性
   - 战斗结束后特性
   - 被动属性加成
   - 行军特性
   - 征兵特性
   - 掠夺特性
   - 特性压制

2. 对每个特性明确适用场景：
   - 进攻有效还是防守有效。
   - `allowedSides` 为空表示不限制角色，不能按习惯默认成“仅进攻方”；玩法同时支持主攻和主防时必须分别验收。`requiredOutcome=win/loss` 必须相对于当前特性拥有者判断，同一配置在攻守两侧的胜负语义都要正确。
   - PVE 有效还是 PVP 有效。
   - NPC、黄巾、副本、增援是否有效。
   - 主动出征、守城、防守增援、掠夺、扫荡是否有效。
   - 不该触发的场景必须明确不会触发。

3. 开发或修复时必须区分三类能力：
   - 被动属性：如 `force` 武力、固定攻击、防御、产量等，只进入属性和 Modifier，不写入战斗触发战报。
   - 战斗触发：如火攻、震慑、复活、减损等，应进入特性触发结果和战报。
   - 玩法过程能力：如行军加速、征兵减耗、掠夺收益，必须验证对应玩法结果，不要误写成战斗伤害。

4. 战报是主要验收入口。
   - 特性触发后，战报必须能说明发生了什么。
   - 战报数值必须和真实状态一致。
   - 标准战报中的每条 `detail.traits` 必须把 `detail` 内的设计参数和本次实际变化逐项展示，不能只显示特性名称或摘要。
   - 战报中的损失、复活、俘虏、减损、追加伤害不能只显示，必须和后端实际扣兵、返还、行军、增援记录一致。
   - 如果战报数值与真实状态冲突，优先修复后端结算和战报生成逻辑，再同步前端展示。

5. 每次修复必须尽量补测试。
   - 后端优先补 Go 单测。
   - 修 BUG 时，优先补能复现旧问题的测试。
   - 有适用场景限制的特性，必须补正反测试：应该触发的场景能触发，不应该触发的场景不能触发。
   - 带 `requiredOutcome=win/loss` 的特性必须分别验收胜利、战败和平局三态；平局既不满足胜利，也不满足战败。事件上下文以及 PVP、NPC、黄巾、增援、轮回等每个玩法适配层都必须直接传递核心的真实胜方，禁止先压成 `won bool`，也禁止用 `!Won` 把平局解释为战败。平局样本必须同时断言最终攻防战力和后端权威 `winner=draw`；双方人数相同不构成平局证据，因为城墙和公共 Modifier 仍可能改变胜负。`draw` 也不代表固定损失比例，各玩法必须分别核对自身核心返回的原始阵亡、存活和经验，前端不得按平局标签统一重算。
   - 随机特性必须把“合法场景但概率未命中”与“方向、场景或胜负条件不允许”分开验收：至少覆盖强制命中、合法场景强制未命中和错误场景三类测试。概率未命中时可以保留将领拥有快照，但不得改变战力、兵力、资源、经验或业务记录，也不得生成旧特性结果和标准时间线条目。若 `allowedSides` 为空或同时允许攻守双方，只要角色反转会改变分发顺序、作用目标、经验归属或战报分侧，就必须分别验收进攻方和防守方的合法未命中，不能用单侧样本代替双角色证据；未命中的随机特性也不得吞掉任一方后续独立特性。
   - 主守军和援军不能因为同属防守联盟就共用一份角色证据。特性允许 `defender` 与 `reinforcement` 时，必须分别验收主守将和援军的强制命中、合法未命中及错误场景，并核对作用来源、Modifier、主守军与各援军损失分配、三方经验、援军独立战报和持久化记录；同兵种也不得跨来源合并后错误加成、减损或返兵。
   - 同一将领同时拥有被动属性与随机战斗特性时，两项能力必须独立结算：随机能力未命中不能撤销被动属性已经进入核心的 Modifier 和战力，被动属性生效也不能让未命中的随机能力出现在触发时间线。兵损、经验和战报应只反映被动处理后的核心结果，不得混入未发生的随机增量。
   - 同一将领的特殊特性和加成特性必须分别校验各自的 `allowedSides`、`allowedScenes` 与胜负条件，不能因为其中一项在当前场景合法就让另一项越过自身限制。尤其在“随机特性合法但未命中、第二特性方向不合法”的组合中，两项都不得产生效果或时间线；拥有快照不能替代独立条件判断。
   - 战报数值修复必须测试战报字段和真实状态是否一致。
   - 如果影响接口字段，必须检查 OpenAPI。
   - 如果影响前端展示，必须同步检查 `web` 和 `web-wlsg`，能写测试就写测试，不能写测试至少跑类型检查或构建。

6. 前端验收要求：
   - `web` 和 `web-wlsg` 都要检查。
   - 战报页必须能正确展示特性名称、触发结果和关键数值。
   - 两个前端都必须消费后端真实 `detail` 字段，显示中文字段名、中文兵种名和实际整数；不得只渲染名称、摘要，或在前端按比例重新计算结果。
   - 不要只修一个前端。
   - 涉及页面展示时，可以使用用户本机安装的 Chrome 做浏览器验收，但 Chrome 验收不能替代自动测试。

7. 完成前必须更新相关文档。
   - 如果新增或调整特性规则，更新 `docs/系统设计/现有将领特性盘点.md`。
   - 如果调整治理标准，更新 `docs/系统设计/将领特性短期治理开发文档.md`。
   - 如果提交代码，提交前必须更新当天 `memory/YYYY-MM-DD.md`。

8. 每批任务必须维护完整性矩阵，不能只凭“代码中存在”判断特性已经完成。
   - 当前正式配置中的每个特性 ID 都必须能对应到：注册实现、触发条件、实际效果、战报结果、后端测试和两个前端的中文展示。
   - 同模板的不同特性 ID 也要逐项验证，避免模板有效但某个 ID 没有注册、没有订阅事件或配置参数写错。
   - 模板级测试只能证明通用执行器有效；涉及真实扣兵、返兵、掠夺、征兵、行军、经验或玩家状态时，还必须补应用层或真实业务流程测试。
   - 对未完成真实流程验收的特性，要在文档中明确标记剩余场景，不能宣称全部完成。

9. 战报数值的完成定义：
   - 特性结果中的变化值必须是本次实际变化量，不能展示配置值冒充结算结果，也不能补出无意义的 `0`。
   - 后端明确返回且具有结算含义的 `0` 必须保留，例如实际压制数为 0；前端不得因为真假值判断而吞掉有效零值。
   - 计算比例属于设计参数，战报中必须明确标记为“设计比例”；真实伤亡、追加损失、减损、复活和归队必须另列本次实际整数变化，不能用百分比替代。
   - 攻击、步兵防御、骑兵防御、指定兵种变化要分别记录；目标兵种或分类必须能命中真实兵种 ID。
   - 战前真实伤亡、临时压制、战后追加伤害、最终减损、复活和归队必须使用各自独立口径。
   - 双方战报、战斗记录、行军或增援记录、玩家最终兵力与资源必须能够相互对账。
   - 已结算战斗的重复读取或重试必须幂等，不能重复发放积分、经验、俘虏兵、复活兵、资源或重复生成战报。
   - 战斗事务之外补发的援军武将经验必须使用稳定事件键，并把“经验写入”和“幂等标记”放在同一仓储事务；回调或数据库提交失败时不得提前占用标记。PVP 返程状态和黄巾已结算状态必须能从持久化战斗或战报恢复补发，不能只依赖首次结算进程继续运行。
   - 攻守双方战报必须合并同一条完整触发时间线，不能因查看视角不同漏掉敌方战前或战后特性。
   - 同一将领多个特性跨阶段生效时，时间线必须保持“战斗前、战斗结算后、战斗结束后”的实际顺序；每项特性分别记录自身的设计参数和本次实际变化，不能互相覆盖或把后阶段结果提前展示。
   - 同一阶段的多项特性也必须保持核心分发顺序：同一触发方按将领配置中的特殊特性、加成特性排列，多触发方按实际分发批次排列，最后才允许用 ID 作为稳定兜底；不得直接按特性 ID 字母排序伪造先后关系。
   - 多个触发方连续修改同一单位属性时，后执行的固定值或比例能力必须读取前序处理后的当前整数，最终战力使用全部处理完成后的属性；每项特性仍分别记录自身的设计参数和本次实际整数变化，不能只展示合并后的净变化，也不能分别基于原始属性重复计算。
   - 同一战斗前阶段同时修改参战人数和单位属性时，核心战力必须使用处理后的实际参战人数与实际单位属性计算；战报要分别保留真实伤亡或临时压制、逐兵种属性修正和最终战力，不能只记录其中一项。
   - 参战将领快照中的等级、属性、Modifier 和特性必须在本场经验结算前冻结，保持与核心本场实际输入一致；战后经验和升级使用奖励字段单独表示，不能用升级后的新属性回写并冒充本场参战属性。
   - NPC 扫荡聚合战报的主侧战力、初始出动兵力和将领快照必须统一使用第一场战前时点；整个扫荡的首次战前等级、最终战后等级和累计经验只由奖励字段表示。聚合层不得把后续场次或最终存档的等级、Buff 回写到初始参战卡，也不得用初始快照代替整个扫荡的升级结果。
   - 将领、PVP、增援和标准战报之间复制参战快照时，必须完整保留并深拷贝 `stats`、`effectiveStats`、`attributes`、`buffs` 和特性中的 `params`、`allowedSides`、`allowedScenes` 等嵌套可变字段；标准战报转换不得只复制将领身份和特性而丢失本场基础四维、被动后的最终四维、属性或 Modifier。后续刷新配置、修改响应对象或推进驻防记录不得反向污染玩家存档、参战快照或历史战报。
   - 玩家查询、敌方情报脱敏和公开分享生成战报响应副本时，必须深拷贝顶层兵力、奖励、特性结果、援军将领，以及标准详情中的属性、Modifier、特性、奖励和动态明细。修改返回对象不得反向污染库存原始战报或轮回战斗记录；敌方将领未揭示时，两个前端也不得从旧 PVP 快照补回敌方将领或特性。
   - 援军武将快照必须冻结累计经验，并在每场结算后推进驻防记录中的经验与等级基线；同一援军连续参战时，下一场战前等级必须承接上一场战后等级。单场经验允许跨越多个等级，测试和前端不得假设每场最多升一级。战报只展示后端给出的本场经验和等级变化，两个前端不得自行推算经验曲线；敌方将领情报未揭示时，援军经验和等级变化必须一并脱敏。
   - 多名玩家的援军特性必须在旧 `traitOutcomes` 和标准 `detail.traits` 中同时保留 `ownerPlayerId`，玩家查询、JSON 序列化和公开分享均不得丢失；两个前端先按玩家精确归属，再以将领 ID 兼容缺少玩家归属的历史战报。即使不同玩家使用同一将领，也只能在各自援军卡片展示自己的结果，不能仅凭 `ownerRole=reinforcement` 复制到全部援军。
   - 没有标准 `detail` 的历史战报必须按 `traitTriggered` 的存储键和顺序读取 `traitOutcomes`，再恢复真实 `traitId`、攻守/援军角色、玩家、将领和结果明细；不能把旧结果清空，也不能从将领拥有快照补造。旧 `pvpReinforcements`、援军损失和权威 `survivedUnits` 必须一并进入兼容详情，保证援军卡片、特性数值和最终存活仍可对账。
   - 部分迁移战报即使已有标准 `detail`，也可能缺少或留空 `detail.traits`。标准时间线存在真实条目时必须作为唯一权威结果；标准时间线为空且旧 `traitTriggered` / `traitOutcomes` 有结果时才允许回退旧时间线，不能把新旧两套结果叠加造成重复触发。标准 `extra.pvp` 即使已存在，也可能只包含部分字段；前端必须逐字段补回旧援军快照与损失，不能用整个标准分区覆盖旧权威数据。历史兵力行缺少名称时必须按正式兵种配置显示中文，不能直接暴露兵种 ID。
   - 部分迁移战报的标准 `rewards` 也可能只是一只空壳。资源、掉落、城金、武将经验、等级和溢出字段缺失时必须逐字段回退旧战报值；标准字段一旦明确存在就保持权威，尤其不能把有结算意义的 `0`、空掉落列表或空溢出表替换成旧正数。
   - 旧战报的 `player*` / `dispatchedUnits` 表示战报所有者，`defender*` / `defenderUnits` 表示其目标，不能永远解释成进攻方和防守方。防守视角必须交换为“来袭方主侧、守城方次侧”，并同步交换战力、将领、兵力、经验和特性归属；援军独立视角只显示自身援军主侧，不能再补出目标卡或把顶层援军快照重复渲染一次。
   - 前端渲染多条同 ID 特性时，列表 key 必须纳入角色或玩家归属并保留稳定序号，不能只使用 `traitId` 或 `traitId + generalId`；不同玩家使用同一将领时不得因 React/Vue 节点复用而显示错误名称或旧数值。
   - 临时兵力压制与特性压制必须使用独立口径：`suppressedUnits` 只表示本场暂不参战且战后保留的士兵，`disabledTraitCount` 只表示本次实际拦截的后续特性数；两者不得相加或互换，被成功拦截的特性不得继续出现在触发时间线。
   - 多项追加伤害命中同一目标时必须逐项基于当前剩余人数封顶，最终累计损失不得超过原始兵力；后执行特性若实际变化为 0，不得生成虚假触发结果，前端也不得根据将领快照补造该特性。
   - 多兵种共享单场总上限时，必须使用明确且稳定的分配顺序，不能直接依赖 Go `map` 或对象键的随机遍历；真实状态、逐兵种结果和战报在相同输入下必须完全一致。
   - 同一将领的多个 `self_city` 留城能力必须使用同一权威占用状态：离城前先结清留城时段，离城期间全部失效，归城释放前先结清离城时段，释放后才恢复当前加成；参战快照可以保留拥有特性，但这些过程能力不得进入战斗触发时间线。
   - 留城过程能力会产出本次行动可使用资产时，行动事务必须先完成权威留城结算，再使用结算后的兵力或资源校验并创建行动；武将锁定离城后立即停止后续留城产出。战报中的出动、损失和存活只按实际参战资产记录，不能把本次产出总量写成战斗触发效果。
   - 俘虏与阵亡必须使用独立口径，但两者都必须从目标权威兵力中扣除；目标标准战报存活数按“战前兵力 - 阵亡 - 被俘”计算，不能把被俘兵继续留在目标库存或存活数中。
   - 俘虏归队或进入驻防的去向以应用层按真实兵种阵营确认的最终结果为准；特性详情、战报扩展字段和实际发兵位置必须一致，不能出现战报写归队但实际进入驻防的情况。
   - 同优先级的压制特性按同时触发处理，只压制优先级更低的后续特性；主战场剩余压制次数应连续作用于同阶段稍后结算的援军特性。
   - 援军的 `self_army` / `reinforcement_self` 只影响所属援军队伍；`enemy_army` / `enemy_traits` 应作用于真实来袭方。PVP 模块可以把援军临时映射为防守联盟参与标准事件排序和共享压制预算，但输出结果必须恢复 `ownerSide=reinforcement` 以及真实玩家、将领、援军记录归属。显式 `allowedSides=attacker` 或 `defender` 的方向限制优先，不能因联盟映射误触发周瑜火攻等主动进攻能力。
   - 副本等玩法模块只要发生标准战斗，就应通过模块适配层复用 `BeforeBattle -> combat.Resolve -> AfterCombatResolve -> AfterBattle`，并按玩家客观攻守身份执行方向约束；不得在玩法内复制特性算法或绕过总线。玩法没有行军、掠夺、征兵、留城、援军等过程时，相应过程能力不触发，也不能伪装成战斗时间线。
   - 被动属性只验证属性和派生战力，不伪装成战斗中触发的特性。
   - 特性写入的属性必须被当前玩法核心公式真实消费；只看到单位字段或战报字段变化，不能证明战斗收益。若特性玩法身份没有被固定，优先调整为当前核心可消费且符合场景边界的效果；若玩法身份不能调整，必须先提出核心扩展决策，不能制造假战报或擅自改动稳定核心。

10. 一批特性只有同时满足以下条件才可以标记“完成”：
   - 正确场景能触发，错误场景有反向测试且不会触发。
   - 武将选择校验失败时，兵力、资源结算时间、非战斗特性进度、武将占用及行军、增援、战报记录必须全部保持不变。
   - 允许不携带将领的战斗必须验证不会借用城内主将的属性、特性、经验或战报快照。
   - 涉及行军中配置变更时，必须先明确该入口的生效时点，并验证战斗效果、参战将领快照和战报时间线使用同一时点。当前 PVP 主攻行军和黄巾来袭中的主城守将，都在到达结算时读取最新配置；已派出的增援固定派出时的部署快照，后续参与 PVP 或黄巾协防时都不受全局配置开关追溯影响。各入口都不得出现效果、快照和时间线分别使用不同配置的情况；前端只能把后端实际时间线当作本场触发依据。
   - 战斗配置读取、保存、临时切换和测试恢复必须隔离 `activeCombatRules`、`rules`、`wallConfig` 等可变映射；读取接口返回深拷贝，保存入口也不得继续持有调用方映射。禁止因临时场景规则修改污染后续 NPC、PVP、黄巾或轮回结算。
   - 行军、征兵、产出等过程特性的效果量必须与“相同玩家状态、相同公共 Modifier、关闭被测特性”的真实事务对照，不能用脱离玩家状态的裸公式冒充业务基线；过程效果生效后继续进入战斗时，拥有快照可以保留，但不得写入本场触发时间线。
   - 征兵、PVP 出征、玩家或 NPC 侦查、NPC 进攻或扫荡、增援等局部动作会先结算资源或非战斗特性时，成功响应必须同时返回并由两个前端采用权威资源、当前产量、资源结算时间和非战斗特性进度，不能只更新兵力或资源数量后保留旧时间基线；请求失败时这些字段、兵力、队列和行军记录必须全部保持不变。
   - 同一玩家可从不同入口并发提交军事动作时，必须增加跨玩法争用验收。例如 PVP 出征与增援、PVP 出征与 NPC 即时战斗，或增援与 NPC 即时战斗，同时结算留城产兵、扣除同一兵力并占用同一将领时，只允许满足当前兵力和占用条件的事务成功；另一条可以因兵力不足或将领已占用合法失败。失败事务不得提交产兵、时间、进度、兵力、占用、经验、次数、战报或业务记录，也不得用旧响应覆盖另一入口刚提交的权威状态。MySQL 局部资产事务与双玩家事务发生可重试死锁或锁等待时，PVP 攻击、玩家侦查、增援和 NPC 战斗都必须有限重试并重新读取权威资产；重试不得重复扣兵或创建记录，也不能把首次可恢复的数据库冲突直接作为最终业务结果。两个前端的攻击、掠夺、侦查和增援必须使用同步命令锁，并且只在成功响应后回写权威状态；跨页面请求即使无法共享组件内锁，也必须依赖后端权威失败并保持当前新状态不变。
   - PVP 或黄巾来袭的防守主将在敌军到达前离城时，必须验证其守城 Modifier、特性、经验和战报快照全部失效；若到达前真实归城，则四项应同步恢复，同时始终保留城墙等非将领公共加成。必须通过真实出征或增援往返修改占用状态，不能只在测试中直接篡改字段。
   - 实际战斗或玩法结果发生了预期变化。
   - 战报名称、说明和数值与真实结果一致。
   - 两个前端只展示后端 `detail.traits` 中的真实触发结果，不用将领快照特性列表推断本场触发。
   - `web` 与 `web-wlsg` 同步支持并通过测试或构建。
   - 后端相关测试通过；涉及页面时再用本机 Chrome 做补充验收。

验收结束时，必须明确汇报：

- 本次处理了哪些特性。
- 修复或补齐了哪些战斗效果。
- 修复或补齐了哪些战报数值。
- 是否同步检查了 `web` 和 `web-wlsg`。
- 跑了哪些测试、构建或浏览器验收。
- 还有哪些特性或场景暂未覆盖。
