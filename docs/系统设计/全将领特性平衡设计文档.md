# 全将领特性平衡设计文档

最后更新：2026-07-22

> 曹操两项特性已于 2026-07-21 收敛；甄宓两项特性已于 2026-07-22 收敛为主动进攻战前各 50% 独立概率的全军攻击 +25% 与敌方全军防御 -25%。具体规则分别以对应特性更新开发文档、当前配置和代码为准。

## 1. 设计结论

Hero3 的将领特性系统采用“无稀有度、全将领同档强度、按战术分工选择”的设计。

本系统不使用将领稀有度决定强弱，不设计传奇将领天然强于普通将领，也不允许某些将领成为纯下位替代。每个将领都必须拥有两条独立特性：一条特殊特性，一条加成特性。玩家选择将领时，核心判断应是“当前战术需要什么能力”，而不是“哪个将领品质更高”。

当前配置中 `generals.json` 仍存在历史字段 `rarity`，该字段后续只允许作为兼容字段保留，不参与战斗强度、特性强度、排序权重、奖励价值和玩家选择引导。前端展示也不应继续强化稀有度概念。

实现备注（2026-07-03）：当前代码实际保留 25 位现有将领（魏国 9 位、蜀国 8 位、吴国 8 位），全部已绑定 `specialTrait` 和 `bonusTrait`。后续如产品要严格收敛为 24 位，应先由用户确认删除或合并哪一位将领，不能由实现时自动移除。

## 2. 设计目标

- 每个现有将领都有两条明确特性。
- 每个将领固定拥有一个特殊特性和一个加成特性。
- 所有特性的总体强度保持同档。
- 特性差异来自触发条件、适用场景、收益类型和风险代价。
- 特性必须接入标准事件管线，不绕过核心直接修改玩家长期资产。
- 战斗类特性必须进入战报，玩家可以看懂“为什么这一战结果不同”。
- 内政、行军、侦查、增援、掠夺类特性要通过可扩展事件补齐，避免写死在玩法代码里。
- GM 配置只能调整安全范围内的参数，不能把某个特性改成破坏平衡的数值。

硬规则：

- 一个将领必须同时配置 `specialTrait` 和 `bonusTrait`。
- `specialTrait` 负责特殊玩法效果，例如征兵、俘虏、火烧、震慑、复活、隐身、压制特性。
- `bonusTrait` 负责直接数值加成，例如攻击、防御、速度、兵种攻击、将领攻击、将领防御、敌方防御降低。
- 两条特性互相独立注册、独立配置、独立触发、独立写入战报。
- 两条特性可以在同一场战斗同时生效，但不能互相写死依赖。

## 3. 特性类型定义

### 3.1 特殊特性

特殊特性指不只是简单加数值，而是改变玩法结果、触发额外流程或产生特殊战斗表现的能力。

典型类型：

- 征兵产出：例如曹操“魏武号令”，固定时间获得虎卫或提高虎卫征兵效率。
- 战前爆发：例如甄宓“美人心计”，按独立概率提升本场全军攻击。
- 资源与消耗：例如郭嘉“神鬼之才”，降低征兵资源消耗。
- 复活：例如刘备“仁德天下”，复活本场阵亡士兵。
- 灌死/火烧/偷袭：例如关羽“水淹七军”、周瑜“火烧赤壁”、陆逊“火烧联营”。
- 控制参战：例如张飞“震慑全军”，让敌方部分兵不参与本场战斗。
- 隐秘行军：例如吕蒙“白衣渡江”，减少预警或延迟暴露。
- 特性压制：例如黄盖“苦肉计”，让敌方部分特性失效。
- 侦查强化：后续孙尚香可预留为侦查零伤亡获得情报。

特殊特性的重点是“效果要有”，不能只写成普通加成。它们必须进入战报或对应业务日志，让玩家知道本次触发产生了什么特殊结果。

### 3.2 加成特性

加成特性指直接作用于自身、将领属性、全军、指定兵种、指定军事属性或指定战斗阶段的数值加成。

典型类型：

- 全军防御提升。
- 步兵攻击提升。
- 骑兵攻击提升。
- 将领攻击提升。
- 将领防御提升。
- 队伍速度提升。
- 敌方防御降低。
- 己方最终损失降低。

加成特性的重点是“作用对象清晰”：必须说明加给谁、加什么、何时生效、能否叠加、是否只影响携带该将领的队伍。

### 3.3 GM 百分比参数

图片中的百分比和数值应进入配置，作为默认参数或参考参数，不应从设计中删除。

处理规则：

- 图片给出的 `35%`、`50%`、`100%`、`20 点`、`500/分钟` 等数值，全部记录到文档和配置建议中。
- GM 可以调整这些参数。
- 后端必须给每个参数设置安全上下限。
- 默认值可以按图片原始值配置，但正式服上线前需要通过战斗模拟和数值测试决定是否下调。
- 强效果必须有 `triggerChance`、`maxAffected`、`maxRate`、`cooldown`、`scope` 等限制字段之一，避免失控。

## 4. 平衡原则

### 4.1 同档强度

所有将领默认处于同一强度层级，不能按名气、历史地位或旧字段稀有度拉开绝对强度差。

正确方向：

- 曹操适合进攻压制。
- 刘备适合低损耗持久战。
- 诸葛亮适合防守控场。
- 甘宁适合掠夺收益。
- 太史慈适合增援驻防。
- 夏侯渊适合快速出征。
- 荀彧适合内政发展。

错误方向：

- 某个将领全场景都强。
- 某个将领只是另一个将领的弱化版。
- 某个特性只有数值，没有玩法判断。
- 强将只堆攻击、弱将只给小资源。

### 4.2 强效果必须有边界

特性可以有明显爽点，但必须通过条件或代价控制。

- 高收益：需要低概率、特定兵种、胜利后、以少打多、纯兵种或仅限某玩法。
- 稳定收益：数值必须较小，避免长期滚雪球。
- 减损/复活：不能抵消真实损耗的核心体验。
- 控制类：被控制的兵不应凭空死亡，必须能在战报解释清楚。
- 内政类：不能比活动、任务、科技、建筑等系统收益更强。

### 4.3 推荐数值带

| 类型 | 推荐范围 | 说明 |
|---|---:|---|
| 触发概率 | 20% - 50% | 强效果低概率，弱效果可稳定触发 |
| 直接额外伤害 | 5% - 15% | 不超过敌方实际兵量 |
| 己方减损 | 5% - 20% | 按实际损失后修正 |
| 战后复活 | 默认可按图片 50%，正式服建议压测后调整 | 必须有单场复活上限和 GM 上下限 |
| 行军缩短 | 10% - 25% | 可和加速系统叠加但需有上限 |
| 掠夺收益提升 | 10% - 20% | 只影响本次掠夺收益 |
| 资源/征兵/建造加成 | 3% - 8% | 长期稳定收益必须保守 |
| 侦查/反侦查偏移 | 10% - 30% | 只影响信息可见性，不直接杀兵 |

### 4.4 图片方案融合规则

本次补充参考了图片中的三国将领特性设计。当前正式方向包括曹操“魏武号令”、司马懿“疑兵偷袭”、甄宓“美人心计”、许褚“破敌防御”、典韦“死战到底”、关羽“水淹七军”、张飞“震慑全军”、赵云“七进七出”、周瑜“火烧赤壁”、陆逊“火烧联营”、吕蒙“白衣渡江”、黄盖“苦肉计”等。

融合时采用以下处理：

- 保留图片方案的特性名字、历史味道和战术方向。
- 图片中的高数值，例如 `+35%`、`+50%`、`+100%`、全军灌死、敌方失去一切特性等，作为 GM 默认参数或参考参数保留。
- 固定类效果、概率类效果都必须走 GM 参数和后端上下限校验。
- “秒到达”“全军不参战”“全部步兵死亡”“失去一切特性”这类强控制，效果可以存在，但必须有触发概率、最大影响比例、最短行军时间、作用范围等安全字段。
- 图片中出现但当前项目没有的将领，如孙尚香，先作为后续扩展预留；当前 24 将领仍以 `generals.json` 为准。
- 当前项目有甘宁但图片中没有甘宁，保留甘宁“锦帆劫掠”定位，保证现有将领全部覆盖。

## 5. 当前系统基础

现有后端已经有将领特性基础框架：

- `go/internal/core/general/trait.go`
- `go/internal/core/general/context.go`
- `go/internal/core/general/bus.go`
- `go/internal/core/general/traits/`

已存在事件：

- `before_battle`
- `after_combat_resolve`
- `after_battle`
- `incoming_attack`
- `resource_settle`
- `building_upgrade`
- `recruit_complete`

已实现或已有基础的特性：

- 甄宓：`meiren`
- 刘备：`rende`
- 周瑜：`huogong`
- 张辽旧实现：`weizhenxiaoyao`（已删除；正式方案使用 `weizhen_zhenhe` 与 `weizhen_xiaoyao`）

需要注意：部分事件常量存在，但不代表所有业务流程已经完成分发接入。开发时必须检查 PVP、NPC、增援、侦查、掠夺、内政、征兵、建筑等流程是否真正调用了特性事件总线。

轮回绝境当前已由玩法模块适配层接入标准战斗事件：进攻波按进攻方、防守波按防守方执行战前、战斗结算后和战斗结束后特性；被动 Modifier 同样进入核心输入。副本不存在的行军、掠夺、征兵、留城和援军过程能力保持不触发，不能仅因参战快照携带该特性就在战报中补造结果。

## 7. 特性事件接入设计

### 7.1 已有战斗事件可直接承载

以下特性优先使用现有战斗事件实现：

| 事件 | 可承载特性 |
|---|---|
| `before_battle` | 疑兵偷袭、美人心计、水淹七军、震慑全军、奇门遁甲、白衣渡江、谋定后发、魅惑扰阵、虎痴冲阵、破敌防御、百步穿杨、盾阵防御、固守汉中、江东固守、死战到底、威震逍遥、武圣破军、万人怒吼、小霸王、美周郎军略 |
| `after_combat_resolve` | 死战到底、火烧赤壁、火烧联营、小霸王、苦肉计 |
| `after_battle` | 仁德天下、神鬼之才 |

注意：部分减损类特性更适合在 `after_combat_resolve` 修正损失，而不是 `after_battle` 再返还兵力。开发时应优先选择能保证战报和资产一致性的事件点。

### 7.2 需要补齐的新事件或上下文字段

| 能力 | 需要事件或字段 | 说明 |
|---|---|---|
| 行军缩短 | `march_create` 或出征/增援创建前特性读取 | 赵云、吕蒙、太史慈需要影响本次队伍行军秒数。 |
| 掠夺收益 | `plunder_resolve` 或战斗结果增加掠夺上下文 | 甘宁、诸葛亮需要影响可掠夺资源。 |
| 内政收益 | `resource_settle`、`building_upgrade`、`recruit_complete` 完整分发 | 曹操、郭嘉、荀彧需要稳定接入核心内政和征兵事件。 |
| 增援防守 | 战斗上下文增加援军来源、队伍归属、携带武将 | 自身范围只影响所属援军；对敌范围作用于来袭方，并保留真实援军玩家和将领归属。 |
| 特性压制 | TraitBus 支持触发率修正或特性禁用标记 | 黄盖需要压制敌方单个将领特性，司马懿需要削弱敌方开战能力。 |
| 城池压制状态 | Buff/Modifier 或城池状态表 | 若后续恢复曹操“进攻压制”版本，应通过标准 Buff/Modifier 实现。 |
| 侦查反侦查 | `scout_resolve` 预留 | 图片中的孙尚香“侦查零伤亡获得情报”可作为未来将领扩展方向。 |

### 7.3 增援武将特性触发规则

增援队伍携带武将时，该武将在参与防守战计算时可以触发特性。该规则适用于玩家城池被攻击时，多路援军和主城守军共同参与防守的场景。

触发边界：

- 增援武将的防守类、减损类、复活类、援军类、速度类特性可以按条件触发。
- 增援武将的 `self_army` / `reinforcement_self` 特性只作用于自己的增援队伍。
- 增援武将的 `enemy_army` / `enemy_traits` 特性作用于真实来袭方，并与防守主将共享同阶段排序和压制预算。
- 增援武将不能默认加成接收方主城兵。
- 增援武将不能默认加成其他玩家的增援队伍。
- 显式限定 `allowedSides=attacker` 或 `defender` 的特性优先服从方向边界，不能因援军属于防守联盟而误触发；无显式攻守限制的对敌特性才允许援军按场景和胜负条件参与。
- 若某个特性设计为“全体守军生效”，必须在配置中显式标明 `scope=all_defenders`，并经过 GM 参数上限校验。

战报要求：

- 战报必须显示是哪位玩家的哪支援军触发了特性。
- 战报必须显示触发武将、特性名称、作用对象和具体结果。
- 示例：玩家 A 的援军武将刘备触发【仁德天下】，该援军阵亡士兵复活 50%。
- 示例：玩家 B 的援军武将张飞触发【震慑全军】，敌方部分进攻兵力本场未参战。

## 8. 数据与配置设计

### 8.1 将领配置

`go/config/generals.json` 中每个将领应配置两条特性：一个 `specialTrait`，一个 `bonusTrait`。

```json
{
  "id": "caocao",
  "name": "曹操",
  "faction": "wei",
  "title": "魏武帝",
  "enabled": true,
  "buffs": {},
  "specialTrait": {
      "traitId": "weiwu_haoling",
      "traitType": "special",
      "enabled": true,
      "params": {
        "guardPerMinute": 300
      }
  },
  "bonusTrait": {
    "traitId": "weiwu_tongyu",
    "traitType": "bonus",
    "enabled": true,
    "params": {
      "defenseBonusRate": 0.15
    }
  }
}
```

配置要求：

- 每个将领必须有且只有一个 `specialTrait`。
- 每个将领必须有且只有一个 `bonusTrait`。
- `specialTrait.traitType` 必须为 `special`。
- `bonusTrait.traitType` 必须为 `bonus`。
- `rarity` 字段不参与任何逻辑判断，后续可迁移删除。
- `params` 必须经过 `ParamSchema` 和边界校验。
- GM 后台只能配置特性允许暴露的参数。
- 特性 ID 必须后端注册、前端展示、战报展示三处一致。
- 图片中的百分比、固定点数、每分钟产出都应进入 `params`，由 GM 调整，不写死在代码里。
- 兼容旧配置时，如果仍存在 `traits: []`，迁移脚本应按 `traitType` 拆分为 `specialTrait` 和 `bonusTrait`。

### 8.2 参数命名规范

特殊特性常用参数：

| 参数 | 含义 | 示例 |
|---|---|---|
| `triggerChance` | 触发概率 | 张飞震慑、刘备复活、黄盖苦肉计 |
| `effectRate` | 主要效果比例 | 火烧 25%、灌死 35%、震慑 50% |
| `resourceCostReduction` | 资源消耗降低 | 郭嘉征兵消耗 -50% |
| `guardPerMinute` | 每分钟产兵数量 | 曹操留城时每分钟 300 虎卫 |
| `maxAffectedRate` | 最大影响比例 | 防止全军直接被控制或杀死 |
| `maxAffectedCount` | 最大影响数量 | 防止超大规模战斗中效果失控 |
| `minMarchSeconds` | 最短行军时间 | 太史慈闪电战不能无限接近 0 |

加成特性常用参数：

| 参数 | 含义 | 示例 |
|---|---|---|
| `attackBonusRate` | 攻击百分比加成 | 典韦步兵攻击 +35% |
| `defenseBonusRate` | 防御百分比加成 | 夏侯渊我军防御 +35% |
| `speedBonusRate` | 速度百分比加成 | 赵云全军速度 +100% |
| `enemyDefenseReductionRate` | 敌方防御降低 | 许褚敌方防御 -35% |
| `forceBonus` | 武将被动武力增加 | 马超武力 +20 点 |
| `generalDefenseFlat` | 全军两类防御固定值（兼容旧参数名） | 魏延全军步防、骑防各 +20 点 |
| `unitAttackFlat` | 指定兵种固定攻击 | 孙策霸王骑攻击 +50 点 |
| `targetUnitType` | 作用兵种 | 步兵、骑兵、霸王骑、虎卫 |

### 8.4 特性注册

每个特性独立文件实现，放入：

```text
go/internal/core/general/traits/
```

要求：

- 文件顶部写中文说明注释。
- 每个功能方法写中文注释。
- `init()` 注册到 `general.Register`。
- `ParamSchema()` 提供 GM 可配置参数和安全边界。
- `Description(params)` 返回玩家可读描述。
- 实际触发后必须写入 `Triggered`，供战报展示。

### 8.5 前端展示

前端 `web/src/utils/traits.ts` 需要同步所有特性元信息。

展示要求：

- 将领详情页显示特性名称、触发条件、简短说明。
- 战报内显示实际触发的特性，不显示未触发特性。
- 不显示“稀有度强弱”引导。
- 特性文案统一描述为“战术定位”，不是“品质优势”。

## 9. 战报展示规则

战斗相关特性必须写入战报，结构建议：

```json
{
  "traitId": "huogong",
  "name": "火烧赤壁",
  "ownerSide": "attacker",
  "ownerGeneralId": "zhouyu",
  "triggered": true,
  "detail": {
    "extraLosses": {
      "infantry": 1200,
      "cavalry": 800
    },
    "triggerChance": 0.35,
    "effectRate": 0.08
  }
}
```

战报文案原则：

- 告诉玩家谁触发了什么。
- 告诉玩家改变了什么结果。
- 只展示本场实际生效数据。
- 不展示过多内部公式。
- 增援特性必须标明“来自某玩家的援军”。

示例文案：

- 周瑜触发【火烧赤壁】，敌方步兵额外损失 1200，骑兵额外损失 800。
- 刘备触发【仁德天下】，战后复活步兵 900，骑兵 300。
- 张飞触发【震慑全军】，敌方 12% 守军本场未参战。
- 黄盖触发【苦肉计】，敌方【火烧赤壁】本场被压制。

## 10. GM 配置与校验

GM 后台需要支持：

- 查看全部已注册特性。
- 按特殊特性、加成特性筛选。
- 查看每个特性的中文名、描述、参数 schema。
- 给将领分别绑定特殊特性和加成特性。
- 调整特性参数。
- 启用或禁用单个特性。
- 保存后触发配置校验。

校验规则：

- 每个启用将领必须绑定一个特殊特性和一个加成特性。
- 每个特性必须有明确类型，特殊特性和加成特性不能混淆保存。
- 特性 ID 必须存在于后端注册表。
- 参数不能超过 schema 上下限。
- 百分比参数必须使用 0 到 1 的小数。
- 行军缩短、减损、复活、额外伤害必须有硬上限。
- 禁止通过 GM 配置让特性 100% 永久压制、无限复活、无限俘虏、无限资源加成。
- 修改线上特性配置应记录操作日志；如果当前 GM 审计暂不做，至少保留更新时间和操作人字段预留。

## 12. 验收标准

功能验收：

- 全部现有将领都有两条特性。
- 全部现有将领都绑定一个特殊特性和一个加成特性。
- 至少 48 条将领特性均有 ID、名称、类型、参数 schema 和展示文案。
- 任一将领不存在稀有度强弱逻辑。
- 后端 `general.All()` 可以列出所有已注册特性。
- `generals.json` 中每个将领都绑定且只绑定一个 `specialTrait` 和一个 `bonusTrait`。
- PVP、NPC、增援参战时战斗类特性可以正常触发。
- 行军、掠夺、内政类特性接入对应事件后能生效。
- 战报能显示实际触发的特性和关键结果。
- GM 配置超出安全范围时保存失败。
- 图片中的百分比和固定数值已进入 GM 参数配置，不写死在代码里。

平衡验收：

- 没有任何将领在进攻、防守、掠夺、增援、内政全场景都最优。
- 没有任何特性成为另一个特性的纯下位替代。
- 所有复活、减损、额外伤害、俘虏、压制效果都有硬上限。
- 稳定长期收益类特性强度低于战斗条件触发类特性。
- 玩家能根据玩法目标选择不同将领，而不是固定选择同一个。

文档与展示验收：

- README 或帮助文档中不再宣传将领稀有度强弱。
- 前端将领详情页显示完整特性说明。
- 战报中显示特性触发结果。
- GM 后台显示特性类型和参数 schema。
- OpenAPI 如新增接口，需要同步文档。

## 13. 风险与后续补充

- 当前 `generals.json` 有 `rarity` 历史字段，短期可以保留，长期应迁移删除或改为纯展示标签。
- 刘备当前 `rende` 参数 `reviveRate = 0.5` 与图片方案一致，可以作为 GM 默认值，但必须配置单场复活上限并经过战斗模拟验证。
- 图片中的多数数值偏强，可以作为默认参数或参考参数，但必须走参数上限和战斗模拟验证。
- 图片中的孙尚香当前不在 `generals.json`，后续如新增吴国将领，可优先继承“侦查零伤亡获得情报”的方向。
- 前端已有 `traits.ts` 中部分特性 ID 与当前将领列表不完全一致，需要统一。
- 黄盖这种“压制敌方特性”的能力，需要 TraitBus 支持触发率修正或特性禁用标记，否则不应硬编码到单个玩法。
- 吕蒙、赵云、太史慈这类行军类特性必须统一进入行军时间计算，不能各玩法单独实现。
- 曹操如果走虎卫产出，必须确认虎卫是否为正式兵种；如果暂未开放，应先用特殊兵征兵效率替代。
