# <span style="color:#16a34a">增援系统修复开发方案</span>

最后更新：2026-07-02

## <span style="color:#16a34a">1. 文档定位</span>

本文档用于修复当前增援系统已发现的功能缺口和体验问题。

本次不是重做增援系统，而是在现有增援模块基础上补齐以下能力：

- 增援行军中可以像 PVP 出征一样加速。
- 增援在路上或抵达后都可以被派出方召回。
- 增援在路上或抵达后都可以被接收方遣返。
- 路上召回或遣返时，直接返程，走了多久就返程多久。
- 派出方能看到返程中的增援队伍。
- 接收方能看到别人正在路上的增援队伍。
- 接收方左侧驻防队伍需要显示来源玩家名字。
- 增援携带武将需要在接收方驻防展示里可见。

当前增援核心链路已经存在，开发时应复用现有 `player_reinforcements`、增援事务、驻防展示、PVP 加速规则、金币流水和战斗接入能力。

## <span style="color:#16a34a">2. 当前现状</span>

### <span style="color:#16a34a">2.1 已完成能力</span>

后端已经具备：

- `SendReinforcement` 发起增援。
- 发起时扣派出方兵力。
- 增援不能发给 NPC。
- 增援不能发给自己。
- 增援可以携带最多 1 个武将。
- 武将派出后会被占用。
- 增援到达后进入 `stationed`。
- 增援能参与防守战斗。
- 援军损耗能写回增援批次。
- 派出方可以召回。
- 接收方可以遣返。
- 返程完成后返还剩余兵力并释放武将。
- `ListSentReinforcements` 可以看到派出的增援。
- `ListReceivedReinforcements` 可以看到收到的增援。

前端已经具备：

- 增援页面。
- 左侧驻防队伍面板。
- 左侧行军倒计时面板。
- 我派出的增援倒计时。
- 我收到的路上增援倒计时。
- 驻防队伍绿色展示。
- 驻防队伍兵种排序。

### <span style="color:#16a34a">2.2 当前缺口</span>

当前缺少：

- 增援行军后加速接口。
- 增援加速按钮。
- 增援加速次数记录。
- 增援加速城金扣费和流水。
- 路上召回/遣返按已行军时间返程。
- 接收方前端对 `marching` 状态显示遣返按钮。
- 左侧倒计时对增援显示召回、遣返、加速按钮。
- 左侧驻防队伍显示来源玩家名字。
- 左侧驻防队伍显示携带武将。

当前风险：

- `SendReinforcementRequest.speedMultiplier` 由客户端传入，后端只做了默认值处理，没有看到上限、扣费或来源校验。需要避免玩家通过接口传入超大倍率实现免费加速。

## <span style="color:#16a34a">3. 最终规则</span>

### <span style="color:#16a34a">3.1 召回规则</span>

派出方可以召回自己派出的增援。

允许召回状态：

```text
marching
stationed
```

不允许召回状态：

```text
fighting
returning
completed
cancelled
failed
```

规则：

- 路上的增援被召回后，直接从当前位置返程。
- 已抵达的增援被召回后，从接收方城池返程。
- 已经返程的增援不能重复召回。
- 正在战斗中的援军不能手动召回。

### <span style="color:#16a34a">3.2 遣返规则</span>

接收方可以遣返别人派来的增援。

允许遣返状态：

```text
marching
stationed
```

不允许遣返状态：

```text
fighting
returning
completed
cancelled
failed
```

规则：

- 路上的增援被遣返后，直接从当前位置返程。
- 已驻扎的增援被遣返后，从接收方城池返程。
- 已经返程的增援不能重复遣返。
- 正在战斗中的援军不能手动遣返。

### <span style="color:#16a34a">3.3 返程时间规则</span>

返程时间不再固定等于完整行军时间，而是按实际已走时间计算。

路上召回或遣返：

```text
返程秒数 = 当前时间 - sent_at
```

约束：

- 最小 1 秒。
- 最大不超过当前实际去程总时长。
- 当前实际去程总时长受增援加速影响。

已抵达后召回或遣返：

```text
返程秒数 = arrived_at - sent_at
```

兜底：

```text
如果 arrived_at 缺失，则返程秒数 = march_seconds
```

战斗全灭返程：

- 如果援军全灭，状态可以进入 `returning` 用于释放武将和归档。
- 全灭返程时间可以使用 1 秒或当前完整返程规则，第一版建议沿用现有逻辑，重点不影响兵力返还，因为剩余兵力为 0。

### <span style="color:#16a34a">3.4 加速规则</span>

增援加速对齐 PVP 加速。

第一版规则：

- 只有派出方可以加速。
- 只有 `marching` 状态可以加速。
- 返程中不能加速。
- 驻扎中不能加速。
- 每次加速消耗固定城金，第一版复用 PVP 固定城金成本。
- 最多加速 2 次，第一版复用 PVP 次数上限。
- 每次加速将剩余到达时间缩短一半。
- 加速后派出方和接收方看到的到达倒计时都同步变短。

计算方式：

```text
elapsedSeconds = now - sent_at
currentArriveAt = sent_at + march_seconds
remainingSeconds = currentArriveAt - now
newRemainingSeconds = ceil(remainingSeconds / 2)
newMarchSeconds = elapsedSeconds + newRemainingSeconds
```

更新：

```text
record.march_seconds = newMarchSeconds
record.metadata.acceleratedTimes += 1
record.speed_multiplier = 原始行军秒数 / newMarchSeconds
record.updated_at = now
```

注意：

- `arriveAt` 当前不是独立存库字段，而是读取时通过 `sent_at + march_seconds` 计算得到。
- 因此第一版加速不需要新增 `arrive_at` 字段，只需要更新 `march_seconds`。
- 如果未来要展示精确加速历史，可以在 `metadata` 中追加 `accelerateLogs`。

## <span style="color:#16a34a">4. 后端修改方案</span>

### <span style="color:#16a34a">4.1 模型补充</span>

当前 `Reinforcement` 已有 `Metadata map[string]any`，第一版可以不新增数据库字段。

在 `metadata_json` 中写入：

```json
{
  "acceleratedTimes": 1,
  "accelerateLogs": [
    {
      "at": "2026-07-02T12:00:00Z",
      "cost": 10,
      "beforeMarchSeconds": 10800,
      "afterMarchSeconds": 5400
    }
  ]
}
```

前端需要读取加速次数时，可以先从 `metadata.acceleratedTimes` 取值。若 TypeScript 类型暂未声明，需要补充。

如为了类型更清晰，也可以在 `Reinforcement` 结构上新增：

```go
AcceleratedTimes int `json:"acceleratedTimes"`
```

但如果新增独立字段，需要同步数据库迁移、OpenAPI 和前端类型。第一版建议先使用 `metadata`，降低改造范围。

### <span style="color:#16a34a">4.2 新增错误</span>

建议新增：

```go
ErrReinforcementNotAccelerable = errors.New("reinforcement cannot be accelerated")
```

错误映射：

- 不是派出方：`404` 或权限错误，沿用现有增援错误风格。
- 状态不可加速：`400` 或 `409`。
- 加速次数已满：`409`。
- 城金不足：复用 `ErrInsufficientCityGold`。

### <span style="color:#16a34a">4.3 新增服务方法</span>

新增：

```go
func (s *Service) AccelerateReinforcement(playerID string, reinforcementID string) (ReinforcementActionResponse, error)
```

如果不新增响应结构，也可以复用：

```go
ReinforcementResponse
```

但为了返回城金和消耗，建议新增：

```go
type ReinforcementActionResponse struct {
    Reinforcement Reinforcement        `json:"reinforcement"`
    Patch         GarrisonActionResult `json:"patch,omitempty"`
    CityGold      FlexInt              `json:"cityGold,omitempty"`
    Cost          int                  `json:"cost,omitempty"`
    ServerTime    string               `json:"serverTime,omitempty"`
}
```

加速逻辑：

```text
1. 校验 playerID 非空。
2. 锁定增援记录和派出方玩家状态。
3. 校验 record.from_player_id == playerID。
4. normalizeGarrisonRecord(record)。
5. 校验 record.source_type == reinforcement。
6. 校验 record.status == marching。
7. 校验当前 arriveAt > now。
8. 从 metadata 读取 acceleratedTimes。
9. 校验 acceleratedTimes < 2。
10. 校验派出方城金足够。
11. 扣城金。
12. 计算 newMarchSeconds。
13. 更新 record.march_seconds。
14. 更新 record.speed_multiplier。
15. 更新 metadata.acceleratedTimes 和 accelerateLogs。
16. 写金币流水。
17. 返回最新增援、cityGold、cost、serverTime。
```

金币流水：

- 可新增 `LedgerRefReinforcementAccelerate = "reinforcement_accelerate"`。
- `Reason = "reinforcement_accelerate"`。
- `RefID = reinforcementID`。

### <span style="color:#16a34a">4.4 修改返程计算</span>

新增函数：

```go
func calculateReinforcementReturnSeconds(record *Reinforcement, now time.Time) int
```

建议实现：

```text
如果 record == nil，返回 1。
解析 sent_at，失败则返回 max(1, record.return_seconds, record.march_seconds)。

如果 status == marching：
  elapsed = now - sent_at
  maxOutbound = record.march_seconds
  return clamp(elapsed, 1, maxOutbound)

如果 status == stationed：
  如果 arrived_at 可解析：
    actualOutbound = arrived_at - sent_at
    return max(1, actualOutbound)
  否则：
    return max(1, record.march_seconds)

其它状态：
  return max(1, record.return_seconds, record.march_seconds)
```

修改 `startReinforcementReturn`：

当前逻辑：

```go
record.ExpectedReturnedAt = now.Add(time.Duration(record.ReturnSeconds) * time.Second)
```

改为：

```go
returnSeconds := calculateReinforcementReturnSeconds(record, now)
record.ReturnSeconds = returnSeconds
record.ExpectedReturnedAt = now.Add(time.Duration(returnSeconds) * time.Second)
```

注意顺序：

- 必须先根据旧状态计算返程时间。
- 再把状态改成 `returning`。
- 否则无法区分 `marching` 和 `stationed` 的返程规则。

### <span style="color:#16a34a">4.5 限制 speedMultiplier 风险</span>

当前 `SendReinforcementRequest.speedMultiplier` 由客户端传入，存在免费加速风险。

建议第一版处理：

- 前端不再传 `speedMultiplier`。
- 后端忽略客户端传入的 `speedMultiplier`，默认使用 `1`。
- 真实行军速度只来自：
  - 建筑加成。
  - 武将加成。
  - Modifier 管线。
  - 后续道具或活动加成。

如果暂时不能删除字段，则至少加限制：

```text
speedMultiplier <= 1 时使用 1
speedMultiplier > 1 时也按 1 处理
```

后续如果要支持道具加速，必须通过物品 Effect 或加速接口处理，不允许客户端自由传倍率。

## <span style="color:#16a34a">6. 数据与兼容</span>

### <span style="color:#16a34a">6.1 不新增数据库字段的方案</span>

第一版推荐不新增数据库字段：

- 加速次数写入 `metadata_json.acceleratedTimes`。
- 加速日志写入 `metadata_json.accelerateLogs`。
- 到达时间继续由 `sent_at + march_seconds` 计算。
- 返程到达时间继续由 `return_started_at + return_seconds` 计算。

优点：

- 不需要迁移。
- 改造范围小。
- 与现有 `player_reinforcements` 表兼容。

缺点：

- `acceleratedTimes` 类型约束弱，需要读写时做好转换。

### <span style="color:#16a34a">6.2 新增字段的方案</span>

如果希望长期规范，可以新增：

```sql
ALTER TABLE player_reinforcements
  ADD COLUMN accelerated_times INT NOT NULL DEFAULT 0;
```

但需要同步：

- MySQL scan。
- insert/update。
- OpenAPI。
- 前端类型。
- 迁移脚本。

本次建议先不新增字段，后续如果加速相关功能变多，再做结构化字段。

## <span style="color:#16a34a">9. 验收标准</span>

后端验收：

- 增援路上召回后直接返程。
- 增援路上遣返后直接返程。
- 返程时间等于已走时间。
- 已驻扎增援返程时间等于实际去程时间。
- 增援行军中可以加速。
- 增援加速消耗城金。
- 增援最多加速 2 次。
- 非派出方不能加速。
- 派出方能看到返程中的队伍。
- 返程完成后兵力和武将正确归还。
- 客户端不能通过 `speedMultiplier` 免费加速。

前端验收：

- 左侧倒计时显示我派出的增援、返程增援、别人增援我的路上队伍。
- 我派出的路上增援有加速和召回按钮。
- 别人增援我的路上队伍有遣返按钮。
- 增援页面中路上和驻扎状态都能按权限召回/遣返。
- 驻防队伍显示 `自己`、`增援 · 玩家名`。
- 驻防队伍显示携带武将。
- 驻防队伍保持绿色风格。
- 兵种顺序保持固定，不跟接口返回顺序跳动。

## <span style="color:#16a34a">10. 需要注意的边界</span>

- 增援返程中不占用接收方驻防来源槽。
- 增援 `marching` 仍然占用接收方来源槽，避免第 6 个来源同时发兵。
- 正在战斗中的增援不允许手动召回或遣返。
- 已全灭援军返程只用于释放武将和归档，不返还兵力。
- 接收方遣返别人路上的增援时，派出方应该在“我派出的”列表和左侧倒计时看到返程。
- 加速只影响到达时间，不影响战斗规则。
- 加速次数和费用以后可以配置化，本次先对齐 PVP。

## <span style="color:#16a34a">11. 最终结论</span>

本次修复的核心不是重建增援系统，而是把现有增援生命周期补完整。

完成后，增援应具备和 PVP 出征一致的基础行军体验：

```text
派出 -> 路上可见 -> 可加速 -> 可召回/遣返 -> 直接返程 -> 返程可见 -> 到家归还
```

同时，接收方驻防体验也要补完整：

```text
看到谁增援我 -> 看到带了哪个武将 -> 看到哪些兵 -> 必要时可以遣返
```
