# 将领特性短期治理开发文档

最后更新：2026-07-20

## 1. 任务定位

本任务作为短期持续运行任务，目标不是重做将领系统，也不是设计一整套新特性。

当前目标是：保留现有将领特性体系，逐个检查现有特性在真实战斗中是否能够正确触发、正确生效、正确影响战斗结果，并能在两个玩家前端中被理解和展示。

## 2. 本轮范围

本轮只处理将领特性相关问题。

重点检查：

- 特性是否已注册。
- 特性是否已配置到将领。
- 特性参数是否合理。
- 特性触发阶段是否正确。
- 特性在实际战斗中是否会被调用。
- 特性是否真实改变战斗输入、战斗结果或战后状态。
- 特性结果是否进入战报。
- `web` 和 `web-wlsg` 是否同步展示。
- 是否有测试覆盖，尽量减少回归 BUG。

不在本轮范围：

- 不重做完整将领资产系统。
- 不大规模调整将领成长、等级、经验和名册。
- 不强行物理拆包。
- 不追求每个名将特性都必须完全贴合历史设定。
- 不优先扩展大量新特性。

## 3. 核心原则

第一，特性可以简单，也可以有随机性，但必须准确。

准确的意思是：触发条件明确、触发结果真实落地、实际战斗有效、战报和前端展示不误导玩家。

第二，多样性要建立在稳定性之上。

当前允许保留攻击加成、防御加成、兵种加成、战前削弱、追加伤害、减损、复活、行军加速、征兵减耗、掠夺收益等不同类型，但每一种都必须能被验证。

第三，战斗特性分阶段治理。

- 战前：只处理战斗输入修正，例如加成、削弱、震慑、俘虏。
- 战斗结算后：只处理 `CombatResult` 修正，例如追加伤害、减损。
- 战斗结束后：只处理真实状态回补、复活、战报补充和后置结果。

第四，前端修改必须双端同步。

凡是将领特性修改影响玩家可见内容、接口字段、战报展示、战斗结果解释或前端交互时，必须同时检查并同步修改：

- `web`
- `web-wlsg`

不能只改其中一个玩家前端。

第五，特性适用场景必须被代码约束。

例如周瑜“火攻”这类只应在主动进攻战触发的特性，必须明确限制为进攻方携带将领时生效，防御战、守城战、增援防守或其他非主动进攻场景不能误触发。

例如孙权“防御 +50%”这类只应在防御战触发的特性，必须明确限制为该将领作为防守方主将或有效防守增援将领时生效，主动进攻、掠夺、扫荡、副本进攻等场景不能误触发。

这类限制不能只依赖文案说明，必须在特性触发判断、战斗上下文和测试里共同约束。

第六，被动属性加成不应当作战斗触发特性。

例如某个将领天生比别人多属性点，或类似“马超额外增加 20 点武力”的能力，属于将领被动属性装配，不属于战斗中发动的特性。

当前系统里“武力”的属性 key 是 `force`；每 1 点 `force` 通过 `GeneralStatPercentPerPoint = 0.02` 转换为 2% 攻击加成，并进入 `StatAttackBonus`。这类被动加成应该在将领属性、Modifier 或战斗单位构建前生效，不应该写入战报的 `TraitTriggered` / `TraitOutcomes`，也不应该在战斗中显示为“触发”。

## 5. 验收标准

将领特性相关修改必须尽量做到自动化验证。

最低验收要求：

- 后端优先补 Go 单测。
- 修 BUG 时，优先补能复现旧问题的测试。
- 影响战斗前、战斗后、战报或状态写入时，必须覆盖对应阶段。
- 有适用场景限制的特性，必须补正反测试：应该触发的场景能触发，不应该触发的场景不能触发。
- 出征或增援请求因武将不存在、忙碌、超出携带上限等原因失败时，必须验证玩家状态完全不变：不得结算特性产出、扣兵、占用武将、推进特性进度或生成行军、增援和战报记录。
- 主动战斗允许不携带将领时，必须验证不会借用城内主将的 Modifier、触发特性或经验归属；战报不得包含参战将领快照和特性时间线，兵力损失仍须与真实状态一致。
- PVP 主攻行军创建后配置可能被 GM 调整，必须明确并测试配置生效时点。当前口径为 PVP 主攻和黄巾来袭主城守将都在到达结算时刷新最新将领配置：已关闭特性不得触发或残留在本次参战快照中，新开启特性必须同步进入效果、快照和时间线，未关闭的将领 Buff 和经验流程仍正常。增援属于已派出的持续部署，固定派出时的将领属性、Buff 和特性快照；驻防期间后来调整全局配置不得追溯改变本批援军。各类入口都必须保证真实效果、参战快照和战报时间线采用各自同一个时点，前端只能以 `detail.traits` 判断本场真实触发。
- 行军、征兵和留城产出等过程特性必须使用同一玩家状态下关闭被测特性的真实事务作为效果基线，保留阵营、公共 Modifier 和其他权威加成；不得直接拿裸公式推算的基础值判断特性是否正确。过程特性生效后进入战斗，参战快照可以展示拥有关系，但新旧战报触发结果和标准时间线必须保持为空。
- PVP 和黄巾来袭的防守将领必须以敌军到达结算时的真实在城状态为准。敌军行军途中主将出征或增援离城后，不得继续提供守城 Modifier、触发防御特性、获得守城经验或进入防守将领快照；若在敌军到达前已通过真实返程归城，则应从该时点恢复守城能力。城墙、阵营等非将领公共加成始终正常生效；测试必须使用真实出征或增援往返流程，不用直接改占用字段代替。
- 援军武将经验必须按“战斗/事件 ID + 援军 ID”形成稳定结算键，经验写入与幂等标记必须同事务提交；失败不得吞错或消耗标记。PVP 战斗进入返程后、黄巾来袭进入已结算后仍须支持从持久化战斗或战报重试，重复读取不得重复经验、战报或前端展示。
- 同一将领多个特性跨阶段生效时，双方战报必须保持“战斗前、战斗结算后、战斗结束后”的真实顺序，并分别保存每项特性的设计值和实际变化；不得因同属一个将领而覆盖、合并或错置阶段。
- 同一阶段内的多特性时间线必须继续使用核心分发顺序：同一触发方按将领配置的 `special -> bonus` 排列，多触发方按实际分发批次排列，ID 只作为同条件下的稳定兜底。不能把无序 map 直接按 ID 字母排序后当作真实触发顺序。
- 同一战斗前阶段既改变参战人数又修改单位属性时，最终战力必须使用两项处理后的真实输入计算；战前真实伤亡或临时压制、逐兵种属性差值和最终战力必须各自可核对，不能把最终战力当成特性明细的替代品。
- 临时兵力压制与特性压制必须分别验收：`suppressedUnits` 只降低本场参战人数，战后不得扣除；`disabledTraitCount` 只统计实际阻止的后续特性，被阻止的特性不得修改结果或进入新旧战报。两个数量不能共用字段、累加或互相代替。
- 同一目标连续受到多项追加伤害时，每项都必须根据前序结算后的剩余人数计算实际可增加值，累计损失不得超过原始出动兵力。后续特性的实际变化若为 0，应视为本场没有产生结果，不写 `TraitOutcomes` 或标准时间线；将领快照仍只表示拥有，两个前端不得据此补造触发。
- 俘虏必须与阵亡分别记录，但目标真实库存要同时扣除阵亡和被俘兵力；目标标准战报的最终存活数必须按“战前兵力 - 阵亡 - 被俘”对账。应用层若把候选归队兵重新路由到驻防，必须同步改写特性详情中的实际去向，避免同一批兵在目标、归队或驻防之间重复存在。
- 战报前端只能把标准详情 `traits` 时间线视为本场真实触发；将领快照中的 `general.traits` 仅表示其拥有的特性，不能据此补写触发结果。
- 战报查询、敌情脱敏和公开分享必须在完整深拷贝上修改：顶层兵力、奖励、特性结果、援军将领，以及标准详情的属性、特性、奖励和动态明细都不能与库存原始战报或轮回记录共享可变引用。敌方将领未揭示时，双前端不得从旧 PVP 快照补回将领或特性。
- 标准战报每条 `detail.traits` 必须逐项渲染 `detail` 中的设计参数和实际变化，不能只显示特性名称或摘要；中文字段、中文兵种、实际整数和有结算语义的零值必须在 `web`、`web-wlsg` 同时可见。
- 历史战报缺少标准 `detail` 时，两个前端必须按 `traitTriggered` 的存储键和顺序读取 `traitOutcomes`，恢复结果中的真实特性 ID、归属玩家、攻守/援军角色、将领和数值。旧援军快照、援军损失及 `survivedUnits` 也必须保留，不能退化成空特性时间线或用“出动减阵亡”覆盖战后权威存活。
- 部分迁移战报已有 `detail` 但 `detail.traits` 缺失或为空时，两个前端必须回退旧 `traitTriggered` / `traitOutcomes`；一旦标准 `detail.traits` 存在真实条目，就只使用标准时间线，禁止与旧结果合并或重复展示。标准 `extra.pvp` 已存在但字段不完整时仍须逐字段补回旧援军快照和损失，不能整块覆盖；历史兵力行缺少名称时必须使用正式中文兵种名兜底。
- 部分迁移战报的标准 `rewards` 缺少单项字段时，两个前端必须分别恢复旧资源、掉落、城金、经验、等级和溢出值；标准明确返回的 `0`、空掉落列表和空溢出表具有结算语义，必须保持标准值，不能因旧字段为正数而回退。
- 历史字段采用“战报所有者/目标”口径，不是固定的“进攻/防守”口径。防守视角必须把目标还原为进攻主侧、所有者还原为防守次侧，并让战力、将领、兵力、经验与特性一起换位；援军独立视角只保留自身援军主侧，不能生成伪目标卡或重复援军卡。
- 有目标兵种限制的特性，`targetUnitType` 必须是已注册兵种 ID 或已存在兵种分类，并验证目标兵种生效、同分类非目标兵种不生效。
- 被动属性加成必须验证派生属性真实变化，但不应出现在战斗触发战报中。
- 影响接口字段时，必须检查 OpenAPI。
- 影响玩家展示时，必须同步检查 `web` 和 `web-wlsg`。
- 两个前端能写测试就写测试；不能写测试时，至少跑类型检查或构建。
- 涉及页面展示时，可以使用浏览器验收，并优先使用用户本机已安装的 Chrome。
- Chrome 验收只能作为补充，不能替代自动测试。

## 6. 推荐执行顺序

短期按风险从高到低推进。

1. 先检查战前特性：因为战前会改变参战兵力，最容易导致真实兵力、损失、经验和战报不一致。
2. 再检查战斗结算后特性：例如追加伤害、减损，重点看 `CombatResult` 是否被正确修改。
3. 再检查战斗结束后特性：例如复活，重点看真实兵力、行军返回、增援记录和战报是否一致。
4. 最后检查非战斗直接结算类特性：行军速度、征兵消耗、掠夺收益等。

## 7. 持续运行方式

后续每次处理将领特性问题时，都按本文档执行。

每次任务结束前，至少更新以下内容之一：

- 已体检的特性清单。
- 已修复的问题。
- 新增的测试。
- 暂缓处理的原因。
- 下一步优先检查的特性。
