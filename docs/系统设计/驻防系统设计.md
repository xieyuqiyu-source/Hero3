# <span style="color:#f97316">驻防系统设计文档</span>

最后更新：2026-06-24
文档状态：planning

## <span style="color:#8b5cf6">1. 系统定位</span>

驻防系统是 Hero3 后续增援、异阵营兵归属、特殊防守兵力的统一底层容器。

它不是单纯的“玩家互相增援”功能，而是先解决一个更基础的问题：

> 主军队只存放玩家自己可主动调用的本阵营兵。  
> 不能主动调用、只能参与防守的兵力，统一进入驻防军队。

因此，驻防系统应作为独立模块设计。后续增援系统只是驻防系统的一种来源。

## <span style="color:#8b5cf6">2. 核心概念</span>

### 2.1 主军队

主军队对应当前 `GameState.Army`。

主军队特点：

- 兵属于当前玩家。
- 兵可以主动调用。
- 兵可以用于攻击 NPC。
- 兵可以用于 PVP 进攻。
- 兵可以用于后续增援别人。
- 正常情况下只存放当前玩家本阵营兵种。

### 2.2 驻防军队

驻防军队是新增的独立容器，建议命名为 `garrisonForces`。

驻防军队特点：

- 可以属于当前玩家、其他玩家或系统。
- 只能参与本城防守。
- 不能主动出征。
- 不能被当作普通军队调用。
- 可以容纳本阵营兵，也可以容纳异阵营兵。
- 按来源、所有权、兵种分开记录，不直接合并成普通 `army`。

### 2.3 判断标准

是否进入主军队，不只看兵种阵营，还要看“所有权”和“是否可主动调用”。

| 场景 | 进入位置 | 原因 |
| --- | --- | --- |
| 魏国玩家自己获得青州军 | 主军队 | 本阵营，且属于自己，可主动调用 |
| 魏国玩家钓到吴国影卫 | 驻防军队 | 异阵营兵，不能编入主军队 |
| 魏国玩家俘虏蜀国南蛮象 | 驻防军队 | 异阵营兵，只能守城 |
| 另一个魏国玩家增援青州军 | 驻防军队 | 虽然同阵营，但不属于当前玩家，不能主动调用 |
| GM 发放特殊守城兵 | 驻防军队 | 系统来源，只能防守 |

## <span style="color:#8b5cf6">3. 第一版目标</span>

第一版只做驻防容器，不做完整玩家互相增援。

必须完成：

- 新增驻防数据结构。
- 玩家状态接口返回驻防军队。
- 驻防军队和主军队分开展示。
- 非本阵营兵可进入驻防军队。
- 驻防军队参与防守战斗。
- 驻防军队战损后从驻防容器扣除。
- 驻防军队不能参与进攻、征兵、派兵、扫荡。
- GM 后台可以查看和调整驻防军队。

第一版暂不做：

- 玩家 A 主动增援玩家 B。
- 行军中、返回中状态。
- 撤回、遣返。
- 驻防粮耗。
- 驻防上限。
- 联盟、好友限制。
- 驻防方将领特性。

## <span style="color:#8b5cf6">4. 数据模型</span>

### 4.1 GameState 增加字段

建议在 `GameState` 中增加：

```go
GarrisonForces []GarrisonForce `json:"garrisonForces,omitempty"`
```

前端类型同步：

```ts
garrisonForces?: GarrisonForce[]
```

### 4.2 GarrisonForce

建议结构：

```go
type GarrisonForce struct {
    ID            string         `json:"id"`
    OwnerType     string         `json:"ownerType"`              // self | player | system
    OwnerPlayerID string         `json:"ownerPlayerId,omitempty"`
    OwnerName     string         `json:"ownerName,omitempty"`
    Source        string         `json:"source"`                 // fishing | reinforcement | capture | gm | event
    SourceID      string         `json:"sourceId,omitempty"`
    Faction       string         `json:"faction"`                // wei | shu | wu | neutral
    Units         map[string]int `json:"units"`                  // unitType -> amount
    Status        string         `json:"status"`                 // stationed | marching | returning
    CreatedAt     string         `json:"createdAt"`
    UpdatedAt     string         `json:"updatedAt"`
}
```

第一版只允许：

- `ownerType = self | system`
- `source = fishing | capture | gm`
- `status = stationed`

但字段要按完整结构预留，避免后续做增援时重构。

### 4.3 为什么不用简单 map

不要只做：

```go
map[string]int
```

原因：

- 后续要区分来源：钓鱼、俘虏、GM、增援。
- 后续要区分所有权：自己的驻防兵、别人增援来的兵。
- 后续战报要展示谁的驻防兵损失。
- 后续撤回/遣返需要知道 owner。

所以第一版也必须用记录结构，而不是单纯兵种数量 map。

## <span style="color:#8b5cf6">5. 进入驻防的规则</span>

### 5.1 通用入口

后端应提供统一 helper，不要让各业务自己改数组：

```go
func AddGarrisonForce(state *GameState, input AddGarrisonForceInput, now time.Time)
```

输入建议包含：

```go
type AddGarrisonForceInput struct {
    OwnerType     string
    OwnerPlayerID string
    OwnerName     string
    Source        string
    SourceID      string
    Faction       string
    Units         map[string]int
}
```

统一入口负责：

- 过滤数量 <= 0 的兵。
- 校验兵种是否存在。
- 推断或校验兵种阵营。
- 合并同 owner/source/faction/status 下的同兵种数量，或按记录追加。
- 更新时间。

第一版可以先简单追加记录，但必须通过 helper，后续再优化合并规则。

### 5.2 本阵营奖励

如果奖励兵种属于玩家当前阵营，并且来源属于玩家自己：

- 进入主军队 `army`。

### 5.3 异阵营奖励

如果奖励兵种不属于玩家当前阵营：

- 进入驻防军队 `garrisonForces`。
- `ownerType = self`
- `source` 按业务来源填写，如 `fishing`、`capture`、`gm`。
- 不能进入主军队。

### 5.4 增援兵

后续真正增援系统上线后：

- 无论兵种是否和目标玩家同阵营，都进入目标玩家的 `garrisonForces`。
- `ownerType = player`
- `ownerPlayerId = 派兵方 playerId`
- `source = reinforcement`
- 目标玩家不能主动调用这些兵。

## <span style="color:#8b5cf6">6. 战斗接入规则</span>

### 6.1 进攻方

进攻方只能选择主军队 `army`。

禁止：

- 从 `garrisonForces` 派兵攻击。
- 从 `garrisonForces` 派兵扫荡 NPC。
- 从 `garrisonForces` 派兵增援别人。

### 6.2 防守方

玩家被攻击时，防守军队由两部分组成：

1. 主军队 `army`
2. 驻防军队 `garrisonForces(status=stationed)`

防守战斗计算时，两部分合并成战斗输入。

### 6.3 防守加成

第一版规则：

- 防守加成按被攻击玩家计算。
- 驻防兵不触发驻防来源方将领特性。
- 驻防兵不吃驻防来源方将领加成。
- 被攻击玩家的防守将领特性可以触发。

原因：

- 规则简单。
- 战斗解释清楚。
- 不需要同时加载多个玩家将领。
- 后续要做“援军将领”时可以单独扩展。

### 6.4 战损扣除

防守战后，损失必须按来源扣除。

建议流程：

1. 构建防守军队时记录每个 unitType 的来源分布。
2. 战斗引擎返回 defenderLostUnits。
3. 后端按比例或固定顺序把损失分摊到：
   - 本城主军队
   - 各驻防记录
4. 更新 `army` 和 `garrisonForces`。
5. 驻防记录中某兵种数量为 0 时删除该兵种。
6. 驻防记录所有兵种都为 0 时删除该记录。

第一版损失分摊建议：

- 同兵种优先按数量比例分摊。
- 比例分摊后剩余的零头，从数量最多的来源开始扣。

示例：

```text
本城青州军 700
驻防青州军 300
青州军总损失 100

本城扣 70
驻防扣 30
```

### 6.5 战报展示

战报应保留两层信息：

- 总防守损失：兼容当前展示。
- 驻防损失明细：新增字段。

建议后续字段：

```go
GarrisonLosses []GarrisonLossReport `json:"garrisonLosses,omitempty"`
```

```go
type GarrisonLossReport struct {
    GarrisonID    string         `json:"garrisonId"`
    OwnerType     string         `json:"ownerType"`
    OwnerPlayerID string         `json:"ownerPlayerId,omitempty"`
    OwnerName     string         `json:"ownerName,omitempty"`
    Source        string         `json:"source"`
    Losses        map[string]int `json:"losses"`
}
```

第一版如果战报改动风险较高，可以先只更新状态，战报明细第二步补。但战损扣除必须正确。

## <span style="color:#8b5cf6">7. 钓鱼系统接入</span>

当前钓鱼库存规则：

- 本阵营兵可以兑换进主军队。
- 非本阵营兵暂时不能兑换。

驻防系统上线后改为：

- 本阵营兵：兑换进主军队 `army`。
- 非本阵营兵：兑换进驻防军队 `garrisonForces`。

兑换结果需要告诉前端：

```json
{
  "redeemedTo": "army" | "garrison"
}
```

或在 toast 文案中明确：

- `已加入军队`
- `已加入驻防军队`

第一版钓鱼接入建议放在驻防容器和展示完成之后，不要一开始就同时改太多。

## <span style="color:#8b5cf6">8. 俘虏系统接入</span>

甄宓“美人计”已存在“俘虏到驻防”的概念。

正式驻防容器上线后，规则应统一为：

- 俘虏本阵营兵：进入主军队。
- 俘虏异阵营兵：进入驻防军队。

战报字段：

- `capturedUnits`：进入主军队。
- `capturedToGarrison`：进入驻防军队。

如果当前代码已有 `capturedToGarrison` 字段，应从“战报展示字段”升级为“真实写入驻防容器”。

## <span style="color:#8b5cf6">9. GM 后台接入</span>

GM 第一版需要：

- 查看玩家驻防军队。
- 给玩家增加驻防兵。
- 扣减玩家驻防兵。
- 清空某条驻防记录。

建议放在 Admin 的玩家详情或玩家操作面板中。

GM 发驻防兵时，需要选择：

- 玩家存档。
- 兵种。
- 数量。
- 来源：默认 `gm`。

后端建议接口：

```http
POST /api/v1/admin/garrison/grant
POST /api/v1/admin/garrison/deduct
DELETE /api/v1/admin/garrison/{garrisonId}
```

第一版如果不想暴露太多接口，可以先只做 `grant` 和 `deduct`。

## <span style="color:#8b5cf6">10. Web 展示规范</span>

### 10.1 左侧菜单

左侧菜单中“军队”下方新增一个和军队同级的展示框：

```text
军队
青州军 1000
虎豹骑 200

驻防军队
影卫 300
南蛮象 50
```

展示原则：

- 主军队和驻防军队必须视觉分开。
- 驻防军队不要出现在可出征选择列表里。
- 驻防军队可显示来源标签，如“钓鱼”“俘虏”“GM”“增援”。

### 10.2 军事页

军事页建议新增或扩展一个“驻防”区域：

- 展示驻防总兵力。
- 按来源分组。
- 按兵种展示。
- 标注“只能防守，不能出征”。

第一版不要做复杂操作，先展示清楚。

### 10.3 移动端

移动端展示必须折叠：

- 默认显示驻防总兵力。
- 点击展开明细。
- 避免左侧菜单过长撑屏。

## <span style="color:#8b5cf6">11. Admin 展示规范</span>

Admin 中驻防应偏操作工具，不做游戏化表现。

建议展示字段：

- 玩家昵称 / playerId。
- 驻防来源。
- 所有者。
- 阵营。
- 兵种和数量。
- 创建时间 / 更新时间。

GM 操作必须二次确认，除非全局“不再提醒”开启。

## <span style="color:#8b5cf6">12. 后端开发顺序</span>

建议按以下顺序开发，避免返工：

### 阶段 1：基础模型

1. `model.go` 增加 `GarrisonForce`。
2. `GameState` 增加 `GarrisonForces`。
3. `hydrateStateForResponse` 或 `GetState` 确保老存档字段为空数组或 nil 安全。
4. 增加 helper：
   - `AddGarrisonForce`
   - `DeductGarrisonForce`
   - `SummarizeGarrisonForces`

### 阶段 2：GM 接口

1. 增加 GM 发放驻防兵接口。
2. 增加 GM 扣减驻防兵接口。
3. 增加必要的参数校验。
4. 增加 Admin UI。

先做 GM 接口的原因：

- 方便手动构造驻防数据。
- 后续战斗接入可以直接测试。

### 阶段 3：Web 展示

1. Web 类型同步。
2. 左侧菜单显示驻防军队。
3. 军事页显示驻防明细。
4. 确认驻防军队不会出现在出征选择里。

### 阶段 4：防守战接入

1. 构建防守方军队时合并驻防军队。
2. 记录来源分布。
3. 战斗后按来源分摊损失。
4. 更新主军队和驻防军队。
5. 增加回归测试。

### 阶段 5：业务来源接入

按风险从低到高接入：

1. GM 发放驻防兵。
2. 钓鱼异阵营兑换到驻防。
3. 甄宓俘虏异阵营兵进入驻防。
4. 活动/信函奖励驻防兵。
5. 真正玩家增援。

## <span style="color:#8b5cf6">13. 测试规范</span>

后端至少补以下测试：

- 本阵营奖励进入主军队。
- 异阵营奖励进入驻防军队。
- 驻防军队不参与进攻校验。
- 防守时驻防军队参与战斗。
- 防守损失能正确扣减驻防记录。
- 驻防记录扣到 0 后清理。
- 老存档没有 `garrisonForces` 时不报错。
- GM 发放驻防兵后 `GetState` 能返回。

前端至少验证：

- 左侧菜单主军队和驻防军队分开展示。
- 驻防军队不会出现在攻击/NPC 扫荡选择列表。
- 移动端不撑爆布局。
- 空驻防状态展示正常。

## <span style="color:#8b5cf6">14. 命名规范</span>

统一使用：

- 中文：驻防军队、驻防兵、驻防记录。
- 英文：garrison。
- 数据字段：`garrisonForces`。
- 单条记录：`GarrisonForce`。

不要混用：

- `reinforcement` 表示“增援行为/来源”。
- `garrison` 表示“已经存放在目标城内的驻防容器”。

也就是说：

- 增援系统 = reinforcement system。
- 驻防容器 = garrison system。
- 玩家增援到达后，生成一条 `source = reinforcement` 的 `GarrisonForce`。

## <span style="color:#8b5cf6">15. 关键边界</span>

### 15.1 驻防不是背包

驻防军队是防守兵力，不是奖励库存。

钓鱼库存仍然记录历史鱼获和剩余库存。玩家兑换后，库存减少，驻防增加。

### 15.2 驻防不是主军队

驻防兵不能主动攻击，不能扫荡 NPC，不能征兵补充，不能被玩家当作本阵营军队调用。

### 15.3 增援不是第一版目标

当前文档第一版目标是驻防容器。玩家间增援要等驻防容器稳定后再开发。

### 15.4 同阵营增援也不能合并主军队

别人增援来的本阵营兵也必须进入驻防军队，因为所有权不属于目标玩家。

## <span style="color:#8b5cf6">16. 推荐第一批任务拆分</span>

下次开发可按以下任务派发：

### 任务 A：驻防基础模型 + GM 发放

- 增加 `GarrisonForce` 数据结构。
- 增加 `GameState.GarrisonForces`。
- 增加 GM 发放驻防兵接口。
- Admin 支持给玩家发驻防兵。
- Web 左侧菜单展示驻防军队。

### 任务 B：驻防参与防守

- 防守战合并驻防兵。
- 战损按来源扣减。
- 战报保留驻防损失明细。
- 增加回归测试。

### 任务 C：钓鱼异阵营兑换驻防

- 非本阵营钓鱼库存可兑换到驻防。
- 本阵营仍兑换进主军队。
- UI 文案区分“加入军队”和“加入驻防军队”。

### 任务 D：俘虏异阵营进入驻防

- 甄宓俘虏异阵营兵真实写入驻防容器。
- 战报展示俘虏去向。

### 任务 E：真正增援系统

- 玩家选择目标玩家。
- 派出主军队。
- 行军到达后写入目标玩家驻防。
- 支持撤回/遣返。

## <span style="color:#8b5cf6">17. 最终目标</span>

驻防系统完成后，Hero3 的兵力归属会变成三层：

1. 主军队：玩家自己的可调用兵力。
2. 驻防军队：只能守城的外来/异阵营/特殊兵力。
3. 库存记录：尚未兑换的奖励或历史记录。

这三层分清后，钓鱼、俘虏、活动奖励、GM 工具、玩家增援都可以共用同一套归属逻辑，后续扩展成本会低很多。
