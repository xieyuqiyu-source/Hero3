# <span style="color:#4f46e5">Hero3 项目最终目的</span>

最后更新：2026-06-26
## <span style="color:#0f766e">1. 一句话目标</span>

Hero3 的最终目的，是做成一个核心稳定、模块可扩展、数据库生产化、文档可传承的长期运营型 SLG 策略游戏项目。

这不是一个只堆功能的小游戏项目，而是一个可以持续开发、持续扩展、持续维护，并且未来能承载复杂玩法和稳定玩家数据的大型游戏项目。

## <span style="color:#0f766e">2. 游戏本质</span>

Hero3 的基础循环是典型 SLG 策略发展循环：

玩家创建存档后，通过升级建筑、建设资源田、每小时获取资源、征兵、打 NPC、获得奖励，再继续发展；后续再扩展到玩家之间的战争、协防、据点争夺、副本活动、武将派遣和世界事件。

基础循环可以概括为：

1. 建城发展。
2. 获取资源。
3. 升级建筑。
4. 征兵。
5. 战斗。
6. 获取奖励。
7. 继续发展。

所有长期玩法都应该围绕这个循环扩展，而不是破坏这个循环。

## <span style="color:#0f766e">3. 核心系统目标</span>

Hero3 的核心系统应该像一个通用 CPU。

核心不负责写死每一个具体玩法，但核心必须提供稳定接口，让外部模块可以安全接入、影响玩家长期状态，并且不会把系统写乱。

核心应该长期稳定包含：

- 玩家账号。
- 玩家存档。
- 资源。
- 货币。
- 道具。
- 建筑。
- 兵力。
- 武将资产。
- 加成体系。
- 奖励发放。
- 事件管线。
- 数据读写。
- 权威表。
- API、路由和统一响应。
- 模块接入标准。

核心不应该直接理解每个具体玩法的细节。例如核心不应该写死“万王争霸怎么排名”“神魔战场怎么推进”“沙巴克怎么占领”。这些规则应该属于玩法模块。

## <span style="color:#0f766e">4. 模块化目标</span>

Hero3 未来会有很多玩法，但这些玩法不应该全部塞进核心。

玩法模块可以有自己的规则、状态、进度、排行榜、活动时间、参与记录和结算记录。

但是一旦玩法模块要影响玩家长期资产，就必须通过核心标准入口。

模块可以自己管理：

- 副本进度。
- 活动状态。
- 据点归属。
- 排行榜。
- 临时战场状态。
- 模块内 NPC。
- 模块内参与记录。
- 模块内结算记录。

模块不能绕过核心直接改：

- 玩家资源。
- 玩家货币。
- 玩家道具。
- 玩家建筑。
- 玩家兵力。
- 玩家武将。
- 玩家 Buff。
- 玩家长期存档。

## <span style="color:#0f766e">5. 数据库目标</span>

Hero3 的数据库目标，是从一个大 JSON 存档，逐步进化为生产级权威表结构。

`players.state_json` 只能作为兼容快照，不应该继续承担所有长期资产的唯一权威来源。

长期资产应该逐步拆成独立权威表，例如：

- 玩家资源权威表。
- 玩家背包权威表。
- 玩家建筑权威表。
- 玩家资源田权威表。
- 玩家兵力权威表。
- 玩家征兵队列权威表。
- 玩家武将权威表。
- 玩家武将派驻权威表。
- 玩家 Buff 权威表。
- 玩法模块实例表。
- 玩法模块参与表。
- 玩法模块结算表。

每一次数据库拆分都必须配套：

- 表结构文档。
- backfill 回填工具。
- verify 校验工具。
- 兼容快照策略。
- 本地迁移验证。
- 上线前回滚方案。

## <span style="color:#0f766e">6. 扩展能力目标</span>

Hero3 的架构必须支持未来不断增加内容，而不是每增加一个内容就大改核心。

理想状态：

- 新增资源类型时，优先通过注册表和配置接入，不应该到处硬编码。
- 新增兵种时，必须进入兵种注册表和配置，再进入玩家兵力权威表。
- 新增武将时，必须进入武将配置和玩家武将权威表。
- 新增建筑时，必须进入建筑注册表和建筑权威表。
- 新增道具时，必须进入道具配置和标准 Effect / Reward。
- 新增加成时，必须进入 Modifier / Buff 管线。
- 新增副本时，应作为玩法模块接入。
- 新增据点时，应作为玩法模块接入。
- 新增活动奖励时，必须通过标准奖励发放。

核心的目标不是“什么都不改”，而是把变化限制在正确位置。

## <span style="color:#0f766e">7. 文档和记忆目标</span>

Hero3 必须能让后续开发者、AI 或换设备后的开发会话继续理解项目方向。

因此项目必须长期维护：

- `AGENTS.md`。
- `PROJECT_RULES.md`。
- `memory/`。
- 根目录 `README.md`。
- `docs/` 文档。
- 数据库设计文档。
- 架构设计文档。
- 开发规划文档。
- 阶段任务文档。
- 精简但当前有效的文档。

文档的目的不是形式化，而是让开发判断有依据。

如果代码和文档冲突，应先指出冲突，再决定是修代码、修文档，还是调整项目规则。

## <span style="color:#0f766e">8. 生产级目标</span>

Hero3 最终应具备生产级项目的基本能力：

- 本地开发环境可稳定启动。
- 前端、Admin、后端有清晰职责。
- 核心 API 有 OpenAPI 文档。
- 数据库表结构可迁移、可校验、可回滚。
- 核心资产写入有事务边界。
- 玩法模块不能随意写长期资产。
- 关键流程有自动化测试。
- 发布前有验收清单。
- 出问题时能定位、回滚和修复。
- 文档能解释当前设计为什么这样做。

## <span style="color:#0f766e">9. 判断项目是否偏离目标</span>

如果出现以下情况，说明项目正在偏离最终目的：

- 新玩法直接写玩家资源、兵力、武将等长期资产。
- 新功能只改 `players.state_json`，不维护权威表。
- 新资产类型没有注册表或配置入口。
- 业务逻辑继续堆进大文件，缺少模块边界。
- Admin、Web、OpenAPI 和 docs 长期不同步。
- 数据库变化没有 backfill 和 verify。
- 浏览器核心流程无法跑通。
- AI 换会话后无法从文档和 memory 理解项目方向。
- 为了短期上线牺牲核心边界。

## <span style="color:#0f766e">10. 最终状态</span>

Hero3 最终应该是一个玩家可以长期玩的三国 SLG 网页游戏。

它的核心稳定，玩法可以不断扩展，数据库能支撑长期运营，文档能支撑长期开发。

最终项目不只是“能玩”，还要做到：

- 能继续开发。
- 能安全扩展。
- 能保护玩家数据。
- 能清晰解释架构。
- 能让不同开发者接手。
- 能让新玩法按标准接入。

这就是 Hero3 的最终目的。
