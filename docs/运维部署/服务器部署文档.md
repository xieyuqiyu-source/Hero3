# <span style="color:#334155">Hero3 服务器部署文档</span>

最后更新：2026-07-03
本文记录 Hero3 当前线上服务器的真实部署结构，以及以后从本地发布到服务器的标准流程。

> 注意：本文不记录数据库密码、SSH 密码、证书私钥等敏感信息。服务器上的敏感配置放在 `/etc/hero3/hero3.env`。

## <span style="color:#334155">当前线上结构</span>

线上入口：

- 玩家站：`https://hero3.ccoos.cn/`
- GM 后台：`https://hero3.ccoos.cn/admin/`
- 健康检查：`https://hero3.ccoos.cn/healthz`

服务器路径：

```text
/opt/hero3/go/bin/hero3-server     # Go 后端可执行文件
/opt/hero3/go/bin/hero3-dbtool     # 数据库维护工具
/opt/hero3/go/config/              # 后端生产配置，如 balance/factions/units
/opt/hero3/source/                 # 服务器本机源码目录，通过本地代理拉取 GitHub 指定提交并构建
/tmp/hero3-build.<commit-sha>/      # 单次部署临时构建目录，部署成功后删除
/var/www/hero3/web/                # 玩家前端静态文件
/var/www/hero3/admin/              # GM 后台静态文件
/var/www/hero3/backups/            # 前端静态文件备份
/opt/hero3/backups/                # 后端文件备份
/etc/hero3/hero3.env               # 后端环境变量
/etc/systemd/system/hero3.service  # systemd 服务
/etc/systemd/system/hero3-battle-report-cleanup.service # 战报清理任务
/etc/systemd/system/hero3-battle-report-cleanup.timer   # 战报清理定时器
/etc/systemd/system/hero3-maintenance-status.service    # 维护巡检任务
/etc/systemd/system/hero3-maintenance-status.timer      # 维护巡检定时器
/etc/systemd/system/hero3-daily-update-announcement.service # 每日更新公告发布任务
/etc/systemd/system/hero3-daily-update-announcement.timer   # 每日更新公告定时器
/etc/systemd/journald.conf.d/hero3-retention.conf # 线上排查日志保留策略
/etc/nginx/conf.d/hero3.ccoos.cn.conf # Nginx 站点配置
```

当前运行方式：

```text
Nginx 80/443
  /         -> /var/www/hero3/web/
  /admin/   -> /var/www/hero3/admin/
  /api/     -> http://127.0.0.1:8081
  /healthz  -> http://127.0.0.1:8081

hero3.service
  WorkingDirectory=/opt/hero3/go
  ExecStart=/opt/hero3/go/bin/hero3-server
  EnvironmentFile=/etc/hero3/hero3.env

hero3-battle-report-cleanup.timer
  每 10 分钟触发一次 hero3-battle-report-cleanup.service
  单次最多清理 4 批，每批 500 条候选战报
  普通/NPC/扫荡保留 72 小时，PVP/防守/侦查保留 168 小时，软删保留 24 小时
  使用 /etc/hero3/hero3.env 中的 HERO3_DATABASE_DSN

hero3-maintenance-status.timer
  每 1 小时触发一次 hero3-maintenance-status.service
  只读输出战报统计、清理索引、可清理候选量和权威表健康状态
  输出进入 systemd journal，用于观察战报增长趋势和上线后巡检失败

hero3-daily-update-announcement.timer
  每天 23:50 触发一次 hero3-daily-update-announcement.service
  基于 /opt/hero3/RELEASE 和 /opt/hero3/source git log 判断是否有新版本
  读取 /opt/hero3/source/announcements/daily/YYYY-MM-DD.md 作为玩家公告正文来源
  公告正文只输出玩家可读的玩法更新、体验优化和问题修复，不展示代码提交或文件修改
  通过 game_configs.daily_update_announcement_cursor 记录已公告提交，避免重复发布
  默认发布到公告中心，不强制弹窗

systemd journal
  使用 /etc/systemd/journald.conf.d/hero3-retention.conf 持久化到 /var/log/journal
  目标保留最近 14 天日志，journal 总量上限 1GB，并保留至少 1GB 磁盘空闲
  后端请求日志、慢请求日志、维护巡检输出都通过 journalctl 查询
```

## <span style="color:#334155">GitHub Actions 自动部署</span>

仓库已配置 `.github/workflows/deploy.yml`。推送到 `main-core` 分支时会自动执行生产部署，也可以在 GitHub 仓库的 **Actions** 页面手动点击 `Deploy Hero3` 运行。

当前部署方式是 GitHub Actions 通过 SSH 进入服务器，服务器在 `/opt/hero3/source` 拉取 `main-core` 的指定提交并完成构建。服务器拉 GitHub 使用本机 `mihomo` 代理 `127.0.0.1:7890`，并已写入 root 用户 Git 全局配置；workflow 中也会显式给本次 `git fetch` 写入临时代理配置。GitHub Actions 不在 runner 上安装 Go/Node，不构建 release 产物，也不上传已构建 release 包。

`/opt/hero3/source` 保留 Git 工作区，因此每日更新公告可以继续基于 git log 生成变更摘要。当前仓库可由服务器通过代理直接读取，workflow 不把 `github.token` 传到服务器，也不把 token 写入服务器 Git remote。

自动部署流程：

```text
push main-core
  -> GitHub Actions SSH 进入服务器
  -> 服务器准备 /opt/hero3/source
  -> 服务器通过 127.0.0.1:7890 本地代理拉取 main-core 的指定提交 GITHUB_SHA
  -> 服务器强制 checkout 到该提交并清理未跟踪文件
  -> 服务器在 /tmp/hero3-build.<commit-sha>/ 构建 Go 后端
  -> 服务器在 /tmp/hero3-build.<commit-sha>/ 构建数据库维护工具 dbtool
  -> 服务器本机执行 pnpm install/build 构建玩家前端 web
  -> 服务器本机执行 pnpm install/build 构建 GM 后台 admin
  -> 服务器备份旧版本
  -> 覆盖后端、配置模板和静态资源
  -> 安装 journald 持久化和 14 天保留策略
  -> 安装并启用战报清理 systemd timer
  -> 安装并启用维护巡检和每日更新公告 systemd timer
  -> 写入 /opt/hero3/RELEASE 记录当前提交
  -> 重启 hero3.service
  -> reload Nginx
  -> 检查 /healthz
```

> 说明：配置文件属于发布模板，不应作为线上 GM 修改后的最终真相。当前仙池垂钓配置已经以数据库 `game_configs.fishing` 为线上权威来源，发布覆盖 `/opt/hero3/go/config/fishing.json` 时不会覆盖数据库中的 GM 配置。其他仍写文件的 GM 配置后续应逐步迁移到 `game_configs`。

需要在 GitHub 仓库中配置 Secrets：

```text
HERO3_SSH_HOST          # 服务器 IP，例如 124.223.111.163
HERO3_SSH_PORT          # SSH 端口，默认 22
HERO3_SSH_USER          # SSH 用户，例如 root
HERO3_SSH_PRIVATE_KEY   # 用于部署的 SSH 私钥内容
```

不需要额外配置 GitHub 源码读取 token。服务器通过本地代理直接拉取当前仓库内容。

Secrets 配置入口：

```text
GitHub 仓库 -> Settings -> Secrets and variables -> Actions -> New repository secret
```

推荐使用 SSH key 部署，不使用 SSH 密码。准备方式：

```bash
ssh-keygen -t ed25519 -C "github-actions-hero3"
```

把生成的公钥追加到服务器部署用户的 `~/.ssh/authorized_keys`，把私钥全文保存到 GitHub Secret `HERO3_SSH_PRIVATE_KEY`。

注意事项：

- 自动部署只在 `main-core` 分支 push 时触发，普通开发分支不会发布线上。
- 手动触发 `Deploy Hero3` 时也只允许 `main-core`，workflow 会拒绝其他分支。
- 发布脚本本身不执行 `make migrate`、`make clone-data`、回填或校验命令。
- 生产环境 `HERO3_RUN_STARTUP_MIGRATIONS` 默认等于 `false`，后端服务重启只连接当前生产库并初始化仓储，不在启动链路执行 `MigrateMySQL`。
- 结构变更、补字段、补索引和兼容回填必须在低峰使用 `hero3-dbtool migrate`、`hero3-dbtool ensure-report-cleanup-indexes --execute --allow-non-test` 或对应回填命令独立执行，避免 API 重启时抢线上 DDL/回填锁。
- 如果 Actions 失败，先看 GitHub Actions 日志；如果已经连上服务器，再看 `journalctl -u hero3 -f`。
- 服务器访问 GitHub 依赖 `mihomo-ai.service` 本地代理，代理监听 `127.0.0.1:7890`。如果 Git 拉取失败，先检查 `systemctl status mihomo-ai.service` 和 `git config --global --get-regexp 'github.com.proxy'`。
- 服务器仍需具备 Go、Node、Corepack、pnpm 依赖下载能力；如果网络受限，应先在服务器手动安装匹配的 Go 版本并准备 pnpm/npm 依赖源。
- 服务器上的数据库密码、环境变量、证书不进入 GitHub，仍然保留在 `/etc/hero3/hero3.env` 和 Nginx 证书目录。
- 当前 workflow 每次发布都会在服务器重新构建并同步后端、配置模板、玩家前端和 GM 后台。安装新静态资源前会备份 `/var/www/hero3/web/` 和 `/var/www/hero3/admin/`。

## <span style="color:#334155">常用运维命令</span>

查看服务状态：

```bash
systemctl status hero3 --no-pager
systemctl status hero3-battle-report-cleanup.timer --no-pager
systemctl status hero3-maintenance-status.timer --no-pager
systemctl status hero3-daily-update-announcement.timer --no-pager
```

查看日志：

```bash
journalctl -u hero3 -f
journalctl -u hero3-battle-report-cleanup.service -n 100 --no-pager
journalctl -u hero3-maintenance-status.service -n 100 --no-pager
journalctl -u hero3-daily-update-announcement.service -n 100 --no-pager
```

后端请求日志会输出 `method`、`path`、`status`、`duration_ms`、`bytes` 和 `remote`。请求耗时超过 500ms 会以 warn 输出，超过 2s 会以 error 输出；排查线上卡顿时优先查看 `journalctl -u hero3 -f` 中的 `slow request handled`。

线上部署会安装 `/etc/systemd/journald.conf.d/hero3-retention.conf`，让 journal 持久化保存到 `/var/log/journal`。当前保留策略是最近 14 天、总量最多 1GB，并保留至少 1GB 磁盘空闲。查询最近几天慢请求：

```bash
journalctl -u hero3 --since "3 days ago" --no-pager | grep "slow request handled"
journalctl -u hero3 --since "2026-07-01 00:00:00" --until "2026-07-01 23:59:59" --no-pager
journalctl --disk-usage
```

重启后端：

```bash
systemctl restart hero3
```

重载 Nginx：

```bash
nginx -t && systemctl reload nginx
```

查看 Nginx 访问日志：

```bash
tail -f /var/log/nginx/hero3.access.log
```

查看 Nginx 错误日志：

```bash
tail -f /var/log/nginx/hero3.error.log
```

玩家辅助权威表回填与校验：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool backfill-currencies --allow-non-test --batch-size 500 --max-batches 10
/opt/hero3/go/bin/hero3-dbtool verify-currencies
/opt/hero3/go/bin/hero3-dbtool backfill-npc-states --allow-non-test --batch-size 500 --max-batches 10
/opt/hero3/go/bin/hero3-dbtool verify-npc-states
/opt/hero3/go/bin/hero3-dbtool healthcheck-authority
```

`backfill-currencies` 和 `backfill-npc-states` 只补缺失行，不覆盖已有权威表行。线上已经被玩家请求写过的新值不会被旧 `players.state_json` 冲掉。回填会按小批次提交，如果输出仍有剩余缺失，可以低峰重复执行，直到对应 `verify-*` 通过。

维护状态汇总：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool maintenance-status
```

`maintenance-status` 是只读巡检命令，会汇总战报统计、战报清理索引、可清理候选量和权威表健康状态。缺少战报清理索引时，它会跳过候选量统计并返回异常，避免巡检命令本身触发无索引扫描。

生产发布会安装并启用 `hero3-maintenance-status.timer`，默认每小时自动执行一次 `maintenance-status`。巡检输出保存在 systemd journal 中，可用以下命令查看最近趋势：

```bash
journalctl -u hero3-maintenance-status.service -n 200 --no-pager
```

每日更新公告预览：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool publish-daily-update-announcement --source-dir /opt/hero3/source --release-file /opt/hero3/RELEASE
```

手动发布每日更新公告：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool publish-daily-update-announcement --execute --allow-non-test --source-dir /opt/hero3/source --release-file /opt/hero3/RELEASE
```

`publish-daily-update-announcement` 默认只预览。正式发布会创建 `update` 类型公告，投放全体玩家，默认只进公告中心、不强制弹窗；正文来自 `announcements/daily/YYYY-MM-DD.md`，会使用受限 HTML 富文本排版，只描述玩法更新、体验优化和问题修复，不展示代码提交、文件路径或版本号。如果当天公告源文件不存在，或没有 `## 玩家公告` 条目，即使有代码更新也不会发布公告。发布后写入 `game_configs.daily_update_announcement_cursor`，记录已经公告到的线上提交。生产定时任务每天 23:50 自动执行一次，可用以下命令查看：

```bash
systemctl list-timers 'hero3-daily-update-announcement.timer'
journalctl -u hero3-daily-update-announcement.service -n 200 --no-pager
```

战报统计：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool report-stats
```

战报清理和可见上限索引检查：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool ensure-report-cleanup-indexes
```

低峰创建缺失的战报生命周期索引：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool ensure-report-cleanup-indexes --execute --allow-non-test
```

`cleanup-battle-reports` 会先预检这些索引；如果索引缺失，清理命令会直接失败，避免定时清理在大表上无索引扫描。可见上限索引也放在同一检查入口里，避免保存战报时按玩家视角裁剪旧记录变慢。

锁等待快照：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool lock-snapshot --min-seconds 1 --limit 30
```

战报清理 dry-run：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool cleanup-battle-reports
```

手动执行一轮战报清理：

```bash
cd /opt/hero3/go
/opt/hero3/go/bin/hero3-dbtool cleanup-battle-reports --execute --allow-non-test --batch-size 500 --max-batches 4 --retention-hours 72 --pvp-retention-hours 168 --defense-retention-hours 168 --scout-retention-hours 168 --deleted-retention-hours 24
```

## <span style="color:#334155">回滚</span>

```bash
rm -rf /var/www/hero3/web

```

```bash
rm -rf /var/www/hero3/admin
tar -xzf /var/www/hero3/backups/admin.时间戳.tar.gz -C /var/www/hero3
```

## <span style="color:#334155">安全注意</span>

- GM 后台 `/admin/` 当前通过公网域名可访问。后续上线封号、补资源、删档、发公告等功能后，建议加 Nginx Basic Auth、IP 白名单或单独后台域名。
- 不要把 `/etc/hero3/hero3.env`、数据库密码、SSH 密码、证书私钥提交到 Git。
- MySQL 如果没有必要，不建议长期开放公网 `3306`。
- 每次发版前先确认本地 `git status` 干净，避免把半成品部署上去。

## <span style="color:#334155">排查清单</span>

如果页面打不开：

```bash
systemctl status nginx --no-pager
nginx -t
tail -n 100 /var/log/nginx/hero3.error.log
```

如果 API 不通：

```bash
systemctl status hero3 --no-pager
journalctl -u hero3 -n 100 --no-pager
curl http://127.0.0.1:8081/healthz
```

如果数据库异常：

```bash
systemctl status mysql --no-pager
mysql -u hero3_user -p -h 127.0.0.1 hero3
```

如果前端页面 200 但功能异常：

- 检查浏览器控制台是否有 `/api/` 请求失败。
- 检查 Nginx 是否仍把 `/api/` 反代到 `127.0.0.1:8081`。
- 检查 `HERO3_ALLOWED_ORIGINS` 是否包含当前访问域名。
