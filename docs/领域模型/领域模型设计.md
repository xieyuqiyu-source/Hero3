# <span style="color:#64748b">Hero3 领域模型设计</span>

最后更新：2026-06-25
文档状态：active

## <span style="color:#64748b">1. 核心聚合</span>

Hero3 的核心数据不应按“页面”组织，而应按“领域”组织。

| 聚合 | 责任 | 主要存储位置 |
|---|---|---|
| Account | 登录、金币、账号级信息 | `accounts` |
| Player | 单个存档、阵营、昵称、城金、军队、建筑、将领 | `players.state_json` |
| BattleReport | 战报、战损、奖励、特性结果 | `battle_reports` |
| Mail | 信函、附件、已读/已领状态 | `mails` |
| MiniGameRecord | 钓鱼/小游戏历史与兑换状态 | `minigame_records` |
| GoldLedger | 金币/城金流水 | `gold_ledger` |

## <span style="color:#64748b">2. 归属原则</span>

- `Account` 管账号级货币和登录态。
- `Player` 管具体玩法状态，是最重要的业务聚合。
- `BattleReport` 和 `Mail` 独立存储，避免撑大主状态。
- `MiniGameRecord` 作为可归档记录单独存储。
- `GoldLedger` 只做审计，不参与玩法主逻辑。

## <span style="color:#64748b">3. 玩家状态边界</span>

`GameState` 是当前主玩法状态的载体，主要包含：

- 资源与容量
- 建筑
- 将领
- 军队
- NPC 状态
- 战报摘要
- 未读数量
- 加成与 Buff

它适合做“单玩家视角快照”，但不适合继续无限膨胀为全服总表。

## <span style="color:#64748b">4. 状态流转</span>

推荐统一为下面的方式：

```text
读出玩家状态 -> 结算时间切片 -> 执行业务规则 -> 写回状态 -> 写入独立记录表
```

原则：

- 读改写必须成组处理。
- 影响货币和库存的动作尽量使用事务。
- 能独立归档的记录，不塞回 `GameState`。

## <span style="color:#64748b">5. 领域拆分建议</span>

后续可以继续把 `internal/app/game` 再细分为：

- `account`
- `playerstate`
- `city`
- `resource`
- `military`
- `general`
- `combat`
- `mail`
- `minigame`
- `economy`
- `npc`

## <span style="color:#64748b">6. 版本演进</span>

当字段需要改名、拆表或迁移时，优先保证：

- 旧数据可读。
- 新旧接口至少一段时间兼容。
- 迁移脚本可重复执行。
