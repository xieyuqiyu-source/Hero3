# <span style="color:#f59e0b">Hero3 数据库设计</span>

最后更新：2026-06-25
文档状态：active

## <span style="color:#f59e0b">1. 当前存储策略</span>

Hero3 采用“账号表 + 玩家主状态 JSON + 业务独立表”的组合：

- 账号和登录信息规范化存储。
- 玩家主状态集中在 `players.state_json`。
- 战报、信函、小游戏记录、流水独立建表。

这种方式适合策略游戏早期快速迭代，但必须严格控制整包覆盖问题。

当前性能风险：

- 许多玩家动作都走 `GetState -> JSON 反序列化 -> 修改内存 -> JSON 序列化 -> SaveState`。
- 每次 `SaveState` 都会整包更新 `players.state_json`。
- 当 `GameState` 越来越大，或者动作频率变高时，写入会变慢。
- 局部 JSON 更新和整包保存并存时，还会带来并发覆盖风险。

## <span style="color:#f59e0b">2. 现有核心表</span>

| 表 | 作用 |
|---|---|
| `accounts` | 账号、密码哈希、账号金币 |
| `players` | 存档主表，保存玩家视角状态 JSON |
| `battle_reports` | 战报归档 |
| `mails` | 信函归档 |
| `minigame_records` | 小游戏记录 |
| `gold_ledger` | 金币/城金流水审计 |

## <span style="color:#f59e0b">3. 索引与约束原则</span>

- 账号名必须唯一。
- `players.account_id` 必须有外键。
- 玩家列表查询、战报列表、信函列表都要围绕 `player_id` 建索引。
- 频繁查询字段优先建联合索引，不靠全表扫。

## <span style="color:#f59e0b">4. 事务边界</span>

必须使用事务的场景：

- 金币与城金互转。
- 发放奖励同时写入流水。
- 领取信函附件。
- 小游戏兑换/领取。
- 任何会同时改账号和玩家状态的操作。

建议规则：

- 先锁住资源，再改状态。
- 先扣除，再发放。
- 失败必须能回滚。

## <span style="color:#f59e0b">5. JSON 状态注意事项</span>

`players.state_json` 的好处是方便快速迭代，缺点是：

- 并发覆盖风险高。
- 字段难以局部索引。
- 复杂查询成本高。

因此：

- 适合放“主状态快照”。
- 不适合放历史流水和高频查询归档。
- 涉及局部更新时，优先统一到事务式更新入口。

## <span style="color:#f59e0b">6. 写入性能与状态拆分方向</span>

当前 `players.state_json` 可以继续作为主状态快照，但不能无限承担所有写入。

### 6.1 当前写入慢的主要来源

主要来源不是 MySQL 单次更新慢，而是写入模式偏重：

```text
读取整份 state_json
  -> 反序列化为 GameState
  -> 执行业务修改
  -> 序列化整份 GameState
  -> 更新整份 state_json
```

这种模式在早期可接受，但后续会受这些因素影响：

- `GameState` 字段越来越多。
- NPC、战报摘要、背包、Buff、队列等状态变大。
- 玩家频繁点击一键升级、征兵、兑换、钓鱼、领取附件。
- 多个请求同时修改同一玩家状态。

### 6.2 不应继续塞进 state_json 的内容

以下内容应优先独立建表或保持独立表，不应继续膨胀主状态：

- 历史战报
- 信函
- 小游戏记录
- 金币/城金流水
- 大量背包流水
- 活动参与记录
- 排行榜/贡献榜
- 据点、世界活动等模块公共状态

### 6.3 建议保留在 state_json 的内容

`state_json` 更适合作为玩家主快照，保留当前页面常用、单玩家强相关的状态：

- 玩家基础信息
- 核心资源数量和容量
- 建筑等级和升级队列
- 当前军队
- 当前武将或武将摘要
- 当前 Buff 摘要
- 必要的未读数和摘要字段

### 6.4 中期拆分建议

后续可以逐步从一个大 `state_json` 演进为“主快照 + 高频资产表”：

| 数据 | 建议存储 |
|---|---|
| 核心资源 | 可先留在 `state_json`，后续拆 `player_resources` |
| 建筑 | 中期可拆 `player_buildings` |
| 军队 | 中期可拆 `player_army` |
| 武将 | 多武将后建议拆 `player_generals` |
| 背包 | 物品增加后建议拆 `player_inventory` |
| Buff | 活动增多后建议拆 `player_buffs` |
| 主快照摘要 | 继续保留 `players.state_json` |

拆分原则：

- 高频写入的数据优先拆。
- 需要独立查询、分页、排行的数据优先拆。
- 影响资产安全的数据优先拆。
- 页面只读展示、体积小、变化少的数据可以继续留在快照。

### 6.5 统一玩家状态事务入口

后续应新增统一状态更新入口，避免各 service 到处手写 `GetState -> SaveState`：

```text
UpdatePlayerState(playerID, fn)
  -> 开启事务
  -> SELECT ... FOR UPDATE 锁定玩家
  -> 读取并结算状态
  -> 执行业务修改
  -> 写回必要字段
  -> 写入战报/信函/流水等奖励副作用
  -> 提交事务
```

这样可以解决：

- 并发覆盖。
- 多次读写。
- 资产变更和流水不一致。
- 模块绕过核心直接改状态。

### 6.6 局部更新规则

如果使用 `JSON_SET` 进行局部更新，必须遵守：

- 不能随后用旧的整包 `state_json` 覆盖掉局部更新。
- 同一个业务动作内，局部更新和整包保存必须在同一事务中统一处理。
- 涉及金币、城金、兵力、道具、武将等资产时，必须记录流水或可追踪记录。
- 优先通过核心资产接口更新，不让玩法模块直接写 SQL。

## <span style="color:#f59e0b">7. 迁移规范</span>

- 迁移必须可重复执行。
- 新字段先加后用，不能直接破坏旧版本。
- 删除字段/表必须有过渡期。
- 发布前先确认回滚不依赖不可逆 SQL。

## <span style="color:#f59e0b">8. 备份建议</span>

- 账号、玩家、战报、信函、流水都应纳入备份。
- 发布前至少保留最近一次可恢复快照。
- 生产事故优先恢复数据，再恢复业务行为。
