# <span style="color:#f59e0b">Hero3 数据库设计</span>

最后更新：2026-06-27
## <span style="color:#f59e0b">1. 当前存储策略</span>

Hero3 采用“账号表 + 玩家轻量兼容快照 + 业务权威表”的组合：

- 账号和登录信息规范化存储。
- 玩家轻量兼容快照保存在 `players.state_json`。
- 战报、信函、小游戏记录、流水独立建表。

这种方式适合策略游戏早期快速迭代，但必须严格控制整包覆盖问题。

当前状态：

- 业务层旧 `SaveState` 写入口已移除。
- 玩家长期状态写入统一通过 `UpdatePlayerState`，已有权威表承载的高频资产不再写回 `players.state_json`。
- 同时触碰账号金币和玩家状态的动作统一通过 `UpdateAccountPlayerState`。
- 信函附件领取、万象幻境兑换等模块状态 + 玩家资产组合动作，已经通过组合事务入口处理。
- 组合事务会跳过无实际变化的 `accounts` / `players` 更新，减少纯模块状态动作造成的主表写入。
- 小游戏兑换事务只更新 `remaining_amount` 发生变化的记录，不再批量重写玩家所有小游戏记录。
- 单条战报已读和单条战报删除只更新仍需变化的行，避免重复点击造成无效写入。
- 本地开发环境应连接 `test_` 前缀测试库，例如 `test_hero3`，不直接写稳定玩家库。

剩余风险：

- 常见玩家状态事务当前仍会读取 `players.state_json` 作为轻量兼容基底。
- 玩家主行锁仍存在，高频操作后续还需要继续拆成更细的局部事务。
- 后续优化应继续减少主表锁和 JSON 读取，把高频动作落到更明确的权威表事务。

## <span style="color:#f59e0b">2. 现有核心表</span>

| 表 | 作用 |
|---|---|
| `schema_migrations` | 数据库轻量迁移记录，记录当前库已经应用过的结构批次 |
| `accounts` | 账号、密码哈希、账号金币 |
| `players` | 存档主表，保存玩家轻量兼容快照 |
| `player_resources` | 玩家资源权威表，保存资源数量和容量；新写入不再保存 `state_json.resources` |
| `player_inventory` | 玩家背包权威表，保存道具数量和时间戳；新写入不再保存 `state_json.inventory` |
| `player_buildings` | 玩家建筑权威表，保存建筑等级、状态和升级时间；新写入不再保存 `state_json.buildings` |
| `player_resource_slots` | 玩家资源田格子权威表，保存资源田类型、绑定建筑和解锁来源 |
| `player_army_units` | 玩家兵力权威表，保存各兵种长期数量；新写入不再保存 `state_json.army` |
| `player_recruit_queues` | 玩家征兵队列权威表，保存正在训练的兵种、数量和结束时间 |
| `player_generals` | 玩家武将权威表，保存已拥有武将、等级、经验和加点 |
| `player_general_assignments` | 玩家武将占用权威表，保存主将、派遣、驻守等占用关系 |
| `player_reinforcements` | 增援批次表，保存援军生命周期、派出兵力、剩余兵力、携带武将和幂等状态 |
| `player_buffs` | 玩家 Buff/Modifier 权威表，保存限时或长期加成 |
| `event_processing_records` | 玩法模块事件处理幂等记录，避免监听事件后重复发奖 |
| `gameplay_module_instances` | 玩法模块实例表，保存副本、活动、据点等模块实例状态 |
| `gameplay_module_participants` | 玩法模块参与记录表，保存玩家参与、分数和状态 |
| `gameplay_module_settlements` | 玩法模块结算记录表，保存奖励结算幂等信息 |
| `battle_reports` | 战报归档 |
| `mails` | 信函归档 |
| `announcements` | 公告主体表，保存运营公告正文、状态、展示策略和有效期 |
| `announcement_targets` | 公告投放规则表，保存全体、指定玩家、账号、阵营和范围投放规则 |
| `announcement_reads` | 玩家公告阅读状态表，保存已读、弹窗展示和关闭状态 |
| `minigame_records` | 小游戏记录 |
| `gold_ledger` | 金币/城金流水审计 |

当前 MySQL 仓储代码已按业务归口拆分：

- `mysql.go`：连接、DSN 工具和轻量迁移。
- `mysql_account.go`：账号、账号金币和玩家列表。
- `mysql_player_state.go`：玩家主状态读写和账号 + 玩家组合事务。
- `mysql_buildings.go`：玩家建筑和资源田格子权威表同步。
- `mysql_army.go`：玩家兵力和征兵队列权威表同步。
- `mysql_generals.go`：玩家武将和武将占用权威表同步。
- `mysql_reinforcements.go`：增援批次和派出方兵力/武将占用事务。
- `mysql_buffs.go`：玩家 Buff/Modifier 权威表同步。
- `mysql_events.go`：事件处理幂等记录。
- `mysql_report.go`：战报归档。
- `mysql_mail.go`：信函归档和信函 + 玩家 + 账号组合事务。
- `mysql_announcement.go`：公告主体、投放规则和玩家阅读/弹窗状态。
- `mysql_minigame.go`：小游戏记录和小游戏 + 玩家组合事务。
- `mysql_ledger.go`：金币/城金流水审计。

后续拆分高频资产表时，应优先在对应归口文件增加端口和实现，不再把所有 SQL 堆回单一 `mysql.go`。

### <span style="color:#f59e0b">2.1 迁移记录表</span>

`schema_migrations` 是数据库结构元数据表，不属于玩家业务数据。

当前定位：

- `MigrateMySQL` 执行完成后，会写入当前轻量迁移批次。
- 重复执行迁移时不会重复插入迁移记录，也不会刷新首次应用时间。
- 该表用于排查“当前库跑过哪些结构初始化和兼容迁移”，不是正式版本化迁移系统的替代品。
- 后续引入正式迁移脚本时，应继续保留迁移记录，不允许玩法模块写入。

复制原则：

- `clone-data` 不复制 `schema_migrations`。
- `clone-data --truncate` 不清空 `schema_migrations`。
- 测试库的迁移历史应由测试库自己的 `make migrate` / `make migrate-test` 产生，不能从稳定库复制过来。

### <span style="color:#f59e0b">2.2 资源权威表</span>

`player_resources` 是玩家资源数量和容量的权威表，也是第一张从 `players.state_json` 中剥离出来的高频资产表。

当前定位：

- 由玩家创建、玩家状态事务、账号 + 玩家组合事务、信函领取事务、小游戏兑换事务同步写入。
- 字段包含 `player_id`、`resource_type`、`amount`、`capacity`、`updated_at`。
- 读取玩家 `GameState` 时，资源从 `player_resources` 聚合后覆盖 `GameState.resources`。
- 新写入不再保存 `players.state_json.resources`；旧快照仅用于历史数据回填和迁移校验，不再作为资源够不够、扣不扣得起的判断依据。
- 旧存档如果缺少资源行，运行时会明确报错，应先通过 `make backfill-resources` 回填。

读写原则：

- 只能从核心事务同步到权威表，不允许玩法模块直接绕过核心写 `player_resources`。
- 玩家状态事务开始时先锁定并读取资源行，再执行业务回调。
- 玩家状态事务内使用 upsert 同步资源行，并删除状态中已经不存在的资源类型，避免每次都整批删除再插入。
- 如果一次玩家状态事务没有改变资源数量或容量，则跳过 `player_resources` 同步写入，减少无效数据库写。
- 如果资源表和旧 `state_json.resources` 不一致，读取和业务判断以 `player_resources` 为准。
- 写完资源权威表后，只更新 `players.state_json` 轻量快照，不再刷新资源大字段。

当前工具：

```bash
make backfill-resources
make verify-resources
```

- `make backfill-resources` 从旧 `players.state_json.resources` 重建 `player_resources`，用于旧存档迁移和测试库修复。
- `make verify-resources` 仅用于旧快照迁移期间校验 `player_resources` 与历史 `state_json.resources` 是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。
- 涉及旧数据回填时，`make verify-resources` 必须通过；普通功能开发不再依赖 `state_json.resources`。

专项方案：

- 资源权威表改造方案已合并进本文档，阶段性方案文档已删除。

### <span style="color:#f59e0b">2.3 背包权威表</span>

`player_inventory` 是继资源之后拆出的第二张玩家高频资产表。

当前定位：

- 字段包含 `player_id`、`item_id`、`amount`、`obtained_at`、`updated_at`。
- 读取玩家 `GameState` 时，背包从 `player_inventory` 聚合后覆盖 `GameState.inventory`。
- 新写入不再保存 `players.state_json.inventory`；旧快照仅用于历史数据回填，不作为道具够不够、能不能消耗的最终依据。
- 空背包允许没有任何 `player_inventory` 行；如果旧 JSON 快照里有道具但表为空，应视为旧数据未回填。

读写原则：

- 只能通过玩家状态事务同步到背包权威表，不允许玩法模块直接写 `player_inventory`。
- 玩家状态事务、账号 + 玩家组合事务、信函领取事务、小游戏兑换事务开始时，先锁定并读取背包行，再执行业务回调。
- 道具发放、道具消耗、信函附件道具奖励、GM 发道具都会同步刷新 `player_inventory`，但不再刷新 `state_json.inventory`。
当前工具：

```bash
make backfill-inventory
make verify-inventory
```

- `make backfill-inventory` 从旧 `players.state_json.inventory` 重建 `player_inventory`，用于旧存档迁移和测试库修复。
- `make verify-inventory` 仅用于旧快照迁移期间校验 `player_inventory` 与历史 `state_json.inventory` 是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。

### <span style="color:#f59e0b">2.4 建筑与资源田格子权威表</span>

`player_buildings` 是玩家建筑长期状态的权威表，`player_resource_slots` 是玩家资源田格子的权威表。

当前定位：

- `player_buildings` 字段包含 `player_id`、`building_id`、`building_type`、`level`、`status`、`upgrade_ends_at`、`status_ends_at`、`updated_at`。
- `player_resource_slots` 字段包含 `player_id`、`slot_id`、`resource_type`、`building_id`、`unlocked_by`、`unlocked_at`、`updated_at`。
- 读取玩家 `GameState` 时，建筑从 `player_buildings` 覆盖 `GameState.buildings`。
- 读取玩家 `GameState` 时，资源田格子从 `player_resource_slots` 覆盖 `GameState.resourceSlots`。
- 新写入不再保存 `players.state_json.buildings` 和 `players.state_json.resourceSlots`；旧快照仅用于历史数据回填。

读写原则：

- 建筑升级、建筑状态变更、账号 + 玩家组合事务、信函领取事务、小游戏兑换事务都会先锁定并读取建筑和资源田格子权威状态。
- 建筑状态变化后，同步刷新 `player_buildings`，但不再刷新建筑快照大字段。
- 资源田格子变化后，同步刷新 `player_resource_slots`，但不再刷新资源田格子快照大字段。
- 当前资源田格子可从资源建筑推导；后续建造司增加资源田时，应写入 `player_resource_slots`，不再靠硬编码建筑列表表达。
- 建造司已接入第一版资源田解锁规则：1/5/10/15/20 级各解锁 1 个额外资源田，总计 5 个；当前额外资源田使用固定类型顺序，后续再扩展为玩家选择。
- 玩法模块不允许直接写 `player_buildings` 或 `player_resource_slots`，必须通过核心事务、建筑变更 Effect 或后续标准建筑入口。

当前工具：

```bash
make backfill-buildings
make verify-buildings
make backfill-resource-slots
make verify-resource-slots
```

- `make backfill-buildings` 从旧 `players.state_json.buildings` 重建 `player_buildings`。
- `make verify-buildings` 仅用于旧快照迁移期间校验 `player_buildings` 与历史 `state_json.buildings` 是否一致；新写入不再保证该字段存在。
- `make backfill-resource-slots` 从旧资源建筑快照或 `state_json.resourceSlots` 重建 `player_resource_slots`。
- `make verify-resource-slots` 仅用于旧快照迁移期间校验 `player_resource_slots` 与历史兼容快照是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。

### <span style="color:#f59e0b">2.5 兵力与征兵队列权威表</span>

`player_army_units` 是玩家长期兵力的权威表，`player_recruit_queues` 是玩家征兵队列的权威表。

当前定位：

- `player_army_units` 字段包含 `player_id`、`unit_type`、`amount`、`updated_at`。
- `player_recruit_queues` 字段包含 `player_id`、`queue_id`、`unit_type`、`amount`、`ends_at`、`queue_order`、`updated_at`。
- 读取玩家 `GameState` 时，兵力从 `player_army_units` 覆盖 `GameState.army`。
- 读取玩家 `GameState` 时，征兵队列从 `player_recruit_queues` 覆盖 `GameState.recruitQueues`。
- 新写入不再保存 `players.state_json.army` 和 `players.state_json.recruitQueues`；旧快照仅用于历史数据回填。

读写原则：

- 征兵、极速完成征兵、战斗扣兵、奖励发兵等长期兵力变化，必须通过核心玩家状态事务、账号 + 玩家组合事务或标准 Effect 入口。
- 玩家状态事务开始时先锁定并读取兵力和征兵队列权威状态，再执行业务回调。
- 如果兵力或征兵队列没有变化，则跳过对应权威表同步写入。
- 兵种类型必须来自兵种注册表；超级兵或模块兵也必须先注册，再进入 `player_army_units`。
- 玩法模块不允许直接写 `player_army_units` 或 `player_recruit_queues`。

当前工具：

```bash
make backfill-army
make verify-army
make backfill-recruit-queues
make verify-recruit-queues
```

- `make backfill-army` 从旧 `players.state_json.army` 重建 `player_army_units`。
- `make verify-army` 仅用于旧快照迁移期间校验 `player_army_units` 与历史 `state_json.army` 是否一致；新写入不再保证该字段存在。
- `make backfill-recruit-queues` 从旧 `players.state_json.recruitQueues` 重建 `player_recruit_queues`。
- `make verify-recruit-queues` 仅用于旧快照迁移期间校验 `player_recruit_queues` 与历史兼容快照是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。

### <span style="color:#f59e0b">2.6 武将权威表与占用表</span>

`player_generals` 是玩家已拥有武将的权威表，`player_general_assignments` 是武将上阵、派遣、驻守等占用关系的权威表。

当前定位：

- `player_generals` 字段包含 `player_id`、`general_id`、`faction`、`level`、`exp`、`stats_json`、`acquired_at`、`updated_at`。
- `player_general_assignments` 字段包含 `player_id`、`assignment_id`、`general_id`、`assignment_slot`、`module_id`、`status`、`assigned_at`、`ends_at`、`updated_at`。
- 读取玩家 `GameState` 时，已拥有武将从 `player_generals` 覆盖 `GameState.generals`。
- 读取玩家 `GameState` 时，武将占用从 `player_general_assignments` 覆盖 `GameState.generalAssignments`。
- `GameState.general` 继续作为当前主将兼容字段，由 `main` 占用指向的武将还原。
- 新写入不再保存 `players.state_json.general`、`players.state_json.generals` 和 `players.state_json.generalAssignments`；旧快照仅用于历史数据回填。

读写原则：

- 武将经验、加点、洗点、切换主将、道具获得武将、活动获得武将，都必须通过核心玩家状态事务、账号 + 玩家组合事务或标准 Effect/Reward 入口。
- 物品、信函、活动如果要产出武将，应使用标准奖励类型 `general`，不直接写表。
- 新武将必须先进入武将注册表和阵营配置，再进入 `player_generals`。
- 派遣类玩法必须写 `player_general_assignments`，不能只在玩法模块私有状态里标记武将占用。
- 玩法模块不允许直接写 `player_generals` 或 `player_general_assignments`。

当前工具：

```bash
make backfill-generals
make verify-generals
```

- `make backfill-generals` 从旧 `players.state_json.general/generals/generalAssignments` 重建武将权威表和占用表。
- `make verify-generals` 仅用于旧快照迁移期间校验 `player_generals` / `player_general_assignments` 与历史兼容快照是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。

### <span style="color:#f59e0b">2.7 增援批次表</span>

`player_reinforcements` 是增援玩法模块的批次状态表，并兼容承载编外驻防队伍，不是接收方长期兵力表。

当前定位：

- 每一批增援保存 `reinforcement_id`、派出方、接收方、目标类型、状态、原始兵力、剩余兵力、携带武将、累计损耗、行军时间、返程时间、邮件/奖励幂等状态。
- 驻防通用字段包含 `owner_player_id`、`host_player_id`、`source_type`、`source_id`、`source_faction`、`rules_json`。
- `source_type = reinforcement` 表示玩家增援；`captured`、`mercenary`、`event_reward`、`system` 表示非增援来源的编外驻防队伍。
- 派出时从派出方 `player_army_units` 扣出可用兵力。
- 携带武将时写入派出方 `player_general_assignments`，`module_id = reinforcement`。
- 援军到达后只在 `player_reinforcements` 中变为 `stationed`，不会写入接收方 `player_army_units`。
- 召回、遣返或全军覆没后进入 `returning`，返程完成后返还剩余兵力并释放武将占用。

读写原则：

- 增援模块只能通过 `ReinforcementRepository` 和军事/武将标准入口改变长期资产，不允许直接把援军写成接收方兵力。
- 同一接收方最多 5 个不同来源玩家占用有效驻防来源槽，同来源可以追加多批。
- 战斗接入时只读取 `stationed` 状态的援军，并保留 `reinforcement_id` 和 `from_player_id` 供战后拆分损耗。
- 非本阵营军队不直接写入常规 `player_army_units`，应以编外驻防队伍进入 `player_reinforcements`，再由 `rules_json` 决定能否参战、转化或释放。

### <span style="color:#f59e0b">2.8 Buff/Modifier 权威表</span>

`player_buffs` 是玩家动态 Buff、DeBuff 和长期 Modifier 的权威表。

当前定位：

- 字段包含 `player_id`、`buff_id`、`source`、`modifier_key`、`modifier_value`、`modifier_mode`、`expires_at`、`created_at`、`note`、`updated_at`。
- 读取玩家 `GameState` 时，Buff 从 `player_buffs` 覆盖 `GameState.buffs`。
- 新写入不再保存 `players.state_json.buffs`；旧快照仅用于历史数据回填。
- Modifier 管线继续通过 `CollectModifierSources` 聚合 Buff、武将、建筑、购买加成、阵营特性等来源。

读写原则：

- GM 发 Buff、标准 `buff` 奖励、Modifier Effect、过期清理、撤销 Buff 都必须通过核心玩家状态事务。
- 新增 Modifier key 必须先进入注册表校验，不允许玩法模块直接使用未注册字符串。
- 玩法模块不允许直接写 `player_buffs`。

当前工具：

```bash
make backfill-buffs
make verify-buffs
```

- `make backfill-buffs` 从旧 `players.state_json.buffs` 重建 `player_buffs`。
- `make verify-buffs` 仅用于旧快照迁移期间校验 `player_buffs` 与历史兼容快照是否一致；新写入不再保证该字段存在。
- `make clone-data` 复制数据后会自动回填并校验资源、背包、建筑、资源田格子、兵力、征兵队列、武将和 Buff 权威表，除非显式传跳过参数。

### <span style="color:#f59e0b">2.9 事件处理幂等记录</span>

`event_processing_records` 是玩法模块处理核心事件时使用的幂等表。

当前定位：

- 字段包含 `module_id`、`handler_key`、`event_key`、`processed_at`。
- 主键为 `(module_id, handler_key, event_key)`。
- 模块监听事件后，如果要发奖或写长期状态，应先调用 `ClaimEventForModule` 声明处理权。
- 第一次声明返回 `true`，重复事件返回 `false`，模块必须跳过重复处理。

读写原则：

- 事件本身仍通过进程内 EventBus 发布。
- 涉及长期资产的事件处理不允许直接改表，必须先 claim，再触发标准 Effect 或模块自身状态事务。
- 玩法模块的 `module_id` 必须先登记到玩法模块注册表。
- `handler_key` 应稳定表达处理器用途，例如 `daily_task_progress`、`dungeon_reward_settlement`。

### <span style="color:#f59e0b">2.10 玩法模块通用表</span>

玩法模块通用表用于承载副本、活动、据点、NPC 动态事件等模块化玩法，不表达任何具体玩法规则。

当前定位：

- `gameplay_module_instances` 保存模块实例，例如一次副本活动、一期据点争夺、一个世界事件。
- `gameplay_module_participants` 保存玩家参与记录、状态和分数。
- `gameplay_module_settlements` 保存玩家结算记录和奖励 JSON，用于避免重复结算。

读写原则：

- 新玩法必须先登记 `GameplayModuleDefinition`，再使用这些通用表或新增模块私有表。
- 玩法模块状态可以写模块表，但长期资产奖励必须通过 Effect Pipeline 或标准 Reward。
- 结算奖励必须有稳定 `settlement_key`，避免重复领奖。
- 如果玩法需要公共世界状态，应优先落在模块实例或模块私有表，不放进玩家 `state_json`。

## <span style="color:#f59e0b">2.10 本地测试库制度</span>

本地开发和架构重构必须使用测试库，默认命名规则：

```text
正式或稳定库：hero3
本地开发测试库：test_hero3
```

执行原则：

- `go/.env` 的 `HERO3_DATABASE_DSN` 在本地开发时应指向 `test_hero3`。
- `hero3` 可以作为稳定玩家库或线上库，不作为日常开发写入目标。
- `HERO3_ENV=development` 时，服务启动默认拒绝连接非 `test_` 前缀数据库。
- 如果确需临时连接非测试库，必须显式设置 `HERO3_ALLOW_DEVELOPMENT_DATABASE=true`。
- 需要从稳定库复制数据到测试库时，只能复制到 `test_` 前缀库，不反向覆盖稳定库。
- 创建测试库需要数据库账号拥有 `CREATE DATABASE` 权限；如果业务账号没有该权限，应由管理员先创建并授权。
- 项目提供 `make migrate-test` 创建并迁移 `test_` 前缀库；权限不足时该命令会失败，不应改为直接写稳定库。
- 项目提供 `make clone-data` 从 `HERO3_SOURCE_DATABASE_DSN` 复制数据到当前 `test_` 目标库；目标库不是 `test_` 前缀时命令会拒绝执行。
- `clone-data` 允许目标测试库比源库多出迁移后的新列，复制时只写公共列并让目标列使用默认值；如果源库列在目标库不存在，则说明目标迁移不兼容，应中止复制。
- `clone-data --truncate` 会清空目标测试库全部普通表，再按源库表复制，避免源库没有的新表在目标库残留旧数据。
- `clone-data` 会跳过 `schema_migrations`，测试库迁移记录只由测试库自己的迁移命令维护。

常用命令：

```bash
make migrate
make migrate-test
make print-test-dsn
HERO3_SOURCE_DATABASE_DSN='源库DSN' make clone-data
make backfill-resources
make verify-resources
make backfill-inventory
make verify-inventory
make backfill-buildings
make verify-buildings
make backfill-resource-slots
make verify-resource-slots
make backfill-army
make verify-army
make backfill-recruit-queues
make verify-recruit-queues
make backfill-generals
make verify-generals
make backfill-buffs
make verify-buffs
make healthcheck-authority
```

说明：

- `verify-*` 是 legacy 迁移期校验，用来对比旧 `players.state_json` 兼容快照和权威表。
- 当前 `players.state_json` 已经是轻量兼容快照，新写入不再保存资源、背包、建筑、资源田、兵力、征兵队列、武将、武将占用、Buff 等大字段。
- 日常开发和测试库验收使用 `make healthcheck-authority`：它检查每个玩家是否具备 `player_resources`、`player_buildings`、`player_resource_slots`、`player_generals` 基础权威数据，并允许 `player_inventory`、`player_army_units`、`player_recruit_queues`、`player_buffs` 为空。

## <span style="color:#f59e0b">3. 索引与约束原则</span>

- 账号名必须唯一。
- `players.account_id` 必须有外键。
- 玩家列表查询、战报列表、信函列表都要围绕 `player_id` 建索引。
- 频繁查询字段优先建联合索引，不靠全表扫。

## <span style="color:#f59e0b">4. 事务边界</span>

必须使用事务的场景：

- 金币与城金互转。
- 发放奖励同时写入流水。
- 领取信函附件。
- 小游戏兑换/领取。
- 任何会同时改账号和玩家状态的操作。
- 任何会扣减、发放、自然结算或改变容量的玩家资源操作。

建议规则：

- 先锁住资源，再改状态。
- 资源不足必须失败并回滚。
- 资源不得扣成负数。
- 失败必须能回滚。

## <span style="color:#f59e0b">5. JSON 状态注意事项</span>

`players.state_json` 的好处是方便快速迭代，缺点是：

- 并发覆盖风险高。
- 字段难以局部索引。
- 复杂查询成本高。

因此：

- 适合放“主状态快照”。
- 不适合放历史流水和高频查询归档。
- 涉及局部更新时，优先统一到事务式更新入口。

## <span style="color:#f59e0b">6. 写入性能与状态拆分方向</span>

当前 `players.state_json` 可以继续作为主状态快照，但不能无限承担所有写入。

### 6.1 当前写入成本的主要来源

当前已经不再允许业务层散落手写 `GetState -> SaveState`，但主快照写入模式仍然偏重：

```text
UpdatePlayerState / 组合事务
  -> SELECT ... FOR UPDATE 锁定玩家
  -> 读取整份 state_json
  -> 反序列化为 GameState
  -> 执行业务修改
  -> 序列化整份 GameState
  -> 更新整份 state_json
```

这种模式在早期可接受，但后续会受这些因素影响：

- `GameState` 字段越来越多。
- NPC、战报摘要、背包、Buff、队列等状态变大。
- 玩家频繁点击一键升级、征兵、兑换、钓鱼、领取附件。
- 多个请求同时修改同一玩家状态。

### 6.2 不应继续塞进 state_json 的内容

以下内容应优先独立建表或保持独立表，不应继续膨胀主状态：

- 历史战报
- 信函
- 小游戏记录
- 金币/城金流水
- 大量背包流水
- 活动参与记录
- 排行榜/贡献榜
- 据点、世界活动等模块公共状态

### 6.3 建议保留在 state_json 的内容

`state_json` 当前只应作为轻量兼容快照，保留尚未拆表且体积可控的字段：

- 玩家基础信息
- 资源结算时间
- 城金、兑换冷却、购买加成时间
- NPC 状态和地图目标等尚未拆表字段
- 必要的未读数和摘要字段

### 6.4 当前权威存储

当前已经从一个大 `state_json` 演进为“轻量兼容快照 + 高频资产权威表”：

| 数据 | 当前存储 |
|---|---|
| 核心资源 | 已拆 `player_resources` |
| 建筑 | 已拆 `player_buildings` |
| 资源田格子 | 已拆 `player_resource_slots` |
| 军队 | 已拆 `player_army_units` / `player_recruit_queues` |
| 武将 | 已拆 `player_generals` / `player_general_assignments` |
| 背包 | 已拆 `player_inventory` |
| Buff | 已拆 `player_buffs` |
| 主快照摘要 | 保留在 `players.state_json`，只作轻量兼容快照 |

拆分原则：

- 高频写入的数据优先拆。
- 需要独立查询、分页、排行的数据优先拆。
- 影响资产安全的数据优先拆。
- 页面只读展示、体积小、变化少的数据可以继续留在快照。

### 6.5 统一玩家状态事务入口

当前已新增统一状态更新入口，避免各 service 到处手写 `GetState -> SaveState`：

```text
UpdatePlayerState(playerID, fn)
  -> 开启事务
  -> SELECT ... FOR UPDATE 锁定玩家
  -> 读取并结算状态
  -> 执行业务修改
  -> 写回必要字段
  -> 写入战报/信函/流水等奖励副作用
  -> 提交事务
```

当前已解决或收敛：

- 并发覆盖。
- 多次读写。
- 模块绕过核心直接改状态。

仍需在数据库重设计时继续加强：

- 把账号资产事务、玩家状态事务、奖励流水、事件流水等边界落进正式 schema 和 migrations。
- 让高频资产从大 JSON 快照逐步拆出。
- 将需要强审计的事件从进程内事件管线升级为持久化事件流水。

### 6.6 局部更新规则

如果使用 `JSON_SET` 进行局部更新，必须遵守：

- 不能随后用旧的整包 `state_json` 覆盖掉局部更新。
- 同一个业务动作内，局部更新和整包保存必须在同一事务中统一处理。
- 涉及金币、城金、兵力、道具、武将等资产时，必须记录流水或可追踪记录。
- 优先通过核心资产接口更新，不让玩法模块直接写 SQL。

## <span style="color:#f59e0b">7. 迁移规范</span>

- 迁移必须可重复执行。
- 新字段先加后用，不能直接破坏旧版本。
- 删除字段/表必须有过渡期。
- 发布前先确认回滚不依赖不可逆 SQL。

## <span style="color:#f59e0b">8. 备份建议</span>

- 账号、玩家、战报、信函、流水都应纳入备份。
- 发布前至少保留最近一次可恢复快照。
- 生产事故优先恢复数据，再恢复业务行为。
