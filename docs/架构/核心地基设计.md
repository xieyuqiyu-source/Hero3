# <span style="color:#0ea5e9">Hero3 核心地基设计</span>

最后更新：2026-06-25
文档状态：active

## <span style="color:#0ea5e9">1. 目标</span>

Hero3 采用“稳定核心 + 可扩展玩法模块”的模块化单体方向。

核心地基的目标不是把所有玩法都塞进核心，而是提供一组稳定能力，让玩法模块可以安全读取、消耗、发放和监听玩家长期资产。

核心要解决的问题：

- 玩家状态如何安全修改。
- 奖励如何统一发放。
- 事件如何统一触发和监听。
- 加成如何统一接入计算。
- 资源、建筑、兵种、武将、道具等内容如何配置化或注册化。
- 玩法模块如何接入核心，而不是绕过核心直接改状态。

## <span style="color:#0ea5e9">2. 核心范围</span>

游戏核心包含：

- 玩家存档
- 存档读写
- 资产事务
- 资源
- 建筑
- 兵力
- 武将
- 道具
- 货币
- Buff/加成
- 时间结算
- 奖励发放
- 事件管线
- 配置/注册中心
- 解锁条件
- 通知/信函/战报端口
- 通用战斗引擎

其中，资源、建筑、兵力、武将、道具、货币、Buff 是玩家长期资产或资产能力；奖励、事件、事务、注册中心是玩法模块接入这些资产的基础接口。

注意：核心需要提供通知、信函、战报的标准端口，但不代表完整信函系统、完整战报系统都属于核心。

## <span style="color:#0ea5e9">3. 玩法模块边界</span>

具体玩法模块负责自己的规则和过程状态，例如：

- 关卡层数
- 难度和词条
- 随机过程
- 临时 Buff
- 模块内进度
- 模块内排行榜
- 模块内结算规则

玩法模块可以独立计算这些内容，但只要触碰玩家长期资产，就必须通过核心接口。

典型接入方式：

```text
玩法模块
  -> 计算本玩法结果
  -> 生成标准奖励、事件、状态变更请求
  -> 核心验证并落库
  -> 核心返回权威玩家状态或结果摘要
```

如果玩法需要新增建筑、兵种、道具、武将、Buff key、奖励类型或事件类型，优先通过配置或注册表接入。

如果现有核心不能接入某个长期资产变化，应先判断核心是否不完整，不允许玩法模块绕过核心直接改玩家状态。

### <span style="color:#0ea5e9">3.1 信函模块边界</span>

信函系统本体按独立模块判断。

信函模块负责：

- 信件实体和收件箱。
- 已读、删除、领取、过期状态。
- 玩家私信。
- GM 发信。
- 附件领取流程编排。
- 信函存储和分页查询。

核心只提供信函模块接入所需的稳定能力：

- 玩家状态事务。
- 账号资产事务。
- 标准奖励应用。
- 货币流水。
- 事件管线。
- 通知/信函端口。

因此，信函附件领取不应被理解为“信函系统进入核心”，而是信函模块通过核心奖励、流水和事件能力修改玩家长期资产。

## <span style="color:#0ea5e9">4. 核心接口规划</span>

### <span style="color:#0ea5e9">4.1 玩家状态事务</span>

已新增统一玩家状态更新入口：

```text
UpdatePlayerState(playerID, fn)
  -> 开启事务
  -> 锁定玩家状态
  -> 读取并执行时间结算
  -> 执行业务修改
  -> 记录奖励、事件、流水、战报、信函等副作用
  -> 写回状态
  -> 提交事务
```

它用于替代散落在各 service 中的 `GetState -> 修改 -> SaveState`。

当前业务层写玩家存档只允许通过 `UpdatePlayerState`。旧 `SaveState` 仓库入口已移除，避免后续模块绕过核心事务直接覆盖玩家状态。

已新增账号资产事务入口：

```text
UpdateAccountPlayerState(accountID, playerID, fn)
  -> 开启事务
  -> 锁定账号资产
  -> 锁定玩家状态
  -> 执行业务修改
  -> 写回账号和玩家状态
  -> 提交事务
```

它用于承接同时触碰账号金币和玩家存档的动作，例如账号金币奖励、金币/城金兑换、将领洗点等。

当前已接入统一玩家状态事务的动作：

- 读取存档时的时间结算和旧档补全
- 资源调整
- 资源填满
- 建筑升级
- 批量建筑升级
- 征兵
- 道具发放
- 道具使用
- Buff 发放
- Buff 撤销
- NPC 城池自动刷新/结算
- NPC 城池手动刷新
- 玩家信函寄件人地址补全
- 付费填满资源
- 极速完成建筑
- 极速完成征兵
- 将领属性加点
- 更换将领
- 购买资源产量加成
- 购买仓库容量加成
- 万象幻境鱼饵消耗
- NPC 攻击结算
- NPC 侦查结算

当前已接入账号资产事务的动作：

- 金币兑换城金。
- 城金兑换金币。
- 将领洗点。
- 账号金币奖励。

当前战斗结算已经完成第一轮事务化：

- 战斗规则和武将特性仍独立计算。
- 扣兵、NPC 状态变化、掠夺资源、溢出城金、武将经验写入统一玩家状态事务。
- 战报作为事务成功后的归档副作用保存。
- 溢出城金写入 `battle_overflow` 货币流水。
- 战斗资源、溢出城金、武将经验整理为战报 `GrantedRewards`。
- 战斗奖励发布 `battle_reward` 来源的 `reward.granted` 事件。
- 战斗完成发布 `battle.finished` 事件。

已新增模块组合事务入口：

```text
UpdateMailPlayerState(playerID, mailID, fn)
  -> 锁定信函记录
  -> 锁定玩家状态
  -> 锁定账号资产
  -> 由应用层执行业务规则和奖励应用
  -> 同时写回信函、玩家、账号

UpdateMiniGamePlayerState(playerID, fn)
  -> 锁定玩家状态
  -> 锁定万象幻境记录
  -> 由应用层执行兑换规则和奖励应用
  -> 同时写回记录和玩家状态
```

组合事务的原则是：仓库只负责锁定和持久化，不能在存储层私自理解奖励规则；信函、万象幻境等模块规则由 service 编排，并通过标准奖励接口修改玩家长期资产。

### <span style="color:#0ea5e9">4.2 奖励发放</span>

奖励发放需要统一为标准奖励包，至少覆盖：

- 资源
- 城金
- 账号金币
- 道具
- 兵力
- 武将经验
- Buff
- 解锁项

信函附件、战斗奖励、万象幻境兑换、活动结算、任务奖励都应走同一套奖励接口。

奖励接口负责：

- 校验奖励类型是否合法。
- 校验阵营、兵种、道具等注册内容。
- 更新玩家资产。
- 写入必要流水或审计记录。
- 触发奖励发放事件。

当前已新增标准奖励结构和状态应用器：

- `internal/core/reward`：定义标准奖励类型常量、`Reward` 和 `RewardGrantContext` 的核心契约。
- `internal/app/game`：保留兼容别名，并负责把标准奖励应用到 `GameState`、账号金币、流水和事件。
- `Reward`：描述标准奖励类型、奖励 ID 和数量。
- `ApplyRewardsToState`：把标准奖励应用到玩家状态。
- `ApplyRewardsToStateWithContext`：带来源上下文的奖励应用入口，可产出事件和流水意图。
- `Service.GrantRewards`：奖励发放编排入口，负责选择玩家状态事务或账号资产事务，并在成功后写流水、发布事件。
- 已覆盖：资源、城金、账号金币、道具、兵力、武将经验、Buff。
- 已接入状态应用器：信函附件领取、万象幻境兵力兑换。
- 已接入发放编排器：GM 增加城金、GM 发放道具。
- 已接入核心流水和事件：信函附件领取、万象幻境兑换事件。

当前限制：

- 账号金币不在玩家存档 JSON 内，因此需要 `UpdateAccountPlayerState` 参与事务。
- 城金和账号金币奖励已经可以在 `GrantRewards` 成功后统一写货币流水。
- 解锁项暂未实现，因为当前还没有明确的长期解锁资产容器；不能为了补奖励类型而硬塞进核心。
- 审计日志仍未形成独立核心接口，当前先由货币流水和事件承担关键追踪。

当前 `GrantRewards` 已经可以统一处理：

- 玩家状态内奖励：资源、城金、道具、兵力、武将经验、Buff。
- 账号奖励：账号金币。
- 成功后统一写货币流水。
- 成功后统一发布 `reward.granted` 事件。

暂缓直接迁入 `GrantRewards` 的奖励来源：

- 信函附件领取：除了发奖励，还要原子标记信函已领取。
- 万象幻境兑换：除了发兵力奖励，还要原子扣减兑换记录库存。
- 战斗掠夺：除了产出奖励，还要同时扣兵、修改 NPC 状态、保存战报、处理武将特性结果。

这些来源不应强行塞进普通 `GrantRewards`。正确方式是使用组合事务：模块记录状态变更由模块事务容器负责，长期资产变化仍通过标准奖励应用器负责。

当前信函附件领取已经完成：

- 信函领取走 `UpdateMailPlayerState` 组合事务。
- 领取规则在 service 层，仓库层不再调用奖励应用。
- 奖励通过 `ApplyRewardsToStateWithContext` 应用到玩家状态。
- 账号金币附件在同一事务中更新账号资产。
- 货币附件写入 `mail_claim` 流水。
- 发布 `mail.claimed` 事件。
- 发布附件对应的 `reward.granted` 事件。

当前万象幻境兑换已经完成：

- 万象幻境兑换走 `UpdateMiniGamePlayerState` 组合事务。
- 兑换规则在 service 层，仓库层不再调用奖励应用。
- 模块记录库存扣减和玩家兵力发放处于同一事务边界。
- 奖励通过 `ApplyRewardsToStateWithContext` 应用到玩家状态。
- 返回标准 `GrantedRewards`。
- 发布 `minigame.redeemed` 事件。
- 发布兑换奖励对应的 `reward.granted` 事件。

当前战斗奖励/产出已经完成：

- NPC 攻击在玩家状态事务内处理兵损、掠夺资源、溢出城金、武将经验。
- 战斗资源、溢出城金、武将经验统一整理为战报 `GrantedRewards`。
- 溢出城金写入货币流水。
- 发布 `battle_reward` 来源的 `reward.granted` 事件。
- 发布 `battle.finished` 事件。

### <span style="color:#0ea5e9">4.3 事件管线</span>

事件管线用于连接核心资产变化和模块监听。

优先注册的事件类型：

- `player.created`
- `resource.changed`
- `building.upgraded`
- `unit.changed`
- `currency.changed`
- `general.changed`
- `item.used`
- `reward.granted`
- `battle.finished`
- `mail.claimed`
- `minigame.redeemed`

事件可以先在进程内同步分发，后续再根据需要扩展为异步队列或审计日志。

当前已新增进程内事件管线：

- `internal/core/event.Event`：标准事件结构。
- `internal/core/event.Bus`：同步订阅和发布。
- `internal/app/game.NewEventBus`：注入事件类型注册校验和项目时间格式。
- `Service.SubscribeEvent`：模块订阅事件入口。
- `Service.publishEvent`：服务内部发布事件入口。
- 事件类型已进入注册中心，未注册事件不会被发布或订阅。

当前已接入事件管线的关键流程：

- 玩家创建：`player.created`。
- 资源调整、资源填满、付费填仓、征兵/建筑消耗、道具资源效果：`resource.changed`。
- 建筑极速完成等显式业务导致的等级变化：`building.upgraded`。
- 征兵极速完成、奖励兵力、道具兵力效果：`unit.changed`。
- 道具使用：`item.used`。
- 奖励发放：`reward.granted`。
- 信函附件领取：`mail.claimed`、`reward.granted`。
- 万象幻境兑换：`minigame.redeemed`、`reward.granted`。
- 金币/城金兑换：`currency.changed`。
- 直接扣城金、万象幻境鱼饵消耗、加成购买、付费填仓、极速建筑、极速征兵、将领洗点、管理员账号金币调整：`currency.changed`。
- 将领洗点：`general.changed`。
- NPC 攻击：`battle.finished`、`reward.granted`。
- NPC 侦查：`battle.finished`。

当前已新增核心资产变更事件辅助：

- `snapshotCoreAssets`：记录资源、建筑等级、兵力快照。
- `publishCoreAssetDiff`：事务成功后根据前后快照发布资源、建筑、兵力变化事件。
- 事件只在事务成功后发布，避免失败事务产生虚假事件。

注意：读取存档时触发的离线时间结算会更新资源、完成建筑或征兵队列，但当前仍优先作为存档补全/结算行为处理，尚未把每个离线切片拆成独立事件流水。后续如果需要强审计级离线事件，应在时间结算核心中增加结算结果对象，而不是让读取接口临时拼事件。

### <span style="color:#0ea5e9">4.4 Modifier 加成管线</span>

Modifier 管线负责统一计算全局加成。

当前核心计算能力已下沉到 `internal/core/modifier`：

- `Modifier`：统一加成表达。
- `Source`：加成来源接口。
- `ComputeAttribute` / `ComputeAttributeAt`：统一数值公式。
- `ComputeIntAttribute` / `ComputeIntAttributeAt`：整数属性计算。
- `IsValidMode`：统一加成模式校验。

`internal/app/game` 仍负责收集具体业务来源，因为这些来源依赖玩家存档、武将、建筑、Buff 和阵营配置。

加成来源可以包括：

- 武将
- Buff
- 建筑效果
- 阵营特性
- 道具效果
- 玩法模块解锁效果
- 活动效果

数值计算不应散落在资源、征兵、战斗等流程中硬编码特殊判断，而应通过统一加成来源收集后计算。

当前已完成：

- 将领加成来源。
- 购买加成来源。
- Buff 列表来源。
- 建筑效果来源。
- 阵营特性来源。
- `RegisterModifierSourceProvider`：模块可注册自己的加成来源。
- Modifier 计算公式已进入 `internal/core/modifier`，业务侧通过别名和适配函数继续使用。

后续模块如果要提供全局加成，应优先注册 Modifier 来源，而不是修改资源、征兵或战斗计算流程。

### <span style="color:#0ea5e9">4.5 内容注册中心</span>

可扩展内容优先配置化或注册化：

- 资源类型
- 建筑类型
- 建筑效果
- 兵种
- 武将
- 道具
- Buff/加成 key
- 奖励类型
- 事件类型
- 战斗规则

新增内容原则上不修改核心流程代码；如果必须修改，说明核心注册能力可能不完整，应先补核心接口。

当前已新增轻量注册中心：

- `internal/core/registry.ResourceTypeDefinition`：资源类型注册。
- `internal/core/registry.RewardTypeDefinition`：奖励类型注册。
- `internal/core/registry.EventTypeDefinition`：事件类型注册。
- `internal/app/game`：保留兼容入口，并负责注册 Hero3 默认资源、奖励和事件类型。
- `combat.RuleConfig`：战斗规则注册。
- 已注册核心资源类型：木材、石料、铁矿、粮食。
- 已注册核心奖励类型：资源、城金、账号金币、道具、兵力、武将经验、Buff。
- 已注册核心事件类型：玩家创建、资源变化、建筑升级、兵力变化、货币变化、武将变化、道具使用、奖励发放、战斗完成、信函领取、万象幻境兑换。
- 已注册默认战斗规则：官方攻击、官方掠夺。
- 战斗场景可通过 `SetActiveRule` 绑定具体规则，例如 `pve_attack`、`pve_plunder`、`pvp_attack`、`pvp_plunder`。
- 建筑效果当前通过 `BuildingConfig.ModifiersByLevel` 接入 Modifier 管线。
- 兵种当前通过阵营兵种配置表接入。

注意：注册奖励类型不等于核心能处理任何新长期资产容器。新道具、新兵种、新 Buff key 走配置/注册表即可；如果新增的是全新长期资产容器，必须先讨论核心是否要扩展。

### <span style="color:#0ea5e9">4.6 建筑生命周期</span>

建筑是玩家长期资产，核心需要提供标准状态和通用变更入口，而不是让玩法直接修改建筑数组。

当前已新增 `internal/core/building`：

- 标准状态：`normal`、`constructing`、`upgrading`、`locked`、`damaged`、`destroyed`、`repairing`、`disabled`、`protected`、`occupied`。
- 标准变更类型：设置状态、等级变化、开始升级、完成升级、损坏、摧毁、修复、锁定、解锁、占领、释放。
- 状态校验：旧存档空状态按 `normal` 处理。
- 操作判断：非正常状态不能直接开始升级；`destroyed`、`disabled` 不再提供产量、容量和建筑 Modifier。

应用层已新增统一建筑变更入口：

```text
MutateBuilding(playerID, mutation)
  -> 玩家状态事务
  -> 结算时间
  -> 校验建筑和状态
  -> 应用建筑变更
  -> 刷新资源/容量/Modifier
  -> 发布建筑事件
```

现有升级流程已接入建筑状态：

- 开始升级时状态变为 `upgrading`。
- 完成升级时状态回到 `normal`。
- 极速完成和离线结算都会恢复状态。
- 建筑状态变化会通过 `building.upgraded` 事件的 `statusChanges` 载荷发布。

后续玩法如果要摧毁建筑、锁建筑、修复建筑、占领建筑，应先通过 `MutateBuilding` 或 Effect Pipeline 产生建筑变更，不允许玩法直接改建筑字段。

### <span style="color:#0ea5e9">4.6.1 建筑系统归口</span>

建筑系统分两层维护：

- `internal/core/building`：只放稳定核心能力，包括建筑状态、建筑变更类型和状态校验。
- `internal/app/game`：放当前游戏建筑规则，包括建筑配置注册表、默认建筑补齐、升级编排、产量/容量效果、建筑 Modifier 来源和建筑事件发布。

当前应用层建筑入口已经按职责归口：

- `building_registry.go`：建筑配置查询、建筑类型判断、核心建筑补齐。
- `building_lifecycle.go`：应用层建筑变更入口和状态适配。
- `building_effects.go`：建筑产量、容量和建筑 Modifier 来源。
- `service_building.go`：建筑升级、批量升级、极速完成等玩家操作。

新增普通建筑时优先走建筑配置注册表；新增建筑长期状态变化时优先走 `MutateBuilding`；新增只属于某个玩法的特殊规则时放在玩法模块内，通过核心接口读写长期资产。

### <span style="color:#0ea5e9">4.7 战斗规则注册</span>

战斗引擎属于通用核心能力，战斗规则已经支持注册和场景绑定。

核心战斗引擎负责：

- 读取参战单位。
- 读取兵种属性。
- 计算攻防、胜负、损失、掠夺。
- 输出标准战斗结果。
- 触发战斗前、中、后事件。

具体规则由玩法注册，例如：

- NPC 攻城
- NPC 掠夺
- PVP 攻城
- 轮回绝境
- 演武场
- 活动战斗

当前已完成：

- `RegisterRule`：注册战斗规则。
- `SetActiveRule`：把玩法场景绑定到具体规则。
- `GetActiveRuleID` / `GetActiveRule`：解析当前场景规则。
- NPC 攻击、NPC 掠夺和战斗模拟已经通过场景读取规则，不再硬编码 `official_attack` / `official_plunder`。

### <span style="color:#0ea5e9">4.8 武将系统归口</span>

武将系统分两层维护：

- `internal/core/general`：只放稳定核心能力，包括武将特性接口、特性注册表、特性事件上下文和 Dispatch 分发。
- `internal/app/game`：放当前游戏武将规则，包括武将配置注册表、成长计算、属性装配、Modifier 来源、加点/洗点/换将操作和战斗适配。

当前应用层武将入口已经按职责归口：

- `general_registry.go`：武将配置查询、武将注册判断、全部武将配置列表。
- `general_growth.go`：等级、经验、属性点和战斗经验计算。
- `general_effects.go`：配置装配、属性拆解、武将 Modifier 来源。
- `general_combat.go`：把玩家武将特性接入战斗特性总线，并把触发结果写入战报。
- `service_general.go`：玩家操作，包括加点、洗点和换将。

新增普通武将时优先走武将配置注册表；新增固定加成时走武将配置的 `buffs` 并进入 Modifier 管线；新增战斗特性时在 `internal/core/general/traits` 实现特性并通过配置挂到武将；如果特性要修改新的长期资产，必须先确认核心是否已有通用资产变更入口。

### <span style="color:#0ea5e9">4.9 兵种/军事系统归口</span>

兵种/军事系统分两层维护：

- `internal/core/combat`：只放稳定核心战斗能力，包括战斗单位、战斗规则、战斗场景绑定和战斗结算。
- `internal/app/game`：放当前游戏军事规则，包括兵种配置、玩家兵力数组、征兵队列、征兵速度加成、战斗可用性校验和战斗单位适配。

当前应用层军事入口已经按职责归口：

- `unit_registry.go`：兵种配置查询、兵种注册判断、按名称查找兵种。
- `army_state.go`：玩家兵力增加、兵力切片和 map 转换、战斗后兵力合并。
- `recruit_timing.go`：征兵时长、通用征兵速度加成和兵种分类征兵速度加成。
- `service_recruit.go`：玩家征兵、极速完成征兵等事务操作。
- `military_combat.go`：出兵扣兵、非战斗兵种限制、模拟战斗单位构建、PVE 场景规则解析。

新增普通兵种时优先走兵种配置注册表；新增玩家兵力奖励或道具产出时走统一奖励/兵力入口；新增某玩法专属临时兵种时先注册配置并由玩法控制产出和下线；新增战斗限制时优先归到 `military_combat.go`，不要散落在具体玩法服务里。

### <span style="color:#0ea5e9">4.10 道具/Buff 系统归口</span>

道具/Buff 系统分两层维护：

- `internal/core/reward`：只放稳定奖励契约，包括 item、buff 等标准奖励类型。
- `internal/core/modifier`：只放稳定 Modifier 计算能力，不知道具体来源。
- `internal/app/game`：放当前游戏道具、背包、道具效果、Buff/DeBuff 状态和具体 Modifier 来源。

当前应用层道具/Buff 入口已经按职责归口：

- `item_registry.go`：道具配置查询、道具注册判断、全部道具配置列表。
- `inventory_state.go`：玩家背包道具增加和消耗。
- `item_effects.go`：道具使用后的效果执行，包括武将经验、资源和按阵营发兵力。
- `service_item.go`：道具发放、道具使用等玩家操作。
- `buff_effects.go`：Buff/DeBuff 状态、过期清理、Modifier scope 校验和 Modifier 来源。
- `service_buff.go`：Buff 发放和撤销等玩家操作。

新增普通道具时优先走道具配置注册表；新增道具产出长期资产时必须复用已有核心资产入口；新增 Buff/DeBuff 时必须先通过 `IsValidStatKey` 和 `IsValidModifierMode` 校验 scope，再进入 Modifier 管线。

### <span style="color:#0ea5e9">4.11 玩法模块边界</span>

玩法模块不是核心地基的一部分，但必须声明自己如何接入核心。

当前已新增 `gameplay_module_registry.go`，用于登记应用层玩法模块边界。每个玩法模块至少应说明：

- 模块 ID 和名称。
- 自己拥有的状态或记录。
- 使用的 Repository 端口。
- 奖励发放入口。
- 会发布或依赖的事件类型。
- 会产出的标准奖励类型。
- 会调用的核心入口。
- 不允许绕过的边界规则。

当前已登记：

- `mail`：信函模块。拥有信函列表、阅读、删除、发送和附件领取规则；附件必须转换为标准 Reward，通过 `ApplyRewardsToStateWithContext` 发放；账号金币附件必须走信函 + 账号 + 玩家组合事务。
- `minigame`：万象幻境模块。拥有小游戏记录、库存和兑换规则；兑换产出必须转换为标准 Reward，通过 `ApplyRewardsToStateWithContext` 发放；跨阵营或不可识别产出不能绕过兵种注册表直接写入玩家兵力。

后续新增活动、副本、限时玩法时，优先注册玩法模块边界；如果它只产出已有长期资产，就通过奖励、事件、Modifier、建筑变更等核心入口接入；如果它需要新增核心从未支持的长期资产容器，必须先讨论核心是否不完整。

### <span style="color:#0ea5e9">4.12 Effect Pipeline</span>

Effect Pipeline 是玩法模块、武将特性、道具效果、建筑效果接入核心长期资产的统一提交规范。

当前分两层：

- `internal/core/effect`：稳定效果契约，只定义标准效果类型，不直接读写玩家存档。
- `internal/app/game/effect_pipeline.go`：应用层执行器，负责在玩家状态事务中执行效果，并复用奖励、建筑变更、Buff/Modifier、事件和资产快照入口。

当前标准效果类型：

- `reward`：标准奖励效果，内部复用 `ApplyRewardsToStateWithContext`。
- `building_mutation`：建筑状态/等级变更效果，内部复用 `applyBuildingMutation` 和建筑生命周期校验。
- `modifier`：Buff/DeBuff 效果，内部转换为标准 Buff 奖励，再进入 Modifier 管线。

当前已接入：

- 建筑变更：`MutateBuilding` 已改为提交 `building_mutation` 效果，通过 `Service.ExecuteEffects` 执行。
- 道具效果：`item_effects.go` 已把武将经验、资源、按阵营兵力等道具效果转换为 `reward` 效果。
- 活动/副本预留：新玩法可直接调用 `Service.ExecuteEffects(playerID, effects, ctx)`，不需要自己改玩家长期资产。

接入规则：

- 能表达为已有长期资产变更的内容，必须提交标准 Effect。
- Effect 执行器内部必须复用已有核心入口，不允许另写一套资源、兵力、道具、建筑或 Buff 变更逻辑。
- 如果玩法提出 Effect Pipeline 不能表达的新长期资产容器，必须先讨论核心地基是否不完整，再决定是否扩展核心。

## <span style="color:#0ea5e9">5. Repository 端口方向</span>

Repository 不应长期保持一个大接口，也不应暴露绕过核心事务的玩家状态写入口。

当前已拆为：

- `AccountRepository`：账号、账号金币、账号归属。
- `PlayerStateRepository`：玩家存档读取和统一状态事务。
- `AccountAssetRepository`：账号资产 + 玩家状态组合事务。
- `ReportRepository`：战报归档和未读状态。
- `MailRepository`：信函归档、已读状态、信函 + 玩家 + 账号组合事务。
- `MiniGameRecordRepository`：万象幻境历史、兑换记录、万象幻境记录 + 玩家组合事务。当前仍是历史命名，后续应随模块拆分改名。
- `GoldLedgerRepository`：金币/城金流水。

当前已移除的旧入口：

- `SaveState`：不再允许业务层直接覆盖玩家存档。
- `AddCityGold` / `DeductCityGold`：城金变更必须走玩家状态事务。
- 仓库层金币/城金兑换方法：兑换必须走账号资产事务。
- 仓库层信函领取/万象幻境兑换业务方法：模块规则必须在应用层编排，仓库只提供组合事务容器。

短期可以由同一个 Memory/MySQL 实现同时满足这些端口；长期再按存储边界细拆实现。

## <span style="color:#0ea5e9">6. 建设顺序</span>

第三阶段按低风险到高风险推进。当前进度：

1. 已完成 Repository 大接口拆为小端口组合。
2. 已完成玩家状态事务入口和账号资产事务入口。
3. 已移除业务层旧 `SaveState` 写入口。
4. 已让资源、建筑、兵力、道具、Buff、武将、货币、万象幻境鱼饵、NPC 战斗/侦查等动作接入统一事务。
5. 已新增标准奖励包和奖励发放接口。
6. 已让 GM 奖励、信函附件、万象幻境兑换等流程接入奖励应用、流水或事件。
7. 已补事件类型注册和进程内事件分发。
8. 已补奖励类型、事件类型和 Modifier 来源注册。
9. 已新增信函、万象幻境组合事务模型，避免模块记录状态和核心奖励发放分散在存储层。
10. 已将 Modifier 纯计算能力下沉到 `internal/core/modifier`，玩法层只保留具体加成来源收集。
11. 已将标准奖励契约下沉到 `internal/core/reward`，奖励应用仍由 `internal/app/game` 按玩家状态事务执行。
12. 已将事件结构和事件总线下沉到 `internal/core/event`，事件类型注册校验由游戏侧注入。
13. 已补齐核心资产事件发布：玩家创建、资源变化、建筑变化、兵力变化、道具使用、货币变化均能通过事件管线被监听。
14. 已将资源、奖励、事件的轻量注册中心下沉到 `internal/core/registry`，游戏侧只负责默认内容注册。
15. 已新增建筑生命周期核心：建筑标准状态、通用变更类型、状态校验和 `MutateBuilding` 统一入口。

下一步重点：

1. 继续审查 `internal/app/game` 中真正通用、稳定且不依赖存档模型的能力，逐步下沉到 `internal/core`。
2. 等数据库重设计时，把这些事务边界同步进 schema 和 migrations。

每一步必须保持：

- 测试通过。
- API 尽量兼容。
- 老存档可读。
- 文档同步。
- 玩法模块不绕过核心直接改长期资产。
