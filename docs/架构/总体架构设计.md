# <span style="color:#0ea5e9">Hero3 总体架构设计</span>

最后更新：2026-06-25
文档状态：active

## <span style="color:#0ea5e9">1. 架构目标</span>

Hero3 采用前后端分离、配置驱动、模块化后端的组织方式，目标是：

- 让核心玩法可独立演进。
- 让玩家端和 GM 后台共享同一套后端能力。
- 让战斗、将领、信函、货币等系统尽量解耦。
- 让存档数据可持续扩展，避免把所有规则写死在前端。

## <span style="color:#0ea5e9">2. 运行时分层</span>

```text
web/     玩家前端，负责交互、展示、局部状态管理
admin/   GM 后台，负责配置、运营、排查
go/      后端核心，负责业务规则、权限、存档、结算
docs/    设计、接口、部署、测试和维护规范
scripts/ 生成型工具脚本
```

## <span style="color:#0ea5e9">3. 后端边界</span>

后端当前按下面几层组织：

1. `internal/transport/api`：HTTP 路由、参数解析、权限校验、响应输出。
2. `internal/app/game`：账号、玩家存档、资源、建筑、军事、信函、小游戏、货币等应用服务与业务编排。
3. `internal/core/combat`：通用战斗计算，不直接依赖 HTTP 和数据库。
4. `internal/core/building`：建筑生命周期、标准状态和通用建筑变更类型。
5. `internal/core/general`：将领特性事件、上下文和特性注册。
6. `internal/core/modifier`：统一加成表达和数值计算公式。
7. `internal/core/event`：标准事件结构和进程内事件总线。
8. `internal/core/reward`：标准奖励类型和奖励发放上下文契约。
9. `internal/core/registry`：资源、奖励、事件等可扩展内容的轻量注册中心。
10. `internal/platform`：鉴权、运行时配置、HTTP Server 等技术平台能力。
11. `internal/infrastructure/storage`：MySQL 持久化实现。

## <span style="color:#0ea5e9">4. 关键原则</span>

- HTTP 输入输出放在 `internal/transport`。
- 业务编排优先放在 `internal/app/game`。
- 可复用领域能力优先沉淀到 `internal/core`。
- 数据库和外部设施实现放在 `internal/infrastructure`。
- HTTP handler 只做参数校验、鉴权、调用和返回。
- 纯计算逻辑不依赖数据库和 HTTP。
- 玩家状态以服务端为准，前端只做展示和交互。
- 配置变更优先走文件和 OpenAPI，再反映到代码。

## <span style="color:#0ea5e9">5. 数据流</span>

典型请求链路如下：

```text
前端发起请求 -> 鉴权中间件 -> Handler -> Game Service -> Repository -> MySQL
                                   -> 战斗/特性/结算模块
                                   -> 保存 state / report / mail / ledger
                                   -> 返回权威状态
```

## <span style="color:#0ea5e9">6. 当前演进方向</span>

后续要继续收敛成“一个核心系统 + 多个领域模块”：

- API 层已按领域拆文件，不再集中到单个 `handlers.go`。
- `internal/app/game` 后续再逐步拆出更清晰的核心资产接口和玩法模块入口。
- Repository 按账号、玩家状态、战报、信函、流水拆分。
- 玩家状态写入统一走事务入口，避免整包覆盖和局部更新并存。
- 核心地基建设参考 [核心地基设计](./核心地基设计.md)。
- OpenAPI、前端 API 封装、后端路由保持同源同步。
