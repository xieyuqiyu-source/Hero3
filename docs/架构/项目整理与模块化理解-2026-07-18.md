# Hero3 项目整理与模块化理解

最后更新：2026-07-18

## 1. 项目总体定位

Hero3 是一个三国题材策略网页游戏项目，当前采用前后端分离 + 模块化单体后端的方向。

项目不是微服务架构，也不应该在当前阶段拆成多个独立服务。它更适合继续按“稳定核心 + 可扩展玩法模块”的方式演进：一个 Go 后端负责权威规则、存档、事务、战斗、奖励和接口，多个前端站点和 GM 后台通过同一套 API 使用这些能力。

当前主要运行单元：

```text
Hero3/
├── go/          # Go 后端，负责权威业务规则、存档、结算、接口和配置
├── web/         # React 玩家前端，发布到 hero3.ccoos.cn
├── web-wlsg/    # 武林三国风格玩家前端，发布到 wlsg.ccoos.cn
├── admin/       # GM 后台，负责运营配置、公告、排查和管理
├── docs/        # 架构、产品、系统设计、接口、运维、测试等长期文档
├── helpdocs/    # 玩家帮助文档内容源
├── memory/      # 每日开发记忆
├── deploy/      # 服务器、nginx、systemd、journald 等部署配置
├── scripts/     # 本地工具脚本
└── 过时文档/     # 不再作为当前判断依据的历史资料
```

## 2. 后端分层整理

Go 后端的主方向是模块化单体，核心代码位于 `go/internal/`。

```text
go/internal/
├── transport/       # HTTP/API 输入输出层
├── app/             # 应用服务与业务编排
├── core/            # 可复用游戏核心能力
├── platform/        # 鉴权、配置、HTTP Server 等技术平台能力
└── infrastructure/  # MySQL 等基础设施实现
```

当前分层理解：

- `transport/api`：负责路由、参数解析、鉴权、错误映射、响应输出。它不应该承载复杂业务规则。
- `app/game`：当前最大的业务编排层，聚合玩家状态、建筑、资源、兵力、武将、物品、战报、信函、万象幻境、NPC、PVP、增援、黄巾起义、轮回绝境等应用逻辑。
- `core`：更接近真正可复用的“游戏核心地基”，包括战斗引擎、建筑生命周期、事件、奖励、Modifier、注册表、武将特性等。
- `infrastructure/storage`：负责 MySQL 读写、事务锁、表结构落点和持久化实现。
- `platform`：负责技术核心，如鉴权、运行配置和 HTTP Server。

当前后端的模块化已经超过“按文件随手拆分”的阶段，已经有明确层次和接口意识；但 `app/game` 仍然是一个大包，说明玩法模块还没有完全物理拆包，更多依赖同包内约定、注册表和仓储接口来维持边界。

## 3. 核心能力整理

按照 `PROJECT_RULES.md`，Hero3 的核心分为技术核心和游戏核心。

技术核心：

- 路由与 HTTP Server
- 统一响应和错误码
- 鉴权
- 配置加载
- 日志
- 数据库连接
- 事务
- OpenAPI

游戏核心：

- 玩家存档
- 资源
- 建筑
- 兵力
- 武将
- 道具
- 货币
- Buff/加成
- 时间结算
- 奖励发放
- 事件管线
- 通知、信函、战报接口
- 存档读写
- 通用战斗引擎

这些核心能力的共同特点是：它们属于玩家长期资产、长期状态或跨玩法复用的基础规则。新增玩法只应该通过标准入口读取、消耗、发放或监听这些能力，不应该直接绕过核心改玩家状态。

## 4. 玩法模块整理

当前已经比较明确的玩法模块包括：

- 信函：拥有信件、收件箱、阅读、删除、附件领取等状态和规则。
- 万象幻境：包含仙池垂钓、军营豪赌、天机轮转，拥有小游戏记录、库存和兑换规则。
- NPC 城池：拥有 NPC 状态、刷新、攻击、侦查、扫荡等规则。
- PVP：拥有行军、侦查、攻击、掠夺、赛季状态和跨玩家战斗结算。
- 增援：拥有增援批次生命周期、驻防展示、召回、遣返和加速。
- 黄巾起义：拥有黄巾势力、行军队列、触发检测和防守结算。
- 轮回绝境：拥有副本实例、波次、战斗记录、累计奖励和结束领奖。
- 物品/背包：介于核心资产和系统模块之间；物品资产属于核心，背包展示、配置维护、流水查询和玩法掉落接入属于系统能力。
- 战报：核心提供标准战报接口和契约，完整战报列表、详情、分享、GM 排查属于独立系统能力。
- 公告：属于运营系统模块，面向玩家展示和 GM 配置。

判断玩法模块的标准：

- 它有自己的开启条件、参与规则或结算规则。
- 它读取、消耗或锁定玩家资产。
- 它发放奖励、战报、信函、排行或模块状态。
- 它可以被单独开发、开关、替换或暂缓上线。

## 5. 当前模块化程度判断

我对当前项目模块化程度的判断是：中高程度的模块化单体，正在从“功能文件拆分”走向“核心接口驱动的玩法接入”。

已经做得比较好的部分：

- 后端大方向正确，`transport / app / core / infrastructure / platform` 分层清晰。
- `core` 已经沉淀出战斗、奖励、事件、Modifier、注册表、武将特性等可复用能力。
- 玩法模块已经开始登记边界，例如 `gameplay_module_registry.go` 明确列出模块状态归属、仓储端口、核心入口、奖励类型和边界规则。
- 奖励发放、事件发布、账号/玩家组合事务、信函/小游戏组合事务已经有统一入口，不再完全依靠每个玩法自己改状态。
- 配置化方向明显，兵种、物品、掉落池、战斗、武将、小游戏、副本、黄巾等都在往配置和 GM 可调方向走。
- OpenAPI 拆成 paths/schemas，前后端接口同步意识较强。
- 文档、记忆、项目规则三套体系已经建立，能支撑长期协作。

仍然偏弱的部分：

- `app/game` 仍是超大包，功能虽然按文件拆了，但物理包边界还不强。
- 很多玩法模块仍共享同一个 `Service`、同一个 `Repository` 聚合接口和同一批模型，模块之间的编译期隔离不够。
- 部分系统同时像核心又像模块，例如战报、信函、物品、背包，需要继续明确“核心端口”和“模块本体”的边界。
- 一些老功能仍可能通过 `GameState` 展示聚合模型进行读写，和“权威资产表 + 展示聚合”的最终方向还有距离。
- 前端 `web-wlsg` 已按玩法域拆目录，但跨域状态、API 类型和页面级组件仍需要继续收敛，避免玩法页面直接知道过多全局细节。
- 文档数量较多，部分阶段性文档已经完成使命，后续需要持续合并到主文档或归档，避免新开发时引用旧结论。

## 6. 当前最重要的边界

后续开发时，最重要的是守住下面几条边界。

第一，玩法模块不拥有玩家长期资产。

玩法可以拥有自己的过程状态，例如副本实例、波次、小游戏记录、行军队列、PVP 赛季状态；但资源、兵力、武将、道具、货币、Buff 等长期资产必须走核心事务和奖励入口。

第二，模块状态和长期资产要在同一事务边界内完成。

例如信函附件领取不能先把信函标记已领取，再单独发奖励；万象幻境兑换不能先扣库存，再另起事务发兵；PVP、增援和黄巾涉及多玩家或多记录时，也必须用专门组合事务承接。

第三，核心应该提供能力，不应该理解所有玩法细节。

核心可以知道“发放奖励”“扣兵”“战斗结算”“发布事件”“写流水”，但不应该把轮回绝境第几波、黄巾触发规则、天机轮转图案权重等玩法细节硬塞进核心。

第四，可扩展内容优先配置化或注册化。

新增资源、兵种、道具、武将、Buff key、奖励类型和事件类型时，应优先通过配置、注册表和标准接口接入，不应修改核心流程来硬编码。

## 7. 后续整理建议

短期建议：

- 保持当前模块化单体，不拆微服务。
- 新增玩法先补模块边界声明，写清楚状态归属、核心入口、奖励类型和事件类型。
- 继续把所有长期资产变更压到标准事务、奖励和事件入口。
- 新接口同步维护 OpenAPI、README 和对应系统设计文档。
- 定期清理阶段性设计文档，把已落地结论合并进 `总体架构设计`、`核心地基设计`、`数据库设计` 或对应系统主文档。

中期建议：

- 从 `app/game` 中逐步抽出更明确的模块包或子服务，例如 `mail`、`minigame`、`reincarnation`、`pvp`、`reinforcement` 等。
- 把 `GameState` 进一步降级为展示聚合模型，让权威资产表和专用事务入口成为真实写入中心。
- 为玩法模块建立统一接入模板：模块状态表、仓储端口、事务入口、奖励接入、事件接入、OpenAPI、前端页面、GM 后台能力。
- 继续治理战报、背包、资产事务的高并发写入，避免玩法越多，锁竞争越重。

长期判断：

Hero3 的方向不应该是“一个玩法一个服务”，而应该是“一个稳定游戏核心，多个清晰边界的玩法模块”。只要核心接口足够稳定、资产事务足够统一、模块状态归属足够清楚，这个架构可以支撑相当长一段时间的玩法扩展。
