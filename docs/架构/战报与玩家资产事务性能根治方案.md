# <span style="color:#0ea5e9">Hero3 战报与玩家资产事务性能根治方案</span>

最后更新：2026-06-30

## <span style="color:#0ea5e9">1. 文档目的</span>

本文档用于明确 Hero3 后续解决以下线上问题的最终方案：

- 战报表三天内增长到数万条，影响启动迁移、查询、备份和长期运维。
- NPC 扫荡、道具使用、奖励发放等高频操作出现 MySQL 死锁。
- 数据库中可见多个 `SELECT ... FOR UPDATE`、`DELETE FROM player_inventory` 等事务排队。
- 玩家端在高频操作时出现卡顿、请求失败或需要依赖重试兜底。

本文档不是临时止血方案。目标是从数据生命周期、写入量、事务边界和资产模型四个层面根治问题，提高游戏速度和稳定性。

## <span style="color:#0ea5e9">2. 当前结论</span>

当前架构方向总体正确：

- 模块化单体适合当前项目体量。
- 玩家长期资产拆分为权威表是正确方向。
- 资源、背包、建筑、兵力、武将、Buff 等资产必须由核心统一管理。
- `players.state_json` 降级为兼容快照是正确方向。

当前问题不在于“是否应该模块化单体”，而在于实现还处于过渡态：

- 业务写入仍大量围绕完整 `GameState` 聚合模型。
- 一个小操作会锁玩家主行并加载多类资产表。
- 背包同步仍有全量同步和删除旧格子的逻辑。
- 高频 NPC 扫荡按每场战斗写完整战报。
- 战报只有查询三天过滤，没有物理清理。

一句话结论：

```text
核心架构方向对，但当前事务颗粒度太粗、战报生命周期缺失、扫荡写入放大过高，需要按资产命令化和数据清理体系继续收敛。
```

## <span style="color:#0ea5e9">3. 线上现象复盘</span>

### <span style="color:#0ea5e9">3.1 战报数据量</span>

线上只读统计显示：

```text
battle_reports 总数: 76,930
三天内: 76,930
软删除: 41,644

2026-06-30: 12,149
2026-06-29: 19,365
2026-06-28: 45,416

前三个玩家战报量:
28,986
26,340
21,276

battle_events: 73,057
battle_report_states: 73,066
battle_report_participants: 146,132
```

这说明三天窗口内也可能出现几万条战报。原因不是数据库异常，而是高频扫荡真实产生了大量战斗记录。

### <span style="color:#0ea5e9">3.2 三天保存的真实含义</span>

当前代码中的三天限制主要体现在查询：

```text
ListReports / ListReportsByQuery / CountUnreadReports
按 created_at > now - 3d 过滤。
```

玩家删除战报时只是软删除：

```text
deleted_by_player = 1
```

当前没有持续运行的物理清理任务。因此：

- 三天前的数据不会自动从表中删除。
- 玩家删除后的数据仍留在表中。
- `battle_events`、`battle_report_states`、`battle_report_participants` 也会继续增长。
- 启动迁移、备份、索引维护和查询统计都会受历史数据量影响。

### <span style="color:#0ea5e9">3.3 事务排队的原因</span>

数据库中出现多个 `SELECT ... FOR UPDATE` 排队是正常锁语义，不是 MySQL 本身异常。

`FOR UPDATE` 会等待前一个事务提交。同一玩家高频操作时，多个请求会竞争同一批玩家资产锁。

当前高频链路包括：

- NPC 攻击。
- NPC 扫荡。
- 使用经验包。
- 领取奖励。
- 信函领奖。
- 掉落入背包。
- 武将经验增长。

这些链路会涉及：

- `players` 主行。
- `player_resources`。
- `player_inventory`。
- `player_army_units`。
- `player_generals`。
- `player_buffs`。
- `battle_reports` 及相关战报表。
- 物品流水、奖励流水、事件记录。

当前问题的关键是：

```text
一次业务操作锁得太多，锁持有时间太长，高频请求叠加后自然排队。
```

### <span style="color:#0ea5e9">3.4 死锁的根本来源</span>

死锁不是因为有锁，而是因为多个事务以不同顺序争抢多张表或多批记录。

典型场景：

```text
事务 A: NPC 攻击
锁 players -> 锁 player_inventory -> 锁 player_generals -> 写战报

事务 B: 使用经验包
锁 players -> 锁 player_inventory -> 锁 player_generals

事务 C: 奖励发放
锁 players -> 锁 player_resources -> 锁 player_inventory
```

如果某些链路的锁顺序不完全一致，或某一步使用全量删除：

```sql
DELETE FROM player_inventory
WHERE player_id = ?
  AND slot_id NOT IN (...)
```

就更容易放大锁范围，形成等待环。

### <span style="color:#0ea5e9">3.5 当前临时修复的定位</span>

当前已经做过的短期修复：

- NPC 攻击事务遇到死锁时短重试。
- 道具使用事务遇到死锁时短重试。
- 同一玩家 NPC 攻击进入 `playerLocks` 串行，减少同玩家并发写。

这些是必要止血，但不是根治。

原因：

- 重试只能降低用户看到错误的概率。
- 玩家锁只能让单进程内同一玩家串行，无法解决所有事务范围过宽问题。
- 如果后续多实例部署，进程内玩家锁不能跨实例生效。
- 战报数据量和背包全量同步仍然存在。

## <span style="color:#0ea5e9">4. 最终目标</span>

### <span style="color:#0ea5e9">4.1 性能目标</span>

- 高频扫荡不再制造成千上万条完整战报。
- 普通玩家操作不因战报表膨胀变慢。
- 使用道具、NPC 攻击、领奖等操作只锁必要资产。
- 同一玩家操作允许短暂排队，但单次事务足够短。
- 不同玩家之间应尽量并行，不互相拖慢。
- 线上不会因为启动迁移、清理任务或查询统计扫大表导致服务不可用。

### <span style="color:#0ea5e9">4.2 数据目标</span>

- 玩家可见战报按规则保留。
- 软删除战报能被物理清理。
- 过期战报相关表能被级联清理。
- 战报事件和参与方快照不会无限增长。
- 高频战斗记录可以聚合、归档或降级保存。

### <span style="color:#0ea5e9">4.3 架构目标</span>

- `GameState` 继续降级为展示聚合模型。
- 写操作不再默认使用完整玩家状态作为事务单位。
- 资产变更通过资产命令和 Effect Pipeline 统一进入核心。
- 背包、武将、资源、兵力等资产支持小事务、增量写入。
- 战报从主事务负担中尽量拆出去，成为可清理、可降级的旁路数据。

## <span style="color:#0ea5e9">5. 总体执行顺序</span>

后续必须按以下顺序推进：

```text
第一步：战报物理清理与保留策略
第二步：限制战报产生量，高频扫荡合并战报
第三步：重构玩家资产事务，收窄锁范围
```

这个顺序不能反过来。

原因：

- 先清理战报，能最快降低表体量和运维风险。
- 再减少战报生成，防止清理后继续暴涨。
- 最后重构资产事务，改动最大，需要在数据量和写入量稳定后进行。

## <span style="color:#0ea5e9">6. 阶段一：战报物理清理与保留策略</span>

### <span style="color:#0ea5e9">6.1 目标</span>

让“三天保存”从查询过滤变成真实的数据生命周期。

最终效果：

- 玩家列表只看三天内战报。
- 三天外战报会被物理清理或归档。
- 玩家已删除战报会更早清理。
- 相关状态表、参与方表、分享链接、事件表同步清理。
- 清理过程分批执行，不锁大表、不影响在线服务。

### <span style="color:#0ea5e9">6.2 保留规则建议</span>

基础规则：

| 数据类型 | 玩家可见 | 物理保留 | 说明 |
| --- | --- | --- | --- |
| 普通 NPC 战报 | 3 天 | 3 天 | 高频数据，不长期保存 |
| NPC 扫荡聚合战报 | 3 天 | 3 天 | 第二阶段上线后作为主记录 |
| PVP 战报 | 3 天 | 7 天 | 后续可按赛季扩展 |
| 防守/被打战报 | 3 天 | 7 天 | 玩家排查需要稍长 |
| 分享战报 | 分享有效期内 | 分享过期后清理 | 分享链接存在时不能提前删 |
| 已删除战报 | 不可见 | 1 小时或 24 小时 | 给误删恢复留极短窗口，可配置 |
| Admin 审计事件 | 不给玩家展示 | 7 到 30 天 | 可单独归档，不放玩家战报主表 |

如果不做归档，建议第一版全部物理删除，先控制体量。

### <span style="color:#0ea5e9">6.3 清理范围</span>

需要一起处理的表：

- `battle_report_links`
- `battle_report_states`
- `battle_report_participants`
- `battle_reports`
- `battle_events`

清理顺序：

```text
1. 找出待清理 report_id 和 event_id
2. 删除 battle_report_links
3. 删除 battle_report_states
4. 删除 battle_report_participants
5. 删除 battle_reports
6. 删除已经没有 report 引用的 battle_events
```

注意：

- `battle_events` 可能对应多份视角战报，不能直接按时间盲删。
- 需要先确认该 event 下所有 report 都已被清理。
- 分享链接未过期的 report 不能清理，除非产品确认分享随战报过期失效。

### <span style="color:#0ea5e9">6.4 清理实现方式</span>

第一版建议实现 `dbtool` 子命令：

```text
go run ./cmd/dbtool cleanup-battle-reports --dry-run
go run ./cmd/dbtool cleanup-battle-reports --batch-size 500
```

能力：

- `--dry-run` 只统计不删除。
- `--batch-size` 控制每批删除条数。
- `--retention-hours` 控制普通/NPC/扫荡战报保留时间，默认 72 小时。
- `--pvp-retention-hours` 控制玩家城池/PVP 来源战报保留时间，默认 168 小时。
- `--defense-retention-hours` 控制防守/被打视角战报保留时间，默认 168 小时。
- `--scout-retention-hours` 控制侦查战报保留时间，默认 168 小时。
- `--deleted-retention-hours` 控制软删除保留时间。
- `--max-batches` 控制单次最多执行多少批。
- 输出每张表删除数量。

线上执行建议：

- 先 dry-run。
- 再低峰执行小批量。
- 观察 MySQL processlist、慢查询、API 延迟。
- 稳定后加入定时任务。

### <span style="color:#0ea5e9">6.5 定时任务方式</span>

第一版可用 systemd timer 或 cron：

```text
每 10 分钟执行一次，每次最多清理 500 到 2000 条。
```

不要在后端 API 请求中触发清理。

不要在服务启动迁移中执行大清理。

### <span style="color:#0ea5e9">6.6 数据库索引要求</span>

需要确认或补齐以下索引：

```sql
battle_reports(player_id, deleted_by_player, created_at)
battle_reports(created_at)
battle_reports(event_id)
battle_reports(deleted_by_player, created_at)
battle_report_states(report_id, player_id)
battle_report_participants(report_id)
battle_report_participants(event_id)
battle_report_links(report_id)
battle_events(id, occurred_at)
```

如果线上已有部分索引，迁移只补缺失项。

索引新增必须走单独迁移方案，不能在启动路径里无条件执行大表变更。

2026-06-30 已补齐第一版索引工具：

- 新库建表会包含战报清理专用索引。
- 已新增 `dbtool ensure-report-cleanup-indexes`，默认 dry-run 检查缺失索引。
- 正式创建缺失索引必须显式执行 `--execute --allow-non-test`，建议低峰操作。
- `cleanup-battle-reports` 执行前会预检这些索引；缺失时直接失败，避免清理任务在大表上无索引扫描。
- 已新增 `dbtool maintenance-status` 只读巡检命令，统一汇总战报统计、清理索引、可清理候选量和权威表健康状态；缺索引时会跳过候选量统计并返回异常。
- 当前检查的清理专用索引包含：

```sql
battle_reports(created_at, id)
battle_reports(deleted_by_player, created_at, id)
battle_reports(player_id, deleted_by_player, created_at)
battle_reports(event_id)
battle_reports(source_type, target_id, created_at)
battle_reports(source_type, view_type, battle_type, created_at)
battle_reports(player_id, view_type, deleted_by_player, created_at, id)
battle_report_links(report_id)
battle_report_states(report_id, player_id)
battle_report_states(report_id, is_deleted, deleted_at)
battle_report_participants(report_id)
battle_report_participants(event_id)
battle_events(occurred_at)
```

### <span style="color:#0ea5e9">6.7 阶段一验收</span>

验收标准：

- dry-run 能正确输出待清理数量。
- 正式清理不会影响线上健康检查。
- 清理后 `battle_reports` 数量稳定在预期范围。
- `battle_report_states`、`battle_report_participants` 不再无限增长。
- 玩家战报列表、未读数量、分享链接行为符合规则。
- 清理脚本可以重复执行，失败后可继续。

## <span style="color:#0ea5e9">7. 阶段二：限制战报产生量</span>

### <span style="color:#0ea5e9">7.1 目标</span>

从源头减少战报写入。

最终效果：

- 手动单次战斗仍有完整战报。
- 扫荡不再每一场都写一条完整战报。
- 高频 NPC 战斗可合并为一条扫荡汇总战报。
- 只有关键事件额外生成完整战报。

### <span style="color:#0ea5e9">7.2 当前写入放大</span>

一场完整战斗可能写入：

```text
battle_reports                 1 条或多视角多条
battle_events                  1 条
battle_report_states           1 条或多条
battle_report_participants     2 条或更多
item_ledger                    掉落时写
gold_ledger                    资源/金币相关时写
players / 权威资产表            多张
```

NPC 扫荡如果连续打 100 场，就会把这个写入放大 100 倍。

### <span style="color:#0ea5e9">7.3 扫荡战报模型</span>

新增或复用战报类型：

```text
source_type = npc_city
battle_type = sweep
view_type = attack
```

扫荡汇总战报保存：

- 扫荡次数。
- 成功次数。
- 失败次数。
- 总出兵。
- 总损失。
- 总击杀。
- 总获得资源。
- 总掉落物。
- 武将总经验。
- 武将升级情况。
- 特殊触发记录。
- 失败场次摘要。

前端展示一条扫荡战报，而不是 N 条普通战报。

### <span style="color:#0ea5e9">7.4 哪些情况仍需完整战报</span>

建议保留完整战报的情况：

- 手动单次攻击。
- PVP 战斗。
- 被打、防守、侦查。
- 战败。
- 武将升级。
- 掉落稀有物品。
- 触发重要特性。
- 系统判定异常或需要排查的战斗。

普通扫荡成功且无特殊结果时，只进入扫荡汇总。

### <span style="color:#0ea5e9">7.5 玩家战报数量上限</span>

在三天保留之外增加玩家维度硬上限：

```text
每个玩家每类 view_type 最多保留 500 到 1000 条可见战报。
```

超过上限：

- 优先软删除最旧可见战报。
- 后台清理再物理删除。

这个上限是防止短时间单玩家刷出几万条的最后保护。

### <span style="color:#0ea5e9">7.6 战报写入异步化边界</span>

长期可以考虑把战报写入改为异步事件，但第一版不建议直接上异步队列。

原因：

- 当前项目仍是模块化单体。
- 战报和奖励、武将经验有强展示关联。
- 先合并战报和物理清理收益更大。

第一版保持事务内写必要战报，但减少写入条数。

后续如果需要异步：

```text
战斗事务提交 -> 写 battle_report_jobs 或事件 -> 后台 worker 生成战报
```

异步化必须保证：

- 战斗结果和奖励已经落库。
- 战报生成失败可重试。
- 玩家不会因为战报失败丢失资产。

### <span style="color:#0ea5e9">7.7 阶段二验收</span>

验收标准：

- 扫荡 100 场不再产生 100 条普通战报。
- 玩家能看到扫荡汇总。
- 掉落、武将经验、损耗、奖励汇总准确。
- 稀有事件仍有明确记录。
- `battle_reports` 每日增长明显下降。
- 前端战报页加载速度提升。

### <span style="color:#0ea5e9">7.8 第一版落地状态</span>

2026-06-30 已落地阶段二第一版：

- 后端新增 `POST /api/v1/map/npc-cities/sweep`。
- 前端 NPC 城池页扫荡按钮改为一次调用扫荡接口，不再在浏览器内循环调用 `/attack`。
- 普通 `AttackNpc` 行为保持不变，手动单次攻击仍写完整单场战报。
- 扫荡内部复用单场 NPC 战斗结算，但不保存每场普通战报。
- 扫荡完成后统一生成一条聚合战报：

```text
source_type = npc_city
battle_type = sweep
view_type = attack
```

- 聚合战报汇总出兵、损失、击杀、资源、掉落、城金、武将经验、等级变化、特性触发。
- 扫荡内部奖励和掉落仍真实发放，并保留奖励/道具流水。
- 扫荡内部不再发布每场奖励事件，改由最终聚合战报统一发布奖励事件和战斗完成事件。
- 增加后端回归测试，确认扫荡两个 NPC 只产生一条 `battle_type=sweep` 战报，且不产生两条普通 `attack` 战报。
- 新增只读 `dbtool report-stats`，用于统计战报总量、最近 N 天增长、软删除量、有效分享量、每日分布、战报类型和玩家 Top。
- 新增只读 `dbtool lock-snapshot`，用于采集当前 MySQL 活跃连接、InnoDB 事务和 `performance_schema` 锁等待关系。

## <span style="color:#0ea5e9">8. 阶段三：重构玩家资产事务</span>

### <span style="color:#0ea5e9">8.1 目标</span>

把玩家资产写入从“大事务聚合写”改为“小事务资产命令写”。

最终效果：

- 用一个经验包只锁背包对应物品和目标武将。
- NPC 战斗只锁战斗必要资产。
- 奖励发放只锁奖励影响的资产。
- 背包不再全量同步删除。
- `players.state_json` 不再参与高频资产写入。

### <span style="color:#0ea5e9">8.2 当前不合理事务</span>

当前 `UpdateItemState` 名义上是道具事务，但实际加载范围较大：

- 玩家主行。
- 资源。
- 背包。
- 建筑。
- 资源田。
- 军队。
- 征兵队列。
- 武将。
- 武将占用。
- Buff。

经验包实际只需要：

- 背包。
- 武将。
- 可能需要玩家基础信息用于返回。

不应该锁建筑、资源田、军队、征兵队列。

### <span style="color:#0ea5e9">8.3 资产命令原则</span>

每个写命令必须明确：

- 要读哪些表。
- 要锁哪些行。
- 要写哪些表。
- 锁顺序是什么。
- 是否需要事务内写流水。
- 是否需要事务后发布事件。

禁止默认加载完整 `GameState` 作为写入前提。

### <span style="color:#0ea5e9">8.4 标准锁顺序</span>

为避免死锁，所有多资产事务必须遵守固定锁顺序。

建议顺序：

```text
1. accounts
2. players
3. player_resources
4. player_inventory
5. player_army_units
6. player_recruit_queues
7. player_generals
8. player_general_assignments
9. player_buffs
10. 玩法实例表
11. 战报和流水表
```

更理想的方向：

- 不需要的资产不锁。
- 能通过单表原子更新解决的，不锁玩家主行。
- 只在需要校验玩家归属或版本时读 `players`。

### <span style="color:#0ea5e9">8.5 背包增量写入</span>

当前全量同步背包的问题：

```sql
DELETE FROM player_inventory
WHERE player_id = ?
  AND slot_id NOT IN (...)
```

这个语句容易扩大锁范围。

目标改造：

```text
InventoryRepository.AddItem(playerID, itemID, amount)
InventoryRepository.ConsumeItem(playerID, itemID, amount)
InventoryRepository.MoveSlot(playerID, fromSlot, toSlot)
InventoryRepository.DeleteEmptySlot(playerID, slotID)
```

使用道具时：

```text
1. 锁定该玩家该 item 的可消耗格子。
2. 扣数量。
3. 数量为 0 时删除对应 slot。
4. 不扫描和删除整个背包。
```

获得道具时：

```text
1. 找可堆叠格子。
2. 只更新可堆叠格子。
3. 不够时插入新格子。
4. 不触碰无关物品。
```

### <span style="color:#0ea5e9">8.6 经验包事务目标</span>

使用将领经验包最终事务：

```text
BEGIN
  SELECT target inventory rows FOR UPDATE
  SELECT target general row FOR UPDATE
  UPDATE player_inventory ...
  UPDATE player_generals ...
  INSERT item_ledger ...
COMMIT
```

不应锁：

- 建筑。
- 资源田。
- 兵力。
- 征兵队列。
- 全部 Buff。
- 全部背包。

2026-06-30 已完成经验包从通用 `UpdateItemState` 分流到 `UpdateGeneralExpItemState`，并继续收窄到目标物品和当前主将：

- 事务内只锁定 `player_inventory(player_id, item_id)` 命中的目标物品格子。
- 事务内只锁定当前主将占用行和当前主将 `player_generals(player_id, general_id)` 行。
- 不再加载资源、兵力、建筑、资源田、征兵队列和 Buff。
- 不再更新 `players.state_json`，避免使用经验包时锁玩家主行。
- 提交后再非锁定读取完整背包和武将名册返回前端，避免把局部背包误当完整状态覆盖。
- 新增 `idx_player_inventory_player_item (player_id, item_id)`，保证目标物品格子查询有稳定索引路径。

### <span style="color:#0ea5e9">8.7 NPC 战斗事务目标</span>

NPC 战斗最终事务：

```text
BEGIN
  锁定玩家资源行
  锁定参战兵力行
  锁定参战武将行
  锁定必要 Buff 行
  更新资源、兵力、武将经验
  写必要奖励和掉落
  写一条战报或扫荡汇总
COMMIT
```

不应在每场普通 NPC 战斗中：

- 全量加载背包。
- 全量同步建筑。
- 全量同步资源田。
- 全量同步征兵队列。
- 写大量独立战报。

### <span style="color:#0ea5e9">8.8 奖励发放事务目标</span>

Reward Pipeline 应先按奖励类型拆分资产影响：

| 奖励类型 | 需要锁的资产 |
| --- | --- |
| 资源 | `player_resources` |
| 道具 | `player_inventory` |
| 兵力 | `player_army_units` |
| 武将经验 | `player_generals` |
| Buff | `player_buffs` |
| 城金 | `player_currencies` |
| 账号金币 | `accounts` |

混合奖励可以在同一事务中执行，但必须按标准锁顺序。

### <span style="color:#0ea5e9">8.9 去除高频 state_json 写回</span>

高频写操作不应每次重写 `players.state_json`。

`state_json` 只保留：

- 玩家基础兼容字段。
- 非高频、小体积兼容字段。
- 后续可以通过后台快照定期刷新。

高频资产以权威表为准：

- 资源看 `player_resources`。
- 背包看 `player_inventory`。
- 武将看 `player_generals`。
- 兵力看 `player_army_units`。
- NPC 城池状态看 `player_npc_states`。
- 城金和兑换冷却看 `player_currencies`。

2026-06-30 已继续拆出 NPC 状态权威表：

- 新增 `player_npc_states`，一名玩家一份 NPC 城池状态 JSON。
- 新建玩家会同步初始化 NPC 状态权威表。
- 旧玩家兼容：如果新表没有数据，读取时仍使用旧 `state_json.npcState`；进入写事务后会把旧快照回填到权威表。
- 新的 `players.state_json` 不再写入 `npcState` 和 `serverTime`。
- `UpdateCombatState` 读取 `players.state_json` 不再使用 `FOR UPDATE`，NPC 战斗只锁定 `player_npc_states` 和本次涉及的资产权威表；只有城金等仍保留在轻量快照内的字段变化时，才会更新 `players` 主行。
- 已补 MySQL 集成测试，验证 NPC 战斗更新 NPC 状态时不会刷新 `players.state_json / updated_at`，并且 `GetState` 会从 NPC 权威表覆盖返回。
- `GetNpcCities` 和 `RefreshNpcCities` 已迁移到 `UpdateNpcState` 专用事务，自动刷新、惰性结算和手动刷新都只锁定并写回 `player_npc_states`，不再通过 `UpdatePlayerMetaState` 锁 `players` 主行。
- 已补 MySQL 集成测试，验证服务层获取 NPC 城池会生成并保存 NPC 权威表，但不会刷新 `players.state_json / updated_at`。

2026-06-30 已继续拆出玩家城金权威表：

### <span style="color:#0ea5e9">8.10 事务后事件</span>

事务内只做必须一致的数据写入。

事务外做：

- WebSocket 或 SSE 推送。
- 日志。
- 非关键统计。
- 可重试的异步战报补充。
- 缓存刷新。

这样可以缩短锁持有时间。

### <span style="color:#0ea5e9">8.11 阶段三验收</span>

验收标准：

- 使用经验包不再查询和锁定建筑、军队、征兵队列。
- NPC 攻击不再同步完整背包和完整玩家快照。
- `DELETE FROM player_inventory ... NOT IN` 从高频路径移除。
- 同一玩家扫荡时事务排队时间下降。
- MySQL processlist 不再长期出现大量同玩家 `FOR UPDATE` 等待。
- 压测下死锁次数显著下降。

- NPC 城池自动刷新、手动刷新和惰性结算已改走 `UpdateNpcState`，不再通过 `UpdatePlayerMetaState` 锁定 `players` 主行。
- 已新增 `dbtool backfill-npc-states` / `verify-npc-states`，用于把旧 `state_json.npcState` 提前迁到 `player_npc_states`；回填按小批次提交，只补缺失行，不覆盖线上已更新的 NPC 状态。
- 城金和兑换冷却已从 `players.state_json` 拆到 `player_currencies`；NPC 战斗溢出城金、城金奖励和城金消费不会因为货币变化刷新 `players` 主行。
- 高频奖励事务不再对 `players` 主行加 `FOR UPDATE`，只锁定奖励涉及的权威表；纯城金奖励只触碰 `player_currencies`。
- 奖励作用域已增加玩家货币边界：纯资源、纯道具、纯兵力或纯武将奖励不会再默认锁定 `player_currencies`，只有城金奖励、扣城金和金币/城金兑换等货币路径才锁定并写回货币权威表。
- `clone-data` 已把玩家货币和旧 NPC 状态纳入自动回填/校验链，`healthcheck-authority` 已检查 `player_currencies` 覆盖、旧 NPC 快照承接，以及 `players.state_json` 是否仍残留 `cityGold`、`lastExchangeAt`、`npcState`、`serverTime` 等大字段。
- 使用经验包返回的前端 patch 不再携带资源、军队、Buff 和加成快照，背包/武将数据来自提交后的非锁定完整读取，避免用局部事务状态覆盖前端完整背包。
- 已补 MySQL 集成测试，验证经验包小事务会扣目标背包格子并更新当前主将经验，不会删除无关物品、不会删除或改写无关武将，也不会写回回调里被改动的资源和兵力。
- 通用 `UseItem` 已按道具效果推导 `RewardAssetScope`，把被消耗道具、奖励道具、资源、目标兵种、当前武将和 Buff 放进明确作用域，不再从应用层直接调用全量 `UpdateItemState`。
- 资源包等普通道具使用只写回作用域内背包格子和对应奖励资产，无关物品不会被刷新 `updated_at`。
- scoped 奖励事务提交后会非锁定读取货币权威表补齐返回视图；不需要写城金的事务不会为了返回字段而持有 `player_currencies` 行锁。
- 已新增应用层静态防回退测试，禁止服务代码重新直接调用旧全量 `UpdateItemState` / `UpdateRewardState` / `UpdateAccountRewardState`，后续新增高频玩法必须走 scoped 资产事务。

后续仍需继续：

- 线上观察 `DELETE FROM player_inventory` 和同玩家 `FOR UPDATE` 等待是否明显下降。
- 使用 `dbtool lock-snapshot --min-seconds 1 --limit 30` 在高峰期采集锁等待，确认排队事务是否仍集中在 `player_inventory`、`player_army_units` 或 `battle_reports`。

## <span style="color:#0ea5e9">12. 最终验收标准</span>

整体根治完成后，应达到：

- 三天内战报数量不会因少数玩家扫荡涨到不可控规模。
- 软删除和过期战报能自动物理清理。
- 扫荡 100 场只产生少量汇总战报。
- 经验包使用不再依赖完整玩家资产事务。
- NPC 高频战斗不会持续制造同玩家长时间锁等待。
- 高峰期死锁不再成为常见用户错误。
- 普通读取和战报列表加载速度明显提升。
- 后续新玩法接入时有明确事务边界和战报写入规范。

## <span style="color:#0ea5e9">13. 审核建议</span>

建议先确认以下产品规则，再开始开发：

1. 普通 NPC 战报物理保留时间是否就是 3 天。
2. 已删除战报是否允许 1 小时或 24 小时后物理删除。
3. PVP、防守、侦查战报是否需要比 NPC 更长保留。
4. 分享战报过期规则。
5. NPC 扫荡是否接受一条汇总战报替代多条单场战报。
6. 稀有掉落、武将升级、战败是否必须单独生成完整战报。
7. 每个玩家每类战报最大可见数量。

确认后即可按本文档三阶段拆任务开发。
