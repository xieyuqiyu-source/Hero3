# <span style="color:#0ea5e9">Hero3 玩家状态读写模型规范</span>

最后更新：2026-06-26

## <span style="color:#0ea5e9">1. 文档目的</span>

本文档用于明确 Hero3 后续玩家状态读写的规范方向。

当前项目已经拆出了资源、背包、建筑、资源田、兵力、征兵队列、武将、武将占用和 Buff 等权威表，但应用层仍有大量业务围绕完整 `GameState` 读写。这个模式在开发早期方便，但继续扩大后会带来几个问题：

- 普通读取容易变成带锁事务。
- 修改一个资产也要加载完整玩家状态。
- `GameState` 同时承担展示模型、写入模型、兼容快照和修复入口，职责过重。
- 权威表已经存在，但应用服务仍以整包玩家状态为中心，架构不够规范。
- 高频业务难以按资产粒度优化，也难以清晰审计每类资产变更。

后续目标是把 `GameState` 从“业务读写中心”降级为“展示聚合模型”，让玩家长期资产通过标准资产服务、资产仓储、小事务、Reward 和 Effect Pipeline 进行变更。

## <span style="color:#0ea5e9">2. 核心结论</span>

后续开发必须遵循一句话：

```text
GameState 只作为展示聚合结果和兼容返回，不再作为所有业务的读写中心。
```

也就是说：

- 查询接口可以组装 `GameState` 或局部视图给前端展示。
- 写操作不应默认读取完整 `GameState` 再修改一小块。
- 长期资产的权威判断应落在对应资产表和资产服务上。
- 玩法模块仍必须通过核心标准入口修改长期资产，不能直接绕过核心写表。

## <span style="color:#0ea5e9">3. 当前不规范点</span>

### <span style="color:#0ea5e9">3.1 普通状态读取承担了写事务责任</span>

当前 `Service.GetState` 会调用 `UpdatePlayerState`。这会导致普通 `GET /api/v1/game/state` 进入玩家状态事务，可能触发：

- `SELECT players ... FOR UPDATE`
- 权威表加载
- 资源结算
- 核心建筑补齐
- 建造司资源田补齐
- 默认武将补齐
- 武将列表补齐
- 兼容快照写回

这不符合读写职责分离。状态读取应该只读取、投影和返回，不应该负责修复或写回玩家长期资产。

### <span style="color:#0ea5e9">3.2 写业务仍以完整状态为事务单位</span>

建筑升级、征兵、资源补满、道具使用、奖励发放等业务当前大量使用 `UpdatePlayerState`。这会让一个小操作加载完整玩家状态，再根据变化同步多类权威表。

更规范的方式是：

- 建筑升级只关心资源、建筑、资源田和必要 Modifier。
- 征兵只关心资源、征兵队列、兵种配置和必要 Modifier。
- 道具使用只关心背包和道具效果影响到的资产。
- 信函领奖只关心信函、账号资产和奖励影响到的资产。
- 小游戏兑换只关心小游戏记录和实际发放的资产。

### <span style="color:#0ea5e9">3.3 修复逻辑和展示逻辑混在一起</span>

旧存档兼容、缺失核心建筑补齐、资源田补齐、默认武将补齐都属于修复或初始化职责，不应长期放在普通查询请求中。

修复逻辑应归口到：

- 创建玩家流程。
- 登录后一次性轻量修复。
- 后台维护入口。
- 数据库回填工具。
- 专门的 repair 命令或 repair API。

## <span style="color:#0ea5e9">4. 目标架构</span>

### <span style="color:#0ea5e9">4.1 读模型</span>

读模型只负责给前端、Admin 和接口调用方展示当前状态。

读模型特点：

- 不使用 `FOR UPDATE`。
- 不修改 `players.state_json`。
- 不同步权威表。
- 不修复长期资产。
- 可以进行内存中的展示投影。
- 可以返回完整 `GameState`，也可以返回局部视图。

推荐命名：

- `PlayerViewService`
- `PlayerStateView`
- `CityView`
- `MilitaryView`
- `InventoryView`
- `GeneralsView`
- `ResourceView`

典型链路：

```text
Handler -> Query Service -> View Repository -> 权威表只读查询 -> 内存投影 -> 返回
```

### <span style="color:#0ea5e9">4.2 写模型</span>

写模型只负责执行业务命令和长期资产变更。

写模型特点：

- 每个命令只锁定必要资产。
- 每个命令只读取必要表。
- 长期资产变更必须通过核心资产服务或标准 Effect。
- 事务边界按业务命令和资产范围定义。
- 写操作完成后可以返回局部结果或重新组装视图，但不能把完整 `GameState` 当作内部唯一状态源。

推荐命名：

- `ResourceAssetService`
- `BuildingAssetService`
- `RecruitAssetService`
- `ArmyAssetService`
- `InventoryAssetService`
- `GeneralAssetService`
- `BuffAssetService`
- `EffectExecutor`

典型链路：

```text
Handler -> Command Service -> Asset Service -> Asset Repository -> 权威表事务 -> 事件/流水 -> 返回
```

### <span style="color:#0ea5e9">4.3 资产仓储</span>

后续应逐步从单一 `PlayerStateRepository` 过渡到按资产归口的仓储接口。

推荐拆分：

- `PlayerViewRepository`：只读聚合视图。
- `ResourceRepository`：资源读取、锁定、增减、容量更新。
- `BuildingRepository`：建筑读取、锁定、升级、状态变更。
- `ResourceSlotRepository`：资源田格子读取、解锁、绑定。
- `ArmyRepository`：兵力读取、增减、战后合并。
- `RecruitQueueRepository`：征兵队列读取、插入、完成、取消。
- `InventoryRepository`：背包读取、增加、消耗。
- `GeneralRepository`：武将读取、获取、升级、占用。
- `BuffRepository`：Buff 读取、增加、过期、移除。
- `AccountAssetRepository`：账号金币等账号级资产事务。

## <span style="color:#0ea5e9">5. `GameState` 的新定位</span>

`GameState` 后续只保留以下职责：

- 玩家端兼容返回。
- 前端完整状态展示。
- Admin 玩家详情展示。
- 测试中的聚合断言。
- 旧接口过渡期适配。

`GameState` 不应继续承担：

- 所有业务写入的唯一内部模型。
- 所有资产变更的事务单位。
- 旧数据修复入口。
- 权威表同步的唯一中间态。
- 高频业务的默认加载对象。

## <span style="color:#0ea5e9">6. `state_json` 的定位</span>

`players.state_json` 已经从大字段权威存档缩身为轻量兼容快照。后续继续保持这个方向。

`state_json` 可以保存：

- 玩家基础字段的兼容快照。
- 非高频、小体积、过渡期字段。
- 旧接口需要的少量兼容数据。

`state_json` 不应保存或作为权威判断来源：

- 资源。
- 背包。
- 建筑。
- 资源田格子。
- 兵力。
- 征兵队列。
- 武将。
- 武将占用。
- Buff/Modifier。
- 未来新增的长期资产。

## <span style="color:#0ea5e9">7. 具体改造步骤</span>

### <span style="color:#0ea5e9">阶段一：状态读取纯读化</span>

目标：

- `GET /api/v1/game/state` 不再走 `UpdatePlayerState`。
- 普通状态读取不锁玩家行、不写库、不修复长期资产。

任务：

- 将 `Service.GetState` 改为只调用只读仓储。
- 确认 MySQL `GetState` 不使用 `FOR UPDATE` 且不写库。
- 抽出展示投影函数，只在内存中计算当前资源、倒计时、升级完成展示。
- 移除普通读取里的补齐和修复逻辑。
- 补测试确认 `GetState` 不修改 `players.updated_at`、`state_json` 和各权威表。

验收：

- 普通状态读取不会触发写事务。
- 返回状态仍包含资源、背包、建筑、资源田、兵力、征兵队列、武将、Buff。
- 旧存档缺权威表时应提示执行回填或修复，不在读请求中静默修复。

### <span style="color:#0ea5e9">阶段二：修复逻辑归口</span>

目标：

- 创建、修复、回填职责从普通查询中剥离。

任务：

- 确认创建玩家时初始化完整核心建筑、资源田、武将、兵力、背包和 Buff 基础结构。
- 新增或整理 `RepairPlayerCoreAssets`，用于后台或维护命令修复旧玩家。
- 回填工具继续负责旧数据迁移。
- 登录流程只做轻量检查，不做重资产修复。

验收：

- 普通 `GetState` 不再调用补齐类函数。
- 新建玩家无需依赖第一次读取来补齐核心资产。
- 旧玩家缺表时有明确错误和修复路径。

### <span style="color:#0ea5e9">阶段三：建筑升级小事务</span>

目标：

- 建筑升级不再加载完整 `GameState`。

任务：

- 新增建筑升级命令入口。
- 事务中只锁定必要资源行、目标建筑行、必要资源田行。
- 读取建筑配置和必要 Modifier。
- 扣资源或扣账号金币。
- 更新建筑等级、状态、结束时间。
- 如果建造司升级解锁资源田，在同一事务中写资源田。
- 发布核心资产事件。

验收：

- 建筑升级不调用通用 `UpdatePlayerState`。
- 建筑升级不能绕过资源和建筑核心规则。
- 资源不足、最大等级、状态阻塞、金币不足仍有测试覆盖。

### <span style="color:#0ea5e9">阶段四：征兵小事务</span>

目标：

- 征兵不再加载完整 `GameState`。

任务：

- 新增征兵命令入口。
- 事务中只锁定资源行、征兵队列行和必要 Buff。
- 读取兵种配置和征兵速度 Modifier。
- 扣资源。
- 插入征兵队列。
- 队列完成时只更新队列和兵力表。
- 发布核心资产事件。

验收：

- 征兵和极速完成不调用通用 `UpdatePlayerState`。
- 兵力、队列、资源变化一致。
- 队列数量限制、资源不足、兵种不可用仍有测试覆盖。

### <span style="color:#0ea5e9">阶段五：Reward 和 Effect 资产命令化</span>

目标：

- Reward 和 Effect 不再必须先应用到完整 `GameState`。

任务：

- 将标准 Reward 分发到具体资产服务：
  - `resource` -> 资源资产服务。
  - `item` -> 背包资产服务。
  - `unit` -> 兵力资产服务。
  - `general` / `general_exp` -> 武将资产服务。
  - `buff` -> Buff 资产服务。
  - `city_gold` / `gold` -> 玩家或账号货币服务。
- `building_mutation` 分发到建筑资产服务。
- Effect Pipeline 保留统一校验、审计、事件和幂等职责。

验收：

- 玩法模块仍提交标准 Effect 或 Reward。
- 玩法模块不直接写资产表。
- Effect 执行不再默认加载完整 `GameState`。

当前落地状态（2026-06-26）：

- 已新增奖励资产级事务 `UpdateRewardState`，标准奖励发放不再调用通用 `UpdatePlayerState`。
- 已新增账号 + 奖励资产级事务 `UpdateAccountRewardState`，含账号金币奖励不再调用通用 `UpdateAccountPlayerState`。
- MySQL 奖励事务只加载奖励需要的资源、背包、兵力、武将、武将占用和 Buff，并保留 `city_gold` 等轻量兼容快照字段。
- `ExecuteEffects` 已按类型分流：纯 Reward / Modifier 走奖励资产事务，纯建筑变更走建筑资产事务。
- 资源调整、普通补满、付费补满已接入 `UpdateResourceState`，不再直接调用通用 `UpdatePlayerState`。
- 当前资源资产事务仍复用资源结算所需的建筑、资源田、兵力和征兵队列范围，后续应继续把资源结算、建筑完成和征兵完成拆成更清晰的命令。
- 道具使用已接入 `UpdateItemState`，不再直接调用通用 `UpdatePlayerState`；事务范围覆盖背包、资源结算依赖资产和道具效果可能影响的奖励资产。
- 武将加点、洗点、切换武将已接入 `UpdateGeneralState` / `UpdateAccountGeneralState`，不再直接调用通用玩家事务。
- Buff 撤销已接入 `UpdateRewardState`，产量/容量加成购买已接入 `UpdateResourceState`。
- 城金扣除、金币兑换城金、城金兑换金币已接入 `UpdateRewardState` / `UpdateAccountRewardState`，不再直接调用通用玩家事务。
- NPC 城池刷新已接入 `UpdatePlayerMetaState`，只更新 `players.state_json` 中的轻量 NPC 字段。
- 钓鱼鱼饵扣城金已接入 `UpdateRewardState`。
- 玩家发信时的邮箱码补齐已接入 `UpdatePlayerMetaState`，不再加载完整玩家资产。
- 小游戏兑换仍走模块事务 `UpdateMiniGamePlayerState`，但 MySQL 实现已缩小为只加载小游戏记录和兵力权威表。
- 战斗攻击和侦查已接入 `UpdateCombatState`，不再直接调用通用 `UpdatePlayerState`。
- 混合 Effect fallback 已关闭，混合资产 Effect 会返回 `ErrMixedEffectAssets`，调用方必须拆成单一资产范围的 Effect 分别提交。

### <span style="color:#0ea5e9">阶段六：前端查询拆分</span>

目标：

- 前端按页面读取局部视图，不再所有页面都依赖完整 `GameState`。

建议接口：

- `/api/v1/game/state`：完整低频兼容快照。
- `/api/v1/game/summary`：玩家摘要。
- `/api/v1/city/view`：城池、建筑、资源田。
- `/api/v1/resources/view`：资源栏和产量。
- `/api/v1/military/view`：兵力和征兵队列。
- `/api/v1/inventory/view`：背包。
- `/api/v1/generals/view`：武将和派驻。

验收：

- 城池页不需要完整玩家状态。
- 军事页不需要完整玩家状态。
- 资源栏可以使用轻量资源视图。
- 完整 `GameState` 只用于低频刷新、兼容和排查。

当前落地状态（2026-06-26）：

- 已新增 `/api/v1/game/summary`、`/api/v1/city/view`、`/api/v1/resources/view`、`/api/v1/military/view`、`/api/v1/inventory/view`、`/api/v1/generals/view` 六个局部视图接口。
- 后端局部视图统一从只读 `GetState` 投影，不触发通用玩家写事务。
- 前端 `gameApi` 和 `gameStore` 已新增局部视图读取入口，用于按页面合并必要字段。
- 城池页进入时刷新 `CityView`，军事页按页签刷新 `MilitaryView` / `GeneralsView`，资源栏刷新 `ResourceView`。
- 完整 `GameState` 仍作为启动兼容快照和跨模块兜底使用；后续新增页面应优先接局部视图，逐步减少对完整状态的依赖。

## <span style="color:#0ea5e9">8. Redis 与缓存定位</span>

Redis 可以作为后续增强，但不应替代核心读写规范。

适合 Redis 的场景：

- 玩家展示状态短缓存。
- 资源栏、城池、军事等局部视图短缓存。
- NPC 城池列表缓存。
- 限流。
- 防重复点击短锁。
- 排行榜。
- 异步非核心统计队列。

不适合 Redis 的场景：

- 代替 MySQL 作为长期资产最终权威。
- 让玩法模块绕过核心直接写资产。
- 在未拆清事务边界前掩盖所有请求都读写完整状态的问题。

建议顺序：

1. 先完成读写模型规范化。
2. 再给读模型加短缓存。
3. 再加限流、防重复点击和排行榜。

## <span style="color:#0ea5e9">9. 不允许的做法</span>

- 不允许普通读取请求修复长期资产。
- 不允许新增玩法直接写资源、背包、兵力、建筑、武将、Buff 权威表。
- 不允许为了性能绕过 Reward、Effect Pipeline 或核心资产服务。
- 不允许把新资产继续塞回 `state_json` 做权威判断。
- 不允许所有新业务默认继续调用 `UpdatePlayerState`。
- 不允许把 Redis 当成长期资产最终权威。
- 不允许只调大连接池来掩盖事务模型过重的问题。

## <span style="color:#0ea5e9">10. 开发判断清单</span>

新增或修改一个业务前，先回答：

- 这个请求是查询还是命令？
- 它是否真的需要完整 `GameState`？
- 它读取哪些资产？
- 它修改哪些资产？
- 它需要锁哪些表或哪些行？
- 它是否需要账号资产参与？
- 它是否通过 Reward 或 Effect Pipeline 修改长期资产？
- 它是否需要发布核心资产事件？
- 它是否需要兼容旧接口返回？
- 它是否可以返回局部视图而不是完整状态？

如果一个业务只修改一种或两种资产，却需要加载完整 `GameState`，应优先考虑拆成资产命令。

## <span style="color:#0ea5e9">11. 最终形态</span>

推荐最终链路：

```text
查询请求：
Handler -> Query Service -> View Repository -> 权威表只读查询 -> 展示投影 -> 返回

写入请求：
Handler -> Command Service -> Asset Service / Effect Executor -> Asset Repository -> 权威表事务 -> 事件/流水 -> 返回
```

不推荐继续扩大的链路：

```text
Handler -> Service -> UpdatePlayerState -> 完整 GameState -> 修改一小块 -> 同步所有可能变化的表 -> 返回
```

这个规范不是要求一次性重写所有代码，而是给后续开发提供稳定方向。后续每改一个高频业务，就应让它从整包 `GameState` 模式迁移到更清晰的读模型或资产命令模型。
