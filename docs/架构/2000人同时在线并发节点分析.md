# <span style="color:#0ea5e9">Hero3 2000 人同时在线并发节点分析</span>

最后更新：2026-06-27

## <span style="color:#0ea5e9">1. 文档目标</span>

本文档对比分析两个工作区的当前架构和数据库设计：

```text
/Users/xieyuqiyu/Documents/game/Hero3-main  分支 main
/Users/xieyuqiyu/Documents/game/Hero3       分支 main-core
```

分析目标：

- 判断当前项目框架在 2000 人同时登录或同时在线时可能出现的并发业务节点。
- 找出高频读写路径、数据库热点表、事务锁竞争点和后台任务压力点。
- 给出后续优化和压测建议。

本文档只做架构和并发风险分析，不直接修改业务实现。

## <span style="color:#0ea5e9">2. 总体结论</span>

### <span style="color:#0ea5e9">2.1 main 分支现状</span>

`Hero3-main` 的 `main` 分支属于较早的一体化结构：

```text
go/internal/api       HTTP 路由和 Handler
go/internal/game      游戏服务、模型、配置、业务逻辑
go/internal/combat    战斗引擎
go/internal/general   武将特性
go/internal/storage   MySQL 仓储
go/internal/auth      JWT 鉴权
go/internal/config    配置读取
go/internal/httpserver HTTP Server
```

数据库主要表：

```text
accounts
players
battle_reports
pvp_marches
mails
announcements
announcement_reads
minigame_records
gold_ledger
```

关键特征：

- 玩家长期状态主要集中在 `players.state_json`。
- PVP 行军已经有独立 `pvp_marches` 表。
- 公告有 `announcements` 和 `announcement_reads`。
- 仓储集中在 `go/internal/storage/mysql.go`，单文件承担大量 SQL。
- 部分高风险业务通过事务写多个表，但普通玩家状态更新仍以整包 JSON 为主。

### <span style="color:#0ea5e9">2.2 main-core 分支现状</span>

`Hero3` 的 `main-core` 分支已经进入核心重构后的分层结构：

```text
go/internal/transport/api          HTTP 路由和 Handler
go/internal/app/game               应用服务和玩法编排
go/internal/core/combat            战斗核心
go/internal/core/building          建筑生命周期核心
go/internal/core/effect            Effect Pipeline 契约
go/internal/core/event             事件核心
go/internal/core/general           武将特性核心
go/internal/core/modifier          加成核心
go/internal/core/registry          注册中心
go/internal/core/reward            奖励契约
go/internal/infrastructure/storage MySQL 仓储
go/internal/platform               鉴权、配置、HTTP Server
```

数据库主要表：

```text
schema_migrations
accounts
players
player_resources
player_inventory
player_buildings
player_resource_slots
player_army_units
player_recruit_queues
player_generals
player_general_assignments
player_reinforcements
player_buffs
event_processing_records
gameplay_module_instances
gameplay_module_participants
gameplay_module_settlements
battle_reports
mails
minigame_records
gold_ledger
```

关键特征：

- 玩家长期资产已经从 `players.state_json` 拆出多张权威表。
- 资源、背包、建筑、资源田、兵力、征兵队列、武将、武将占用、Buff、增援都有独立表。
- 仓储按领域拆分，读写路径比 main 更清晰。
- Effect Pipeline、事件处理记录、玩法模块实例和参与表已经具备模块化扩展地基。
- 仍保留 `players.state_json` 作为兼容聚合快照，很多事务仍会锁 `players` 行。

### <span style="color:#0ea5e9">2.3 2000 人同时在线的基本判断</span>

如果 2000 人只是同时完成登录并读取状态，当前 Go 服务本身问题不大，主要压力会落在：

- 登录鉴权查询。
- 玩家列表读取。
- 进入游戏后的状态聚合读取。
- 前端同时拉取多个视图接口。
- 数据库连接池排队。

如果 2000 人同时进行资源领取、建筑升级、征兵、战斗、信函领取、小游戏兑换、增援等写操作，瓶颈会明显转向：

- 单玩家行锁。
- 多玩家事务锁。
- `players.state_json` 兼容写回。
- 高频资产表更新。
- 战报、邮件、流水的写入放大。
- 请求触发型结算造成的尖峰。

当前默认 MySQL 连接池为：

```text
MaxOpenConns = 20
MaxIdleConns = 10
ConnMaxLifetime = 30 分钟
```

`main-core` 额外补了默认连接、读、写超时：

```text
timeout = 5 秒
readTimeout = 5 秒
writeTimeout = 5 秒
ConnMaxIdleTime = 5 分钟
```

因此 2000 人同时触发数据库请求时，不会有 2000 个数据库连接同时打开，而是会在应用层连接池排队。连接池保护了数据库，但也会让请求延迟快速上升。

## <span style="color:#0ea5e9">3. 登录并发链路</span>

### <span style="color:#0ea5e9">3.1 登录请求</span>

登录接口：

```text
POST /api/v1/accounts/login
```

主要操作：

- 按用户名查询 `accounts`。
- 校验密码哈希。
- 签发 JWT。

数据库命中：

```text
accounts.username UNIQUE
```

并发风险：

- 2000 人同时登录会集中查询 `accounts`。
- 如果登录后前端立刻拉取玩家列表和玩家状态，真实压力不在登录本身，而在登录后的连锁请求。
- 当前密码哈希是 SHA-256，计算成本低，不会成为 CPU 主要瓶颈，但安全性不如 bcrypt/argon2。

建议：

- 登录接口本身可以支撑较高并发，重点压测登录后 3 秒内的请求风暴。
- 登录成功后前端应避免同时拉取过多接口。
- 可以在前端做首屏请求合并或延迟加载。

### <span style="color:#0ea5e9">3.2 登录后玩家列表</span>

接口：

```text
GET /api/v1/accounts/{accountId}/players
```

主要操作：

- 查询账号下玩家。
- 读取玩家摘要。

`main` 风险：

- 玩家摘要依赖 `players.state_json` 中的统计字段。
- 大量并发读取 `state_json` 会造成较高 JSON 传输和解析成本。

`main-core` 改进：

- 已有 `PlayerSummaryView`、`CityView`、`ResourceView`、`MilitaryView` 等视图接口和资产权威表。
- 但如果玩家列表仍读取 `state_json`，仍有 JSON 解析成本。

建议：

- 玩家列表只返回轻量摘要，不返回完整 `state_json`。
- 后续可建立玩家摘要表或从 `players` 轻字段 + 权威资产表聚合。

### <span style="color:#0ea5e9">3.3 进入游戏状态读取</span>

接口：

```text
GET /api/v1/game/state
GET /api/v1/game/summary
GET /api/v1/city/view
GET /api/v1/resources/view
GET /api/v1/military/view
GET /api/v1/generals/view
GET /api/v1/inventory/view
```

并发风险：

- 如果前端进入游戏后同时发多个视图请求，2000 人会放大成数千到上万次数据库查询。
- `main-core` 的视图接口更适合按页面分片读取，但需要避免首屏一次性全拉。
- `GET /api/v1/game/state` 返回完整聚合状态，适合兼容，不适合作为高频首屏唯一接口长期使用。

建议：

- 首屏优先请求 `summary` 或必要视图。
- 页面进入时再拉取对应视图。
- 对 `bootstrap`、配置类接口做前端缓存或 CDN 缓存。

### <span style="color:#0ea5e9">4.3 后台和请求触发任务</span>

当前项目更偏“请求触发结算”，并非独立任务队列。

可能并发出现的任务：

- 离线资源结算。
- 建筑升级完成结算。
- 征兵完成结算。
- Buff 过期清理。
- 小游戏库存兑换。
- 邮件附件领取。
- 战报未读统计。
- 增援到达结算。
- 增援返程结算。
- PVP 行军到达结算。这个主要存在于 `main` 分支。
- 事件处理幂等记录。这个主要存在于 `main-core` 分支。

风险：

- 请求触发结算会把“玩家打开页面”转化为“写数据库”。
- 2000 人同时登录后进入城池页，可能同时触发资源、建筑、征兵等结算。
- 如果一个请求内结算太多模块，会拉长事务时间。

建议：

- 把登录后的结算限制为轻量结算。
- 重型结算放到具体页面触发，或后续做后台任务分批处理。
- 增援、PVP 到达这类跨玩家结算应使用幂等状态抢占，避免多请求重复处理。

## <span style="color:#0ea5e9">5. 数据库并发风险</span>

### <span style="color:#0ea5e9">5.1 连接池排队</span>

两个分支 MySQL 连接池默认都是：

```text
MaxOpenConns = 20
MaxIdleConns = 10
```

2000 人同时在线时，如果每人瞬间发起 3 个数据库请求，就是 6000 个请求排队争用 20 个连接。

现象：

- 请求平均延迟升高。
- 写请求等待连接期间堆积。
- 前端可能重复点击，进一步放大写请求。
- 如果没有前端防抖和后端幂等，容易出现重复操作。

建议：

- 压测前先明确数据库机器规格，再调整连接池。
- 不建议盲目把连接池开到几百；需要结合 MySQL 最大连接数、CPU、IO 和慢查询观察。
- 可以先压测 20、50、100 连接三档，观察 P95/P99 延迟和数据库 CPU。

### <span style="color:#0ea5e9">5.2 单玩家行锁</span>

`main-core` 里很多写操作仍会执行：

```text
SELECT state_json, mail_code FROM players WHERE id = ? LIMIT 1 FOR UPDATE
```

同时还会加载相关资产表：

```text
player_resources
player_inventory
player_buildings
player_resource_slots
player_army_units
player_recruit_queues
player_generals
player_general_assignments
player_buffs
```

影响：

- 同一个玩家并发点击多个操作时，会串行等待。
- 这对数据正确性是好事，但会降低单玩家突发吞吐。
- 2000 人如果是 2000 个不同玩家，锁竞争相对分散。
- 如果多人同时攻击同一个玩家、增援同一个玩家，会出现目标玩家锁热点。

建议：

- 单玩家写操作继续串行是合理的。
- 跨玩家操作必须固定锁顺序，避免死锁。
- 对前端按钮做提交中状态，减少重复写。

### <span style="color:#0ea5e9">5.3 跨玩家事务</span>

跨玩家节点：

- `main` 的 PVP 结算：攻击方、 防守方、两份战报、行军记录。
- `main-core` 的增援：派出方、接收方、增援记录。
- 未来 PVP 接入增援后：攻击方、防守方、多个援军派出方、战报、邮件。

风险：

- 多玩家互相攻击时，容易形成锁等待链。
- 如果事务内战斗计算或 JSON 序列化耗时较长，会放大锁持有时间。
- 多个援军来源参与战斗时，会从双玩家事务变成多玩家事务。

建议：

- 事务内只做必要的读取、校验和写入。
- 战斗计算尽量在锁外使用必要快照完成，锁内只做最终校验和落库。
- 多玩家锁必须按稳定顺序获取，例如按 `player_id` 字典序。
- 增援和 PVP 损耗应设计为可重试、幂等的结算步骤。

### <span style="color:#0ea5e9">5.4 `players.state_json` 整包写</span>

`main` 的主要风险：

- 大多数长期资产都在 `players.state_json`。
- 每次资源、建筑、征兵、战斗、道具变化都要写整包 JSON。
- JSON 越大，网络传输、编码、解码和 InnoDB 行更新成本越高。

`main-core` 的改进：

- 已拆出多张资产表。
- 但 `players.state_json` 仍作为兼容快照存在，并且很多事务仍会读写它。

建议：

- main 分支不建议继续承载更重玩法，应优先以 main-core 为后续开发基线。
- main-core 后续继续把 `state_json` 降级为展示快照，不作为高频权威写中心。
- 高频接口优先读写资产表和视图接口，减少完整 `GameState` 往返。

### <span style="color:#0ea5e9">5.5 战报、邮件、流水写入放大</span>

战斗和奖励类操作通常不是单写：

```text
玩家资产变化
战报写入
邮件写入
奖励状态
货币流水
事件处理记录
```

2000 人同时参与战斗或兑换时，会出现写入放大。

风险表：

```text
battle_reports
mails
gold_ledger
event_processing_records
minigame_records
```

建议：

- 战报和邮件列表必须分页。
- 战报保留策略要明确，例如只默认查询最近 3 天或最近 N 条。
- 高频流水查询只用于 GM，不应被玩家端频繁调用。
- 事件处理记录要定期归档或清理。

## <span style="color:#0ea5e9">6. main 与 main-core 对比</span>

| 维度 | main | main-core |
| --- | --- | --- |
| 后端分层 | `api/game/storage` 较扁平 | `transport/app/core/infrastructure/platform` 更清晰 |
| 玩家资产 | 主要在 `players.state_json` | 多张资产权威表 + 兼容快照 |
| 仓储组织 | `mysql.go` 大文件集中 | MySQL 仓储按领域拆分 |
| PVP | 有 `pvp_marches` 和行军接口 | 当前未保留 main 的 PVP 主线，重点在增援和核心 |
| 增援 | 旧路由有 `/map/players/reinforce` | 独立 `/api/v1/reinforcements` |
| 公告 | 有公告表和公告接口 | 当前主结构未见公告表 |
| 事件幂等 | 不明显 | 有 `event_processing_records` |
| 玩法模块表 | 不明显 | 有模块实例、参与、结算表 |
| 数据库超时 | 未自动补 DSN 读写超时 | 自动补连接、读、写超时 |
| 运维工具 | 较少 | dbtool 回填、校验、测试库工具更完整 |

判断：

- 如果目标是继续开发大玩法和承载更高并发，应以 `main-core` 为主。
- `main` 中可参考的内容是 PVP 行军表、公告系统和部分前端玩法经验。
- 不建议把 `main` 的 PVP 直接搬进 `main-core`，应按 `main-core` 的核心资产和 Effect Pipeline 重新接入。

## <span style="color:#0ea5e9">7. 2000 人并发场景拆解</span>

### <span style="color:#0ea5e9">7.1 场景 A：2000 人同时登录</span>

请求估算：

```text
2000 次 /accounts/login
2000 次 /accounts/{id}/players
2000 次 /game/bootstrap 或配置读取
2000 次首屏状态读取
```

主要瓶颈：

- 数据库连接池排队。
- `accounts.username` 查询。
- 玩家列表和状态读取。
- 配置接口重复读取。

风险等级：中。

建议：

- 配置接口缓存。
- 首屏只读摘要。
- 登录成功后的请求分批发出。

### <span style="color:#0ea5e9">7.2 场景 B：2000 人同时进入城池页</span>

可能触发：

- 资源离线结算。
- 建筑完成结算。
- 资源视图读取。
- 建筑视图读取。
- 战报未读数。
- 信函未读数。

主要瓶颈：

- 单玩家 `players` 行锁。
- 资源和建筑资产表读取。
- 战报和邮件未读统计。

风险等级：中到高。

建议：

- 未读数可以降频刷新。
- 城池视图和资源视图尽量合并或按页面需要拉取。
- 离线结算要避免每个视图接口重复执行。

### <span style="color:#0ea5e9">7.3 场景 C：2000 人同时征兵或升级建筑</span>

可能触发：

- 资源扣减。
- 建筑状态更新。
- 征兵队列写入。
- 兵力结算。

主要瓶颈：

- 单玩家资产事务。
- `player_resources`、`player_buildings`、`player_recruit_queues` 热写。
- 如果前端重复点击，会出现大量无效写请求。

风险等级：高。

建议：

- 前端按钮提交中禁用。
- 后端对重复请求加幂等键。
- 事务内少做 JSON 大对象处理。

### <span style="color:#0ea5e9">7.4 场景 D：2000 人同时领取邮件或兑换小游戏奖励</span>

可能触发：

- 邮件 `FOR UPDATE`。
- 玩家资产更新。
- 账号金币更新。
- 奖励发放。
- 小游戏库存更新。

主要瓶颈：

- `mails`、`minigame_records` 行锁。
- 玩家奖励资产锁。
- 含金币奖励时账号锁。

风险等级：高。

建议：

- 领取类接口必须幂等。
- 批量领取要限制单次数量。
- 奖励发放统一走 Effect Pipeline，保持事务边界清晰。

### <span style="color:#0ea5e9">7.5 场景 E：大量战斗、增援或未来 PVP</span>

可能触发：

- 攻击方资产扣减。
- 防守方资产读取和损耗。
- 多个援军派出方损耗。
- 战报写入。
- 邮件通知。
- 奖励和积分。

主要瓶颈：

- 多玩家事务。
- 目标玩家热点。
- 战报和邮件写入放大。
- 战斗计算 CPU。

风险等级：很高。

建议：

- 战斗结算必须幂等。
- 多玩家锁顺序必须固定。
- 增援/PVP 战斗先形成快照，再短事务落库。
- 大规模 PVP 前必须做专项压测。

## <span style="color:#0ea5e9">8. 优先优化建议</span>

### <span style="color:#0ea5e9">8.1 立即建议</span>

1. 以后开发以 `main-core` 为主线。
2. 保持玩法模块不绕过核心资产入口。
3. 首屏减少完整 `game/state` 依赖，优先使用视图接口。
4. 前端写操作全部加提交中状态，避免重复点击。
5. 领取、兑换、战斗、增援等接口增加幂等设计。
6. 压测前暴露基础指标：请求耗时、DB 等待、慢查询、错误率。

### <span style="color:#0ea5e9">8.2 数据库建议</span>

1. 对 2000 人场景压测 20、50、100 三档连接池。
2. 观察 MySQL 慢查询，特别是 `battle_reports`、`mails`、`players` 和高频资产表。
3. 继续减少 `players.state_json` 高频写入。
4. 战报、邮件、事件记录需要归档策略。
5. 跨玩家表和未来 PVP 表必须从第一版就设计好索引。

### <span style="color:#0ea5e9">8.3 服务端建议</span>

1. 保持 `main-core` 的分层，不把新玩法塞回通用 `service.go`。
2. 跨玩家业务统一封装事务入口。
3. 多玩家事务按稳定顺序锁定玩家。
4. 事务内避免远程调用、复杂文件读写和大规模计算。
5. 请求触发结算要加“已结算到某时间点”的幂等保护。

### <span style="color:#0ea5e9">8.4 前端建议</span>

1. 登录后不要同时打满全部接口。
2. 配置、bootstrap、静态资料做缓存。
3. 页面级数据按需加载。
4. 高频刷新接口加节流。
5. 写操作按钮禁用直到请求返回。

## <span style="color:#0ea5e9">9. 建议压测清单</span>

### <span style="color:#0ea5e9">9.1 登录压测</span>

目标：

```text
2000 个账号在 1 分钟内完成登录
登录后读取玩家列表
进入首屏读取 summary 或必要视图
```

观察：

- 登录 P95/P99。
- 数据库连接池等待。
- `accounts` 查询耗时。
- 首屏接口总请求数。

### <span style="color:#0ea5e9">9.2 城池压测</span>

目标：

```text
2000 个玩家同时打开城池页
触发资源、建筑、军事视图读取
部分玩家有离线结算
```

观察：

- `players` 行锁等待。
- `player_resources` 查询耗时。
- `player_buildings` 查询耗时。
- 未读战报和邮件统计耗时。

### <span style="color:#0ea5e9">9.3 写操作压测</span>

目标：

```text
500 到 2000 个玩家同时执行建筑升级、征兵、道具使用、邮件领取
```

观察：

- 锁等待。
- 死锁。
- 重复请求处理。
- 事务耗时。
- 错误率。

### <span style="color:#0ea5e9">9.4 战斗和增援压测</span>

目标：

```text
多个玩家同时攻击或增援同一目标
多批援军参与防守结算
战报和邮件同时写入
```

观察：

- 目标玩家热点。
- 多玩家事务耗时。
- 战报写入耗时。
- 邮件写入耗时。
- 是否出现重复损耗或重复返还。

## <span style="color:#0ea5e9">10. 风险分级</span>

| 风险 | main | main-core | 说明 |
| --- | --- | --- | --- |
| 登录查询压力 | 中 | 中 | 主要是账号查询和后续连锁请求 |
| 完整状态读取压力 | 高 | 中 | main-core 有视图和资产表改善 |
| 玩家写操作锁竞争 | 高 | 中到高 | main-core 锁更细但仍锁玩家行 |
| 跨玩家战斗事务 | 高 | 高 | PVP 和增援都需要重点设计 |
| 战报邮件写入放大 | 中到高 | 中到高 | 两边都需要归档和分页 |
| 数据库连接池排队 | 高 | 高 | 默认 20 连接面对 2000 人会排队 |
| 代码维护风险 | 高 | 中 | main-core 分层更适合继续演进 |
| 模块接入风险 | 高 | 中 | main-core 有模块登记和 Effect Pipeline |

## <span style="color:#0ea5e9">11. 最终建议</span>

对于 2000 人同时登录和后续玩法扩展，建议结论如下：

1. **以 `main-core` 作为继续开发主线。**  
   它已经具备更清晰的架构分层、多资产表、模块接入、事件幂等和 Effect Pipeline。

2. **不要把 `main` 的 PVP 直接搬进 `main-core`。**  
   `main` 的 PVP 行军设计可以参考，但应按 `main-core` 的兵力权威表、武将占用、增援表、战报和 Effect Pipeline 重新接入。

3. **2000 人同时登录本身不是最大风险，登录后的请求风暴才是。**  
   首屏接口、离线结算、未读统计、资源视图和写操作才是主要压力来源。

4. **跨玩家业务是未来最大并发风险。**  
   增援、PVP、攻城、协防都会产生多玩家事务，必须提前设计锁顺序、快照、幂等和失败恢复。

5. **数据库连接池需要通过压测调参。**  
   默认 20 个连接偏保守，能保护数据库，但 2000 人同时操作时会排队。是否提升到 50 或 100，需要看数据库规格和慢查询结果。

6. **继续削弱 `players.state_json` 的权威写入职责。**  
   main-core 已经走在正确方向上，后续高频资产应尽量读写独立表，把 `state_json` 保持为兼容快照和展示聚合。

7. **战报系统需要单独规划。**  
   战斗、增援、PVP 上来后，战报和邮件会成为写入放大点。后续应单独设计战报摘要、详情、归档、未读数和查询索引。
