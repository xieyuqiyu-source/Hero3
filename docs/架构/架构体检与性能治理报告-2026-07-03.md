# <span style="color:#0ea5e9">Hero3 架构体检与性能治理报告</span>

最后更新：2026-07-03

## <span style="color:#0ea5e9">1. 结论</span>

Hero3 当前不需要推翻“模块化单体后端”的方向。真正的问题是项目已经进入中大型单体阶段，但核心资产读写还没有完全从 `GameState` 聚合事务切换到小范围资产命令。

当前最主要的风险可以概括为三句话：

- 维护困难来自 `internal/app/game` 单包继续膨胀，玩法编排、核心资产接口、测试内存仓储和领域模型仍混在一起。
- 请求延迟主要来自部分接口仍会加载、比较、同步多类玩家资产；NPC 扫荡等高频链路会把单次事务按目标数量线性放大。
- 表越来越大不是单纯索引问题，而是战报、流水、模块记录和玩家长期资产还缺少统一的数据生命周期和冷热分层策略。

后续治理优先级：

```text
第一优先级：补观测，知道慢在哪里
第二优先级：限制高频接口的单请求工作量
第三优先级：把玩家资产写入从完整 GameState 事务继续拆成命令式小事务
第四优先级：按数据生命周期治理大表
第五优先级：拆分 app/game 单包，稳定模块边界
```

## <span style="color:#0ea5e9">2. 已确认的良好基础</span>

当前架构方向仍然成立：

- 技术分层已经具备：`transport`、`app`、`core`、`platform`、`infrastructure` 边界清楚。
- 玩家长期资产已经开始拆权威表：资源、背包、建筑、资源田、兵力、征兵队列、武将、Buff、NPC 状态等都已有对应表或迁移工具。
- 战斗、将领特性、奖励、事件管线已经从玩法代码里部分抽出，符合“核心稳定，玩法模块标准接入”的长期规则。
- 已有运维工具：`maintenance-status`、`report-stats`、`lock-snapshot`、`cleanup-battle-reports`、权威表健康检查和战报清理 timer。
- NPC 扫荡已经从“每场保存完整战报”改为“保存聚合战报”，说明性能治理方向是对的。

这些基础应该继续收敛，不应该因为变慢就改成微服务或让玩法模块绕过核心直接写表。

## <span style="color:#0ea5e9">3. 当前维护性风险</span>

### <span style="color:#0ea5e9">3.1 app/game 单包过大</span>

代码规模信号：

```text
go/internal 总计约 45003 行
go/internal/app/game 约 25713 行
go/internal/infrastructure/storage 约 11670 行
go/internal/app/game/service_pvp.go 约 2997 行
go/internal/app/game/repository.go 约 2062 行
go/internal/app/game/service_combat.go 约 1725 行
go/internal/app/game/service_minigame.go 约 1285 行
go/internal/infrastructure/storage/mysql_player_state.go 约 1223 行
```

风险：

- 新玩法很容易继续塞进 `game.Service`。
- Repository 总接口越来越大，导致所有模块理论上都能碰所有仓储能力。
- 内存仓储和接口定义放在同一大文件，测试便利性和模块边界互相缠绕。
- PVP、NPC、小游戏、副本、增援等玩法虽然分文件，但仍共享同一个应用包和大服务对象。

治理方向：

- 保持一个进程、一个部署单元，不拆微服务。
- 在 Go 包级别拆应用模块，例如 `app/player`、`app/combat`、`app/report`、`app/minigame`、`app/pvp`、`app/reinforcement`。
- 核心资产端口单独归口，例如 `app/assets` 或 `core/asset`，玩法只能依赖这些端口。
- Repository 大接口拆成模块所需的小接口，避免新增玩法拿到全仓储能力。

### <span style="color:#0ea5e9">3.2 启动入口重复配置加载</span>

`go/cmd/server/main.go` 在启用数据库前后各创建一次 `game.Service`，并重复调用一组配置加载方法。

风险：

- 后续新增配置时容易只改一处。
- 启动逻辑越来越长，失败路径不好维护。

治理方向：

- 抽出 `buildGameService(cfg, repo)`。
- 所有配置路径只在一个函数里绑定。

这不是响应延迟主因，但属于维护性低成本治理项。

## <span style="color:#0ea5e9">4. 当前性能风险</span>

### <span style="color:#0ea5e9">4.1 请求耗时观测已补第一版</span>

体检时确认 `requestLogMiddleware` 只记录：

```text
method, path, remote
```

当时缺少：

- HTTP 状态码。
- 请求耗时。
- 响应体大小。
- 玩家 ID / 账号 ID / request id。
- 慢请求阈值日志。

结果是线上出现“延迟”时，只能靠用户现象和数据库排查，不能快速知道是哪类接口、哪个玩家、哪段代码变慢。

当前第一版已落地：

- HTTP 请求日志记录 `method`、`path`、`status`、`duration_ms`、`bytes`、`remote`。
- 请求耗时超过 500ms 记为 warn。
- 请求耗时超过 2s 记为 error。
- panic 恢复后的请求也会留下 500 状态码和耗时日志。

治理方向：

- 对关键业务接口记录轻量阶段耗时，例如扫荡目标数、战斗事务耗时、战报写入耗时。
- 后续补玩家 ID / 账号 ID / request id，便于按玩家追踪。

### <span style="color:#0ea5e9">4.2 完整玩家状态事务仍然过重</span>

`UpdatePlayerState` 仍会：

- `SELECT players.state_json ... FOR UPDATE`
- 覆盖资源、货币、NPC、背包、建筑、资源田、兵力、征兵队列、武将、Buff
- 生成多类 previous snapshot
- 执行业务回调
- 比较并同步多张权威表
- 必要时更新 `players.state_json`

这对创建玩家、低频综合动作可以接受，但不适合高频动作。

风险：

- 一个很小的操作也可能锁住玩家主行和多类资产。
- 同一玩家高频点击会排队。
- 事务里 JSON 反序列化、快照比较和多表同步会放大响应耗时。

治理方向：

- 后续新增写接口默认禁止直接使用完整 `UpdatePlayerState`。
- 每个高频写接口必须先声明资产作用域。
- 已有接口逐步迁移到 `UpdateResourceState`、`UpdateItemState`、`UpdateCombatState`、`UpdateScopedRewardState` 等范围化事务。

### <span style="color:#0ea5e9">4.3 NPC 扫荡是线性放大链路</span>

当前 NPC 一键扫荡已从同步长请求改为后台 `sweep_task`，玩家端提交任务后轮询进度。任务内部不再循环调用完整 `attackNpc` 事务，而是在一次批量战斗资产事务中连续结算多个 NPC，并最终保存一条聚合战报。

风险：

- 任务执行期间仍会占用该玩家的战斗资产锁，同一存档其他关键写操作需要等待或被限流。
- 多玩家同时扫荡仍会共同消耗数据库连接、共享表索引和写入 I/O，需要继续观察任务耗时和连接池压力。
- 当前后台任务由服务进程内 goroutine 执行；服务启动时会把上一次进程遗留的 `queued/running` 任务标记失败，避免玩家被永久活跃任务卡住。
- 单次扫荡任务最多 50 个目标；如果后续真实日志显示 50 个目标仍导致锁等待或事务过长，应继续拆分为多批任务。

治理方向：

- 已完成：扫荡任务化，前端提交任务并轮询结果，HTTP 长请求不再等待完整战斗结算。
- 已完成：扫荡批量结算，一次事务读取当前资产，内存内连续结算多个 NPC，最后一次性写回资产和聚合战报。
- 已完成：奖励流水和道具流水改为批量仓储写入，战报奖励事件和战斗完成事件按聚合战报发布一次。
- 已完成：同一玩家活跃扫荡任务在仓储层原子创建，服务启动会恢复中断任务为失败，任务记录按 14 天近期排查窗口清理。

### <span style="color:#0ea5e9">4.4 战报查询仍有 COUNT + OFFSET 成本</span>

`ListReports` / `ListReportsByQuery` 每页查询会先 `COUNT(*)`，再按 `ORDER BY created_at DESC LIMIT OFFSET` 读取 JSON。

风险：

- 战报量大时 COUNT 会成为固定成本。
- 深分页 OFFSET 会越来越慢。
- `report_json` 字段较大，列表页读取完整 JSON 会带来 IO 和反序列化成本。

治理方向：

- 列表接口优先读取标准列和 `detail_json` 摘要，不默认读取完整 `report_json`。
- 分页从 offset 逐步改为基于 `created_at + id` 的游标分页。
- 未读数、总数可以缓存或降级，不强求每次精确 COUNT。

### <span style="color:#0ea5e9">4.5 数据库连接池和超时不可配置</span>

当前 MySQL 连接池固定：

```text
MaxOpenConns = 20
MaxIdleConns = 10
ConnMaxLifetime = 30m
ConnMaxIdleTime = 5m
```

风险：

- 玩家变多后，固定 20 个连接可能成为排队瓶颈。
- 连接池等待时间目前没有日志暴露。
- 不同机器和数据库规格无法通过环境变量调整。

治理方向：

- 增加 `HERO3_DB_MAX_OPEN_CONNS`、`HERO3_DB_MAX_IDLE_CONNS`、`HERO3_DB_CONN_MAX_LIFETIME`、`HERO3_DB_CONN_MAX_IDLE_TIME`。
- 在维护巡检或健康接口里输出 `db.Stats()` 摘要。

## <span style="color:#0ea5e9">5. 当前大表风险</span>

### <span style="color:#0ea5e9">5.1 战报表</span>

战报已经有清理方案和 timer，这是正确方向。后续重点不是继续堆索引，而是确认清理任务真的持续生效。

需要持续观察：

- `battle_reports` 总数。
- 最近 3 天新增量。
- 软删除数量。
- 可清理候选量。
- 清理 timer 是否每次成功。
- 有效分享链接是否阻止大量旧战报清理。

### <span style="color:#0ea5e9">5.2 流水表</span>

`gold_ledger`、`item_ledger` 这类审计表会持续增长，后续应补生命周期策略。

建议：

- 玩家端近期流水保留 30 到 90 天。
- GM 审计保留更久，但可以按月归档。
- 高频玩法流水应区分“必须审计”和“可聚合统计”。

### <span style="color:#0ea5e9">5.3 players.state_json</span>

`players.state_json` 已经降级为兼容快照，但写事务仍会读取并可能更新它。

后续目标：

- 展示聚合读取可以继续使用兼容快照兜底。
- 高频写入不应依赖完整 `state_json`。
- 继续减少 `state_json` 中残留的大字段。

## <span style="color:#0ea5e9">6. 治理路线</span>

### <span style="color:#0ea5e9">6.1 立即执行</span>

这些改动风险低，优先做：

1. 已完成：增强 HTTP 请求日志，补 status、duration、bytes 和慢请求标记。
2. MySQL 连接池参数改为环境变量，并暴露 `db.Stats()` 巡检输出。
3. 已完成：NPC 扫荡从同步 HTTP 长请求改为后台任务和前端轮询。
4. 已完成：NPC 扫荡从每城一次战斗事务改为任务内批量战斗资产事务，并保留目标数、成功数、总耗时、读状态耗时、战斗耗时和战报写入耗时日志。
5. 确认生产 `hero3-battle-report-cleanup.timer`、`hero3-maintenance-status.timer` 持续运行。

### <span style="color:#0ea5e9">6.2 短期执行</span>

这些改动能明显降低延迟：

1. 战报列表改为摘要列表，不读取完整 `report_json`。
2. 战报分页改游标分页或至少限制深分页。
3. 已完成：扫荡从同步长请求改为后台任务，避免请求超时。
4. 高频奖励发放全部改为 `UpdateScopedRewardState`。
5. 继续替换仍在高频路径上的完整 `UpdatePlayerState`。

### <span style="color:#0ea5e9">6.3 中期执行</span>

这些改动解决维护困难：

1. 拆分 `app/game` 单包。
2. 拆分 Repository 大接口。
3. 把玩家资产命令标准化，例如 `GrantReward`、`ConsumeItems`、`ApplyArmyDelta`、`ApplyGeneralExp`。
4. 让玩法模块只提交资产命令，不直接拿完整 `GameState` 自由修改。
5. 把内存仓储测试桩移到专门测试包或按模块拆分。

### <span style="color:#0ea5e9">6.4 长期执行</span>

这些是项目变大后的长期治理：

1. 建立大表生命周期规范：战报、邮件、流水、玩法记录、公告阅读状态分别保留多久。
2. 对大表按时间归档或分区，先从战报和流水开始。
3. 建立线上性能基线：P50、P95、P99、错误率、DB 等待、慢查询。
4. 每个新玩法设计必须先写资产读写范围，符合 `PROJECT_RULES.md` 的核心接入原则。

## <span style="color:#0ea5e9">7. 下一步建议</span>

建议下一轮直接做“第一阶段性能观测与止血”：

```text
1. 已完成：HTTP 请求日志增强
2. 数据库连接池配置化
3. 扫荡上限收窄和耗时日志
4. 维护巡检补 DB Stats
5. README 和运维文档同步
```

完成后再根据真实日志决定是优先改战报列表、扫荡任务化，还是继续拆资产事务。
